Password Storage Design

From plaintext to memory-hard hashing — each design was forced by the attack that broke the one before, and the choice decides how a leaked database ages.

Race: password storage only starts to matter after the database leaks — the hash's per-guess cost is then all that stands between the leaked table and a cracked user base.

1. The evolution ladder

  • Plaintext: earliest systems stored passwords as readable text
  • Exposure: any leak, backup, or admin read disclosed everything
  • Fast unsalted hash: one-way hashing hid the stored text
  • Flaw: identical passwords produced identical hashes
  • Rainbow tables: precomputed lookups reversed human picks in bulk
  • Per-user salt: a unique random value mixed into each user's hash
  • Win: every stored value distinct — precomputation dead
  • Residual flaw: the hash itself was still fast to compute
  • Throughput: billions of per-user guesses/s on commodity hardware
  • Memory-hard hash: each guess made costly in both time and memory
  • Tunable cost: work factors let per-guess cost rise with hardware
Reactive: every rung was adopted only after an attack broke the one below — defenders always one leak behind, never proactive.

2. Offline vs online attack framing

  • Online guessing: the attacker submits guesses to the live server
  • Server control: the server throttles, locks out, and alerts
  • Consequence: even weak passwords survive a few attempts/hour
  • Offline cracking: after a leak the attacker holds the hashes
  • Hardware speed: guessing runs on machines the attacker owns
  • No recourse: nothing the server does after the leak slows it
  • Design lever: only the cost of one guess stays in defender hands
  • Slow hashing: memory-hard designs raise exactly that cost
Pivot: storage design is irrelevant until the leak — then its slowness is the only barrier to mass cracking.

3. Storage design decides which composition rules matter

  • Slow-hash regime: per-guess cost is so high that length dominates
  • Length wins: every extra character multiplies the attacker's bill
  • Classes lose: extra character classes add almost nothing
  • Fast-hash regime: throughput fells any human-chosen password
  • No rescue: no rule saves a pick from the predictable subspace
  • Storage-side half: the other half of the composition-rules story
  • Stakes: class rules only matter when the stored hash is slow
Order: user-facing rules are second-order — the first-order defense is the per-guess price the user never sees.

4. Extra layers, current vs historical

  • Pepper: a per-deployment secret mixed into every hash
  • Kept outside: stored in a config store or hardware module
  • Win: a database-only leak can't even be guessed against
  • Hardware wrapping: high-security sites hash inside a hardware module
  • Effect: cracking pinned to the defender's rate-limited device
  • Migration limit: hashes can't upgrade in place without the password
  • Rehash-on-login: wrap or rehash at the next successful login
  • Retirement: the legacy scheme is retired gradually
  • Table stakes: salted slow hashing is now the baseline
  • Frontier: tuning memory-hardness against evolving hardware
  • Credential stuffing: replayed leaks elsewhere bypass cracking entirely
Limit: storage hardening cannot protect a password already leaked on another site — reuse defense is a separate problem.
