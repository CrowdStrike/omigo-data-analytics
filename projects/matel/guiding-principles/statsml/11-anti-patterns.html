Anti-Patterns & Design Patterns for Data Systems

Common mistakes in data collection, analysis, and ML — paired with the correct design. If you see yourself on the left: switch to the right.

Data Collection

Anti-Pattern
Impute all missing values with column mean

Treats all NULLs as "data collection failure." Fills with population average. Destroys the signal that absence carries.

Healthcare: makes healthy patients look sick. Cybersecurity: hides log deletion.
Design Pattern
Create is_missing feature + classify missingness type

MCAR: safe to impute. MAR: conditional imputation. MNAR: absence IS the feature. Always create binary "is_missing_X" alongside any imputation. Test if missingness predicts the target — often it's stronger than the value itself.

Anti-Pattern
UNION multiple sources into one table trusting schema match

Same column names + same types = same data, right? Wrong. "Amount" in USD from source A, cents from B, local currency from C.

Multi-hospital labs. Cross-region billing. Multi-platform analytics.
Design Pattern
Tag source_id + profile each source independently before joining

Add source_system_id to every row. Profile distributions PER SOURCE: mean, std, null rate, category values. If they differ for "same" column → semantic mismatch. Compare before combining, not after.

Anti-Pattern
Use "current state" queries for historical analysis

Query the database today for what happened last quarter. But: earnings restated, addresses changed, codes updated. Current values overwrite history.

Finance: restated earnings. HR: changed job titles. E-commerce: updated prices.
Design Pattern
Point-in-time database: store snapshots, query "as-of date X"

Every record versioned by timestamp. "What was this customer's address on March 15?" Not "what is their address now?" Requires append-only storage + temporal query capability. SCD Type 2 tables or event sourcing.

Profiling & Shape Detection

Anti-Pattern
Profile the entire column as one distribution

Compute mean, std, shape across ALL data. But if data has gaps, spikes, or sub-populations → the global profile is meaningless (mean in an empty gap).

Troponin: two clusters. Capital gain: spike + continuous. Hemoglobin: male + female.
Design Pattern
Value existence mapping → split → profile each segment

Step 1: Where does data EXIST? (gaps, spikes, clusters). Step 2: Split at structural boundaries. Step 3: Profile each segment independently. A mean across two clusters is fiction. Profile within each cluster.

Anti-Pattern
Use one bin count for all features

20 bins for everything. Power-law feature: 1 bin has 80% of data, 19 bins are empty. Uniform feature: works fine. One-size-fits-all = wrong for most.

Income. Hospital charges. File sizes. Any skewed distribution.
Design Pattern
Multi-resolution + percentile-width + meta-distribution Gini

Run at multiple bin counts (doc 13). Use equal-count bins where width encodes density (doc 27). Compute meta-distribution Gini (doc 28) — if > 0.7: feature needs adaptive treatment. Let the data tell you the right resolution.

Anti-Pattern
Report a single summary statistic ("mean = 50")

If distribution is bimodal (peaks at 20 and 80), mean = 50 represents a state that NEVER occurs. Summary stats are insufficient — they hide multi-modality, spikes, and tails.

CPU utilization. Income. Latency (cache hit vs miss).
Design Pattern
Always report shape + distribution alongside summary stats

Shape class (bell/skew/bimodal/spike) is as important as mean/std. Bimodal with mean 50? The mean is a lie — report the two peaks. Include at minimum: shape, skewness, Gini, max/mean ratio. Summary + shape together = truth.

Statistical Testing

Anti-Pattern
Report p-value without effect size

At n=100,000: enrichment 1.006× is "significant" (p<0.001). But useless for classification. Statistical significance ≠ practical significance.

Large datasets. Clinical trials. Any high-n analysis.
Design Pattern
Require BOTH p < threshold AND enrichment > minimum practical level

Gate: p < 0.05/n_tests (Bonferroni) AND enrichment > 1.5× (or whatever is actionable for your domain). Reject anything that's significant but trivially small. Report effect size FIRST, p-value second.

Anti-Pattern
Fine-bucket rare classes (20 buckets at 0.01% positive rate)

20 buckets × 0.01% positive = 12 positives per bucket. Below any statistical minimum. Every bucket is unvalidatable noise.

Fraud. Rare disease. Security attacks. Any extreme imbalance.
Design Pattern
Fewer buckets (5 max) or skip bucketing entirely → use rank tests

Mann-Whitney doesn't need bucketing — ranks positives vs negatives directly. If you must bucket: compute minimum n_positive needed per bucket (30). Then: max_buckets = total_positives / 30. At 600 positives: max 20 buckets. At 60: max 2.

Anti-Pattern
Check A/B test results daily until significant

"Peeking" inflates false positive rate from 5% to 25-50%. You stop when it looks good but would never stop when it looks bad.

Every A/B test platform. Product teams. Growth teams.
Design Pattern
Fix sample size upfront (power analysis). Don't peek. Or use sequential testing.

Pre-commit: "we will evaluate at n=5000 per group, not before." OR: use always-valid p-values / group sequential methods that mathematically account for continuous monitoring. No color-coding results until test is COMPLETE.

Feature Engineering

Anti-Pattern
Use CTR / engagement as item quality feature

CTR is 90% determined by position shown, not quality. Item at position 1: 30% CTR. Same item at position 10: 2%. The feature encodes YOUR bias, not the entity's property.

Search ranking. Recommendations. Ad targeting. Any system with position effects.
Design Pattern
Debias: CTR adjusted for position. Or: use random-position holdout traffic.

Option A: "CTR relative to position-average" as feature. Option B: Reserve 5% traffic for random ranking → measure CTR without position bias → use THAT as quality signal. Option C: Log position alongside every event and train position-aware models.

Anti-Pattern
Include a feature without checking causal direction

"Collection calls made" perfectly predicts loan default. But calls happen BECAUSE of default. It's a consequence, not a cause. Feature encodes the label.

Treatment predicting disease. Support tickets predicting churn. Retention call predicting loyalty.
Design Pattern
Timeline audit: for every feature, draw WHEN it was generated relative to target event

If feature_timestamp ≥ target_event_timestamp: it's leakage, remove it. This catches: post-event features, backfilled data, and consequence-as-cause. Automate: assert max(feature_timestamps) < min(prediction_timestamps) per entity.

Anti-Pattern
Remove protected attribute and assume fairness

Removed "gender" from model. But zip code, university, first name all correlate 0.8+ with gender. Model still discriminates through proxies.

Hiring. Credit. Insurance. Policing. Any regulated domain.
Design Pattern
Audit correlations with protected attributes. Remove proxies, not just the attribute.

Compute correlation of EVERY feature with protected attributes. If r > 0.5 with race/gender: it's a proxy. Either remove it, or apply fairness constraints (equalized odds, demographic parity). Test: does model output differ by protected group? If yes: unfair regardless of which features were removed.

Training & Evaluation

Anti-Pattern
Random train/test split on time-ordered data

Shuffles time. Future data in train, past data in test. Model "predicts" the past using future. Gap between random and temporal split: 10-30%.

Every financial dataset. User behavior. IoT sensors. Clinical events.
Design Pattern
Temporal split: train on [t₀,t₁], test on [t₁,t₂]. Never shuffle across time.

Simulate reality: model trained on everything up to date X, evaluated on everything after date X. This is what production actually faces — predicting the future from the past. If performance drops vs random split: that gap WAS leakage.

Anti-Pattern
Evaluate with accuracy on imbalanced data

"95% accuracy!" on 95/5 data = predicting majority class always. Recall on rare class = 0%. Completely useless detector.

Fraud (0.1%). Cancer (1%). Cybersecurity (0.001%). Any rare event.
Design Pattern
Evaluate with precision/recall/F1 on the minority class. Report at multiple thresholds (PR curve).

Ask: "of the things you flagged, how many were real?" (precision) and "of the real events, how many did you catch?" (recall). Report both + the tradeoff curve. Business decides where on the curve to operate based on cost of FP vs FN.

Anti-Pattern
Select features on full dataset, then split into train/test

Feature selection used test data to decide which features matter. Test is no longer independent. Performance inflated by 5-10%.

Univariate feature selection. Correlation screening. PCA. Any dimensionality reduction.
Design Pattern
Feature selection INSIDE cross-validation loop. Re-select per fold.

Pipeline: for each CV fold → select features on TRAIN fold only → build model on selected features → evaluate on TEST fold. Each fold independently selects features. Final feature set = intersection of what was selected across folds.

Anti-Pattern
Repeated evaluation on the same test set across iterations

Evaluate → tune → re-evaluate on same test data → tune again. Each iteration fixes errors this dataset surfaces. Other failure modes remain invisible. Published accuracy reflects coverage of one sample's error surface, not generalization.

ML model development. Kaggle-style iteration. Paper benchmarks. Any iterative model tuning.
Design Pattern
Rotate test sets. After a few evaluation cycles, retire the test set and source a new one.

A test set that has informed multiple rounds of tuning is no longer independent — you have corrected for its specific error surface. Retire it. Collect or sample a fresh test set from current production data. The new set will expose different failures — the ones the old set never surfaced. Budget for periodic test set refresh the same way you budget for retraining.

Anti-Pattern
Publish percentage accuracy without sample size or confidence interval

"99% accuracy" on 100 curated examples looks identical to 99% on 100,000 production samples. The percentage format erases the denominator. Less effort (small dataset) → higher variance → more likely to land a favorable number → publish without CI → nobody can tell.

ML papers. Startup pitch decks. Product announcements. Any published model evaluation.
Design Pattern
Always report n, confidence interval, dataset provenance alongside any published metric.

Minimum: the number, the sample size, the 95% CI, and a description of what the evaluation set represents. At n=100 with 99% observed: CI is [94.6%, 99.9%]. At n=100,000: CI is [98.9%, 99.1%]. Same percentage — entirely different knowledge. Without these, the number is a claim, not a finding.

Anti-Pattern
Fix failures as encountered without quantifying their frequency

You see the model fail on a specific case. You fix it immediately. You never asked: how often does this class of failure occur? You spent two weeks on a 0.3% problem while a 12% failure class was never investigated — because nobody happened to look at it.

Model debugging. Bug prioritization. Incident response. Any reactive fixing workflow.
Design Pattern
Classify failures first, quantify each class, fix largest class first.

Step 1: observe failures (yes, look at them). Step 2: classify into categories. Step 3: count how big each category is. Step 4: fix the largest, regardless of which you saw first. Never fix a failure without first answering "how big is this class?" Effort follows quantification, not accident of observation.

Deployment & Monitoring

Anti-Pattern
Deploy model and check results quarterly

Model silently degrades for 3 months. By the time you notice: thousands of wrong predictions served. Cause: upstream data change 2 months ago that nobody detected.

Silent schema changes. Feature store staleness. Concept drift. Population shift.
Design Pattern
Data validation on every input + distribution monitoring on every output

INPUT: schema checks, range checks, KS test vs last week, null rate changes → alert BEFORE serving. OUTPUT: prediction distribution vs expected → alert if predictions shift. Weekly: compare predictions vs actual outcomes (if available). Cheap, catches 90% of silent failures.

Anti-Pattern
Trust model confidence at face value

Model says "85% probability." But model was never calibrated. Actual rate when model says 85%: could be 50% or 95%. Confidence is a NUMBER, not a calibrated probability.

All probabilistic models. Risk scores. Churn prediction. Medical diagnosis.
Design Pattern
Calibrate predictions + report calibration curve alongside performance

Platt scaling or isotonic regression post-training. Verify: when model says "80%", does the event happen 80% of the time? Plot calibration curve (reliability diagram). If not calibrated: model probabilities are ordinal (ranking) not cardinal (probabilities).

Anti-Pattern
Train on batch-computed features, serve with real-time features

Batch: "30-day average" from perfect SQL query. Serving: same metric from streaming pipeline with different edge cases, NULL handling, timestamps. Subtle differences → silent performance drop.

Feature stores. Real-time ML. Any batch-train + online-serve system.
Design Pattern
Unified feature pipeline (same code for batch and serving) + feature parity monitoring

One function computes the feature, called both during training and serving. If impossible: log serving-time features, compare against batch-computed features for same records offline. Alert on systematic deviation. Any gap = training-serving skew.

Data Operations & Hygiene

Anti-Pattern
Same metric, same data — cherry-pick the aggregation level

"Engagement rate" computed per-user: +2%. Per-session: +12%. Per-click: +40%. Same metric name, same underlying data, three different truths depending on denominator. Pick the level that makes your case. The subtle part: this isn't lying — all three numbers are correct. But a per-click metric dominated by one power user's 500 clicks is a different claim than a per-user metric showing most people are unaffected.

Growth reviews. Engagement dashboards. Funnel analysis. Any hierarchical data: user → session → event → sub-event.
Design Pattern
Let statistical assumptions choose the aggregation level, then declare it upfront.

The correct level is where observations are independent units — not the finest granularity with the most rows. Independence, normality, and the metric's natural unit dictate the level: engagement rate per SRP belongs at the search-page level (each search is one decision). Time-on-site is a session-level metric (within-session pages are correlated). Picking per-click inflates N with non-independent duplicates → pseudoreplication → guaranteed but meaningless significance. Declare the level before analysis, justify it from the metric's semantics, and if levels disagree, report the discrepancy as concentration: "per-click +40%, per-user +2% — 3 power users driving 80% of new clicks."

Anti-Pattern
No source_id logged with ingested data

Data flows from 5 upstream systems into one table. When something looks wrong, you can't trace which source produced the bad row. "Where did this come from?" → nobody knows.

Multi-hospital labs. Cross-region billing. Multi-platform event streams. Merged datasets.
Design Pattern
Tag every row with source_system_id + ingestion_timestamp

Mandatory metadata on every record: which system produced it, when it arrived. When anomalies appear: filter by source and profile each independently. Source attribution is free at ingestion, expensive to reconstruct after the fact.

Anti-Pattern
No row count assertion after JOIN

Users table (10K rows) JOIN Orders (50K rows) = 50K rows. Nobody checked. "Revenue per user" computed on 50K rows: wrong by 5×. Or: LEFT JOIN drops 2K users silently. Nobody noticed the row count changed.

Any pipeline with joins. ETL workflows. Feature engineering on relational data.
Design Pattern
Assert row count before and after every join. Alert on unexpected change.

Rule: if count(output) > count(left_input) → you have a fanout → investigate. If count(output) < count(left_input) → you dropped rows → investigate. Automate this assertion in every ETL step.

Anti-Pattern
ETL pipeline with no data quality checks between stages

Data flows: raw → cleaned → transformed → modeled → served. No validation between steps. Garbage produced at step 2 propagates silently to step 5. Discovered weeks later by a user complaint.

Any multi-stage pipeline. Airflow DAGs. Spark jobs. dbt models.
Design Pattern
Validation gate between every stage: schema + distribution + business rules

After each step: assert column types, null rates within tolerance, value ranges within bounds, row counts within expected ±10%. HALT the pipeline if any check fails. Cheap (seconds of compute) and prevents cascading garbage. Great Expectations, dbt tests, custom assertions.

Anti-Pattern
Overwrite yesterday's data without versioning

Daily pipeline overwrites the "current" table. Bug introduced yesterday → today's table is wrong. But yesterday's table is gone — overwritten. Can't compare, can't roll back, can't investigate.

Any daily/hourly batch pipeline. Feature store updates. Reporting tables.
Design Pattern
Partition by date. Never delete. Compare today vs yesterday automatically.

Store each run as a dated partition (dt=2024-08-01). Current = latest partition. Investigation: diff any two dates. Rollback: point to previous partition. Storage is cheap; lost data is expensive. Keep 30+ days of history minimum.

Anti-Pattern
Hard-code thresholds from one dataset

"Anomaly if value > 1000" — works great on THIS dataset. Deploy to new client/region: normal values are 5000+. Threshold is meaningless outside its training context. Magic numbers everywhere.

Alerting systems. Feature engineering. Anomaly detection. Data validation.
Design Pattern
Derive thresholds from data statistics (percentiles, std from mean)

Instead of "value > 1000": "value > p99 of trailing 30 days" or "value > mean + 3σ." Threshold adapts to each deployment context. Self-calibrating. Works across populations without manual tuning.

Anti-Pattern
Relative time in pipeline queries (NOW() - INTERVAL)

WHERE ts > NOW() - INTERVAL '1 hour'. Pipeline fails at 10:02, auto-retries at 10:07 — window silently shifts 5 minutes. Different data, no error, "success." Backfill? Impossible. Debug? Can't reproduce. Every partial-failure recovery corrupts the output slightly.

Any scheduled ETL. Airflow DAGs. Cron-triggered pipelines. Feature store refresh. Monitoring queries.
Design Pattern
Pre-construct absolute time boundaries. Pass as parameters.

Scheduler computes window_start, window_end once. Query receives them as bind parameters. Retry = same parameters = same results. Backfill = pass any historical window. Query is a pure function of its inputs. Separate "when to run" from "what range to query." Log the boundaries for audit.

AI Assistants & LLM Analysis

Anti-Pattern
AI assistant agrees with everything you say (confirmation bias as a service)

User says "I think feature X matters." AI: "Yes! Feature X is very important because..." User feels validated. But AI would say the same about feature Y, Z, or any claim. The agreement is reflexive, not evidence-based. LLMs are sycophantic by training — optimized to be "helpful" which in practice means agreeable.

ChatGPT. Claude. Copilot. Any LLM used for data analysis.
Design Pattern
Demand evidence, not agreement. Ask "why might I be wrong?" not "am I right?"

Prompt for: "What's the strongest counter-argument?" "Under what conditions would this conclusion be false?" "What data would DISPROVE this?" Treat AI agreement as zero evidence. Only treat AI DISAGREEMENT or SPECIFIC COUNTER-EVIDENCE as information. If it agrees too easily: it's not thinking, it's pleasing.

Anti-Pattern
Using LLM output as ground truth without verification

"Claude said the p-value for this test should be 0.03" → used directly. But: LLMs hallucinate statistics, invent citations, confuse formulas. The output LOOKS authoritative (confident language, proper formatting) but may be completely fabricated.

Any AI-assisted analysis. Code generation. Statistical interpretation.
Design Pattern
LLM output = hypothesis to verify, never ground truth

AI generates analysis → run the ACTUAL computation to verify. AI suggests a test → check the assumptions YOURSELF. AI cites a paper → look it up. Treat LLM output the way you'd treat a junior analyst's first draft: probably directionally right, possibly wrong in details, NEVER trustworthy without review.

Anti-Pattern
Asking LLM the same question differently until it gives the answer you want

AI says "this correlation is likely spurious." Re-ask with leading framing: "Given that X is clearly related to Y, explain why..." Now AI agrees. You got the answer you wanted. But you just p-hacked the AI — tried multiple phrasings until one confirmed your bias.

Prompt engineering for confirmation. Iterative rephrasing. "Make it say what I believe."
Design Pattern
Ask ONCE with neutral framing. If AI disagrees: that's MORE informative than agreement.

The first answer (before you inject bias) is the least contaminated. If it contradicts you: investigate WHY, don't reframe until it agrees. AI disagreement = signal to check your assumption. AI agreement after 5 rephrasings = you trained it to echo you.

How to use: For any decision in your pipeline, find the anti-pattern that matches what you're about to do. If you see yourself on the left side: switch to the right side. Every anti-pattern on the left has burned real teams with real consequences — often silently for months before discovery.
