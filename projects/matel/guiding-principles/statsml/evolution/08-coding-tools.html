Evolution of Coding Tools

Punched cards to conversational agents — how the act of writing code has been instrumented.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
2005 onward
Distributed history
Git, Mercurial
Every clone held the complete history, making commits and branches local and cheap. This changed team workflow more than any tool of the period: branching per feature became routine, and merging stopped being an event to schedule.
2008 onward
Collaboration as a platform
GitHub, GitLab, pull requests, code review
Hosting plus the pull request turned code review into a standard gate and made open-source contribution a mechanical process. Issues, review, discussion and history collected around the repository, which is also what made large distributed projects tractable.
2011 onward
Automated verification and delivery
Jenkins, Travis, GitHub Actions
Every commit triggered builds and tests automatically, and deployment became a pipeline rather than a manual procedure. Release cadence shifted from quarterly to continuous for many teams, with automated checks carrying the confidence that used to come from a manual QA phase.
2015 onward
Environments as configuration
Docker for development, devcontainers, Codespaces
The development environment itself became a declared artefact, largely eliminating the class of problem where code worked on one machine and not another. Onboarding compressed from days of setup to cloning and starting a container.
2021 onward
Assistance inside the editor, then agents
Copilot, chat assistants, Claude Code and similar
Models trained on public code began completing multi-line blocks from context, then chat interfaces made explanation, review and generation conversational. More recently, agentic tools operate across a whole repository — reading files, running tests, editing and iterating — which moves the developer's activity toward specifying intent and reviewing results. The effect on defect rates and long-term maintainability is not yet established, and claims in either direction should be treated as open.
1950s – 1970s
Code as physical objectsgone
Punched cards, batch job submission
Programs were punched onto cards and submitted to an operator, with results returned hours later. A single syntax error cost a full cycle, so correctness was established by reading code carefully before submitting it — desk checking was a genuine skill because iteration was expensive.
1970s – 1980s
Interactive editing
ed, then vi and Emacs
Time-sharing terminals made editing interactive, initially one line at a time, then full-screen. vi and Emacs both date from this period and both remain in daily use roughly fifty years later — unusual longevity for any software category, largely because keyboard-driven editing over a remote connection has no better answer.
1980s – 2000s
Tracking changes centrallygone
RCS, CVS, Subversion
Version control moved from personal backup copies to a shared server holding history. The model required connectivity to commit, and branching was expensive enough that teams avoided it — which shaped how work was organised for two decades.
1990s onward
The integrated environment
Visual Studio, Eclipse, IntelliJ, VS Code
Editor, compiler, debugger and later refactoring tools combined into one application with a persistent index of the codebase. Static analysis of the whole project enabled reliable renaming, jump-to-definition and error detection before running anything.

What Disappeared

Ended as mainstream practice:
  • Punched cards and overnight batch turnaround — iteration measured in hours rather than seconds
  • Centralised version control — CVS and Subversion, and the practice of locking files to avoid conflicts
  • Printed language manuals at the desk — reference lookup was a physical act before online documentation
  • Long integration phases — the scheduled period at project end for making separately written components work together
  • Manual deployment runbooks — documented sequences of steps performed by hand on release night
  • "Works on my machine" as an accepted state — largely removed by containerised environments
Alive, but only in niches:
  • vi and Emacs — not niche in any real sense: still standard for remote editing, and their keybindings are emulated by most modern editors
  • Makefiles — still the build tool of choice for systems software after roughly fifty years
  • Print-statement debugging — unchanged in popularity despite decades of better debuggers being available
