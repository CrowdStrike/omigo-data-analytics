Evolution of Data Footprint

Kilobytes to petabytes in one working lifetime — and what stopped being a constraint at each step.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
2006 – 2015 — the big data wave
Petabytes on commodity hardware, and a named movement
Hadoop, HDFS, MapReduce, NoSQL, "the three Vs"
Distributing storage and computation across cheap machines made the petabyte affordable. The economics inverted: keeping everything became cheaper than deciding what to keep, so schema-on-read replaced schema-on-write and sampling stopped being mandatory. This period is when the capability acquired a name and a vocabulary — volume, velocity, variety — along with dedicated job titles, conference tracks and a distinct budget line. The naming matters for what happened next.
2006 onward
Object storage and separated compute
S3, GCS, Azure Blob
Durable storage became an API with effectively unlimited capacity, and crucially it decoupled storage from compute — you could store a petabyte and pay for processing only when you touched it. This is what made the Hadoop cluster obsolete.
2015 onward — after the wave
The term retires; the capability becomes assumed
Managed warehouses, NoSQL as ordinary infrastructure
"Big data" largely stopped being said, and not because it was abandoned. Handling volumes that required a dedicated cluster and a specialist team in 2010 became a configuration choice in a managed service, and document and wide-column stores became ordinary components rather than a movement. When a capability is universally available it stops needing a name — nobody describes a system as having "a database" as a distinguishing feature. The vocabulary retired while the capability became the default assumption, which is a common pattern and easy to mistake for a technology having failed.
2015 onward
Lakehouse and columnar formats
Parquet, Delta, Iceberg, Snowflake, BigQuery
Columnar files with statistics and transactional metadata gave lake-scale storage warehouse-grade query behaviour. Scanning a terabyte became a matter of seconds, and the warehouse/lake distinction largely dissolved.
2019 onward
Corpora as the unit of scale
Web crawls, token counts, model checkpoints
The largest datasets stopped being business records and became text and images scraped from the open web, measured in tokens rather than rows. Model weights themselves became a storage class, with single checkpoints reaching hundreds of gigabytes.
1950s – 1970s
Cards, tape, kilobytesgone
Punched cards, magnetic tape
Storage was sequential and measured in kilobytes. A program and its data had to be physically carried, and because random access did not exist, algorithms were designed around reading data in order — a constraint that shaped decades of file-processing design.
1970s – 1990s
Removable media and megabytesgone
Floppy disks, early hard disks
The megabyte arrived and with it the idea of a personal data file. Capacity was small enough that people deleted things routinely and chose what to keep — a habit that has almost entirely disappeared.
1990s — before the wave
Gigabytes, schema first
Oracle, SQL Server, MySQL, PostgreSQL
Random access plus indexing made the relational model practical at scale. Data got a schema, a normal form, and transactional guarantees. Storage was still expensive enough that schema design and normalisation were economically necessary, not stylistic choices.
Late 1990s – 2000s — before the wave
Terabytes and the warehouse
Star schemas, OLAP cubes, ETL
Analytical workloads outgrew the operational database, so a separate warehouse appeared with its own denormalised shape. Reporting shifted from querying live systems to querying a nightly copy — and the nightly batch became the unit of freshness for a generation of business reporting.
2010s
Streams and continuous data
Kafka, Kinesis, change data capture
The append-only log became a primary structure. Instead of tables holding current state, systems kept the full sequence of events and derived state from it, which made point-in-time reconstruction and replay routine.

What Disappeared

Ended as mainstream practice:
  • Punched cards and sequential tape processing — tape survives for cold archival, card-based data entry does not
  • Floppy disks and the sneakernet — carrying data physically between machines as normal practice
  • CD and DVD as data distribution — software and datasets once shipped on optical discs by post
  • Deleting files to make room — a routine weekly activity that consumer storage economics eliminated
  • The term "big data" itself — retired as vocabulary rather than as capability: the scale became the default assumption, so it stopped distinguishing anything
  • The on-premise Hadoop cluster — the defining big-data investment of the 2000s, made redundant by object storage plus elastic compute
  • OLAP cubes with pre-computed aggregates — necessary when scans were slow, now largely replaced by querying columnar storage directly
  • MapReduce as a programming model — the mental model persists, writing raw mapper and reducer classes does not
Alive, but only in niches:
  • Magnetic tape — still the cheapest medium per byte for archival, quietly holding a great deal of the world's cold data
  • Nightly batch ETL — still standard in finance and reporting where a daily close is the natural boundary
  • Normalisation to third normal form — still correct for transactional systems, largely abandoned for analytical ones
