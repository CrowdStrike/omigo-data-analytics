Evolution of Data Query Languages

One idea, repeatedly re-learned: describe the result and let a compiler decide the method — including the decade the industry tried the opposite — and why plain-language questions are an input to that pipeline rather than a new link in it.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
1950s – 1960s
No language: you wrote the access pathgone
Programs that walked the file
The question and the method of answering it were the same thing. You wrote loops that opened a file and followed pointers between records, so the retrieval strategy was source code. Two consequences defined the era: every new question needed a new program, and changing how data was stored broke every program that read it.
1974 onward
Declarative: separate the question from the method
SQL
The pivotal idea in this entire history. You state the result you want; a component called the optimiser decides how to obtain it. Because the query no longer names an access path, the engine is free to change indexes, join order and storage layout without a single query being rewritten. This is what made data independence real, and everything after it is a variation on the same move.
1986 onward
Standardised: the language outlives the engine
ANSI SQL
Once the grammar was fixed by a standard rather than by a vendor, a query became portable across implementations and a skill became durable. This is the reason SQL is still the baseline fifty years on: the language was decoupled first from the storage, then from the product.
2003 – present
A different grammar for a different question
Splunk SPL, Kusto KQL, LogScale
SQL assumes you are combining tables. Log and event analysis assumes you are narrowing a stream, so these languages are built as pipelines — each stage takes the previous stage's output and reduces it further. The general point is that grammar follows the shape of the question, which is why a purpose-built language can beat a universal one and still stay confined to its domain.
2004 – 2012
Regression: you become the optimiser againgone
MapReduce
Distributing work across many machines initially meant abandoning declarative querying and writing execution stages by hand. It is worth studying as the one clear reversal here — scale was thought to require giving up the optimiser. The lesson learned was that expressing intent is more valuable than controlling execution, because a machine plans better than a person once the plan gets complicated.
2006 – present
A compiler for clusters
Pig Latin, HiveQL, Spark SQL
The correction: keep a high-level language, and compile it into distributed work. These languages parse a query into a logical plan, optimise the plan, then emit physical stages that run across a cluster — exactly the classical compiler pipeline, with the cluster as the target architecture. Pig Latin and HiveQL were the transitional forms; the pattern they proved is now how every distributed engine works.
2010 – present
One language, interchangeable engines
Same SQL over new execution engines
Trino, BigQuery, Snowflake and Redshift are dialects, not new languages. The significant fact is the inversion: the language became the stable layer while the engine underneath was replaced repeatedly. Compatibility with an existing grammar turned into the main adoption strategy for new systems, because the cost of a new language is retraining everyone who uses it.
2023 – present
Natural language as input, not as a language
Generated SQL, vector similarity search
A plain-language question is not a query language — it has no fixed grammar, no optimiser and nothing to compile deterministically. It is an input, and it resolves one of two ways. Either it is translated into a real query language, almost always SQL, and executed as normal; or it is turned into a vector and matched by similarity against embeddings, which is retrieval by resemblance rather than by stated condition. The two are different in kind: one returns exactly the rows meeting a condition, the other returns the closest matches with no guarantee any of them qualify. This puts SQL roughly where assembly sits relative to a high-level language — still executed, still decisive, increasingly not typed by hand — and it makes reading a query more valuable rather than less, because the failure mode of a generated query is not a syntax error. It runs cleanly and answers a different question than the one asked.

What Disappeared

Ended as mainstream practice:
  • Writing the access path by hand — the retrieval strategy living in application code rather than in an optimiser
  • Hand-planned MapReduce jobs — the one period when scale was thought to require abandoning declarative querying
  • Pig Latin — a necessary transitional language, made redundant once SQL itself compiled to distributed plans
  • Vendor-only query dialects — standardisation made the grammar something no single vendor owned
Alive, but only in niches:
  • Pipeline log languages — dominant in operations and security, deliberately not general-purpose
  • Graph and time-series languages — Cypher, SPARQL and PromQL fit their data shapes better than SQL and stay confined to them
  • Stored procedures as business logic — still load-bearing in banking and ERP systems
