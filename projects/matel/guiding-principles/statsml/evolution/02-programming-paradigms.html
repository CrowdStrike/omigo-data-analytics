Evolution of Programming Paradigms

Not what we wrote code in, but how we organised it — and how the unit of composition kept getting smaller, then larger again.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
2015 onward
Serverless and declarative infrastructure
Lambda, Kubernetes, Terraform, dbt
Two convergent moves: compute became per-invocation with no server to manage, and infrastructure itself became something you declare rather than configure. Domain-specific languages spread into build systems, deployment, data transformation and policy.
2022 onward
Orchestrating models
Prompts, tool use, agent frameworks
The newest unit of composition is a natural-language instruction to a model, chained with tool calls. It resembles the earlier declarative move — state intent, let the system find the steps — but with a non-deterministic executor, which is genuinely new.
1950s – 1960s
Unstructured control flowgone
goto, line numbers, jumps
Execution jumped anywhere in the program. It worked for small programs and became unmaintainable past a few hundred lines, producing the "spaghetti code" that structured programming was invented to eliminate.
1960s onward
Procedural
Subroutines, functions, local scope
The procedure became the unit of reuse: a named block with inputs, outputs and its own scope. This is still the substrate everything else is built on — every paradigm since has been a way of organising procedures, not replacing them.
1970s
Declarative & logic programming
SQL, Prolog, regular expressions
Describe the result, let the system determine the steps. SQL is the enduring success: you state which rows you want and the query planner decides how to get them. Logic programming stayed academic, but the idea — separating intent from execution — kept resurfacing.
1980s – 1990s
Object orientation
Classes, inheritance, encapsulation
State was bundled with the code permitted to modify it. Deep inheritance hierarchies were heavily promoted at the time and are now generally avoided; encapsulation proved the more durable of the two ideas. The industry eventually settled on composition over deep inheritance trees.
1990s – 2000s
Distributed objects, then servicesgone
CORBA, DCOM, EJB, SOAP, WSDL
The attempt to make a call across the network look identical to a local call. It failed on the thing it tried to hide: networks fail, and pretending otherwise pushed the failure somewhere less convenient. SOAP and its XML contracts were heavy enough that REST displaced them almost entirely.
Late 2000s
Functional revival
Map/reduce, immutability, pure functions
Multicore made shared mutable state the central difficulty, and ideas from Lisp and ML became mainstream because immutability parallelises safely. Notably these were not new — they were fifty-year-old ideas that finally had a hardware reason to matter.
2010s
Microservices
Small services, independent deploys, REST/gRPC
The monolith split into independently deployable services, trading a compile-time boundary for a network one. It bought team autonomy and independent scaling, and it meant a single user action might touch a dozen services — each with its own datastore, and no single place to see the whole transaction.

What Disappeared

Ended as mainstream practice:
  • goto-driven control flow — survives as a constrained construct in a few languages, but structured blocks replaced it for control flow
  • CORBA, DCOM and distributed objects — the ambition to make remote calls indistinguishable from local ones, abandoned
  • SOAP, WSDL and the WS-* stack — enterprise-standard web services, displaced by REST and later gRPC
  • Enterprise JavaBeans — the heavyweight component model that made "enterprise Java" a pejorative
  • Deep inheritance hierarchies — taught as the point of OO, now widely treated as a design smell
  • The application server — deploying a WAR into a running container, replaced by self-contained services
Alive, but only in niches:
  • Logic programming — Prolog and its descendants persist in constraint solving and some verification work
  • Monolithic architectures — never actually died, and were partly rehabilitated once microservice operational costs became clear
  • Aspect-oriented programming — the ideas survive inside frameworks as annotations and interceptors rather than as a paradigm
