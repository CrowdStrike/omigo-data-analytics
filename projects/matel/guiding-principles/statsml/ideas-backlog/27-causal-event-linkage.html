Causal Event Linkage: Source/Target ID over Timestamp Ordering

TO DISCUSS

When event B was caused by event A, the logging system must record that explicit link (source_event_id → target_event_id). Relying on timestamp proximity alone to reconstruct causal chains is fragile — events arrive out of order, share timestamps at millisecond granularity, or get batched and delayed.

Motivating Example: E-commerce Search → View

The Causal Chain

User searches "running shoes" → sees results → clicks product → views product page.

The product view was caused by a specific search result impression. This is not just "two events close in time" — it's a directed link:

  • search_event_id: s_123 → produced impression_id: imp_456
  • impression_id: imp_456 → caused product_view_id: pv_789
  • Each hop has a source_id and target_id — the chain is explicit
Without this linkage: "user searched then viewed" could mean they searched, gave up, browsed homepage, and clicked a recommendation. Timestamp says the same thing — the causal path is completely different.
What Timestamp-Only Gets Wrong
  • Out-of-order delivery: product_view event logged before search event (async pipelines, different service latencies)
  • Batched writes: 50 events arrive with identical timestamps from a batch flush
  • Concurrent actions: user has two tabs open — search in tab A, browse in tab B. Timestamps interleave, causality doesn't cross tabs
  • Clock skew: client-side timestamp from phone is 3 seconds behind server timestamp from search service
  • Retry storms: same event logged 5 times with slightly different timestamps — which is the "real" one?
The risk: Analysis that assumes search→view based on timestamp proximity builds false funnels, miscalculates conversion rates, and attributes revenue to the wrong source.

More Domains Where Explicit Linkage Matters

Where Timestamp Ordering Fails
  • Ad click → conversion: Click happened on day 1, purchase on day 14. Timestamp gap is huge — only a click_id on the conversion event ties them. Without it, attribution is guesswork.
  • Alert → investigation → remediation (security): Analyst opens 5 alerts from a queue. Investigation of alert #3 starts before they close alert #1. Timestamp says #1 was remediated after #3 — wrong causal order.
  • API request → downstream calls: Microservice A calls B calls C. Response from C arrives before B's span closes. Distributed tracing (trace_id, span_id, parent_span_id) exists precisely because timestamps don't preserve call trees.
  • Medical: order → lab draw → result: Lab result timestamp is when the system processed it, not when blood was drawn, not when doctor ordered it. Three different timestamps, one causal chain — only order_id links them.
  • CI/CD: commit → build → test → deploy: Build might start before previous commit's test finishes. Pipeline DAG defines causality, not wall clock.
  • Financial: trade → settlement → confirmation: Settlement is T+2. Confirmation might arrive out of order. Only trade_id links the lifecycle.
The Structural Problem

Timestamp ordering gives you a total order of events. But causality is a partial order (DAG). You cannot reconstruct a DAG from a total order without additional information.

  • Events A and B might be concurrent (no causal link) — timestamp picks an arbitrary winner
  • Event C might cause event D despite D's timestamp being earlier (network delay, clock skew)
  • Two events at the same timestamp might be causally linked (sub-ms causality) or completely independent
This is Lamport clocks 101 — "happened before" is not the same as "has earlier timestamp." Distributed systems solved this decades ago. Data analytics still pretends ORDER BY timestamp is causality.

What Good Linkage Looks Like

Explicit Causal Fields
  • event_id — unique identifier for this event
  • caused_by_event_id — the event that triggered this one (nullable if root cause / user-initiated)
  • correlation_id — groups all events in a single logical flow (like trace_id)
  • sequence_number — monotonic counter within a flow (clock-independent ordering)
What This Enables for Analysis
  • True funnel construction: follow the chain, not the clock
  • Accurate attribution: which search/ad/recommendation actually caused the purchase
  • Latency measurement: time between cause and effect, not between arbitrary events
  • Anomaly detection: broken chains (effect without cause) = logging bug or system failure
  • Counterfactual analysis: what happens to downstream events when you remove a cause

Key Discussion Points

  • How does the pipeline detect when an analysis is relying on timestamp proximity to infer causality? (Signal: assumed sequence breaks under reordering)
  • When explicit linkage doesn't exist in the data — can we reconstruct probable causal chains? (Probabilistic matching by key + time window + constraints)
  • What metadata should a logging system capture to make causal analysis possible downstream?
  • Relationship to entity key granularity (#25): the "right key" for a causal chain is the chain itself, not any single entity
  • How does this interact with temporal dataset handling (#17)? Temporal ordering is necessary but not sufficient for causality
