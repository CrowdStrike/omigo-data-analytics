Anti-Pattern → Design Pattern Pairs

Left: the mistake (with domain example). Right: the correct design. Side-by-side pairs a system designer can directly implement.

Data Collection

Anti-Pattern
Impute all missing values with column mean

Treats all NULLs as "data collection failure." Fills with population average. Destroys the signal that absence carries.

Healthcare: makes healthy patients look sick. Cybersecurity: hides log deletion.
Design Pattern
Create is_missing feature + classify missingness type

MCAR: safe to impute. MAR: conditional imputation. MNAR: absence IS the feature. Always create binary "is_missing_X" alongside any imputation. Test if missingness predicts the target — often it's stronger than the value itself.

Anti-Pattern
UNION multiple sources into one table trusting schema match

Same column names + same types = same data, right? Wrong. "Amount" in USD from source A, cents from B, local currency from C.

Multi-hospital labs. Cross-region billing. Multi-platform analytics.
Design Pattern
Tag source_id + profile each source independently before joining

Add source_system_id to every row. Profile distributions PER SOURCE: mean, std, null rate, category values. If they differ for "same" column → semantic mismatch. Compare before combining, not after.

Anti-Pattern
Use "current state" queries for historical analysis

Query the database today for what happened last quarter. But: earnings restated, addresses changed, codes updated. Current values overwrite history.

Finance: restated earnings. HR: changed job titles. E-commerce: updated prices.
Design Pattern
Point-in-time database: store snapshots, query "as-of date X"

Every record versioned by timestamp. "What was this customer's address on March 15?" Not "what is their address now?" Requires append-only storage + temporal query capability. SCD Type 2 tables or event sourcing.

Profiling & Shape Detection

Anti-Pattern
Profile the entire column as one distribution

Compute mean, std, shape across ALL data. But if data has gaps, spikes, or sub-populations → the global profile is meaningless (mean in an empty gap).

Troponin: two clusters. Capital gain: spike + continuous. Hemoglobin: male + female.
Design Pattern
Value existence mapping → split → profile each segment

Step 1: Where does data EXIST? (gaps, spikes, clusters). Step 2: Split at structural boundaries. Step 3: Profile each segment independently. A mean across two clusters is fiction. Profile within each cluster.

Anti-Pattern
Use one bin count for all features

20 bins for everything. Power-law feature: 1 bin has 80% of data, 19 bins are empty. Uniform feature: works fine. One-size-fits-all = wrong for most.

Income. Hospital charges. File sizes. Any skewed distribution.
Design Pattern
Multi-resolution + percentile-width + meta-distribution Gini

Run at multiple bin counts (doc 13). Use equal-count bins where width encodes density (doc 27). Compute meta-distribution Gini (doc 28) — if > 0.7: feature needs adaptive treatment. Let the data tell you the right resolution.

Anti-Pattern
Report a single summary statistic ("mean = 50")

If distribution is bimodal (peaks at 20 and 80), mean = 50 represents a state that NEVER occurs. Summary stats are insufficient — they hide multi-modality, spikes, and tails.

CPU utilization. Income. Latency (cache hit vs miss).
Design Pattern
Always report shape + distribution alongside summary stats

Shape class (bell/skew/bimodal/spike) is as important as mean/std. Bimodal with mean 50? The mean is a lie — report the two peaks. Include at minimum: shape, skewness, Gini, max/mean ratio. Summary + shape together = truth.

Statistical Testing

Anti-Pattern
Report p-value without effect size

At n=100,000: enrichment 1.006× is "significant" (p<0.001). But useless for classification. Statistical significance ≠ practical significance.

Large datasets. Clinical trials. Any high-n analysis.
Design Pattern
Require BOTH p < threshold AND enrichment > minimum practical level

Gate: p < 0.05/n_tests (Bonferroni) AND enrichment > 1.5× (or whatever is actionable for your domain). Reject anything that's significant but trivially small. Report effect size FIRST, p-value second.

Anti-Pattern
Fine-bucket rare classes (20 buckets at 0.01% positive rate)

20 buckets × 0.01% positive = 12 positives per bucket. Below any statistical minimum. Every bucket is unvalidatable noise.

Fraud. Rare disease. Security attacks. Any extreme imbalance.
Design Pattern
Fewer buckets (5 max) or skip bucketing entirely → use rank tests

Mann-Whitney doesn't need bucketing — ranks positives vs negatives directly. If you must bucket: compute minimum n_positive needed per bucket (30). Then: max_buckets = total_positives / 30. At 600 positives: max 20 buckets. At 60: max 2.

Anti-Pattern
Check A/B test results daily until significant

"Peeking" inflates false positive rate from 5% to 25-50%. You stop when it looks good but would never stop when it looks bad.

Every A/B test platform. Product teams. Growth teams.
Design Pattern
Fix sample size upfront (power analysis). Don't peek. Or use sequential testing.

Pre-commit: "we will evaluate at n=5000 per group, not before." OR: use always-valid p-values / group sequential methods that mathematically account for continuous monitoring. No color-coding results until test is COMPLETE.

Feature Engineering

Anti-Pattern
Use CTR / engagement as item quality feature

CTR is 90% determined by position shown, not quality. Item at position 1: 30% CTR. Same item at position 10: 2%. The feature encodes YOUR bias, not the entity's property.

Search ranking. Recommendations. Ad targeting. Any system with position effects.
Design Pattern
Debias: CTR adjusted for position. Or: use random-position holdout traffic.

Option A: "CTR relative to position-average" as feature. Option B: Reserve 5% traffic for random ranking → measure CTR without position bias → use THAT as quality signal. Option C: Log position alongside every event and train position-aware models.

Anti-Pattern
Include a feature without checking causal direction

"Collection calls made" perfectly predicts loan default. But calls happen BECAUSE of default. It's a consequence, not a cause. Feature encodes the label.

Treatment predicting disease. Support tickets predicting churn. Retention call predicting loyalty.
Design Pattern
Timeline audit: for every feature, draw WHEN it was generated relative to target event

If feature_timestamp ≥ target_event_timestamp: it's leakage, remove it. This catches: post-event features, backfilled data, and consequence-as-cause. Automate: assert max(feature_timestamps) < min(prediction_timestamps) per entity.

Anti-Pattern
Remove protected attribute and assume fairness

Removed "gender" from model. But zip code, university, first name all correlate 0.8+ with gender. Model still discriminates through proxies.

Hiring. Credit. Insurance. Policing. Any regulated domain.
Design Pattern
Audit correlations with protected attributes. Remove proxies, not just the attribute.

Compute correlation of EVERY feature with protected attributes. If r > 0.5 with race/gender: it's a proxy. Either remove it, or apply fairness constraints (equalized odds, demographic parity). Test: does model output differ by protected group? If yes: unfair regardless of which features were removed.

Training & Evaluation

Anti-Pattern
Random train/test split on time-ordered data

Shuffles time. Future data in train, past data in test. Model "predicts" the past using future. Gap between random and temporal split: 10-30%.

Every financial dataset. User behavior. IoT sensors. Clinical events.
Design Pattern
Temporal split: train on [t₀,t₁], test on [t₁,t₂]. Never shuffle across time.

Simulate reality: model trained on everything up to date X, evaluated on everything after date X. This is what production actually faces — predicting the future from the past. If performance drops vs random split: that gap WAS leakage.

Anti-Pattern
Evaluate with accuracy on imbalanced data

"95% accuracy!" on 95/5 data = predicting majority class always. Recall on rare class = 0%. Completely useless detector.

Fraud (0.1%). Cancer (1%). Cybersecurity (0.001%). Any rare event.
Design Pattern
Evaluate with precision/recall/F1 on the minority class. Report at multiple thresholds (PR curve).

Ask: "of the things you flagged, how many were real?" (precision) and "of the real events, how many did you catch?" (recall). Report both + the tradeoff curve. Business decides where on the curve to operate based on cost of FP vs FN.

Anti-Pattern
Select features on full dataset, then split into train/test

Feature selection used test data to decide which features matter. Test is no longer independent. Performance inflated by 5-10%.

Univariate feature selection. Correlation screening. PCA. Any dimensionality reduction.
Design Pattern
Feature selection INSIDE cross-validation loop. Re-select per fold.

Pipeline: for each CV fold → select features on TRAIN fold only → build model on selected features → evaluate on TEST fold. Each fold independently selects features. Final feature set = intersection of what was selected across folds.

Deployment & Monitoring

Anti-Pattern
Deploy model and check results quarterly

Model silently degrades for 3 months. By the time you notice: thousands of wrong predictions served. Cause: upstream data change 2 months ago that nobody detected.

Silent schema changes. Feature store staleness. Concept drift. Population shift.
Design Pattern
Data validation on every input + distribution monitoring on every output

INPUT: schema checks, range checks, KS test vs last week, null rate changes → alert BEFORE serving. OUTPUT: prediction distribution vs expected → alert if predictions shift. Weekly: compare predictions vs actual outcomes (if available). Cheap, catches 90% of silent failures.

Anti-Pattern
Trust model confidence at face value

Model says "85% probability." But model was never calibrated. Actual rate when model says 85%: could be 50% or 95%. Confidence is a NUMBER, not a calibrated probability.

All probabilistic models. Risk scores. Churn prediction. Medical diagnosis.
Design Pattern
Calibrate predictions + report calibration curve alongside performance

Platt scaling or isotonic regression post-training. Verify: when model says "80%", does the event happen 80% of the time? Plot calibration curve (reliability diagram). If not calibrated: model probabilities are ordinal (ranking) not cardinal (probabilities).

Anti-Pattern
Train on batch-computed features, serve with real-time features

Batch: "30-day average" from perfect SQL query. Serving: same metric from streaming pipeline with different edge cases, NULL handling, timestamps. Subtle differences → silent performance drop.

Feature stores. Real-time ML. Any batch-train + online-serve system.
Design Pattern
Unified feature pipeline (same code for batch and serving) + feature parity monitoring

One function computes the feature, called both during training and serving. If impossible: log serving-time features, compare against batch-computed features for same records offline. Alert on systematic deviation. Any gap = training-serving skew.

How to use: For any decision in your pipeline, find the anti-pattern that matches what you're about to do. If you see yourself on the left side: switch to the right side. Every anti-pattern on the left has burned real teams with real consequences — often silently for months before discovery.
