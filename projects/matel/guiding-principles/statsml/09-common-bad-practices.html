Common Bad Practices in Data & ML

Practices that corrupt data pipelines, waste months of collection time, produce unreliable models, and create technical debt that compounds — specifically because data mistakes are measured in calendar time, not compute time. These aren't accidents. They're strategies that work for the individual while poisoning the data foundation.

Why data work is uniquely vulnerable: In software, a bad decision costs a sprint. In data science, a bad decision costs MONTHS — because models need time to collect training data, A/B tests need time to reach significance, and corrupted pipelines poison everything downstream silently. Each practice below exploits this asymmetry: the individual benefits immediately while the data/ML cost accumulates invisibly over months.
MANUFACTURED WIN

1. Model Rot & Refresh Theater

Deliberately let model degrade for months → stale predictions serve users. Refresh later, claim the improvement as new work. Cost: months of degraded predictions affecting downstream decisions.
MANUFACTURED WIN

2. Weak Baseline Selection

Compare your model against a naive baseline instead of the actual production system. "40% lift" vs random — not vs the rule-based system that already gets 35%. Team invests in a model that barely beats what exists.
MANUFACTURED WIN

3. Seasonal Attribution

Deploy model change before a natural data uptick. Seasonal pattern inflates your A/B test. Model change gets locked in based on inflated lift — when season ends, performance drops but the change is permanent.
MANUFACTURED WIN

4. Novelty Effect Harvesting

Any new recommendation/ranking change spikes engagement temporarily. Measure during novelty window → declare success. Model evaluated on non-representative data, long-term degradation hidden.
MANUFACTURED WIN

5. Fragmenting Simple Work

One feature engineering improvement split into 5 "model versions," each requiring its own A/B test (4-6 weeks each). 20-30 weeks of testing for what could ship in one iteration.
VISION

6. The 15% Solution Sold as 100%

Build the model for the easy 15% of cases, claim it "works." Remaining 85% (edge cases, rare events, distribution tails) never addressed. Model in production fails silently on hard cases nobody tests.
VISION

7. Demo-Driven Development

Hand-pick 5 examples where model works perfectly for the demo. Production data is messier, noisier, adversarial. Leadership greenlights based on curated inputs — model fails on real distribution.
VISION

8. Prototype-as-Product

Notebook with 3 examples → "proved it works" → ship. No held-out validation, no edge cases, no monitoring. Model in production with no drift detection, failing silently for months.
COMPLEXITY

9. Intentional Opacity

Pipeline with undocumented transformations, magic numbers, hardcoded thresholds. Only one person can debug it. When data quality issues arise: weeks of reverse-engineering before anyone can fix the pipeline.
COMPLEXITY

10. Over-Engineering as Empire Building

Feature extraction needs 200 lines of SQL. Instead: 5 microservices, a feature store, custom orchestrator. Data latency increases, more failure points, simple schema changes become month-long projects.
COMPLEXITY

11. Rewrite Theater

Declare pipeline "unmaintainable," propose rewrite. 18 months of zero model improvements while rebuilding what worked. Training data collection paused during migration. Competitors iterate while you rebuild.
METRICS

12. Sandbagging Estimates

Model retraining takes 3 weeks, estimate 8. "Deliver early." Those 5 sandbagged weeks = another experiment, another feature, another model iteration lost. In data work, each lost week is data not collected.
METRICS

13. Metric Redefinition at Measurement Time

Model accuracy target was 90% on hard cases. Redefine eval set to include easy cases. New accuracy: 92%. Model deployed with inflated metrics — fails on the hard cases that were the original motivation.
METRICS

14. Dashboard Cherry-Picking

Model has 12 evaluation metrics. 9 degraded, 3 improved. Present the 3. Model ships with known regressions hidden. Downstream systems consume degraded predictions for months.
METRICS

15. Alert Suppression Before Reviews

Silence data quality alerts before review cycle. No incidents on paper. Data quality issues accumulate silently — models train on corrupted data during the suppression window.
ATTRIBUTION

16. Riding the Tide

Platform grows 30% organically. Model contributes 2% incremental. Claim: "model drove 30% growth." Model gets investment disproportionate to its value. Resources misallocated from higher-impact data work.
ATTRIBUTION

17. Owning the Denominator

Model conversion rate low? Exclude hard-to-predict users from eval set. Rate "improves." Model never evaluated on cases where it fails. Production performance diverges from reported metrics.
ATTRIBUTION

18. Credit Arbitrage

Multiple teams built the data pipeline. You present results to leadership. People with actual data context get sidelined. Architecture choices made by someone who doesn't understand the data constraints.
SABOTAGE

19. Data Access Gatekeeping

Control access to key datasets. Competing team blocked for weeks on "governance review." In data work, delays are fatal — models need months of training data. 6-week delay on 8-week project = project killed.
SABOTAGE

20. Tribal Knowledge Monopoly

Pipeline logic, schema semantics, edge cases — undocumented, held by one person. Wrong preprocessing = months of training wasted. Wrong join = corrupted features. Departure = months of re-discovery.
NEGLIGENCE

21. Ignoring Silent Pipeline Corruption

No semantic validation at pipeline boundaries. Wrong-but-plausible values pass structural checks. Models train on poisoned features for months. Business decisions made on corrupted aggregations.
NEGLIGENCE

22. Skipping Data Checkpoints

Not persisting data at each transformation step. When model accuracy drops, can't inspect intermediate stages. Must re-run from scratch — if non-deterministic, may never reproduce.
NEGLIGENCE

23. Testing During Non-Standard Periods

Running A/B tests during holidays, fiscal year-end, elections. Data distribution is non-representative. Model "wins" on anomalous behavior, fails for the other 48 normal weeks. Results don't generalize.
NEGLIGENCE

24. Building Without Understanding Compliance

Pipeline works perfectly — and is illegal. Right-to-deletion impossible, data crosses borders, consent scope violated. Discovered 6 months post-launch. Retrofit costs 10-50× vs building it in from day one.
SABOTAGE

25. Silence After Noticing Data Issues

You notice data collection is broken or biased. You don't raise it — because fixing it delays YOUR project, resets YOUR timeline, or invalidates YOUR previous results. Every day of silence = another day of bad data poisoning downstream.
NEGLIGENCE

26. Abandoned Custom Features in Pipeline

Added tracking/feature for a short-term project. Project ended or didn't launch. Feature still runs — consuming compute, adding latency, polluting schemas. Nobody removes it because nobody owns it. Pipeline accumulates dead weight.
NEGLIGENCE

27. Schema Compliance Without Data Compliance

New feature launched with different event naming, different granularity, different timestamp format than existing systems. Can't JOIN or compare with historical data. Creates a parallel data universe that requires custom ETL to integrate.
METRICS

28. Beat the Metric

Engineering and science optimized to pass the test rather than improve the system. Goodhart's Law weaponized: VW detected test conditions to fake emissions, schools drill test patterns instead of teaching, companies staff ESG-reporting teams instead of reducing impact. Metric improves; system doesn't.
NEGLIGENCE

29. Stakeholder Favorite Examples

Learn which specific examples the decision-maker always tests, then optimize for exactly those inputs. They walk away "validated." The system barely works on everything else. Confirmation bias weaponized against the person doing the spot-check.
THEATER

30. Mathematical Costume

Same signal wrapped in unnecessary transforms to appear novel. CTR = clicks/impressions becomes 2^(log(clicks) − log(impressions)) — identical ranking, longer formula. The math adds no predictive power; it makes the decision harder to challenge.
PROCESS

31. A/B Test as Launch Justification

Every feature must pass an A/B test — not to learn, but to produce a green slide for launch review. The test has zero information value because a negative result would never kill the launch. Wastes experiment capacity with theater.
MEASUREMENT

32. Top-Line Metric Mandate

Requiring every feature to move company-wide metrics (GMV, Revenue, DAU) regardless of scope. Tiny features can't move macro-metrics in feasible sample sizes — good UX improvements die because of a power problem, not an effectiveness problem.
DARK PATTERN

33. Manufactured Engagement

Red badges, forced-login emails, urgency-framed notifications — exploiting cognitive reflexes to inflate DAU. The dashboard shows growth, but the user opened the app out of manufactured anxiety, not genuine interest. Metric is real; engagement is hollow.
DARK PATTERN

34. Notification Fatigue

When everything is marked urgent, nothing is. Flooding users with alerts drains cognitive capacity, destroys signal-to-noise ratio, and makes them unable to engage with genuine features. Each notification "works" individually while the sum degrades the product.
BEAT THE METRIC

35. Deployment Freeze for Uptime

The trivial way to meet your site uptime SLO: stop deploying. Nothing changes, nothing breaks, metric hits 99.97%. Meanwhile: fraud rules, security patches, revenue features all blocked. You "beat" reliability by making the system useless. Goodhart's Law in its purest form.
SABOTAGE

36. Malicious Compliance

Follow a directive to the letter while deliberately ignoring its spirit. "Retrain quarterly" → retrain with identical data. "Include confidence intervals" → report CI spanning [−∞, +∞]. Technically correct execution that produces the opposite of the intended outcome.
METRICS

37. Unqualified Percentage Reporting

Publish "99% accuracy" without sample size, confidence interval, or dataset provenance. Percentage normalization erases the denominator — results on 100 curated examples look identical to results on 100,000 production samples. Less effort → smaller dataset → more favorable numbers → format hides the shortcut.
SABOTAGE

38. Slow-Walking Competitors

Never say no — blocking is visible and politically risky. Instead, bury the competing project in process: schema alignment (+3 weeks), a security review (+2), a cost analysis (+2). You look collaborative; the project dies of delays before its window closes.
SABOTAGE

39. Strategic Incompetence

Do unwanted work badly enough that someone else takes it from you. Excellent at promotable projects, mysteriously terrible at documentation, on-call, and legacy maintenance — until the task migrates away and your plate is free for visible wins.
