## The Filing Clerk Inside the Coffee Shop's Till

**Tags:** `core idea` (blue), `everywhere default` (green), `Linux` (orange)

- **The till** — a coffee shop's Linux point-of-sale box appends every order to `orders.csv` on its disk
- **The clerk** — ext4 is the layer that turns "save orders.csv" into actual blocks written on the disk
- **The lookup** — a directory entry maps the name `orders.csv` to inode #482, the file's record card
- **The card** — the inode holds owner, size, timestamps, and the list of disk blocks the file uses
- **The default** — ext4 entered mainline Linux in 2008 and became the stock choice on major distros

*Example (italic):* When the barista rings up a latte, ext4 finds inode #482 from the name, follows it to the file's blocks, and appends the new row — the shop never thinks about it.

**Key point:** A filesystem is the bookkeeping between file names and raw disk blocks; ext4 is the unexciting, battle-tested version of that bookkeeping running on most Linux machines.

## One 400 MB Video, 102,400 Blocks, Four Extents

**Tags:** `worked example` (blue), `extents` (green)

- **The file** — the shop saves a 400 MB training video; with 4 KB blocks that is 102,400 blocks
- **The old way** — ext2/ext3 kept one 4-byte pointer per block: 102,400 pointers ≈ 400 KB of bookkeeping
- **The extent** — ext4 records a run instead: "start at block 20,000, length 30,000" is one 12-byte entry
- **Hand-check** — the video sits in 4 contiguous runs, so 4 extents × 12 bytes = 48 bytes total
- **The bonus** — up to 4 extents fit inside the inode itself, so this file needs no extra index blocks

*Example (italic):* 400 KB of block pointers versus 48 bytes of extents — about 8,500× less bookkeeping for the same 400 MB video, because the runs are contiguous.

**Key point:** Extents describe files as a few long runs instead of thousands of per-block pointers — the core upgrade ext4 made over ext3, and why it handles big files gracefully.

## The Power Cut at Closing Time

**Tags:** `where it's used` (blue), `journaling` (green), `crash safety` (orange)

- **The crash** — the shop loses power mid-write; half-updated bookkeeping used to mean a corrupted disk
- **The journal** — ext4 first writes intended metadata changes to a log, then applies them to the disk
- **The replay** — after reboot, ext4 replays or discards journal entries; the books are consistent again
- **The old cost** — pre-journal filesystems ran a full-disk `fsck` scan after a crash, minutes to hours
- **Where you meet it** — your Linux laptop's home dir, most cloud VMs, and Android devices run ext4
- **The lesson** — a data scientist's "server rebooted, data intact" moments are mostly ext4's journal working

*Example (italic):* After the 9pm power cut, the till reboots, replays the journal in about 2 seconds, and `orders.csv` opens cleanly — no 45-minute full-disk check before the morning rush.

**Key point:** Journaling turns "crash during a write" from a corrupted-filesystem event into a few seconds of replay — the reliability that made ext4 the boring default everyone trusts.

## The Journal Protects the Books, Not Your Latest Bytes

**Tags:** `common mistake` (red), `journal modes` (orange)

- **The confusion** — people hear "journaling" and assume no written data can ever be lost in a crash
- **Three modes** — ext4 offers `journal` (data + metadata), `ordered` (the default), and `writeback`
- **The default** — `ordered` mode journals metadata only; file contents go to disk outside the journal
- **What survives** — after a crash the filesystem structure is consistent, but seconds of data can vanish
- **Delayed allocation** — ext4 buffers writes before picking blocks, so unsynced data waits in memory
- **The fix** — programs that must not lose a write call `fsync`; ext4 guarantees durability only then

*Example (italic):* The till crashes right after printing a receipt; on reboot `orders.csv` is a healthy, readable file — missing the last order, because that row never reached the disk.

**Common mistake:** Reading "journaled filesystem" as "my data is crash-proof". Default ext4 guarantees the bookkeeping is consistent, not that your last unsynced write survived — durability needs `fsync`.
