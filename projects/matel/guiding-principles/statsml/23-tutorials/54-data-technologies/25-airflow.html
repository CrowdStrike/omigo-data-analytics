Airflow

Airflow runs your data pipelines on a schedule — a Python file declares the tasks and their order as a DAG, and a scheduler wakes up every night to run them

The Pipeline That Wakes Up at 2am

core ideaDAGsAirflow
  • The pipeline — a shop's nightly job: extract orders → transform → load warehouse → email report
  • The DAG — one Python file lists the four tasks and the arrows between them (a directed acyclic graph)
  • The scheduler — Airflow reads the schedule (2:00am daily) and creates each night's run by itself
  • The workers — worker processes pick up a task only after everything upstream of it turns green
  • The UI — a grid of colored squares shows every task of every run: success, failed, retrying, queued
  • Born at Airbnb — open-sourced in 2015; now the default heartbeat of most data platforms

At 2:00am the scheduler creates tonight's run on its own; extract starts first, and report cannot start until load is green.

Key point: An Airflow workflow is just Python declaring tasks and dependencies as a DAG — the scheduler decides when things run, the workers do the running.

The 2:07am Failure That Fixed Itself

worked exampleretries
  • The run — extract pulls 48,200 order rows between 2:00 and 2:04am and turns green
  • The failure — transform's attempt 1 dies at 2:07am on a dropped warehouse connection
  • The config — the task declares retries=2 with a 5-minute retry delay; no human is paged yet
  • The retry — attempt 2 starts at 2:12am and finishes green at 2:15am
  • The finish — load runs 2:15–2:21, the report mails at 2:22am; the morning dashboard never noticed

One dropped connection cost 8 minutes — 3 failing plus 5 waiting — and the pipeline still delivered before anyone woke up.

Key point: Retries are declared, not hand-coded — the scheduler reruns a failed task automatically, and downstream tasks simply wait until it turns green.

Backfills: Rerunning the Past

where it's usedbackfill
  • The heartbeat — nearly every table a data scientist queries was filled by a DAG run like this one
  • Run per date — each run is stamped with its data date; Monday's run fills Monday's partition
  • The outage — the warehouse is down Tue–Thu, so three nightly runs fail past their retries
  • The backfill — one command replays the three missed dates; each run fills only its own day
  • Sensors — sensor tasks wait for an upstream file or table to exist before the day's run proceeds

A backfill of Tue–Thu creates three dated runs; by Friday 9am the sales table holds all seven days again.

Key point: Because every run is tied to a data date, missed history is repaired by replaying dates — backfills are a built-in feature, not an emergency.

Run It Twice, Load It Twice

common mistakeidempotency
  • The discipline — a task rerun must produce the same result as running it once (idempotency)
  • The trap — a load step that appends with INSERT INTO sales SELECT ... adds the rows again on retry
  • The blowup — attempt 1 inserts 48,200 rows then dies; the automatic retry appends 48,200 more
  • The fix — delete-then-insert or overwrite the day's partition, so every rerun lands on a clean slate
  • Backfill chaos — replay a date twice more with an append task and that day quietly triples

After one retry the append version holds 96,400 rows for the day — the overwrite version holds exactly 48,200 no matter how many reruns.

Common mistake: Trusting retries and backfills with non-idempotent tasks. Both features assume a rerun is harmless — an appending load turns every one of Airflow's safety nets into a data-duplication machine.
