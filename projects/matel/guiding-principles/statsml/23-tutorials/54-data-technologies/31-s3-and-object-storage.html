S3 & Object Storage

Amazon S3 (2006) stores whole objects in buckets behind plain HTTP GET/PUT — cheap, extremely durable bytes that quietly became the disk under the whole modern data stack

A Bucket of Keys, Not a Disk of Folders

core ideakey → bytesHTTP
  • The shop — a web shop logs every click; each hour of traffic becomes one gzipped event file
  • The bucket — instead of a server disk, each file is PUT over HTTP into a bucket named shop-events
  • The key — an object's full name is one string: events/2026/08/26/hour-14.json.gz
  • No folders — the slashes are just characters in the key; the bucket is a flat key → bytes map
  • The API — the whole interface is roughly PUT, GET, LIST, DELETE over HTTP (S3, launched 2006)

The 2pm file goes up with one HTTP PUT and comes back later with one GET on the same key — no mount, no filesystem, no server to log into.

Key point: An object store is a giant key → bytes dictionary behind HTTP: whole objects in, whole or byte-range reads out, no in-place edits — addressed by key, not a disk you mount.

Pricing Two Terabytes of Click Events

worked exampleGB-monthlifecycle tiers
  • The pile — after a year the shop holds 2,000 GB of hourly event files in the bucket
  • Storage bill — standard tier at $0.023 per GB-month makes 2,000 GB cost $46.00 a month (illustrative)
  • Request bill — operations bill too: 1 million PUTs ≈ $5.00, 1 million GETs ≈ $0.40 (illustrative)
  • Lifecycle rule — files older than 90 days slide to infrequent access at $0.0125/GB-mo → $25.00
  • Cold tiers — archive at $0.004/GB-mo → $8.00; deep archive at $0.00099/GB-mo → $1.98
  • Hand-check — 2,000 × 0.023 = 46.00 and 2,000 × 0.00099 = 1.98 (exact arithmetic on illustrative rates)

The same 2,000 GB costs $46.00 a month hot, $25.00 in infrequent access, $8.00 archived, and $1.98 in deep archive — about 23× cheaper cold than hot.

Key point: You rent bytes by GB-month and pay per request; lifecycle rules slide aging data down storage classes, so the same objects get roughly 23× cheaper as they cool.

The Substrate of the Modern Data Stack

where it's useddurabilitydata lake
  • Durability — S3 documents 99.999999999% (11 nines) durability, kept by copies across availability zones
  • What that means — store 10 million objects and expect to lose one about every 10,000 years (documented)
  • Data lake — the shop's Parquet event files sitting in the bucket ARE the data lake; no database needed
  • Warehouses — modern warehouses keep table storage on object stores and rent query compute separately
  • Lakehouse — table formats (Iceberg, Delta, Hudi) are metadata layers over the same bucket of files
  • One copy — several engines read the shop's same 2,000 GB in place; nothing is copied per tool

The shop's analysts point a SQL engine straight at the bucket and query a year of clicks — the "warehouse disk" is the bucket itself.

Key point: Once bytes were cheap, 11-nines durable, and reachable over HTTP by anything, storage stopped living inside databases — the bucket became the shared bottom layer of the data stack.

It Looks Like a Filesystem — It Isn't

common mistakewhole-object writes
  • The trap — the keys look like paths, so the shop's intern treats the bucket like a mounted disk
  • No partial writes — fixing one bad row in a 1 GB object means GET 1 GB, edit, PUT 1 GB back
  • No rename — "moving" a key is a full copy to the new key plus a delete of the old one
  • No real dirs — listing a "folder" is a prefix scan over keys; an empty folder cannot even exist
  • Design around it — write many immutable objects and add new files instead of editing in place

Appending one 200-byte event to a 1 GB object re-uploads the whole 1 GB (sizes illustrative); appending to a local file writes just the 200 bytes.

Common mistake: Treating an object store as a filesystem. The unit of change is the whole object — tools that thrive on S3 (Parquet, Iceberg, Delta) are built around immutable files plus new-file appends, never in-place edits.
