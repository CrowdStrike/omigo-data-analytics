MongoDB

MongoDB stores each record as a JSON-like document — your objects go in shaped as they are, and adding a field needs no schema migration

The Catalog Where Every Product Is Different

core ideadocument databaseJSON
  • The store — an online shop sells t-shirts, laptops, and books from one product catalog
  • The mismatch — a t-shirt has size and color; a laptop has RAM and screen; a book has author and pages
  • The relational fix — one wide table with every column, mostly NULL, or a tangle of joined side tables
  • The document way — each product is one JSON-like document holding exactly its own fields
  • BSON — MongoDB stores documents as BSON, a binary form of JSON with real types like dates and numbers
  • No migration — a new attribute is just a new key in the next document written; no ALTER TABLE

The laptop document carries ram_gb: 16 and the book carries pages: 320 — same collection, different shapes, both valid.

Key point: A document database stores each record as a self-contained JSON-like object, so records with different attributes live naturally side by side in one collection.

Counting the Empty Cells

worked examplenulls vs documents
  • The catalog — 3 products; the union of all their attributes comes to 9 distinct columns
  • The wide table — 3 rows × 9 columns = 27 cells in the relational version
  • Filled cells — the t-shirt uses 4, the laptop 5, the book 4 — 13 cells actually hold a value
  • The nulls — 27 − 13 = 14 cells are NULL: 52% of the table stores nothing (exact here)
  • The documents — stored as documents, the same catalog is 13 fields total and zero NULLs
  • Hand-check — add a plant with 2 new attributes: the table becomes 11 columns and 27 NULLs

Adding one potted plant with pot_cm and sunlight pushes the table to 11 columns × 4 rows with 27 NULLs — the document version just gains one 4-field document.

Key point: The more varied the records, the more a single relational table fills with NULLs — documents pay only for the fields each record really has.

Why Developers Reached for It

where it's useddeveloper ergonomicsscaling
  • Ergonomics — the app's objects go in as they are; no object-to-rows mapping layer to maintain
  • New field, no ceremony — start writing warranty_months today; older documents simply lack it
  • Replica sets — the data lives on several servers; if the primary dies, a secondary takes over
  • Sharding — a collection splits across machines by a shard key, scaling writes horizontally
  • Growing up — lax durability defaults drew fire; acknowledged writes and WiredTiger answered it
  • Transactions — multi-document ACID transactions arrived in version 4.0, closing an old gap

The team ships the warranty feature the same afternoon (illustrative): documents written after 2pm carry warranty_months: 24, older ones read as missing.

Key point: MongoDB's pull was never raw speed — it was that developers could store data shaped like their code and change that shape without a migration.

Schemaless Doesn't Mean Design-Free

common mistakeimplicit schema
  • The trap — "schemaless" gets read as "no data design needed"; the schema just moves into app code
  • Field drift — with nothing enforcing names, color, colour, and Color quietly coexist
  • Silent misses — a query on color simply skips documents spelled differently; no error is raised
  • The old reputation — early write defaults returned success before data was safely on disk
  • The fix exists — per-collection schema validation rules and stricter write concerns are opt-in

A filter on color: "red" scans 4,020 documents spelled color, while 405 products spelled colour or Color stay invisible (counts illustrative).

Common mistake: Treating a document store as structure-free. The application still has a schema — it is just implicit, and every unchecked writer becomes a migration nobody reviewed.
