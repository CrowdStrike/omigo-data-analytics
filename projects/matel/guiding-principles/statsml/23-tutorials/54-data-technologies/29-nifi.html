NiFi

Apache NiFi moves data through a drag-and-drop flow of boxes and queues — and records every record's full history, so you can always ask "where did this come from?"

A Canvas Where Data Flows Through Boxes

core ideadataflowApache NiFi
  • The pipeline — a records team must pull a partner's nightly files off an FTP server and land them in a warehouse
  • The canvas — instead of code, they drag processors (GetFTP, RouteOnAttribute, PutHDFS) onto a canvas and wire them
  • FlowFiles — each file becomes a FlowFile: content (the bytes) plus attributes (filename, type, size)
  • The queues — every arrow between two processors is a queue; a FlowFile waits there until the next box is ready
  • The origin — NiFi began inside the NSA as "Niagarafiles" and was open-sourced through Apache in 2014

At 2:00am GetFTP pulls invoices.csv; it enters the flow as a FlowFile with attributes filename=invoices.csv, size=48 KB.

Key point: NiFi is flow-based programming: data travels as FlowFiles through a graph of processors connected by queues — a pipeline you draw, not one you code.

Routing 120 Files by Type

worked exampleback-pressure
  • The batch — tonight's FTP pull delivers 120 files: 70 CSV, 35 JSON, and 15 of unknown type
  • The route — RouteOnAttribute reads each FlowFile's filename attribute and sends it down one branch
  • Hand-check — 70 + 35 + 15 = 120; every file takes exactly one branch, none duplicated, none lost
  • Back-pressure — the csv queue is capped at 50 FlowFiles; when it fills, the upstream processor pauses
  • The drain — the warehouse writer empties the queue, the pause lifts, and the last 20 CSVs flow through

70 CSVs meet a 50-file queue cap: the first 50 queue up, back-pressure propagates upstream to pause GetFTP, and the remaining 20 enter only as the writer drains the queue.

Key point: Queues make the flow self-regulating — back-pressure pauses the upstream box instead of letting a slow downstream box get buried.

Every Record Remembers Where It Came From

where it's usedprovenanceaudit
  • Provenance — NiFi records an event for every FlowFile at every step: received, routed, modified, sent
  • The trace — clicking one FlowFile shows its full lineage, from the FTP fetch to the warehouse landing
  • The question — "where did this bad row come from?" is one provenance query, not a night of log-grepping
  • Regulated fields — government, healthcare, and finance adopted NiFi largely for this built-in audit trail
  • Replay — provenance keeps enough history to re-send a FlowFile through the flow from a recorded point

The lineage of invoices.csv reads RECEIVE 2:00:04 → ROUTE 2:00:05 → CONTENT_MODIFIED 2:00:07 → SEND 2:00:09 — four queryable events.

Key point: Data provenance is NiFi's signature feature — a queryable chain of custody for every record, which is why environments that must prove where data went choose it.

A Flow Manager, Not a Compute Engine

common mistakescope
  • The confusion — the canvas looks like an ETL tool, so teams try to run heavy joins and aggregations in it
  • What it is — NiFi moves, routes, and lightly transforms records; it is not built for big set-vs-set math
  • The cost — every step writes content and provenance to disk, so a 10M-row join thrashes the repositories
  • The split — the documented pattern: NiFi delivers data to a compute engine, then picks up the results
  • A cousin mix-up — attributes live on the JVM heap; stuffing whole payloads into attributes exhausts memory

A team rebuilds a warehouse join as a NiFi flow; the 10M-row merge that took SQL 40 seconds runs for hours while repositories churn.

Common mistake: Treating NiFi as the transformation engine. It is dataflow management with provenance — hand heavy computation to a system built for it and let NiFi manage the movement on either side.
