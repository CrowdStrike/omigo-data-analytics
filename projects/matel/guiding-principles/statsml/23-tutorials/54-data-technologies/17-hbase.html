HBase

The open-source Bigtable — one giant table kept sorted by row key, sliced into regions across many servers, built for billions of tiny timestamped rows

One Giant Sorted Table, Cut Into Regions

core ideawide columnBigtable
  • The table — a utility stores readings from 1,000 smart meters, one row per meter per minute
  • The row key — each row is named meterId#timestamp, like 0042#202608261407
  • Always sorted — HBase keeps every row in lexicographic row-key order, like a phone book
  • Regions — the sorted key space is cut into ranges called regions, each served by one server
  • Sparse — a row stores only the columns it has; a missing column costs zero bytes

Meter 0042's 2:07pm reading lands in the region covering keys 0250 down to 0000 — the server holding that slice of the alphabet writes it.

Key point: HBase is one huge sorted map from row key to columns; sorting is what makes range scans cheap, and cutting the sort order into regions is what makes it scale.

Scanning One Meter's Day by Hand

worked examplerange scan
  • The ask — plot meter 0042's usage for Aug 26: every reading whose key starts 0042#20260826
  • The scan — start at row 0042#20260826..., read forward, stop at 0042#20260827 — one range
  • The count — one reading per minute × 24 hours = 1,440 rows, all contiguous, all in one region
  • Sparse cells — every row has m:kwh; only 3 of the 1,440 carry an a:alert column
  • Versions — with the table set to VERSIONS=3, each cell keeps its last 3 timestamped copies
  • Padding matters — unpadded 42#... would sort after 100#...; zero-padding keeps meters together

The day's chart needs exactly 1,440 rows (exact: 60 × 24), fetched as a single sorted scan instead of 1,440 separate lookups.

Key point: Because rows are sorted, all of one meter's history sits shoulder to shoulder — a whole day is one cheap sequential read, not thousands of scattered ones.

Why Messenger and Time-Series Systems Picked It

where it's usedscale out
  • The paper — HBase is the Hadoop ecosystem's open-source build of Google's Bigtable design, on HDFS
  • Messenger — early Facebook Messenger stored its message history in HBase (publicly documented)
  • Time series — meters, metrics, and logs fit naturally: entity-prefixed keys, time-ordered scans
  • Per-row consistency — a read of one row always sees its latest write; no cross-row transactions
  • Auto-split — a region that grows too big splits in two; the new region can move to another server

As the meter table grows from 12 GB to 96 GB over four months, regions split from 2 to 12 with no manual resharding.

Key point: HBase trades SQL joins and cross-row transactions for a simpler promise — strongly consistent single rows, sorted scans, and tables that keep splitting as they grow.

The Hotspot: When Sorted Keys Backfire

common mistakerow-key design
  • The trap — key the table timestamp#meterId and every new row has the largest key so far
  • One region — sorted order sends all 60,000 writes/min to the tail region on one server
  • Idle fleet — the other servers hold cold history and do nothing; adding servers doesn't help
  • The fix — lead with the meter: meterId#timestamp spreads live writes across all regions
  • Other fixes — a salt prefix or a reversed timestamp does the same for purely time-keyed data
  • The cost — meter-first keys give up one global "latest everything" scan; queries go per meter

Timestamp-first, region server 1 absorbs all 60,000 writes/min; meter-first, the four servers take 15,200 / 14,900 / 15,100 / 14,800.

Common mistake: Choosing a row key that grows monotonically. Sorted storage turns "newest keys" into "one server" — the row key, not the cluster size, decides whether writes spread.
