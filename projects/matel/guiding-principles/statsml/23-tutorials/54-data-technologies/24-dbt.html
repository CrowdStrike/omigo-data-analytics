dbt

dbt turns SQL SELECT statements into a versioned, tested pipeline — transformations live in files, build in dependency order, and fail loudly when the data is bad

A SELECT Statement That Lives in a File

core ideaELTSQL
  • The load — an online shop copies raw order rows into the warehouse untouched, every night
  • ELT — extract and load come first; all transformation happens later, inside the warehouse
  • The model — a dbt model is a file holding one SELECT; running it builds a table or view
  • stg_orders — a staging model renames columns, casts types, and filters raw_orders
  • daily_revenue — a second model SELECTs from stg_orders and sums revenue per day
  • ref() — daily_revenue writes ref('stg_orders'), not a table name; the refs form a dependency DAG

One command, dbt run, walks the graph and builds stg_orders before daily_revenue — nobody remembers the order by hand.

Key point: dbt does not move data into the warehouse — it organizes the SELECT statements that transform data already there, and ref() tells it which SELECT must run first.

From 1,000 Raw Rows to 7 Daily Totals

worked exampledependency DAG
  • The raw table — raw_orders holds 1,000 rows for one week: order id, timestamp, amount, status
  • The staging step — stg_orders keeps only completed orders, dropping 12 cancelled test rows → 988 rows
  • The rollup — daily_revenue is SELECT order_date, SUM(amount) ... GROUP BY order_date → 7 rows
  • The totals — Mon $1,420, Tue $1,315, Wed $1,480, Thu $1,390, Fri $1,610, Sat $2,240, Sun $2,050
  • Hand-check — Saturday's 180 completed orders (illustrative) average $12.44 each: 180 × $12.44 ≈ $2,240
  • The rerun — a fix in stg_orders? dbt run rebuilds both models in order, no copy-paste

The week's 988 completed orders collapse into 7 rows whose totals sum to $11,505 — the exact sum of the seven bars.

Key point: A dbt project is a chain of SELECTs — each model's output table is the next model's input, and one command rebuilds the whole chain in DAG order.

Tests, Reviews, and the Analytics Engineer

where it's usedsoftware discipline
  • Version control — models are text files, so every change is a commit that can be reviewed and reverted
  • Code review — a teammate reads the diff to daily_revenue before it touches production, like any code
  • Tests — one YAML line declares not_null on amount; dbt test runs it as a query after each build
  • The catch — 3 rows arrive with NULL amounts; the test fails the build before dashboards read bad totals
  • Built-ins — dbt ships not_null, unique, and relationships (every order's customer must exist)
  • The role — this workflow created the "analytics engineer": SQL work run with engineering discipline

Without the test, Tuesday would silently undercount by 3 missing orders; with it, the run halts and someone gets paged instead.

Key point: dbt's contribution is not new SQL — it wraps SQL in the practices software teams already trust: git, review, automated tests, and docs generated from the project itself.

Hardcoding a Table Name Deletes the Edge

common mistakeref()
  • The shortcut — writing FROM analytics.stg_orders instead of ref('stg_orders') still runs today
  • What's lost — without ref(), dbt cannot see the dependency, so build order is no longer guaranteed
  • The failure — daily_revenue can build before stg_orders refreshes, quietly summing yesterday's rows
  • Environments — ref() also swaps schemas per environment; a hardcoded name points dev runs at prod
  • The rule — inside a dbt project, every model-to-model reference goes through ref(), no exceptions

A hardcoded daily_revenue built at 6:00am against a stg_orders refreshed at 6:05am reports the entire day one day stale.

Common mistake: Treating ref() as decoration. It is the mechanism that builds the DAG — skip it and the SQL still runs, but the ordering, lineage, and environment safety dbt exists for are gone.
