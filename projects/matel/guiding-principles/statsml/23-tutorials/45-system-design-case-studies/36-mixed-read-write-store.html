Mixed Read/Write Store

An order-status store where every write is read again within seconds — the read-optimized layout and the write-optimized layout each ruin the other path, so the answer is not a compromise engine but a decomposition: split by data age, then set the quorum dial

Both Paths Are Hot at the Same Time

core ideaboth paths hotno middle ground
  • The service — an order-status store where each write is read again within seconds by three apps
  • Both paths hot — reads and writes are both thousands per second; neither path is the rare one
  • Read-optimized — keep four pre-shaped copies: a read is one hop, but a write must touch all four
  • Write-optimized — append and compact later: a write is one op, but a read merges four fragments
  • The contradiction — each layout turns the other path's one unit of work into four; no middle wins

The courier taps "picked up"; seconds later the customer's map, the courier's job card, and the restaurant's board all read that same row.

Key point: When both paths are hot, the read-optimized and the write-optimized answers contradict each other — whichever path you make one hop, the other becomes four. Stop hunting for one layout and decompose the workload instead. Illustrative Example.

Split by Age, Not by Averaging

worked examplehot windowtwo tiers
  • The shape — reads pile onto rows written moments ago and fall off sharply with row age
  • The hot window — about 94% of reads land on rows less than a day old (illustrative mix)
  • The small share — one day out of a 30-day retention window is roughly 3% of stored rows
  • The hot tier — that 3% fits in memory, pre-shaped, so recent reads stay a single hop
  • The cold tier — older rows age out to an append-optimized engine where writes stay cheap

A read for an order placed four minutes ago never touches disk; a support agent's read of a three-week-old order pays the merge cost, and nobody minds.

Key point: Split by access pattern rather than averaging over it — a small memory-resident window of recent rows serves most of the reads, and everything older can live in an engine tuned purely for cheap writes. Illustrative Example.

The Quorum Dial: R + W > N

worked exampletunable consistencylatency dial
  • The replicas — each order key sits on N = 3 copies; a write waits for W of them, a read for R
  • The rule — R + W > N forces the read set and the write set to share at least one replica
  • Favor reads — R=1, W=3: a read answers from the nearest copy, a write waits for all three
  • Favor writes — R=3, W=1: a write is acknowledged at once, a read must consult every copy
  • Balanced — R=2, W=2: both paths wait for a majority, and both survive one node being down
  • The unsafe setting — R=1, W=1 sums to 2, not more than 3, so a read can miss the write entirely

Pin the courier's session to the replica that accepted his write and he sees "picked up" instantly, while the restaurant's board catches up a beat later.

Key point: R + W > N is the whole guarantee: the read set and the write set must overlap, so a read is forced to touch a replica that saw the write. Which side you make slower is a dial you choose, not a property of the database.

What Goes Wrong

failure modecontentionlast-write-wins
  • The averaged ratio — one service-wide read:write number can be true of the service and of no table in it
  • Per table instead — a profile table is read-heavy, an event log write-heavy; pick a layout per table
  • Lock contention — reads and writes on one hot key serialize, so read latency spikes behind the writes
  • Last-write-wins — drop the lock and the highest timestamp wins, whichever write actually came second
  • The silent loss — a slow clock makes the later write look earlier, so it is dropped with no error logged

The support agent sees "cancelled" confirmed on screen, and twenty seconds later every reader is back to "picked up" with nothing in the logs.

Common mistake: Sizing one engine for an averaged ratio, then trusting wall-clock timestamps to order concurrent writes. On a key both paths hammer, the choice is lock contention or a silently lost update — version vectors or a compare-and-set on the status field, not a clock.
