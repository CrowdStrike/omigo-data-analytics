## The Loop That Learns

**Tags:** `core idea` (blue), `JIT compilation` (green), `V8` (orange)

- **The engine** — V8 is Google's JavaScript engine, shipped inside Chrome at its 2008 launch
- **The job** — a checkout page calls `total(cart)` 10,000 times while re-rendering an order list
- **Interpret first** — Ignition turns the function into bytecode and just runs it, no compile wait
- **Watch for heat** — V8 counts calls; a function run about a thousand times is marked "hot"
- **Compile hot code** — TurboFan compiles the hot function to machine code using the types it saw
- **Keep a way back** — if a type assumption later breaks, V8 deoptimizes back to bytecode

*Example (italic):* After ~1,000 calls, V8 has only ever seen number prices — so TurboFan compiles a numbers-only fast version of `total`.

**Key point:** JIT tiering means starting slow-but-instant in an interpreter, then spending compile time only on code that has proved it is hot.

## Warm-Up, Speed-Up, and One Bad String

**Tags:** `worked example` (blue), `deoptimization` (red)

- **Warm-up** — calls 1–1,000 run interpreted at ~50 ns each: 50,000 ns spent while V8 learns
- **Tier-up** — from call ~1,000 the optimized version runs at ~5 ns per call, 10× faster
- **The bet** — TurboFan's machine code assumes `price` is always a number, since that's all it saw
- **The break** — at call 6,000 one item carries price "12.99" as a string; the assumption fails
- **Deopt** — V8 discards the machine code, falls back to ~50 ns bytecode, re-learns, re-optimizes
- **Hand-check** — 1,000×50 + 5,000×5 + 1,000×50 + 3,000×5 = 140,000 ns vs 500,000 interpreted

*Example (italic):* The 10,000-call run costs 140 µs with tiering — even after paying for one deopt — versus 500 µs interpreted-only, about 3.6× faster.

**Key point:** Deoptimization is the safety net that lets TurboFan gamble on observed types: wrong guesses cost a fallback, not a wrong answer.

## The Engine That Left the Browser

**Tags:** `where it's used` (blue), `runtimes` (green)

- **Node.js (2009)** — Ryan Dahl wrapped V8 with file and network APIs: JavaScript on the server
- **Electron (2013)** — desktop apps such as editors and chat clients ship a bundled Chromium + V8
- **Deno (2018)** — Dahl's second runtime, still V8 at the core, with a different security model
- **Cloudflare Workers (2018)** — V8 isolates run code at the network edge with fast cold starts
- **The point** — one engine's JIT speed made "JavaScript everywhere" a credible architecture

*Example (italic):* The same `total(cart)` function runs unchanged in a browser tab, a server process, and an edge isolate — V8 executes it in all three.

**Key point:** V8 made JavaScript fast enough that runtimes outside the browser adopted it wholesale, reshaping server-side development around one engine.

## One Shape, Fast; Many Shapes, Slow

**Tags:** `common mistake` (red), `hidden classes` (orange)

- **Hidden classes** — V8 gives objects with the same property layout a shared internal "shape"
- **Inline caches** — each `item.price` site remembers the shape it saw and jumps to a fixed offset
- **The mistake** — building items with properties added in different orders creates many shapes
- **Megamorphic** — past ~4 shapes the cache gives up; every lookup does a slow dictionary search
- **The fix** — construct objects with the same properties in the same order (one constructor path)

*Example (italic):* Items built in half a dozen different property orders turn every `item.price` lookup from ~1 ns into ~11 ns.

**Common mistake:** Treating property access cost as fixed. In V8 it depends on shape discipline — dynamic lookups are only fast while inline caches stay monomorphic.
