Confirmation Bias

Asymmetric scrutiny — failures get debugged, successes get celebrated uncritically

The Trap

You already hold a belief, then selectively notice confirming instances and dismiss contradictions. Skepticism is asymmetric — bad results get debugged, good results get celebrated.

  • 8 ML experiments fail — each one is thoroughly debugged
  • Run 9 shows AUC 0.91 — you stop. No leakage check, no seed variation
  • The desire to confirm was waiting for any number that permitted it

Example: Team spent 3 months on a redesign. Conversion flat overall. Slice by 20 dimensions until "mobile, West coast, week 2" shows +8% (n=1,200 of 50,000). Report: "works in our core segment."

Defense: Apply the same rigor to successes as failures. If run 9 looks great, ask "what bug would produce this?" Try to kill your result before believing it.

Where It Strikes

Domain Confirming behavior
A/B testing Slice until a subgroup shows significance
Model selection Report best fold / best seed / best metric
Feature engineering Keep features that "make sense" narratively
Code review Approve code that matches your mental model
Hiring Weight signals that match first impression
Research papers Cite papers that support your hypothesis
Product decisions Amplify positive user quotes in presentations
Debugging Test only the path you think is broken
Pattern: In every domain, the asymmetry is the same — time and rigor flow toward what contradicts your belief, while confirming evidence passes through unexamined.

In the ML Pipeline

Data science workflows offer countless opportunities for confirmation bias to slip in unnoticed:

  • Cherry-picking features — selecting variables that tell a compelling narrative rather than those with strongest signal
  • Early stopping — halting experiments when results first look favorable, skipping robustness checks
  • Ignoring failed folds — reporting mean CV but discarding the fold where the model collapsed
  • Seed shopping — running 20 random seeds and presenting the one that produced the best metric

Example: "We ran 5 seeds. Seed 42 gave AUC 0.89. The paper reports 0.89." The other four seeds gave 0.71, 0.74, 0.76, 0.73. The true expected performance is 0.77.

Defense: Report all seeds. Report the distribution, not the max. If you ran it 5 times, those 5 numbers ARE the result.

Pipeline Defense

Automation removes the human decision point where bias enters. The pipeline doesn't care which result you wanted:

  • Blind holdout — test set locked before training; no peeking, no re-splitting
  • Pre-registered analysis plan — metrics, thresholds, and stopping rules defined before data arrives
  • All-candidate evaluation — every model, seed, and fold gets equal treatment in the report
  • Immutable logging — you cannot delete the run that contradicts your story

The pipeline doesn't have a hypothesis. It doesn't want any particular result. It runs everything and reports everything — the antidote to selective attention.

Principle: If a human can choose what to report, confirmation bias is present. Remove the choice.
