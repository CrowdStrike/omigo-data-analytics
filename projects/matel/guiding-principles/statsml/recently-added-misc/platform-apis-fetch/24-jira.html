Jira Cloud REST API Backlog

Issues, workflow changelog and transitions, worklogs, boards and sprints — the record of what work was requested, and how long it sat in each state.

Last verified: August 2026

Overview

What It Provides

Separate APIs share one Jira Cloud site and are easy to confuse:

  • Platform REST API (/rest/api/3/) — issues, fields, comments, attachments, worklogs, projects, users, permissions, and the per-issue changelog.
  • Jira Software Agile API (/rest/agile/1.0/) — boards, sprints, backlog, epics, and rank. Sprints do not exist in the platform API; if you need sprint start/end/complete dates you must use the Agile API.

The issue document itself is a snapshot: current status, current assignee, current story points, plus a handful of timestamps (created, updated, resolutiondate). It answers "where is this now", not "how did it get here".

Workflow timing lives in the changelog, nowhere else. Cycle time, time-in-status, rework loops, and reassignment churn are all derived by replaying changelog.items where field == "status" (or assignee, priority, a custom field, …). No field on the issue holds "days in review".
Authentication & Scopes
  • Basic auth with an API token — account email plus an Atlassian API token, base64 encoded. Simplest path for a scheduled collector; carries that account's full permissions.
  • OAuth 2.0 (3LO) — for apps acting on behalf of a user, via api.atlassian.com/ex/jira/{cloudId}/…. Requires an explicit scope list.
  • Connect / Forge apps — JWT or Forge-managed auth, installed into the site.

Classic and granular scopes worth knowing:

read:jira-work read:jira-user read:issue:jira read:issue.changelog:jira read:issue-worklog:jira read:comment:jira read:field:jira read:sprint:jira-software read:board-scope:jira-software read:audit-log:jira
Granularity
  • One record per issue, with fields keyed by system name or customfield_NNNNN.
  • One record per changelog entry (a single user action), each containing one or more items — a field-level before/after pair with both raw ids (from, to) and rendered labels (fromString, toString).
  • One record per worklog: author, started, timeSpentSeconds, optional comment. This is self-reported effort, not observed effort.
  • One record per sprint, with state, startDate, endDate, completeDate.
Key Endpoints
  • GET /rest/api/3/search/jql — JQL search with nextPageToken cursor pagination and an explicit fields list. The older offset-based /rest/api/3/search is deprecated; new collectors should assume cursors.
  • GET /rest/api/3/issue/{issueIdOrKey} — single issue; expand=changelog,renderedFields,transitions.
  • GET /rest/api/3/issue/{issueIdOrKey}/changelog — the full history, paginated on its own (startAt, maxResults, isLast).
  • POST /rest/api/3/changelog/bulkfetch — changelogs for several issues in one call; far cheaper than one request per issue.
  • GET /rest/api/3/issue/{issueIdOrKey}/transitions — transitions available now to the caller, not transitions taken.
  • GET /rest/api/3/issue/{issueIdOrKey}/worklog, plus /rest/api/3/worklog/updated and /worklog/deleted for incremental sync.
  • GET /rest/api/3/field — the custom-field id to name mapping. Fetch this first; ids are site-specific.
  • GET /rest/agile/1.0/board, /board/{id}/sprint, /sprint/{id}/issue, /board/{id}/backlog.
  • GET /rest/api/3/auditing/record — administrative audit trail (permission and configuration changes), separate from issue changelogs.
  • POST /rest/api/3/webhook — register webhooks dynamically (OAuth apps only), each with a JQL filter and an event list such as jira:issue_updated, jira:issue_created, comment_created. GET /rest/api/3/webhook lists them; PUT /rest/api/3/webhook/refresh extends their life.

Webhooks can also be configured by an administrator in the UI, which is a different mechanism with different lifecycle rules from the API-registered kind.

Rate Limits
  • Jira Cloud applies cost-based rate limiting: a budget consumed at different rates by different endpoints, rather than one uniform requests-per-hour figure. Published budgets differ by auth type and endpoint class and change over time — do not hard-code a number.
  • Handle 429 by honouring Retry-After. Treat throttling as normal operation, not an error condition.
  • Expensive shapes are punished: fields=*all, expand on a large page, and one-changelog-request-per-issue. Request a narrow fields list and use the bulk changelog endpoint.
Business Scenarios
  • Cycle time and flow efficiency — time-in-status per issue, replayed from the changelog, split into working versus waiting states.
  • Rework / churn detection — count of backwards status transitions (In Review → In Progress) as a quality signal that no status field exposes.
  • Sprint commitment versus delivery — issues added after startDate (scope creep) require joining sprint dates to changelog entries on the sprint field.
  • SLA and ageing reports — first-response and first-transition latency.
  • Capacity reconciliation — worklogs against estimates, with an explicit caveat about self-reporting.
Restrictions & Gotchas
  • expand=changelog is paginated separately and truncated. The embedded changelog carries its own startAt/maxResults/total, independent of the search page size. Long-lived issues return a partial history with no error — the only signal is total exceeding what you received. Use the dedicated /changelog or bulk-fetch endpoint whenever completeness matters.
  • Results are silently filtered by permissions. An issue the collector's account cannot browse is absent from JQL results rather than returned as forbidden. A narrowed permission scheme looks identical to a drop in work volume.
  • Custom field ids are per-site. customfield_10014 means different things on different sites, and a field can be renamed without changing its id. Resolve names through /field every run.
  • API v3 returns Atlassian Document Format for descriptions and comments — a nested JSON node tree, not text. Plain text requires either walking the ADF or requesting rendered fields.
  • Changelogs do not cover every field. Comments, attachments and worklogs are their own resources; some field types and bulk/system operations produce no changelog item. Absence of an entry is not proof nothing changed.
  • Timestamps carry offsets and JQL is timezone-sensitive. updated >= -1d resolves against the caller's configured timezone, so the same query run by two accounts returns different sets.
  • Deletion is destructive. A deleted issue and its changelog leave no tombstone in the platform API, so a historical extract can shrink between runs.
  • Boards can be filter-backed. A board's issue list is defined by a saved filter that anyone can edit, so "issues on the board" is not a stable population over time.
  • Dynamically registered webhooks expire. Webhooks created through POST /rest/api/3/webhook have a limited lifetime and must be refreshed before they lapse. An unrefreshed integration stops delivering silently — there is no failure event, just an absence of events. Never use a webhook as the only source of a dataset; pair it with a periodic updated-window reconciliation read.
  • Webhook delivery is at-most-once in practice. Payloads can be dropped on delivery failure and are not replayed on demand, and events for issues the webhook's JQL filter excludes never fire at all. Bulk operations may emit one event, several, or none.
Changelog data is metadata about state, not the reasoning behind it. It tells you an issue moved to Blocked at 14:02 and by whom; the reason lives in a comment, a chat thread, or nobody's notes. Analyses that infer intent from transition patterns are inferring, not measuring.
