Salesforce & HubSpot BACKLOG

SOQL over Accounts, Contacts and Opportunities, stage-transition history, Field Audit Trail, Bulk API 2.0 and Platform Events; HubSpot CRM objects, engagements, email events, and the timeline.

Last verified: August 2026

Overview

What It Provides — Salesforce
  • Standard objects — Account, Contact, Lead, Opportunity, OpportunityLineItem, Case, Campaign, CampaignMember, Task, Event, User.
  • OpportunityHistory — one row per change to StageName, Amount, Probability, or CloseDate, each with CreatedDate. This is the object that makes pipeline analytics possible.
  • OpportunityFieldHistory and the per-object *FieldHistory tables — field-level old/new value pairs for fields explicitly enabled for history tracking.
  • Field Audit Trail — an add-on that extends field-history retention well beyond the standard window and exposes FieldHistoryArchive, queryable only in restricted ways.
  • SetupAuditTrail — administrative and metadata changes, distinct from data changes.
  • Bulk API 2.0 — asynchronous CSV-based extract and load for large volumes.
  • Platform Events and Change Data Capture — streaming change notifications over a replay-capable channel.
  • Reports & Analytics API — run existing reports and read their results.
What It Provides — HubSpot
  • CRM objects — contacts, companies, deals, tickets, line items, products, quotes, plus custom objects. All share one v3 CRM API shape with properties, associations, and search.
  • Associations API — typed many-to-many links between object records; this is where HubSpot's relational structure lives.
  • Engagements — calls, emails, meetings, notes, tasks, as first-class objects associated to records.
  • Email events — sent, delivered, open, click, bounce, spam report, unsubscribe, at the individual event level for marketing email.
  • Timeline API — write your own custom events onto a contact's timeline.
  • Property history — HubSpot returns per-property change history on a record when you ask for it via propertiesWithHistory.
  • Webhooks — subscription-based change notifications per app.
Authentication & Scopes
  • Salesforce — OAuth 2.0 via a Connected App. Common flows: web server (user context), JWT bearer (server-to-server, certificate-signed), and client credentials. Every request carries the org's instance_url, which differs per org and can change.
  • Salesforce permissions are layered. OAuth scope, profile/permission-set object and field-level security, and sharing rules all apply. A SOQL query run by an integration user returns only what that user can see — silently, with no indication rows were filtered. Field-level security can also make a queried field simply absent.
  • HubSpot — private app access tokens for single-account integrations, or OAuth apps with granular scopes (crm.objects.deals.read, sales-email-read, etc.). Legacy API keys have been retired in favour of these.
  • HubSpot tier gating. Object availability and API allowances depend on the subscription tier; custom objects, for instance, require Enterprise.
Always extract under a dedicated integration user with an explicitly documented permission set, and record which user produced each extract. A row-count drop after an admin edits a sharing rule is indistinguishable from a business decline unless you can attribute it.
Granularity

Salesforce: individual record, and individual field change where history tracking is on. HubSpot: individual record and individual engagement or email event. Both expose a last-modified timestamp (SystemModstamp / LastModifiedDate; hs_lastmodifieddate) that is the basis for incremental sync.

Key Endpoints
  • SOQL: GET /services/data/v61.0/query?q=SELECT+..., paginated via nextRecordsUrl.
  • GET /services/data/v61.0/sobjects/Opportunity/describe — field metadata, including picklist values.
  • Bulk 2.0: POST /jobs/query → poll → GET /jobs/query/{id}/results (CSV).
  • queryAll — includes soft-deleted and archived records that query omits.
  • HubSpot: GET /crm/v3/objects/deals?properties=...&propertiesWithHistory=dealstage
  • HubSpot: POST /crm/v3/objects/deals/search — filtered search with its own, tighter rate limit.
  • HubSpot: GET /email/public/v1/events — marketing email event stream.
Rate Limits

Salesforce governs by a 24-hour rolling org limit on total API calls, sized by edition and licence count, plus separate concurrent-long-running-request limits and Bulk API job/batch limits. The consequence: your budget is shared with every other integration and managed package in the org, so a well-behaved pipeline can be starved by someone else's. Check GET /services/data/v61.0/limits and the Sforce-Limit-Info response header rather than assuming headroom. SOQL itself also has governor limits — query row caps, and selectivity requirements on filters over large objects, which produce a non-selective-query error rather than a slow query.

HubSpot applies per-app and per-account limits with a short-window burst cap plus a daily cap, both tier-dependent, and returns remaining allowance in X-HubSpot-RateLimit-* headers. Search endpoints are limited far more tightly than plain reads, which surprises people who build extraction on /search.

For any full extract from Salesforce, use Bulk API 2.0. A million-record SOQL pagination loop consumes a million-ish calls against a shared 24-hour org budget; the equivalent Bulk job consumes a handful. This is not an optimisation, it is the difference between working and taking the org's other integrations down with you.
Business Scenarios
  • Pipeline velocity and stage-duration analysis — time in each stage, from history.
  • Win-rate modelling — features must be as-of-decision-time, which requires history (see below).
  • Forecast accuracy — comparing forecast-date snapshots against outcomes.
  • Lead-to-close attribution — campaign members joined to opportunities.
  • Rep activity correlation — tasks, calls, and meetings against outcomes.
  • Data-quality auditing — required fields left blank, stages skipped, close dates repeatedly pushed.
Key Restrictions & Gotchas
  • Field history must be enabled in advance, per field. If nobody turned it on for Amount two years ago, that history does not exist and cannot be recovered. This is the single most consequential configuration decision for CRM analytics, and it is usually made by someone who was not thinking about analytics.
  • Standard field-history retention is limited (on the order of a couple of years) unless Field Audit Trail is licensed. Long-horizon studies quietly lose their early cohorts.
  • FieldHistoryArchive is not a normal object. Field Audit Trail's archive supports only restricted query patterns — you generally must filter on the field-history-tracked entity and a bounded date range, and cannot treat it like a warehouse table.
  • OpportunityHistory only records the tracked subset — stage, amount, probability, close date. Other field changes go to OpportunityFieldHistory, if tracked, and are a separate query.
  • Deleted records vanish from query. Use queryAll to see IsDeleted rows, and know the recycle bin has a retention limit after which they are gone entirely.
  • Formula and roll-up fields are computed at read time. They are not historised and will not match a value you saw last month even if nothing "changed".
  • Salesforce Reports are not a data source. The Analytics API returns a report's rendered output, including its row limits, groupings, and filters. It is a view, not the underlying data, and its numbers depend on the report definition someone may edit.
  • HubSpot deals do not carry stage-duration fields you can trust as raw data — the hs_date_entered_* / hs_time_in_* properties are HubSpot-calculated, and they are derived from the same stage changes you can read directly. Prefer reconstructing from propertiesWithHistory=dealstage so your definition is explicit.
  • HubSpot property history has a depth limit per property and does not go back indefinitely. Long-lived records lose their earliest transitions.
  • HubSpot email open events are inferred from a tracking pixel and are systematically distorted by image proxying and pre-fetching. Open rate is not a measurement of attention; it is a measurement of pixel loads, and the relationship between the two has changed over time in ways that break year-over-year comparison.
  • Activity history is a record of logging, not of activity. A Task, Event, or HubSpot engagement exists because a human created it, a workflow generated it, or an email plug-in was installed and enabled. It does not exist because a conversation happened. Absence of an activity is not evidence the activity did not occur — mobile calls, corridor conversations, and meetings outside the connected calendar leave no trace.
  • Logging propensity varies systematically — by rep, by tenure, by manager, by whether the team is measured on activity counts, and by which integrations are deployed. That variation is not noise; it correlates with the outcomes being modelled, which makes it confounding rather than error.
  • Neither platform is a source of truth about revenue. A closed-won opportunity is a sales record, not a booking. Reconcile against the billing or ledger system.
  • Custom picklist values change. A stage renamed in the UI leaves old history rows carrying the old label. Any stage-based aggregation must map labels across time or it will split one stage into two.
"Deals with more logged activities close at a higher rate" is not a finding about sales effort. It is confounded at least three ways: longer-lived deals accumulate more activities regardless of outcome (exposure bias), reps invest logging effort in deals they already believe will close (reverse causality), and logging discipline varies by rep in ways that correlate with win rate for unrelated reasons. Condition on deal age, normalise per rep, and check whether the effect survives — it usually shrinks sharply. Where engagement must be measured rather than described, prefer machine-captured signals (email events, page views, calendar-integration meetings) whose capture is consistent, and treat hand-logged activity as an unevenly observed annotation.
This is the clearest case in this section for history over current state. An Opportunity row tells you the deal is Closed Won at $48,000 with a close date in August. OpportunityHistory tells you it entered Proposal in March at $72,000, sat there eleven weeks, was pushed three times, and was discounted twice. Every interesting question — which stage leaks, whether discounting predicts closing, whether pushed close dates ever recover — is answerable only from the second. And a win-rate model trained on current-state fields is trained on values that were set after the outcome, which is target leakage: it will validate beautifully and be useless in production, because at scoring time those fields do not yet hold their final values.

Salesforce vs HubSpot — Extraction Comparison

Dimension Salesforce HubSpot
Query model SOQL — relationship queries, parent and child subqueries, no arbitrary joins. REST list and /search with filter groups. No join; you traverse Associations.
Stage history OpportunityHistory as a queryable child object, filterable and joinable in SOQL. propertiesWithHistory on the record. Not independently queryable across records.
Field-level history Per-object *FieldHistory, must be enabled per field, capped field count per object. Property history is available broadly, with a depth limit per property.
Extended retention Field Audit Trail add-on, exposing FieldHistoryArchive with restricted query patterns. No comparable archive product; depth limits are the ceiling.
Bulk extract Bulk API 2.0 — async CSV jobs. Mandatory for large volumes. Paginated reads at page-size limits. No true async bulk export API.
Rate-limit shape 24-hour rolling org-wide call budget, shared with all other integrations. Per-app and per-account burst plus daily caps; /search far tighter than reads.
Streaming changes Platform Events and Change Data Capture, with replay IDs for gap recovery. Webhook subscriptions per app. No replay by ID; reconcile on hs_lastmodifieddate.
Deleted records queryAll surfaces IsDeleted; recycle bin has a retention limit. archived=true parameter; archived records are readable for a period.
Visibility filtering Sharing rules and field-level security silently reduce results per integration user. Scope-based; narrower and more visible in its failure mode.
Marketing engagement Requires Marketing Cloud or Pardot — a separate API and separate data model. Native: email events, timeline, and engagements in the same API.
Change provenance CreatedById on history rows; automation appears as the running user. sourceType distinguishes CRM_UI, WORKFLOWS, INTEGRATION, IMPORT.
