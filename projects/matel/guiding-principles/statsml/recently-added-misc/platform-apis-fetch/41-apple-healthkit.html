Apple HealthKit BACKLOG

On-device health datastore on iOS and watchOS. There is no server API — data is readable only by code running on the user's own device.

Last verified: August 2026

Overview

What It Provides

A typed, sample-level local store, HKHealthStore, holding health and fitness records written by Apple's own apps, by paired devices such as Apple Watch, and by third-party apps. It is an aggregator and a permission broker, not a measurement system of its own.

There is no HealthKit API to call from a server. No REST base URL, no OAuth server-to-server flow, no client credentials, no way for a backend to pull a user's health data. Reads happen only from code executing on that user's iPhone or Apple Watch, against the local store, with per-type permission granted by that user. Health data is encrypted on device; when the user enables iCloud sync it moves between their own devices under Apple's control and is not exposed to developers.

Pipeline consequence: any design that assumes a scheduled server-side fetch is impossible here. You must ship a mobile app. Ingestion is device-initiated, happens only when that app is launched or briefly woken in the background, and stops permanently on uninstall. Gaps are the normal case, not an incident.
Authentication & Permissions
  • Per-data-type authorization, with read and write requested independently via requestAuthorization(toShare:read:). There is no "all health data" grant.
  • Requires the HealthKit capability/entitlement plus purpose strings in Info.plist.
  • The user can grant, deny, or later revoke any single type from the Health app, at any time, with no callback to your app.
com.apple.developer.healthkit NSHealthShareUsageDescription NSHealthUpdateUsageDescription HKObjectType.quantityType(.heartRate) HKObjectType.categoryType(.sleepAnalysis) HKObjectType.workoutType()
Missingness is not identifiable. An app can query its write authorization status, but deliberately cannot determine read authorization. A denied read does not error — it returns an empty result set, indistinguishable from "this user has no data of that type". So an absent value means one of: permission denied, device not worn, or a true zero, and the API will not tell you which. Every imputation rule, every complete-case average, and every "engagement dropped" conclusion drawn from HealthKit data rests on an unobservable missingness mechanism. Record your own permission-request outcomes over time; it is the only way to partially recover the distinction.
Granularity
  • Optical heart rate on Apple Watch is duty-cycled, not continuous. Background readings are intermittent — sparse when the wrist is still, suppressed during motion, and absent when the watch is off. During an active workout session the sampling is far denser. Two days with the same nominal "heart rate" coverage can differ by an order of magnitude in sample count.
  • heartRateVariabilitySDNN arrives opportunistically — a handful of readings per day, taken under conditions the API does not describe. It is not a continuous series and daily means over it are means of a convenience sample.
  • oxygenSaturation background readings are periodic and frequently absent altogether.
  • stepCount arrives as interval samples with a start and end. These must be summed over non-overlapping windows. Averaging them, or summing overlapping ones, is wrong.
  • Every sample carries HKSourceRevision (writing app and build) and optionally HKDevice (hardware, model, firmware).
Source metadata is part of the measurement definition, not bookkeeping. A heart rate from a chest strap is derived from beat-to-beat R-R intervals. One from an optical wrist sensor is a periodic, motion-sensitive, duty-cycled estimate. One typed in by hand is a single spot reading. All three land in HealthKit under heartRate in count/min. Sleep staging from actigraphy plus PPG is a model inference, not polysomnography. Pooling across sources without a source or device term confounds algorithm and hardware with physiology, and the resulting "effect" can be entirely an artefact of who owns which watch.
Key Record Types
  • HKQuantityType — heartRate (count/min), heartRateVariabilitySDNN (ms), restingHeartRate, walkingHeartRateAverage, stepCount, distanceWalkingRunning, activeEnergyBurned, basalEnergyBurned, vo2Max (mL/kg·min), oxygenSaturation (%), respiratoryRate, bodyMass, appleExerciseTime, appleStandTime.
  • HKCategoryType — chiefly sleepAnalysis, whose HKCategoryValueSleepAnalysis values are inBed, asleepUnspecified, the stage values asleepREM / asleepCore / asleepDeep, and awake. Each is its own interval sample, so a night is a sequence of adjacent samples rather than one record.
  • HKElectrocardiogram — single-lead Apple Watch ECG with voltage measurements and a classification. Separate from the irregular-rhythm and high/low heart rate notifications, which are events emitted by Apple's own algorithms with their own thresholds and detection latency, not raw signal.
  • HKWorkout with HKWorkoutActivityType; routes via HKWorkoutRoute under HKSeriesType; dense series such as beat-to-beat data via HKQuantitySeries.
Sleep stages are not guaranteed to exist historically. The asleepREM / asleepCore / asleepDeep values arrived with iOS 16 and watchOS 9. Data recorded before that, and data written by third-party apps that do not stage, appears only as asleepUnspecified or inBed. A stage-level time series therefore has a hard left edge determined by OS version and by which app was writing — a discontinuity that looks exactly like a change in the user's sleep architecture if you do not check the value distribution by date.
Queries
  • HKSampleQuery — raw samples over a predicate, with sort and limit.
  • HKStatisticsQuery — one aggregate over one window. HKStatisticsCollectionQuery — bucketed rollups (hourly, daily) that apply HealthKit's own source handling, which is why it is the right tool for "steps per day".
  • HKAnchoredObjectQuery — incremental sync. Returns additions and deletions since an opaque anchor. Persist the anchor rather than a timestamp; a timestamp cannot express a retraction.
  • HKObserverQuery plus background delivery to wake the app when new data of a type lands.
  • HKQuery.predicateForSamples(withStart:end:options:) — the standard time predicate.
Rate Limits & Quotas

There are no request quotas, because there are no requests — reads are local storage and IPC. The real constraints are OS-side and qualitative rather than published numbers:

  • Background delivery frequency is a hint. Wake-ups are coalesced and throttled by the system according to battery, thermal state, and Low Power Mode. Immediate delivery is available only for a small subset of types, blood glucose being the canonical example; for most types the effective cadence is much coarser than requested.
  • Large historical queries are memory-bound. Pulling years of heart-rate samples in a single query can be terminated by the OS. Page by date range and by limit.
  • Upload throughput is your own backend's problem, plus whatever connectivity the user happens to have.
Business Scenarios
  • Decentralised clinical trials and remote patient monitoring, where a companion study app is the capture layer.
  • Insurance and workplace wellness programmes tied to activity targets — noting that the incentive to inflate the source is created by the programme itself.
  • Fitness and coaching apps that read workouts and heart rate, and write workouts back so the user's Health app stays coherent.
  • Chronic condition management: glucose, blood pressure, weight trend.
  • Sleep and activity cohort research, with the standing caveat that the cohort is iPhone owners who installed and kept an app.
Key Restrictions & Gotchas
  • No server API and no bulk export for developers. A user can export their own Health archive from the Health app; you cannot request one. No cross-user access, no population queries, no way to read anyone else's store.
  • No guaranteed backfill. You see what is on the device when your app first runs. History that predates the device, or that was pruned, is simply not there.
  • Deletions require handling. Only HKAnchoredObjectQuery surfaces deleted objects. Ignore them and your copy silently diverges from what the user sees in Health.
  • Multi-source double counting. The iPhone pedometer, a paired Watch, and a third-party app can all write steps for the same hour. The Health app applies a user-visible source priority ordering, and some types are de-duplicated for display, so the number the user sees is not the sum of raw samples. A pipeline that sums raw samples inflates — and inflates most for users with the most devices, which correlates with income and engagement.
  • Composite scores are model outputs, not measurements. Third-party apps write readiness, recovery, stress, and sleep scores into the store as opaque values. Those models change with app and firmware versions, so a long series of a vendor score is a series of different definitions.
  • Per-type revocation makes ragged panels. A user can revoke heart rate on day 40 while leaving steps on. Your panel becomes unbalanced mid-study, silently.
  • Availability is conditional. Gate on HKHealthStore.isHealthDataAvailable(); support varies by device class, and some types exist only where the relevant sensor does.
  • Policy limits, not just technical ones. App Review requires a health-related primary purpose, and HealthKit data may not be used for advertising or sold to data brokers. This constrains business models, not only code.
  • User-entered values are unvalidated. Hand-typed weights and injected step counts are indistinguishable from sensor data except through source metadata.
