Cloud Audit Logs Backlog

Control-plane and data-plane audit trails across AWS CloudTrail, GCP Cloud Audit Logs and Azure Activity Log — where the default configuration determines what is knowable later.

Last verified: August 2026

Overview

What It Provides

All three hyperscalers converge on the same conceptual split, and the split is the whole story:

  • Management / admin-activity events — API calls that create, modify, or delete resources and permissions. Who created the bucket, who attached the policy, who opened the security group. These are on by default everywhere, and their volume is modest.
  • Data events / data-access logs — API calls against the contents of a resource. Every GetObject on S3, every read of a Cloud Storage object, every DynamoDB item operation. These are off by default, are billed by volume, and can outnumber management events by several orders of magnitude in a busy account.

Per provider:

  • AWS CloudTrail — Event history in the console covers a short rolling window of management events only. A trail or event data store must be created to persist anything, and data events require explicit event selectors per resource type. Also: Insights events (anomalous call-rate detection) are separately enabled.
  • GCP Cloud Audit Logs — four streams: Admin Activity (always on, cannot be disabled, retained free for a long default window), Data Access (off by default except BigQuery, must be enabled per service and per permission type in IAM audit config), System Event (always on), and Policy Denied.
  • Azure Activity Log — subscription-level control-plane events retained for a short fixed window with no charge. Everything else — resource logs, resource metrics, and export beyond that window — requires a diagnostic setting per resource routing to Log Analytics, Event Hubs, or storage. Entra ID sign-in and audit logs are exported the same way.
These logs contain no user content — only metadata about actions. A CloudTrail GetObject record names the bucket and key that were read; the object body is not in the log. This is the defining characteristic of the audit-log category. The corollary is that these feeds are safe to centralise broadly, but they can never answer a question about what was in the data.
Authentication & Scopes
  • AWS — IAM role assumed by the reader; cloudtrail:LookupEvents for the short-window API, or s3:GetObject on the trail's destination prefix for the durable copy. cloudtrail:StartQuery for Lake/event data stores. Cross-account collection uses a role with an external id.
  • GCP — service account with roles/logging.viewer, or roles/logging.privateLogViewer which is additionally required to read Data Access logs. Read via entries.list on the Logging API, or from a sink destination (BigQuery, GCS, Pub/Sub).
  • Azure — Entra service principal with Reader at the appropriate scope, plus Log Analytics Reader to query a workspace. Note that a subscription-scoped reader does not see other subscriptions; management-group-level collection needs its own assignment.
Granularity

One record per API call, per provider's own schema — there is no cross-cloud normalised form, and mapping them onto a common model is the bulk of the engineering work. All three carry an actor identity, a source IP, a target resource, a request timestamp, and a success/error field. AWS separates requestParameters and responseElements; GCP uses protoPayload of type AuditLog with authenticationInfo, authorizationInfo and methodName; Azure uses an operationName plus authorization block. Identity representation differs most: AWS userIdentity distinguishes root, IAM user, and assumed role with its own session context; GCP reports a principal email that may be a service account; Azure reports an object id that must be resolved against the directory.

Key Endpoints
  • AWS: cloudtrail:LookupEvents (short window, management events, low throughput), cloudtrail:StartQuery / GetQueryResults against an event data store, or read gzipped JSON objects directly from the trail's S3 prefix — which is the only sane path for bulk.
  • GCP: POST /v2/entries:list with a filter on logName (cloudaudit.googleapis.com%2Factivity vs %2Fdata_access) and timestamp; or query the BigQuery dataset a log sink writes to.
  • Azure: GET /subscriptions/{id}/providers/Microsoft.Insights/eventtypes/management/values for the Activity Log, or a KQL query against the AzureActivity / AzureDiagnostics tables in Log Analytics.
Rate Limits
  • LookupEvents is throttled hard — it is an interactive lookup API, not a bulk extraction path. Attempting a backfill through it will take far longer than reading the S3 objects.
  • GCP entries.list has per-project read quotas and paginates with nextPageToken; a broad filter over a long window will page for a long time. Sink-to-BigQuery sidesteps this entirely.
  • Azure Resource Manager throttles per subscription per principal and returns the remaining budget in response headers; Log Analytics separately limits query concurrency and result size.
  • Across all three, the batch/export path is the supported way to move volume, and the query API is for investigation. Choosing the wrong one is the most common reason a collector cannot keep up.
Business Scenarios
  • Blast-radius reconstruction after an incident — what did this credential touch, in what order, from which IP.
  • Unused-permission analysis — actions actually invoked by a role over a window, versus what its policy allows. Requires data events to be meaningful for storage services.
  • Cost attribution and drift detection — which principal created the resources that appeared on the bill, and whether they were created outside of infrastructure-as-code.
  • Cross-account and cross-region anomaly detection — first-seen region, first-seen service, first-seen principal pairs.
  • Compliance evidence — demonstrating that privileged changes were reviewed, which requires the log to have existed continuously, not just to exist now.
Key Restrictions & Gotchas
  • Data events are off by default, everywhere. CloudTrail data events require event selectors; GCP Data Access logs require an IAM audit config per service (BigQuery being the notable exception that is on); Azure resource logs require a diagnostic setting per resource. The default posture answers "who changed the configuration" and is silent on "who read the data" — which is usually the question that actually matters after a breach.
  • Free retention windows are short and differ by provider and stream. CloudTrail console event history and the Azure Activity Log both retain only a short rolling window at no cost; GCP's Admin Activity default retention is considerably longer, and its Data Access default is short. Verify the current figure for your provider and stream — the values have changed over time — but treat all of them as "shorter than your audit cycle" unless you have configured export.
  • Delivery is near-real-time but not instant, and the lag is structural. CloudTrail batches events into S3 objects on a delivery interval measured in minutes; GCP writes are fast but sinks add their own latency; Azure diagnostic settings add ingestion delay into Log Analytics on top of Activity Log delay. Any query whose window ends at now systematically undercounts, and the undercount is largest for the most recent minutes. Lag your window, re-read with overlap, and deduplicate on the provider's event id (eventID, insertId, Azure correlation/event id).
  • Events can arrive out of order and occasionally late by more than the nominal interval. A pipeline that finalises a partition the instant the clock passes it will drop the tail.
  • Regional and global scoping is a real gap source. A CloudTrail trail that is not multi-region misses activity in other regions; some global service events are emitted in one region only. In GCP, organisation-level sinks are needed to catch projects created later. In Azure, per-subscription diagnostic settings do not cover subscriptions added afterwards.
  • Volume and cost are the reason data events stay disabled — and therefore the reason the audit trail has a hole. This is a budget decision masquerading as a technical default.
  • Enabling a log does not make the enablement retroactive, and no provider offers a way to reconstruct the period before it was on.
An event not enabled at the time it occurred is unrecoverable. You cannot backfill an audit log. Every other limitation on this page has a workaround: throttling yields to batch export, schema divergence yields to a normalisation layer, cost yields to sampling or tiering. This one has none. The consequence is that the configuration decision must be made before you know which question you will need to answer — which is why the defensible default is "enable broadly, retain cheaply, and tier down later" rather than "enable when a need appears."
