Web Search APIs BACKLOG

The retired Bing Search API and its substitutes, Brave and Google Programmable Search, Common Crawl as a bulk corpus, and Search Console Search Analytics — where query rows are privacy-filtered and therefore do not sum to totals.

Last verified: August 2026

Overview

What It Provides

Two unrelated things get called "search APIs" and conflating them is the most common design error in this area:

  • Search-result retrieval — you send a query, you get back documents. Google Programmable Search, Brave, Exa, SERP-proxy services. This tells you what a search engine returns.
  • Search performance reporting — Google Search Console Search Analytics. This tells you how your own property performed in Google Search: queries, clicks, impressions, CTR, position. It cannot tell you anything about anyone else's site.

Google Programmable Search Engine JSON API

This is not a general web-search API. It queries a Programmable Search Engine that you configure. You can set that engine to search the entire web, but the product remains engine-scoped: results can and do differ from what google.com returns for the same string, because the engine has its own configuration, refinements and ranking treatment. Using it as a proxy for "what Google shows people" is an unvalidated assumption, not a given.
  • Returns items[] with title, link, snippet, displayLink, and pagemap (structured data lifted from the page)
  • Supports date restriction, site restriction/exclusion, language and country restriction, safe search
  • Pagination via a start offset that is capped — you cannot page deeply into the result set, so "total results" is not a set you can enumerate
  • Pricing mechanism: a small free daily query allowance, paid queries above it, and a hard daily ceiling beyond which the API stops serving regardless of willingness to pay. The ceiling is the part that breaks study designs — it bounds queries per day, not per month, so you cannot buy your way through a large one-off crawl.

Bing Web Search API — Retired

The standalone Bing Search APIs were retired. Microsoft ended them and directed customers toward "Grounding with Bing Search" in Azure AI. That replacement is designed to ground a model's answer, not to hand you a raw ranked SERP for analysis — the output is a grounded response with citations, not an ordered result list with positions you can measure. It is a different instrument aimed at a different job. Many independent search-data products were built on Bing's API and had to substitute something else.

API Access Changes Break Longitudinal Research

A keyword-visibility or SERP-composition series that spans a provider retirement or substitution contains a discontinuity caused by changing the instrument, not by anything changing in the world. Different providers have different indexes, different crawl freshness, different snippet extraction, and different personalization and localization defaults. They are not interchangeable sensors. If your series steps at the same date you switched vendors, the null hypothesis is the vendor switch — and unlike a sampling problem, you cannot fix it after the fact by reweighting. The only mitigation is to run both providers in parallel across an overlap window and characterise the offset before you cut over.

Alternatives, and What They Are Actually Good At

  • Brave Search API — backed by an independent index, tiered plans, JSON results with snippets. Independent index means independent coverage: agreement with Google is an empirical question.
  • Serper and similar SERP-proxy services — return Google-like SERP structures. Two open questions attach to these: ongoing availability (they sit downstream of a party that did not authorise them) and terms compliance.
  • Exa — embedding/neural retrieval over its own crawled index. Built for semantic relevance, explicitly not for reproducing a SERP.
  • DuckDuckGo, Mojeek and other independent indexes; self-hosted options such as an index derived from Common Crawl.

The trade-off is worth stating plainly: reproducing Google's ranking and retrieving relevant documents are different objectives. Almost every alternative is good at the second and none of them is a faithful substitute for the first. Decide which one your analysis actually needs before picking a vendor — if the answer is "relevant documents", the retirement risk mostly stops mattering.

Common Crawl — a Bulk Corpus, Not a Search API

Common Crawl belongs in a different category from everything above. It is an open, non-profit web archive publishing monthly crawl snapshots as static files — there is no query endpoint, no ranking, no freshness. You do not ask it a question; you download or scan a corpus and compute over it. It answers "what is on these pages, in bulk", never "what does the web currently say about X, ranked".
  • Formats: WARC (raw HTTP request/response including full response bodies), WAT (extracted metadata including every outbound link, which is what makes web-graph work possible), WET (plain-text extraction, the usual starting point for NLP and language-model corpora).
  • Columnar index in Parquet, partitioned by crawl, queryable with Athena or Spark to select URLs by host, status code, MIME type or language before touching a single WARC file.
  • CDX index API — look up which crawls contain a given URL and at what byte offset, so you can range-fetch one record instead of a whole archive file.
  • Access: no API key, no tier, no quota. Files are publicly readable. The cost is your own egress and compute, and a monthly crawl is petabyte-scale, so the columnar index is the difference between a feasible job and an infeasible one.
  • Reproducibility is its underrated advantage. A study built on a live search API cannot be replicated — the ranker and the index have both moved and there is no version identifier telling you so. A study built on a named Common Crawl snapshot can be re-run byte-for-byte years later, because crawls are immutable. Where the work must be defensible, that outweighs freshness.
But it is not a uniform sample of the web. The crawl is seeded and link-driven, so well-linked pages are over-represented and long-tail hosts are thin; per-host fetch limits mean large sites are sampled rather than exhausted; robots.txt is honoured, so disallowed sections are structurally absent; and there is no JavaScript rendering, so client-rendered content appears as an empty shell. That last one is a bias that has grown as the web moved to SPA frameworks — meaning an older and a newer crawl are not equally representative even of the same sites. Language and country composition also shift between crawls, so comparing two snapshots without normalising by host and language will attribute crawl-composition change to real web change.

Google Search Console API — Search Analytics

A completely different animal: it reports on your own verified property.

  • Dimensions: query, page, country, device, searchAppearance, date
  • Metrics: clicks, impressions, CTR, average position
  • Also URL Inspection, Sitemaps, and Sites resources
  • Authentication is OAuth with the Search Console / webmasters scope; you must be a verified owner or a delegated user of the property
https://www.googleapis.com/auth/webmasters.readonly
  • Rolling window of approximately 16 months. Older data is dropped. If you want a longer history you must extract and warehouse it yourself, continuously — a backfill attempted later cannot recover what has already aged out.
  • Reporting lag. Data for the most recent days is incomplete and continues to fill in, so the last few points of any series will revise upward. Charting them as final produces a spurious decline at the right edge.

Query Rows Are Filtered and Anonymized

Google withholds rare queries to protect user privacy, and the consequence is arithmetic: the sum of clicks and impressions across query-dimension rows does not reconcile with the page-level or property-level totals for the same period. Analysts discover this gap, assume a bug or a pagination mistake, and go looking for the missing rows. They are not missing — they were never going to be returned.

What follows from it:

  • This is expected behaviour, not sampling error. It is a deterministic suppression rule applied to low-volume queries, not a random subsample. You therefore cannot correct it by rescaling to the known total — rescaling assumes the withheld rows resemble the returned ones, and they do not. They are systematically rarer by construction.
  • Long-tail query analysis systematically understates the tail, because the tail is precisely what gets withheld. Any conclusion of the form "most of our traffic comes from head terms" is partly an artifact of the filter.
  • The withheld share is larger for smaller sites and for niche topics — thinner traffic means more queries fall below the suppression threshold. So cross-site comparisons of "share of traffic from long-tail queries" are confounded by site size.
  • You cannot recover the missing rows by paginating further. More pages give you more of the returned set, never any of the suppressed set.
  • Monitor a query coverage ratio — summed query-row clicks divided by total clicks for the same period — as a data-quality indicator. Treating it as 1 is wrong; treating it as a constant is also wrong, since it moves with traffic mix. Watching it move is how you notice that a trend in "tail traffic" is really a trend in coverage.
Do not conflate the two truncations. A single Search Analytics request returns a bounded number of rows and you page through with a start row offset — that is a row-limit truncation and it is fixable by paginating. Privacy filtering is a separate mechanism and is not fixable at all. If you diagnose the reconciliation gap as a pagination bug, you will page forever and the gap will not close.

Business Scenarios

  • SEO and content performance reporting on owned properties (Search Console)
  • Competitive SERP monitoring, subject to the terms caveats
  • Retrieval augmentation for LLM applications — where relevance beats rank fidelity
  • Brand and misinformation monitoring
  • Academic study of search result composition and ranking behaviour

Key Restrictions & Gotchas

  • SERP results are localized and personalized. An unspecified locale gives you results for an unspecified population — the request is underdetermined, so the measurement is too.
  • Ranking is a moving target. Two identical queries minutes apart are not repeated measurements of the same quantity; there is no stable value being estimated.
  • Scraping SERPs directly violates Google's terms, which is why SERP-proxy vendors carry availability risk as a structural feature, not bad luck.
  • Snippets are extractive and regenerated independently of the page — snippet text can change while the page does not, so snippet diffs are a poor change-detection signal for content.
  • Search Console's position is an impression-weighted average, so it mixes together appearances in very different contexts. A "position improvement" can be a change in which queries were shown at all.
  • Programmable Search's capped start offset means result-set size is not enumerable; do not build metrics on "number of results".
  • Result counts are estimates, not counts. The totalResults field, and the "about N results" line on any consumer SERP, is an extrapolation from a partial evaluation of the index. It is known to be unstable — the same query can report very different totals minutes apart, and the figure typically shrinks as you paginate. Using it as a measure of prevalence, popularity or share of voice is one of the more common quantitative errors in this area.
  • Terms restrict what you may retain. Search providers generally forbid storing or caching results beyond a short window, re-serving them, or using the API to build a competing index; free tiers add attribution conditions. These constrain your architecture, not just your paperwork.
  • Snippets are not page content. Snippets are query-conditional extracts selected to match the query, so running sentiment or topic analysis on them measures the snippet generator's selection behaviour rather than what the pages say. Fetch the page, or use Common Crawl WET text.
  • Independent indexes are scarce. With Bing's API gone, the set of providers running their own crawl and serving it programmatically is small, and most "search APIs" on the market resell one of them. Vendor diversity in a procurement list is often not index diversity — two suppliers can fail together.
  • Every index here is survivorship-biased, and that is its defining property. Deleted pages, de-indexed pages, paywalled and login-walled content, robots-excluded sections, and anything removed under legal or policy pressure are all absent. Any estimate of how common something is on the web — a misinformation claim, a product assertion, leaked data — is computed on the surviving subset and therefore understates it. The shortfall is not random: removal correlates with exactly the material such studies are usually about, so the measurement error is largest precisely where the research question is.
  • Longitudinal comparison warning. Every quantity on this page has an unstable definition over time: what counts as a result, how totals are estimated, which pages a crawler chose to fetch, and whether JavaScript content was captured. A multi-year series drawn from search APIs or crawl archives is comparing measurements taken with different instruments. Record the provider, endpoint version, crawl id and full query parameters alongside every stored value, or the series cannot be interpreted later.
