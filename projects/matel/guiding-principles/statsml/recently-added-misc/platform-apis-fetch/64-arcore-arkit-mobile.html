ARCore & ARKit Mobile BACKLOG

Phone and tablet AR perception — pose, planes, depth, scene mesh, face blendshapes, body skeletons. Computed per frame on the device; with one narrow exception there is no server-side surface to query.

Last verified: August 2026

Overview

What It Provides — ARCore (Android)

  • Motion tracking — six-DoF device pose in a session-local world frame, from camera imagery fused with the IMU, carrying a tracking state and a reason for degradation
  • Plane detection — horizontal and vertical planes with polygon extents, growing and merging as tracking proceeds
  • Point cloud — the tracked visual feature points motion tracking is built on, exposed per frame with confidence values
  • Depth API — per-frame depth maps derived from device motion, and from a hardware depth sensor where one is present; enables occlusion of virtual content and coarse distance estimates
  • Light Estimation — ambient intensity and colour correction, plus directional and environmental HDR estimates so rendered objects sit plausibly in the scene
  • Augmented Faces — a front-camera face mesh with a fixed vertex topology, plus named region poses (nose tip, forehead left, forehead right)
  • Geospatial API — a high-accuracy global pose via Google's Visual Positioning System, and Geospatial anchors (WGS84, rooftop, terrain) shareable across devices and sessions; Streetscape Geometry in supported areas
  • Cloud Anchors — anchor descriptors hosted by Google so several devices can resolve the same physical anchor

What It Provides — ARKit (iOS)

  • ARFaceAnchor — a face mesh plus roughly 52 named blend-shape coefficients (eyeBlinkLeft, jawOpen, mouthSmileLeft, browInnerUp, tongueOut, and others), each a 0..1 value updated per frame. The richest facial-expression signal on any consumer device, and entirely local.
  • ARBodyAnchor — a skeleton of named joints in 3D with a defined parent/child hierarchy, from a single rear camera
  • Scene reconstruction — a scene mesh on LiDAR-equipped devices, with per-face mesh classification (floor, wall, ceiling, table, seat, window, door)
  • Plane detection with classification, people occlusion, and ARWorldMap for saving and relocalizing a mapped space — serializable, and shareable between devices by the app itself
  • Image and object detection/tracking against reference assets registered ahead of time

Authentication & Scopes

There is no OAuth surface and no bearer token, because there is no account-scoped data service. What gates access is the OS permission model plus, on Android, a runtime dependency and a device allowlist.

NSCameraUsageDescription android.permission.CAMERA ACCESS_FINE_LOCATION (Geospatial) Google Play Services for AR ARCore device allowlist API key / token (Geospatial, Cloud Anchors)

Only Geospatial and Cloud Anchors involve credentials at all, because only those cross the network.

The Geospatial Exception

Geospatial and Cloud Anchors are the one place a server is involved — and what comes back is a pose, not a history. VPS matches the live camera feed against Google's Street View imagery to resolve a global pose; Cloud Anchors store anchor descriptors so a second device can resolve the same point. Neither returns a queryable record of where users have been. These are localization services, not mobility datasets.

Granularity

  • Per frame — pose, point cloud, depth map, light estimate, face blendshapes, body joints: the current frame's state, then discarded
  • Per anchor, revised in place — planes and scene mesh, keyed by anchor ID and updated as scanning continues. Sampling the same physical table early and late in a session gives two different answers
  • Nothing is written to a timestamped store you can re-read. If the app does not capture it, it does not persist

AR Sensor Data Is OS-Mediated By Design

With the narrow exception of geospatial and cloud-anchor resolution, every signal above is computed on the device, handed to the running app for that frame, and dropped. There is no endpoint that returns a user's face blendshape history, body skeleton track, room mesh, or depth maps. There is nothing to backfill, nothing to re-query, and no cross-user dataset. If the app does not derive features and upload them — with consent and with the matching App Store / Play data disclosure — the data does not exist anywhere. Anyone planning perception-based analytics needs to know this before designing the study, not after.

Analytical Consequences

  • The dataset is a property of your app build. Coverage, sampling rate and field set are whatever your code chose to capture. Version-stamp every record with app build, OS version and device model; otherwise a change in capture logic is indistinguishable from a change in user behaviour.
  • Device heterogeneity is a first-class confound. LiDAR exists only on some iPhone and iPad models; Android depth quality varies enormously by device and by whether a hardware depth sensor is present; ARCore support is an explicit allowlist. A pooled AR dataset is a mixture over device capability, and an apparent improvement over time may only be a shift in the device mix of your user base. Better-sensor devices also cost more, so capability is entangled with the user population itself.
  • Frame rate is not guaranteed. Thermal throttling and tracking loss produce gaps and variable intervals, and throttling is worst in exactly the longest, most-engaged sessions. Treat AR streams as irregularly sampled, not as fixed-cadence time series — anything assuming constant Δt (differencing, FFT, naive velocity) inherits the throttling pattern as signal. Define rates per unit of wall-clock time and log the actual cadence.
  • Tracking loss is missing-not-at-random. Frames drop out in poor light, on featureless surfaces, and under fast motion. Those are not random omissions; they are a systematic sample of the harder conditions.

Business Scenarios

  • Virtual try-on and in-place product placement
  • Measurement apps built on planes and depth
  • Physical-space capture for floor plans and fit checks
  • Facial-expression-driven avatars, and expression or head pose as an accessibility input channel
  • Location-anchored AR experiences via Geospatial anchors

Key Restrictions & Gotchas

  • Camera permission gates everything; a denial is a silent no-data condition, not an error you will see in logs
  • Tracking state can degrade to limited or not-available and must be handled explicitly
  • Face and body tracking are biometric-adjacent and subject to platform policy on collection, retention, sharing and disclosure. The technical ability to compute a blendshape is not permission to keep it
  • ARCore requires Google Play Services for AR and a supported device; the allowlist is the effective population definition
  • Motion-derived depth on Android needs parallax — a stationary device produces poor depth
  • Capability probes are first-class API, not an afterthought. A dataset gathered without logging what was actually supported is a dataset of unknown composition
  • Simulators do not reproduce real sensing; anything sensor-dependent must be validated on hardware

ARKit face blendshapes — Swift (illustrative, abridged)

import ARKit

// Capability decides what the dataset even contains.
guard ARFaceTrackingConfiguration.isSupported else { return }

let config = ARFaceTrackingConfiguration()
config.maximumNumberOfTrackedFaces = 1
session.run(config)

// Delegate callback, once per tracked frame
func session(_ s: ARSession, didUpdate anchors: [ARAnchor]) {
    for a in anchors {
        guard let face = a as? ARFaceAnchor, face.isTracked
            else { continue }

        // ~52 named coefficients, each 0.0 ... 1.0
        let bs = face.blendShapes
        let jawOpen   = bs[.jawOpen]?.floatValue        ?? 0
        let blinkL    = bs[.eyeBlinkLeft]?.floatValue   ?? 0
        let smileL    = bs[.mouthSmileLeft]?.floatValue ?? 0
        let browInner = bs[.browInnerUp]?.floatValue    ?? 0

        // face.geometry.vertices -> fixed-topology mesh
        // face.transform         -> head pose (4x4)

        // These are rig-driving weights from an estimator,
        // not a physiological measurement. Persisted ONLY
        // if this app chooses to persist them.
        record(t: s.currentFrame?.timestamp,
               jawOpen, blinkL, smileL, browInner)
    }
}
