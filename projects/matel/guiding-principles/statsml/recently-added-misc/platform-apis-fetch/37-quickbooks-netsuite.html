QuickBooks & NetSuite BACKLOG

The general ledger as an API — invoices, bills, journal entries, chart of accounts, and vendors in QuickBooks Online; SuiteQL, REST records, and saved searches in NetSuite.

Last verified: August 2026

Overview

What It Provides

Both systems expose the accounting record itself, which makes them qualitatively different from a payments or commerce API. Stripe tells you money moved; the ledger tells you how the business decided to classify that movement. The classification is the point — and it is periodically restated.

QuickBooks Online (QBO) — transaction entities and name-list entities:

  • Invoice, Bill, Payment, BillPayment, CreditMemo — AR and AP transactions with line detail.
  • JournalEntry — direct debit/credit lines, the manual-adjustment path.
  • Account — the chart of accounts, with AccountType, AccountSubType, and Classification.
  • Vendor, Customer, Item, Employee — name lists.
  • Reports API — pre-built P&L, Balance Sheet, Trial Balance, AR/AP Aging, as QuickBooks itself computes them.

NetSuite — the record catalogue is far larger and configurable. Access is through:

  • SuiteQL — SQL-92-style queries over NetSuite tables (transaction, transactionline, account, customer, entity), with joins. This is the analytical interface.
  • REST Record Service — CRUD on individual records with a metadata catalog.
  • Saved Searches — searches defined in the UI, invokable programmatically. Business logic lives in the saved search, not in your code.
  • SuiteScript / RESTlets — custom server-side endpoints when the standard surface is insufficient.
  • SOAP SuiteTalk — the older, still-supported interface with richer write semantics for some records.
Authentication & Scopes
  • QBO — OAuth 2.0 with the com.intuit.quickbooks.accounting scope. Access tokens are short-lived (about an hour); the refresh token is long-lived but rotates on use and expires after prolonged inactivity. You must persist each new refresh token, or the connection dies silently.
  • QBO realm — every request is scoped to a realmId, i.e. one company file. Multi-entity groups mean one connection per entity and no cross-entity query.
  • NetSuite — Token-Based Authentication (OAuth 1.0a signatures) or OAuth 2.0, scoped to a role. The role's permissions determine what your query can see, so the same SuiteQL run under two integration roles returns different rows without erroring.
  • NetSuite account IDs appear in the hostname (<account>.suitetalk.api.netsuite.com), and sandbox accounts have a distinct ID suffix.
NetSuite's row-level security is applied silently. A pipeline that returns fewer rows after a permissions change looks exactly like a pipeline reporting a genuine business decline. Reconcile row counts against a known total, and record which role produced each extract.
Granularity

QBO: header plus Line[] array, each line carrying an account or item reference and amount. NetSuite: transaction header joined to transactionline, where the line is the ledger-posting grain — and where NetSuite adds its own system-generated lines that are not user-entered.

Key Endpoints
  • QBO query: GET /v3/company/{realmId}/query?query=SELECT * FROM Invoice WHERE ... — a SQL-like dialect, deliberately limited: no JOINs, no aggregates, no subqueries.
  • QBO CDC: GET /v3/company/{realmId}/cdc?entities=Invoice,Bill&changedSince=... — returns entities changed since a timestamp, including deletions. This is the incremental-sync mechanism.
  • QBO reports: GET /v3/company/{realmId}/reports/ProfitAndLoss?start_date=...
  • NetSuite SuiteQL: POST /services/rest/query/v1/suiteql with Prefer: transient header.
  • NetSuite records: GET /services/rest/record/v1/salesOrder/{id}
Rate Limits

QBO enforces a per-realm request rate and a lower per-app concurrency ceiling; the practical constraint is that batch and query endpoints cap returned rows (commonly 1,000 with pagination via STARTPOSITION/MAXRESULTS), so large extracts are many sequential calls against a modest rate. NetSuite governs by concurrency, not requests-per-second: an account has a limited number of simultaneous integration requests, determined by its service tier and any SuiteCloud Plus licences, and exceeding it returns a concurrency error rather than a rate-limit error. NetSuite also applies SuiteScript governance units to RESTlets, so an expensive script fails on units even when concurrency is fine.

Exact ceilings on both platforms are tier-dependent and revised over time, so treat them as configuration read from the response headers at runtime rather than constants compiled into a client.

These are different failure modes and need different client designs. QBO wants a slow serial loop with backoff. NetSuite wants a bounded worker pool — adding parallelism there does not speed you up, it starts failing other integrations sharing the same concurrency budget.
Business Scenarios
  • Financial reporting automation — nightly P&L and balance sheet extraction into a warehouse.
  • Revenue and spend reconciliation — tying commerce or payment data to what was actually booked.
  • AP/AR aging and DSO — collections analytics from invoice dates, due dates, and payment application.
  • Spend-by-vendor and category analysis — bills and expense lines rolled up by GL account.
  • Multi-entity consolidation — one QBO connection per entity, or NetSuite subsidiaries in one account.
  • Audit support — journal entries with who posted them and when.
Key Restrictions & Gotchas
  • The ledger is mutable and gets restated. Accountants reclassify, void, and adjust prior periods, often weeks after close. An extract of "March" taken in April and one taken in July will differ, legitimately. Version your extracts by as-of date or you will be unable to explain why last quarter's numbers changed.
  • Period close is a data event with no API flag. QBO has a closing date; NetSuite has period status. Neither surfaces prominently in transaction payloads. Data before the close date should be considered final; after it, provisional. Most pipelines ignore this distinction entirely.
  • QBO deletions are only visible through CDC. A plain query cannot tell you an invoice you ingested yesterday has been deleted — it simply is not in the result set, which is indistinguishable from a filter mismatch. Voided transactions, by contrast, persist with zeroed amounts.
  • QBO query has no JOIN and no aggregation. You cannot ask for revenue by account; you pull lines and aggregate yourself. This is the single biggest surprise for anyone expecting SQL.
  • QBO does not expose a general audit-history endpoint. The Audit Log exists in the UI. Objects carry MetaData.CreateTime and LastUpdatedTime — a last-write timestamp, not a change history. You can see that an invoice changed; you cannot see what it changed from.
  • NetSuite custom fields are account-specific. custbody_* and custcol_* names differ per customer implementation, so nothing built against them is portable, and the metadata catalog must be read, not assumed.
  • NetSuite saved searches embed logic outside your repository. Someone editing a saved search in the UI changes your pipeline's semantics with no code change and no deploy.
  • SuiteQL's dialect is not standard SQL. Function support is partial, and the underlying table shapes are not the documented record shapes — transaction/transactionline in SuiteQL do not map one-to-one onto the REST record model.
  • Currency and subsidiary. NetSuite amounts exist in both transaction and base currency; picking the wrong one in a consolidated report is a common and quiet error.
Neither system gives you field-level change history as a first-class query. This is the mirror image of Stripe's event log: you get authoritative current state and a last-modified stamp, but reconstructing how a figure evolved requires that you snapshot it yourself on a schedule. If "why did last quarter move?" is a question anyone will ask, the answer must be built into your ingestion from day one — it cannot be recovered later from the API.

NetSuite — POST /services/rest/query/v1/suiteql

{
  "q": "SELECT t.tranid, t.trandate, t.type, t.status,
               tl.id AS line_id, tl.debitforeignamount,
               tl.creditforeignamount, a.acctnumber, a.accountsearchdisplayname
        FROM transaction t
          JOIN transactionline tl ON tl.transaction = t.id
          JOIN account a ON a.id = tl.expenseaccount
        WHERE t.trandate BETWEEN TO_DATE('2026-07-01','YYYY-MM-DD')
                             AND TO_DATE('2026-07-31','YYYY-MM-DD')
          AND t.posting = 'T'
        ORDER BY t.trandate"
}

t.posting = 'T' matters: omit it and you pull non-posting transactions such as sales orders and estimates into a ledger extract, inflating every total.

QuickBooks Online vs NetSuite — Extraction Comparison

Dimension QuickBooks Online NetSuite
Query language Restricted SQL-like dialect. No JOIN, no GROUP BY, no aggregate functions. SuiteQL — real joins, aggregates, subqueries over relational tables.
Where aggregation happens In your code, after pulling all lines. In NetSuite, which is far cheaper for wide extracts.
Incremental sync CDC endpoint by changedSince; includes deletions. Filter on lastmodifieddate in SuiteQL. Hard deletes are not reported.
Throttling model Request rate per realm, plus row caps per page. Concurrent-request budget per account, plus SuiteScript governance units.
Right client shape Serial loop, exponential backoff, resumable cursor. Bounded worker pool sized below the concurrency budget.
Multi-entity One connection and one realmId per company. No cross-entity query. Subsidiaries within one account; consolidation is queryable, currency handling is on you.
Schema stability Fixed entity set. Custom fields are limited and well-bounded. Per-account custom records and custbody_* fields. Read the metadata catalog; assume nothing.
Pre-built reports Reports API returns QuickBooks' own P&L / Balance Sheet computation. Saved searches; logic is owned by whoever edits them in the UI.
Change history Not exposed. SyncToken and LastUpdatedTime only. System notes exist in the UI; not a convenient bulk query surface.
Non-posting records Estimates and sales receipts are distinct entities you must choose to include. Everything lives in transaction; you must filter posting = 'T' explicitly.
