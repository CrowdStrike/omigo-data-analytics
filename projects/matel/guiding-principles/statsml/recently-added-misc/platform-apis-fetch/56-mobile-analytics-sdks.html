Mobile Analytics SDKs BACKLOG

Firebase Analytics, GA4 Data API, Amplitude, Mixpanel. The only APIs in this group where you own the schema — and therefore own the gaps.

Last verified: August 2026

Overview

What It Provides

First-party in-app instrumentation. Unlike Screen Time, UsageStatsManager, or the store consoles, nothing here is withheld by the platform — the SDK records what you told it to record, about your own app, and hands you the raw stream if you pay for the export path.

  • Firebase Analytics (GA4 for apps) — automatically collected events (first_open, session_start, screen_view, app_remove, app_update, in_app_purchase, app_exception) plus logEvent custom events with parameters, setUserProperty, and setUserId. Reading paths: BigQuery export (event-level rows) and the GA4 Data API (aggregate reports).
  • Amplitude — HTTP V2 event ingest; reads via the Export API (gzipped JSON of raw events by hour range), the Dashboard/Batch REST APIs for chart-shaped results, and Behavioral Cohorts for segment membership.
  • Mixpanel — /track and /import for ingest; raw event export endpoint for event-level data, Query APIs (segmentation, funnels, retention) for aggregates, plus JQL for server-side custom computation over the raw store. Note that Mixpanel has been steering new work toward the newer query surfaces, so treat JQL as legacy-but-present rather than the default recommendation.
Authentication & Scopes
  • Firebase / GA4: SDK writes with the bundled config file (no server credential). Reads: BigQuery via Google Cloud IAM on the dataset; GA4 Data API via OAuth or a service account granted a role on the GA4 property. The property-level grant is separate from Cloud IAM and is a common misconfiguration.
  • Amplitude: API key for ingest; API key + secret key (HTTP Basic) for Export and Dashboard APIs. Region matters — EU-residency projects use different hostnames, and calls to the wrong region return empty rather than an error.
  • Mixpanel: project token for ingest; service account (username/secret) or project secret for exports and queries, with EU/US residency hostnames again distinct.

Granularity — the crux of this page

Every vendor here exposes two tiers, and they are different datasets, not two views of one:

  • Raw / event-level export. BigQuery events_YYYYMMDD tables, Amplitude Export, Mixpanel raw export. One row per event with the full parameter bag, the user pseudo-id, device and geo columns. Full fidelity. This is what you model on.
  • Aggregate report API. GA4 Data API, Amplitude Dashboard, Mixpanel Query. Pre-computed metrics over dimensions, subject to the vendor's own cardinality handling, thresholding, and — in GA4's case — sampling on large or complex queries. This is what your dashboard shows.

GA4 responses carry explicit metadata for this: samplingMetadatas, and (other) rows when a dimension exceeds cardinality limits. Amplitude and Mixpanel apply their own row limits and top-N truncation on chart queries. Read those flags; they are the difference between "the number moved" and "the estimator changed".

Aggregate and raw will disagree, legitimately. The instinct on discovering a gap between a GA4 dashboard figure and a BigQuery COUNT(*) is to declare one of them broken and reconcile to the other. That is the wrong frame. They differ for identifiable, non-bug reasons: sampling on the aggregate side; cardinality bucketing into (other); thresholding when demographic or signals-derived dimensions are requested on small audiences; different session and attribution definitions applied at query time versus stored on the row; late-arriving events landing in BigQuery after the aggregate snapshot; and time-zone/day-boundary differences between the reporting property and the export table suffix. The correct practice is to pick one as the system of record for each question, document which, and expect a stable non-zero delta — then alert on changes in the delta, because a change means a pipeline problem while a constant offset does not.
Key Endpoints & Interfaces
  • GA4 Data API: POST properties/{id}:runReport, :runRealtimeReport, :batchRunReports, :runPivotReport
  • BigQuery: analytics_<property_id>.events_YYYYMMDD, plus events_intraday_* when streaming export is on
  • Amplitude: GET /api/2/export?start=YYYYMMDDTHH&end=..., GET /api/2/events/segmentation, /api/5/cohorts
  • Mixpanel: GET /api/2.0/export, /api/query/segmentation, /api/query/funnels, /api/query/retention, POST /api/query/jql
Rate Limits

Described qualitatively because published figures differ by plan and change often — read the vendor's current limits page and the response headers rather than trusting a number in a doc:

  • GA4 Data API enforces per-property token-bucket quotas (concurrent requests, tokens per day/hour) and returns quota consumption in the response when requested. Complex, high-cardinality reports consume far more tokens than simple ones, so the effective limit depends on query shape.
  • BigQuery has no per-request analytics quota but charges by bytes scanned — partition-prune on the table suffix or a full-history scan gets expensive fast.
  • Amplitude Export is bounded by time window per call (hour-granularity ranges, with a cap on span) and by response size; large days must be paged by hour.
  • Mixpanel raw export is rate-limited and concurrency-limited; query endpoints have separate, tighter limits than export.
  • All three: exports are eventually consistent. Re-pulling yesterday tomorrow returns more rows.
Business Scenarios
  • Funnel and retention analysis, cohort LTV modelling
  • Feature-adoption measurement and experiment readouts
  • Churn prediction — feature engineering off raw event streams
  • Crash/exception correlation with behavioural sequences
  • Cross-platform user journey stitching via your own user ID
Key Restrictions & Gotchas — what these do NOT give you
  • No visibility outside your app. No competing-app usage, no device-wide behaviour. See the Screen Time and UsageStatsManager pages — this is where that limit lands.
  • Consent gating. ATT on iOS governs IDFA, not first-party analytics, but consent frameworks and Firebase's own consent-mode settings do suppress or degrade collection. Your event volume is a function of consent rates, which vary by region.
  • Post-ATT data is a non-random subset. Users who allow tracking are not a random draw from your base — permission rates vary systematically with region, OS version, age, and privacy attitude, and those same attributes predict engagement and spend. So attribution, ad-source and any IDFA-joined analysis describes the more permissive slice of your users, and enlarging the install base does not shrink that gap. It is bias, not noise.
  • The newest period is always short. The SDK batches on device and uploads opportunistically, so an offline device delivers hours or days later while keeping the original event timestamp. A day's row count therefore keeps rising after the day closes, and Firebase's events_intraday_* table is explicitly the open, incomplete day. Charting it beside closed days — or comparing today against last week — manufactures a decline that belongs to the pipeline, and the "recovery" a day later is the same artefact unwinding.
  • Retention windows. Vendor-side event retention is finite and plan-dependent, and GA4's own reporting retention is shorter than most people expect. BigQuery export is the durable copy — if you are not exporting, your history has an expiry date you did not choose.
  • Backfill does not exist. BigQuery export begins when you enable it. An event you did not instrument in March is not recoverable in April. This is the single most consequential property of the whole category.
  • Schema drift. Renaming an event or changing a parameter type creates a silent discontinuity: the old name simply stops appearing. Nothing errors.
  • Identity is fragile. Reinstalls mint a new pseudo-id; setUserId after the fact does not retroactively merge earlier anonymous events on all vendors. Merge semantics differ between Amplitude, Mixpanel and GA4 — do not assume they agree.
  • Cardinality caps. High-cardinality parameters get bucketed into (other) in aggregate views, so a per-item breakdown that works in staging silently collapses in production.
Methodological consequence. Because you define the schema, gaps in this data are self-inflicted rather than platform-imposed — which makes them easier to fix prospectively and impossible to fix retrospectively. That asymmetry should drive design: instrument the events an eventual model will need before you know you need them, export raw from day one, and treat aggregate endpoints as presentation rather than as a source for training data. Two specific traps. First, thresholding and sampling in aggregate APIs reproduce exactly the small-segment missingness described for the store consoles, so a cohort analysis built on runReport will quietly lose its smallest cohorts. Second, an event that stops firing because of a client-side regression looks identical to a behaviour change — the only defence is volume monitoring per event name with an alert on the derivative, not on the level. Third, consent gating means segment comparisons across platforms are confounded by the consent step rather than measuring the platform: compare within consent state, or model the consent decision, but do not read an iOS-versus-Android delta as a product finding.
