iOS Screen Time BACKLOG

Screen Time API — FamilyControls, DeviceActivity, and ManagedSettings. An API designed so that app-usage data cannot be collected.

Last verified: August 2026

Overview

What It Provides

Three cooperating frameworks, introduced with iOS 15 and extended in iOS 16+:

  • FamilyControls — authorization, and the FamilyActivityPicker UI through which the user selects apps, categories, and web domains.
  • DeviceActivity — schedules and usage-threshold events (DeviceActivityMonitor extension), plus DeviceActivityReport for rendering usage summaries.
  • ManagedSettings — enforcement: shield an app, block web content, restrict account/passcode/Siri settings via a ManagedSettingsStore.

The intended product shape is a screen-time / focus / parental-control app that acts on usage locally. It is not an analytics pipeline.

The central design fact: selected apps and categories are handed to your code only as ApplicationToken, ActivityCategoryToken, and WebDomainToken values. These are opaque. There is no API to resolve a token to a bundle identifier, an app name string, or a URL. Tokens are also scoped — they are not stable, meaningful identifiers you can ship to a server and join across users or devices.
Authentication & Entitlements
  • AuthorizationCenter.shared.requestAuthorization(for:) with .individual (self-managed) or .child (guardian-approved via Apple Account password).
  • Requires the com.apple.developer.family-controls entitlement. For App Store distribution this entitlement must be requested from Apple and justified; it is not self-serve.
  • Authorization is per-device and revocable by the user at any time.
com.apple.developer.family-controls AuthorizationCenter .individual / .child
Granularity — aggregate vs event-level

Neither, in the usual sense. What you get is:

  • Threshold callbacks — eventDidReachThreshold(_:activity:) fires in your DeviceActivityMonitor extension when a named event's app/category set collectively passes a duration you specified. You learn that the event fired, not which app consumed the time.
  • Interval callbacks — intervalDidStart / intervalDidEnd against a DeviceActivitySchedule.
  • Report data — inside a DeviceActivityReportExtension you receive an async sequence of activity segments with totalActivityDuration, per-category and per-application breakdowns keyed by token, and pickers/labels for display.

Durations exist. They just cannot leave the sandbox, and the identities attached to them cannot be read.

Key APIs
  • FamilyActivitySelection → applicationTokens, categoryTokens, webDomainTokens
  • DeviceActivityCenter.startMonitoring(_:during:events:)
  • DeviceActivityEvent(applications:categories:threshold:)
  • DeviceActivityMonitor (app extension subclass)
  • DeviceActivityReport(_:filter:) + DeviceActivityReportExtension
  • ManagedSettingsStore.shield.applications, .shield.webDomains
  • Label(_ token:) — renders name + icon in SwiftUI without exposing the underlying strings
Rate Limits

Not a request-quota API. The practical constraints are extension budgets rather than rate limits: the DeviceActivityMonitor extension is woken briefly for callbacks and is expected to do minimal work, and the report extension runs under a memory ceiling that large date ranges can exceed. There is a documented cap on the number of concurrently monitored activities/events per app; treat "a few dozen" as the working assumption and design so you do not need many.

Business Scenarios
  • Parental controls and guardian-side allowance enforcement
  • Focus / digital-wellbeing apps that shield distracting apps on a schedule
  • Habit and screen-time coaching where the summary is shown to the user, on-device
  • Employer or school device policy — but via MDM, not this API
Key Restrictions & Gotchas
  • No exfiltration. The DeviceActivityReportExtension is sandboxed and has no network access. This is deliberate: the extension is allowed to see usage precisely because it cannot transmit it.
  • No token resolution. There is no public API mapping a token to a bundle ID. Attempts to fingerprint tokens by rendering the label and reading it back are working against the design and against App Review.
  • No enumeration. You cannot ask "what apps are installed" or "what did the user use". You only ever see what the user picked in the system picker.
  • No retroactive history before authorization, and report queries are bounded by the system's own retention window.
  • Thresholds are one-way. An event that fires at 30 minutes tells you 30 minutes elapsed; it does not tell you the total, and re-arming across intervals is fiddly.
  • Authorization loss is silent from the server's point of view — shields and monitoring stop, and you have no server-side signal that they did.
Methodological consequence. A study of the form "measure how much our users use competing apps" is not blocked by a missing endpoint that Apple might add later. It is blocked by the security model: the identity of the app and the ability to transmit the measurement are separated on purpose. Any dataset that appears to contain iOS per-app usage was collected some other way — self-report, VPN/proxy interception, MDM on supervised hardware, or panel software — and each of those carries its own, usually severe, selection bias. Budget for that at study-design time rather than treating it as an integration problem.

Swift — authorization, selection, threshold monitoring

import FamilyControls
import DeviceActivity
import ManagedSettings

// 1. Authorization (user or guardian approves)
try await AuthorizationCenter.shared
        .requestAuthorization(for: .individual)

// 2. The USER picks. You receive opaque tokens.
@State var selection = FamilyActivitySelection()
// FamilyActivityPicker(selection: $selection)
//
// selection.applicationTokens : Set<ApplicationToken>
// selection.categoryTokens    : Set<ActivityCategoryToken>
//
// token.bundleIdentifier   -> does not exist
// String(describing: token) -> opaque blob, not a name

// 3. Threshold event: "these apps, 30 minutes, today"
let event = DeviceActivityEvent(
    applications: selection.applicationTokens,
    categories:   selection.categoryTokens,
    threshold:    DateComponents(minute: 30)
)

let schedule = DeviceActivitySchedule(
    intervalStart: DateComponents(hour: 0,  minute: 0),
    intervalEnd:   DateComponents(hour: 23, minute: 59),
    repeats: true
)

try DeviceActivityCenter().startMonitoring(
    .init("daily.social"),
    during: schedule,
    events: [.init("cap30"): event]
)

// 4. In the DeviceActivityMonitor extension:
class Monitor: DeviceActivityMonitor {
  let store = ManagedSettingsStore()

  override func eventDidReachThreshold(
      _ event: DeviceActivityEvent.Name,
      activity: DeviceActivityName) {
    // You know: "cap30" fired.
    // You do NOT know which app burned the 30 min.
    // No URLSession here that would help you anyway.
    store.shield.applications = shieldedTokens
  }
}

DeviceActivityReport extension — usage is visible, and stays put

struct TotalsView: DeviceActivityReportScene {
  let content: (String) -> Text

  func makeConfiguration(
    representing data: DeviceActivityResults<DeviceActivityData>
  ) async -> String {
    var total: TimeInterval = 0
    for await d in data {
      for await seg in d.activitySegments {
        total += seg.totalActivityDuration
        for await app in seg.categories
                            .flatMap({ $0.applications }) {
          // app.application.token  -> opaque
          // app.application.localizedDisplayName -> nil
          //   (unavailable to your code; renderable via Label)
          _ = app.totalActivityDuration
        }
      }
    }
    // Sandboxed extension: no outbound network.
    // This number can be DRAWN, not SENT.
    return formatted(total)
  }
}
