Android Health Connect BACKLOG

On-device health datastore and Android API surface that replaced the Google Fit APIs. No REST endpoint exists — records are readable only on the user's device.

Last verified: August 2026

Overview

What It Provides

A local, typed datastore plus a per-type permission model, accessed from an Android app through the Health Connect Jetpack client (HealthConnectClient). It is part of the platform on Android 14 and later; on earlier versions it shipped as a separately installed app from Play. Like HealthKit, it is an aggregator and a consent broker — it holds whatever installed apps and paired devices choose to write, and validates almost none of it.

There is no Health Connect server API. No REST base URL, no service account, no OAuth server-to-server pull, no way for a backend to read a user's records. Code must be running on that user's device, holding per-record-type permission, and any data that reaches your servers got there because an app you shipped explicitly uploaded it.

Pipeline consequence: ingestion is device-initiated and intermittent. It happens when your app is in the foreground, or during whatever constrained background window the OS grants — subject to Doze, App Standby buckets, and OEM battery managers that are considerably more aggressive than stock Android. Gaps of days are normal, not incidents. Uninstall ends the series permanently and retroactive recovery is impossible.
The Google Fit APIs are gone, and that closed the last cloud path on Android. Google deprecated the Google Fit REST API and the Fit Android/SDK surfaces, announcing the wind-down in 2024 with Health Connect as the stated migration target and shutdown proceeding over the following years. This matters more than a routine deprecation: the Fit REST API was one of the few genuine server-to-server health endpoints, where a backend holding a refresh token could pull a user's steps without any app running. That capability no longer exists. An architecture inherited from a Fit-era integration and redrawn against Health Connect is wrong at the transport layer, not merely at field mapping.
Authentication & Permissions
  • Per-record-type read and write permission strings, declared in the manifest and granted by the user through the Health Connect permission UI. There is no aggregate health scope.
  • Reading records older than a rolling recent window — roughly the last 30 days by default — additionally requires the historic-data permission. Reading while your app is not in the foreground requires its own separate permission.
  • Google operates a declaration and review process for apps requesting health permissions on Play. Access is not self-serve.
  • If the user revokes all permissions, the OS can reset your app's access state entirely, and later reads return nothing until access is re-granted.

Granularity — the interval / instantaneous split

The data model distinguishes two record shapes, and that distinction determines which aggregations are legitimate:

  • IntervalRecord — has a start and an end time. StepsRecord, DistanceRecord, ActiveCaloriesBurnedRecord. Summing these over non-overlapping windows is valid; that is what they are for.
  • InstantaneousRecord — a single timestamp. WeightRecord, RestingHeartRateRecord, BloodPressureRecord. Summing these is meaningless. Averaging them is defensible only once you accept that the sampling times were chosen by the user or by an opaque device policy, never by you.
  • Series records — HeartRateRecord carries a list of samples, so one record spans a period and contains many values. Its density reflects the writing device's duty cycle, not a fixed rate, and it collapses when the wearable is off the wrist.
Health Connect does not de-duplicate across apps, and this is the most common analysis error. If a phone pedometer, a wearable's companion app, and a fitness tracker all write steps for the same walk, you read three overlapping StepsRecord sets. Naive summation triple-counts. There is no platform-side reconciliation to lean on: every record carries dataOrigin.packageName precisely because deduplication is the consumer's responsibility. Do it per data origin, over non-overlapping time windows, with a documented priority rule for choosing an origin. The bias is not uniform — it is largest for users with the most devices and apps, which correlates with engagement and income, so the inflation is confounded with the outcome you probably care about.
recordingMethod and dataOrigin are part of the measurement definition. Metadata carries a recording method — automatically recorded, actively recorded (a user-started session), or manual entry — which lets you separate a typed-in weight from a scale reading, and a sensor-derived step count from a hand-logged one. Treat these as covariates, not provenance trivia: a heart rate from a chest strap (beat-to-beat R-R intervals), from an optical wrist sensor (periodic, motion-sensitive, duty-cycled), and from a manual spot entry are three different measurements sharing one class name. Sleep staging from actigraphy plus PPG is a model inference, not polysomnography. Pooling across origins without a source term confounds hardware and algorithm with physiology.
Key Record Types
  • Activity — StepsRecord, DistanceRecord, TotalCaloriesBurnedRecord, ActiveCaloriesBurnedRecord, SpeedRecord, PowerRecord, CyclingPedalingCadenceRecord.
  • Cardio & vitals — HeartRateRecord (series), RestingHeartRateRecord, HeartRateVariabilityRmssdRecord, OxygenSaturationRecord, RespiratoryRateRecord, BloodPressureRecord, BloodGlucoseRecord.
  • Sleep — SleepSessionRecord, containing a list of Stage entries with types AWAKE, SLEEPING, OUT_OF_BED, LIGHT, DEEP, REM. Stage presence depends entirely on the writing app: a session may contain only SLEEPING, or no stages at all, so a stage-level series is not guaranteed to exist.
  • Exercise — ExerciseSessionRecord with laps, segments, and an optional ExerciseRoute.
  • Body & nutrition — WeightRecord, BodyFatRecord, NutritionRecord, HydrationRecord.
Vendor composite scores are not first-class types. There is no readiness, recovery, strain, or sleep-score record. When a vendor app writes such a value it lands as an opaque number attributed to that package, and its definition changes with app and firmware releases. A multi-year series of a sleep score is therefore a series of different models, not a longitudinal measurement, and part of any trend in it is the vendor's release history rather than the user's sleep.
Reading & Aggregation
  • readRecords with a time-range filter and an optional data-origin filter.
  • getChangesToken / getChanges — differential sync, and the correct incremental ingestion mechanism. It reports deletions as well as upserts, and signals when a token has expired so you know a full re-read is required.
  • aggregate, plus aggregateGroupByPeriod and aggregateGroupByDuration for bucketed rollups. The aggregate result exposes which data origins contributed — exactly the information needed to detect overlap — but it does not resolve the overlap for you.
  • clientRecordId with clientRecordVersion — your app's idempotency key for writes, and the mechanism for upserting a correction instead of duplicating a record.
Rate Limits & Quotas

No network quota, because there is no network call. The constraints are OS-side and better treated qualitatively than as a budget to count against:

  • The platform rate-limits reads and writes to protect the datastore and the battery, surfacing this to the client as an exception rather than degrading silently. The enforced thresholds are not a published fixed table, so batch bulk operations and implement back-off rather than assuming a number.
  • Large historical reads must be paged. A year of heart-rate series records in one call is a memory hazard.
  • Background execution is the real ceiling. Doze, App Standby buckets, and vendor battery managers determine how often a sync worker actually runs, and this varies enormously across manufacturers. Two users on the same app build can have very different data latency for reasons unrelated to their health.
Business Scenarios
  • Cross-app fitness and wellness aggregation, which is the case Health Connect was built for.
  • Remote patient monitoring and decentralised trials on Android, with a study app as the capture layer.
  • Insurance and employer wellness programmes — where the absence of platform deduplication combined with permitted manual entry makes the incentive structure a data-quality problem.
  • Migration work: replacing a Google Fit REST integration, which in practice means re-architecting from a server pull to a device push.
Key Restrictions & Gotchas
  • No REST endpoint, no server credentials, no cross-user or population queries. One user, one device, one app, with that user's explicit per-type consent.
  • No raw sensor stream. Health Connect is a records datastore. Live accelerometer or PPG access is a different surface — SensorManager on the phone, Health Services on Wear OS — with different permissions and different battery behaviour.
  • No record type is guaranteed to be present. Coverage is a function of which apps the user installed and permitted. A study requiring SpO2 will find a large fraction of participants with none, and that fraction correlates with device price.
  • Default history is a short rolling window. Without the historic-data permission a fresh install yields roughly a month of backfill at best.
  • A denied read looks like an empty result. As with HealthKit, absence conflates refusal, non-wear, and a true zero. Log your own permission grant state over time or the missingness mechanism is unrecoverable.
  • Per-type revocation produces ragged panels — unbalanced mid-study, silently, with no server-side signal.
  • Manual entry is indistinguishable from sensor data except via recordingMethod. Filter on it deliberately; do not discover it after the analysis.
  • Aggregates hide the overlap. A daily step total from aggregate looks authoritative. Inspect the contributing data origins before believing it.
