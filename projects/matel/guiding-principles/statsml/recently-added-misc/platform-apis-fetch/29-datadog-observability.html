Datadog & Observability APIs Backlog

Metrics, logs, events, traces and monitors — machine telemetry where the sampling, aggregation and indexing decisions are made before you ever query.

Last verified: August 2026

Overview

What It Provides

Datadog is representative of the whole observability category (New Relic, Grafana Cloud, Splunk, Honeycomb differ in syntax, not in the shape of these constraints). The data types have genuinely different physics:

  • Metrics — numeric time series keyed by name plus tags. Pre-aggregated at ingest and rolled up further with age. Cheap to query, lossy by construction.
  • Logs — timestamped records with arbitrary attributes. Retained in full only if indexed; index filters and exclusion filters are applied at ingest and are irreversible.
  • Events — discrete occurrences (deploys, alerts, scaling actions) used to annotate timelines.
  • Traces / spans — per-request distributed timing. Almost always sampled; head-based and tail-based sampling decide what survives.
  • Monitors and SLOs — definitions, states, transition history, downtimes, and the notification trail.
Authentication & Scopes
  • DD-API-KEY — required for all calls; identifies the organisation and authorises submission.
  • DD-APPLICATION-KEY — additionally required for most reads. Bound to a user, and inherits that user's role permissions.
  • Site matters. The host differs per region — api.datadoghq.com, api.datadoghq.eu, api.us3.datadoghq.com, and others. A key is valid only on the site it was created on; a wrong-site call returns 403 rather than a helpful redirect.
  • Application keys can be scoped down to specific permissions:
metrics_read timeseries_query logs_read_data logs_read_index_data logs_read_archives events_read apm_read monitors_read slos_read dashboards_read audit_logs_read
Granularity
  • Metrics: one point per interval per unique tag combination. The interval you get back is chosen by the backend from the time range you asked for — a query over a week does not return the same resolution as a query over an hour, even with identical syntax.
  • Logs: one record per line, with timestamp, message, service, host, status and a free-form attributes map.
  • Spans: one record per span, joined into a trace by trace_id, with parent/child links and per-span duration.
  • Monitors: one record per monitor definition, plus separate state-transition history.
Key Endpoints
  • POST /api/v2/query/timeseries and POST /api/v2/query/scalar — the current metrics query API. The older GET /api/v1/query?query=…&from=&to= still works and is what most scripts use.
  • POST /api/v2/logs/events/search — log search with a filter (query, from, to, indexes), sort, and cursor pagination via meta.page.after.
  • POST /api/v2/logs/analytics/aggregate — server-side grouping and aggregation over logs, so you do not have to page millions of rows to get a count.
  • GET /api/v2/events and POST /api/v2/events/search — the event stream.
  • POST /api/v2/spans/events/search, POST /api/v2/spans/analytics/aggregate — APM span search and aggregation.
  • GET /api/v1/monitor, GET /api/v1/monitor/{monitor_id}, GET /api/v1/downtime, GET /api/v1/slo, GET /api/v1/slo/{slo_id}/history.
  • GET /api/v1/metrics and GET /api/v2/metrics/{metric_name}/all-tags — metric and tag discovery.
  • POST /api/v2/audit/events/search — who changed which dashboard or monitor, and when.
  • Log Archives to S3/GCS/Azure — the escape hatch for long-term raw retention, queried outside Datadog or rehydrated back in.
Rate Limits
  • Limits are per endpoint family, per organisation, and several are negotiable on the account. The log-search and metric-query families carry different budgets from submission endpoints. Numbers change; the mechanism does not.
  • Read the response headers on every call: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset, X-RateLimit-Period, X-RateLimit-Name. The Name header tells you which bucket you are draining, which is the only reliable way to attribute a 429 to a caller.
  • Log search caps both page size and maximum pagination depth, so "export everything matching this query" is not a supported use of the search API. Use the aggregate endpoint for counts, or archives for bulk.
Business Scenarios
  • Reliability reporting — SLO attainment and error-budget burn pulled into a business dashboard.
  • Incident post-mortem automation — assemble the deploy events, monitor transitions and error-rate series around an incident window.
  • Alert-quality analysis — precision of each monitor: what fraction of alerts led to an action, and which monitors flap. This is where alert fatigue becomes measurable.
  • Cost attribution — custom-metric cardinality and indexed log volume by team, the two things that actually drive an observability bill.
  • Capacity and performance regression — latency percentiles across deploys, taken from spans rather than averages.
Restrictions & Gotchas
  • Log indexing delay makes the most recent window incomplete. A log is written, shipped by an agent, buffered, processed by a pipeline, and only then indexed and searchable. Records keep arriving into a time bucket after that bucket's wall-clock end. Querying "the last few minutes" therefore systematically undercounts, and a daily job that aggregates up to now undercounts today. Query up to now - lag, and treat the newest bucket as provisional and subject to restatement.
  • Rollup is silent and range-dependent. The same metric query over one hour and over one month returns different resolutions, so a max over the long range is the max of averages — a lower number than the true peak. Percentiles fare worse: percentiles of pre-aggregated buckets are not percentiles of the underlying distribution and cannot be averaged.
  • Exclusion filters delete data at ingest. If a log was excluded from indexing, no query can recover it — only an archive rehydration can, and only if archiving was configured beforehand. Retention is per index and per plan.
  • Traces are sampled. Span counts are not request counts. Without the sampling rate you cannot scale up, and tail-based sampling deliberately over-retains errors, so an error rate computed from spans is biased upward.
  • Tag cardinality is the hidden cost and the hidden failure mode. A tag with unbounded values (user id, request id) multiplies time series, inflates the bill, and can cause queries to be truncated or refused.
  • Metric type semantics are not interchangeable. A count, a gauge and a rate behave differently under rollup; summing a gauge across hosts is usually meaningless, and averaging a rate over a window with gaps is wrong in a way no error message reports.
  • Monitor history is bounded and monitors are mutable. A monitor's threshold can be edited without changing its id, so a year of transition history may span several different definitions of the same alert. The audit event feed is the only record of that edit.
  • Clock skew is real. Timestamps come from the emitting host. Skewed hosts produce points slightly in the future or the past, which shows up as phantom gaps or duplicate buckets.
  • Query-time versus ingest-time attributes. Log-processing pipelines, remappers and facets are applied at ingest, so changing a parsing rule affects only future logs. Historical records keep the old shape.
Telemetry is metadata about system behaviour, not about intent. A span records that an endpoint took 900 ms; it does not record whether the user cared. And because ingestion is asynchronous at every layer, recency and completeness are in direct tension — the freshest data is always the least complete, which is precisely the data an on-call dashboard shows most prominently.

Retention Tiers, and the Same Constraints Elsewhere

Historical Granularity Is Permanently Lower Than Live Granularity

Every one of these platforms stores recent data at fine resolution and progressively coarser resolution as it ages. The mechanism differs — Datadog rolls up at query time based on range, Prometheus relies on recording rules and remote-write downsampling, New Relic and Splunk move data between tiers — but the consequence is identical and irreversible.

  • Rollup is lossy and one-way. Once raw points are aged out, the peak inside a coarse bucket is gone. No later query can recover it, because the underlying samples no longer exist.
  • The same query returns different answers over time. A dashboard panel asking for the max over "last 30 days" gives a higher number today than the identical panel will give for the same 30 days once those days have been downsampled.
  • Percentiles do not survive rollup. A p99 of pre-aggregated buckets is not the p99 of the requests. Percentiles cannot be re-derived from stored aggregates, which is why they must be computed at ingest (as distributions/histograms) if you want them to remain valid later.
  • Alert thresholds silently change meaning. A monitor tuned against 10-second data behaves differently when evaluated against 5-minute rollups. Comparing a current breach to a year-old breach compares two different measurements.
Any year-over-year comparison of a latency or spike metric is comparing fine-grained recent data against coarse historical data. The apparent improvement — peaks look lower in the past, or higher now — is often entirely an artefact of the retention boundary. If a long-horizon comparison matters, snapshot the aggregate you care about at ingest time and store it yourself; do not plan to re-query it later.
Where To Put Long-Horizon Truth
  • Compute and persist the metric you will be asked about (daily p99, daily peak concurrency) while raw data still exists, into your own warehouse.
  • Archive raw logs to object storage before exclusion filters and index retention take effect. Rehydration is possible; resurrection is not.
  • Record the sampling rate and the rollup interval alongside every extracted value. A number without its resolution is not comparable to anything.

Platform Query language / API How granularity is lost
Datadog Datadog query syntax; /api/v2/query/timeseries Backend picks interval from the range; per-index log retention
Prometheus PromQL; /api/v1/query, /api/v1/query_range Local retention is short by design; recording rules and remote-write downsampling define what survives
Grafana / Mimir / Loki PromQL and LogQL over Grafana's HTTP API Grafana queries datasources — retention belongs to the backing store, not Grafana
New Relic NRQL over the NerdGraph GraphQL API Retention is per event type and per plan; TIMESERIES bucket width scales with the range
Splunk SPL via search jobs (/services/search/jobs) Index buckets age hot → warm → cold → frozen; frozen data leaves the index entirely
OpenTelemetry collectors No query API — an ingest pipeline Sampling and aggregation processors decide, before any backend sees the data
