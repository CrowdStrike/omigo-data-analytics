Android Usage Stats BACKLOG

UsageStatsManager — per-package foreground time and launch events, gated behind a special access grant the user must toggle by hand.

Last verified: August 2026

Overview

What It Provides

android.app.usage.UsageStatsManager is the platform's app-usage history. Unlike iOS Screen Time, the package name is readable — this is a genuine per-app usage dataset. What guards it is the permission, not obfuscation.

  • queryUsageStats(interval, begin, end) → List<UsageStats>, one bucket per package: totalTimeInForeground, lastTimeUsed, firstTimeStamp, lastTimeStamp, and on newer API levels totalTimeVisible / lastTimeVisible.
  • queryEvents(begin, end) → an event stream: ACTIVITY_RESUMED, ACTIVITY_PAUSED, ACTIVITY_STOPPED, SCREEN_INTERACTIVE, SCREEN_NON_INTERACTIVE, KEYGUARD_SHOWN/HIDDEN, STANDBY_BUCKET_CHANGED, plus notification and configuration events on some levels.
  • queryAndAggregateUsageStats → convenience map of packageName → merged UsageStats.
  • getAppStandbyBucket() → the caller's own App Standby bucket (active / working set / frequent / rare / restricted).
  • Launch counts are not a first-class field. You derive them by counting ACTIVITY_RESUMED transitions in queryEvents, or use UsageStats#getAppLaunchCount() where available. Deriving from events is the more portable route.
Permission is the whole story. android.permission.PACKAGE_USAGE_STATS is not a runtime permission — it cannot be requested with a dialog. It is signature/privileged-level, and ordinary apps obtain it only through the Special App Access screen. You declare it in the manifest (with tools:ignore="ProtectedPermissions"), then send the user to Settings.ACTION_USAGE_ACCESS_SETTINGS and hope they flip the toggle. Verify with AppOpsManager OPSTR_GET_USAGE_STATS; an unauthorized call does not throw — it returns an empty list.
Authentication & Scopes
PACKAGE_USAGE_STATS ACTION_USAGE_ACCESS_SETTINGS AppOpsManager.OPSTR_GET_USAGE_STATS QUERY_ALL_PACKAGES (labels)

Resolving a package name to a human-readable app label additionally runs into package visibility filtering (API 30+): without QUERY_ALL_PACKAGES or a <queries> manifest entry, PackageManager lookups for third-party packages fail even when usage rows for them are returned. Play Store policy treats QUERY_ALL_PACKAGES as a sensitive declaration.

Granularity — aggregate vs event-level

Both, and they are not the same dataset:

  • Aggregate: queryUsageStats with INTERVAL_DAILY, INTERVAL_WEEKLY, INTERVAL_MONTHLY, INTERVAL_YEARLY, or INTERVAL_BEST. Returns pre-rolled buckets.
  • Event-level: queryEvents gives ordered transitions with millisecond timestamps, from which you compute sessions yourself.

Retention differs by bucket: daily rows are kept for a relatively short window (on the order of days to a couple of weeks), while coarser buckets persist longer. Raw events have the shortest retention of all. So the longest history and the finest resolution are mutually exclusive — a fact that quietly shapes any longitudinal design.

Bucket boundaries do not respect your query window. queryUsageStats returns every bucket that overlaps [begin, end], not a window-clipped total. A daily bucket may also contain more than one row for the same package. Correct usage is: filter, then sum per package — never assume one row per app, and never assume the returned totals are confined to your requested range. Off-by-one-day errors here are extremely common and produce plausible-looking but inflated numbers.
Rate Limits

No published request quota. The real constraints are different in kind:

  • Background execution limits, Doze and App Standby mean a background collector does not run when you assume it does — the collector's own sampling is throttled by the same subsystem it is measuring.
  • queryEvents over wide ranges allocates large result sets; iterate rather than materializing.
  • Foreground-service and exact-alarm restrictions on recent Android versions further constrain scheduled polling.
Business Scenarios
  • Digital wellbeing / focus apps and app blockers
  • Parental control products (usually paired with Android Management API or a device-owner setup)
  • Enterprise device-usage compliance on managed hardware
  • Opt-in research panels — where the consent flow and the Settings toggle are the study's actual bottleneck
Key Restrictions & Gotchas — what it does NOT give you
  • Digital Wellbeing has no public API. The numbers Google's own Digital Wellbeing screen shows are not exposed to third parties, and they will not match your UsageStatsManager-derived totals, because the definitions of "used" differ.
  • No in-app content. You get "Chrome was foreground 42 min", never the URLs, screens, or actions.
  • Silent empty results. No permission → empty list, not an exception. A collector that does not distinguish "zero usage" from "no access" will encode revoked-permission users as abstainers.
  • Foreground time is not attention. A visible-but-idle activity accrues time; picture-in-picture, split-screen, and always-on displays make totalTimeInForeground and totalTimeVisible diverge.
  • OEM divergence. Aggressive vendor battery managers kill collectors, and some OEM builds populate these fields inconsistently. Cross-device comparability is weaker than the API surface suggests.
  • Reboots and clock changes introduce gaps and non-monotonic timestamps in the event stream.
  • Play policy. Even with the toggle, using usage access for analytics unrelated to a disclosed core function is a policy problem, not just an ethical one.
Methodological consequence. Both mobile platforms deliberately block per-user app-usage collection, by different mechanisms: iOS makes the identity unreadable and the data untransportable; Android makes the data readable but puts a manual Settings toggle in front of it. On Android the resulting bias is the sharper problem, because the sample is self-selected at the toggle. Users who grant usage access are systematically not average — they are more engaged, more privacy-tolerant, and more likely to have sought out a screen-time product in the first place. Grant rates well under half are normal. Reporting mean daily usage from granters as if it estimated the population mean ignores a selection effect that plausibly exceeds the effect being measured. If you need a population estimate, you need a weighting scheme and a measured grant rate, not a bigger install base.

Kotlin — permission check, daily aggregate, derived launch counts

// AndroidManifest.xml
// <uses-permission
//     android:name="android.permission.PACKAGE_USAGE_STATS"
//     tools:ignore="ProtectedPermissions" />

fun hasUsageAccess(ctx: Context): Boolean {
    val ops = ctx.getSystemService(AppOpsManager::class.java)
    val mode = ops.unsafeCheckOpNoThrow(
        AppOpsManager.OPSTR_GET_USAGE_STATS,
        android.os.Process.myUid(),
        ctx.packageName
    )
    return mode == AppOpsManager.MODE_ALLOWED
}

// No dialog exists. You can only deep-link to Settings.
if (!hasUsageAccess(ctx)) {
    ctx.startActivity(
        Intent(Settings.ACTION_USAGE_ACCESS_SETTINGS))
    return   // and the user may simply not do it
}

val usm = ctx.getSystemService(UsageStatsManager::class.java)
val end   = System.currentTimeMillis()
val begin = end - 7L * 24 * 60 * 60 * 1000

// Buckets OVERLAPPING the window are returned,
// and a package may appear more than once.
val perPackage = usm.queryUsageStats(
        UsageStatsManager.INTERVAL_DAILY, begin, end)
    .groupBy { it.packageName }
    .mapValues { (_, rows) ->
        rows.sumOf { it.totalTimeInForeground }
    }

// Launch counts: derive from the event stream.
val launches = mutableMapOf<String, Int>()
val events = usm.queryEvents(begin, end)
val e = UsageEvents.Event()
while (events.hasNextEvent()) {
    events.getNextEvent(e)
    if (e.eventType == UsageEvents.Event.ACTIVITY_RESUMED) {
        launches.merge(e.packageName, 1, Int::plus)
    }
}

// Empty map is ambiguous:
//   genuinely no usage  OR  access revoked.
// Record the permission state alongside the data.
