Cisco Webex BACKLOG

Messaging spaces and messages, meetings and recordings, meeting-quality telemetry, and device/workspace metrics — each behind a different licence and role gate.

Last verified: August 2026

Overview

Webex presents one REST surface at webexapis.com/v1 covering messaging, meetings, recordings, analytics and hardware. What makes it awkward for data collection is not the endpoints but the access model: the identity you authenticate as determines how much of the org you can see, and several of the most useful surfaces need either a specific administrative role or a paid Control Hub add-on. The same request can succeed for one caller and return an empty list for another without any error.

What It Provides
  • Messaging — rooms (spaces), memberships, messages with text/markdown/HTML and files, teams, attachmentActions for adaptive cards.
  • Meetings — scheduled meeting objects, series versus instances, invitees, transcripts, and per-meeting participant records.
  • Recordings — cloud recording inventory with downloadUrl/playbackUrl, plus a separate admin/compliance listing.
  • Meeting Qualities — per-participant network and media quality samples for a past meeting.
  • Devices and Workspaces — registered room hardware, and workspace metrics such as people count, sound level, ambient noise and air quality where sensors exist.
  • Admin Audit Events — administrative configuration changes in the org.
Authentication & Scopes
spark:rooms_readspark:messages_readspark-compliance:rooms_readspark-compliance:messages_readmeeting:schedules_readmeeting:recordings_readanalytics:read_allaudit:events_read
  • Personal access token — issued to a developer from the docs portal, short-lived (on the order of half a day) and scoped to that human. Useful for exploration only; it is not a service credential and will expire mid-collection.
  • Integration (OAuth) — a user authorises the app; the app acts as that user and inherits exactly their visibility.
  • Bot token — long-lived, but a bot is a separate identity that only sees what it has been added to.
  • Service App — the intended pattern for org-wide, unattended access: requires org admin authorisation and then uses a refresh-token flow without a human in the loop.
  • Scopes are colon-delimited, for example spark:rooms_read, spark:messages_read, meeting:schedules_read, meeting:recordings_read, analytics:read_all, audit:events_read, and the compliance family spark-compliance:messages_read / spark-compliance:rooms_read.
A bot is not an observer. A bot sees messages only in spaces where it is a member, and in group spaces it receives only the messages in which it is explicitly @mentioned. Ordinary conversation between humans in a space containing a bot is not delivered to that bot at all. Building a "read all our Webex chat" pipeline on a bot token will silently produce a tiny, biased sample consisting of exactly the messages people addressed to the bot.
Org-wide message access is a role, not a scope upgrade. Reading messages the caller did not send or receive requires the Compliance Officer role assigned in Control Hub plus spark-compliance:* scopes. Without that role, no amount of admin privilege on other surfaces grants message visibility — and the compliance path is deliberately auditable, so its use is itself logged.
Granularity

Messages are one row per message with a created timestamp and roomId; edits and reactions are not separate historical rows. Meetings distinguish a recurring series from its instances via meetingType and scheduledType, and you must ask for instances explicitly. Meeting Qualities is one record per participant per session, containing arrays of interval samples for audio, video and share streams.

Key Endpoints
  • GET /v1/rooms, GET /v1/memberships?roomId= — space inventory and membership.
  • GET /v1/messages?roomId= — messages in a space; GET /v1/messages/{id} for one message.
  • GET /v1/meetings (with meetingSeriesId for instances), GET /v1/meetingParticipants?meetingId=.
  • GET /v1/meetingTranscripts and /meetingTranscripts/{id}/download.
  • GET /v1/recordings and GET /v1/admin/recordings.
  • GET /v1/meeting/qualities?meetingId= — meeting quality samples.
  • GET /v1/devices, GET /v1/workspaces, GET /v1/workspaceMetrics, GET /v1/workspaceDurationMetrics.
  • GET /v1/adminAudit/events — administrative changes.
  • Webhooks — resources messages, memberships, rooms, meetings, recordings, attachmentActions.
Rate Limits
  • Throttling is applied per application and per organisation, so several collectors sharing one integration compete for the same budget, and a busy tenant throttles sooner than a quiet one.
  • Exceeding it returns 429 Too Many Requests with a Retry-After header. The correct implementation honours that header rather than assuming a fixed requests-per-second figure; the published limits vary by endpoint family and are subject to change.
  • Message and membership listing over a large org is the usual offender because it fans out per space. Prefer webhooks for ongoing capture and reserve listing for backfill.
Business Scenarios
  • Collaboration-graph analysis — who shares spaces with whom, and how cross-team communication changes after a reorganisation.
  • eDiscovery and retention response — targeted message and file retrieval under the compliance role.
  • Meeting quality versus site — join failures and poor-audio complaints attributed to network segment or device model.
  • Room utilisation — workspace people-count metrics against booked calendar time, to find rooms booked but unused.
  • Hardware fleet health — device software versions and connection status ahead of an upgrade.
Key Restrictions & Gotchas
  • Meeting Qualities requires Pro Pack for Control Hub. This is a paid add-on. Without it the endpoint is unavailable regardless of admin role, and the advanced/longer-retention analytics views in Control Hub are also gated the same way.
  • Webhooks carry identifiers, not content. A messages/created webhook payload gives you id, roomId, personId and timestamps — the message body is not included. You must call GET /v1/messages/{id} to retrieve the text, which means the message must still exist and your token must still be able to see it. Deletion between notification and fetch loses the content permanently.
  • Recording visibility depends on who asks. A host sees their own recordings via /v1/recordings; org-wide listing uses /v1/admin/recordings and requires admin or compliance authority. Download URLs are time-limited and must be used promptly.
  • Transcripts are conditional. A meeting transcript exists only if recording/transcription was active for that meeting and the feature is enabled for the site. There is no retroactive transcription endpoint.
  • Series versus instance confusion. Listing meetings returns the series object for recurring meetings. Participant, recording and quality data attach to instances, so a join on the series id finds nothing. Resolve instances first.
  • 1:1 spaces are not enumerable as conversations. Direct spaces appear with type: "direct" and are only visible to their two participants unless accessed through the compliance path.
  • Workspace metrics depend on hardware. People count, ambient noise and air-quality readings only exist where a device with the relevant sensor is present and the feature is switched on. Absence of data means absence of a sensor, not an empty room — an easy inference error.
  • Retention is org-configured. Message and recording retention is set by the org (and can be unlimited or short); the API cannot return what retention already purged. Analytics data has its own, shorter retention window than the raw objects.
  • Deleted and edited messages. Deletion removes the message from the API; there is no tombstone with the original text. Edits replace content without exposing a revision history.
  • Webex Calling and Contact Center are separate products with their own APIs and licences — call detail records do not appear in the meetings surface.
