Slack API BACKLOG

Messages, threads, reactions and channel history — observable only through the channels a bot was invited to, only as far back as the plan retains, and only in their current edited state.

Last verified: August 2026 — rate-limit figures deliberately not reproduced, see below

Overview

What It Provides

Messages, thread replies, reactions, files, channel membership, user profiles and workspace metadata. Real-time delivery via the Events API (HTTP callbacks) or Socket Mode (WebSocket). The Conversations API unifies public channels, private channels, group DMs and DMs behind one resource family.

Authentication
xoxb- bot xoxp- user xapp- app-level
  • Bot tokens (xoxb-) — workspace-scoped, installed once, persist across users. Sees only what the bot is a member of.
  • User tokens (xoxp-) — act as a specific user, inheriting that user's channel visibility. Different token, different population.
  • App-level tokens (xapp-) — Socket Mode connections only.
The token type determines the sample, not just the permissions. A bot token and a user token pointed at the same workspace return different channel sets, so a change of token mid-study is a change of population. Record which token produced every extraction.
Granularity

Individual messages, addressed by channel plus a ts timestamp that doubles as the message's primary key. Thread replies hang off a parent via thread_ts. Reactions arrive as an aggregated array on the message, with the reacting user IDs enumerated.

Key Endpoints
  • conversations.list — channel enumeration
  • conversations.history — messages in a channel
  • conversations.replies — a thread
  • conversations.members — membership
  • chat.postMessage
  • reactions.add / reactions.get
  • users.list
  • File upload is now the two-step files.getUploadURLExternal then files.completeUploadExternal. The older single-call files.upload has been deprecated — code written against it will need replacing.
Rate Limits — Shape, Not Numbers

Slack assigns each method to a tier, and the tiers span roughly two orders of magnitude in requests per minute. Consequences that hold regardless of the current figures:

  • Budgeting must be per method, not per app. One global throttle either wastes the fast tiers or violates the slow ones.
  • The history-reading methods sit in the restrictive tiers, which is exactly backwards from what a bulk backfill wants.
  • Some methods carry their own limits independent of their tier.
  • Short bursts above tier are tolerated, then throttled. Honour Retry-After; a retry loop that ignores it makes the throttle worse.
  • Marketplace listing is a gating dimension. Slack has applied tighter limits to apps not listed in the Slack Marketplace — including, for the conversation-history methods, both a reduced request rate and a reduced number of objects returned per request. Two apps calling the same endpoint can therefore have throughput budgets differing by orders of magnitude.
Exact tier figures are not reproduced here, on purpose. They have changed, they differ by Marketplace status, and a wrong quota in a design document is worse than no quota — it produces a pipeline sized for capacity that does not exist, which fails as an endless 429 loop rather than an error. Read the current limits from Slack's docs at design time, and record the figure you designed against alongside the pipeline. The per-request object count is the number people forget: halving it doubles the call count for the same history, independent of the rate.

  • Collaboration and communication-pattern analysis, subject to everything on the right
Not Provided
  • History from channels the bot never joined — no backfill, at any tier
  • DMs and private channels absent explicit installation into them
  • Message history older than the plan's retention
  • Prior versions of an edited message, or the content of a deleted one
  • Bulk workspace export (that is the admin export or Discovery API, separately gated)
  • Read receipts, or who saw a message without reacting

conversations.history returns current state, not the historical record. Edits are applied and deletions are omitted, so a backfill of last month and an Events API stream captured live during that month will disagree — and the backfill is the lossy one. Neither is wrong; they answer different questions. Anything about how communication unfolded needs the live stream captured at the time, which cannot be reconstructed later. Two clocks matter: ts (when posted) and edited.ts (when last altered).

What a backfill actually observes. Two independent truncations stack. The bar outline is the message history that exists; solid fill is what the bot can reach; the red region is additionally lost to plan retention.

Bot-membership coverage is informative missingness, not random. Bots get invited to the channels people care about — incidents, releases, active projects — and reach quiet channels late or never. So observed coverage correlates with the activity being measured. Every unadjusted aggregate is then biased toward high-traffic collaboration: "message volume per team" is partly a measure of how early that team adopted the bot. Store the bot's join timestamp per channel and treat the observable window as a per-channel property, not a workspace constant.
Retention truncation is left-censoring. On plans that cap history, older messages are unavailable rather than absent — you know activity occurred, you cannot see it. Its two failure modes: a workspace's apparent history begins at the retention boundary regardless of its real age, so tenure and lifecycle analysis is meaningless without accounting for it; and the boundary moves forward with wall-clock time, so re-running the same extraction later returns less history, making the query non-reproducible unless results are warehoused on first pull. A backfill attempted after the fact cannot recover what has aged out.

Bot-authored messages inflate volume. subtype: "bot_message" rows are alerts and integrations, not human communication. Channels differ enormously in bot share, so counting messages without splitting on bot_id measures monitoring noise as collaboration — and the noisiest channels are usually the ones a bot joined first.
