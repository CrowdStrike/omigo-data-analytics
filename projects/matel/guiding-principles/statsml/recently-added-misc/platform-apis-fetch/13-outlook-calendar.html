Outlook Calendar BACKLOG

Microsoft Graph calendar surface — events, calendars and calendar groups, rooms and places, free/busy via getSchedule, findMeetingTimes, and attendee response tracking.

Last verified: August 2026

Overview

The calendar surface looks like a single resource with several convenience endpoints. It is not. /events, /calendarView, /getSchedule, and findMeetingTimes return structurally different things at different fidelity, and picking the wrong one produces answers that are internally consistent and quietly wrong — most often by undercounting recurring meetings by an order of magnitude.

Recurrence is the organising difficulty. Exchange stores a recurring meeting as one master object plus a small set of exception objects, and expansion into occurrences is a server-side operation you must explicitly ask for.

GET /events does not return recurring occurrences. A weekly standup running for two years appears as exactly one item with type: "seriesMaster" and a recurrence block. Any "meeting hours per person" or "room utilisation" metric built on /events counts that standup once. Use GET /calendarView?startDateTime=&endDateTime=, which expands the series server-side into occurrence and exception items, or GET /events/{id}/instances for a single series. The failure is silent — the response is valid, the totals are plausible, and nothing signals that the expansion did not happen.
What It Provides
  • Events — subject, start / end as dateTimeTimeZone, organizer, attendees[] with type (required, optional, resource) and status.response, location / locations[], isAllDay, isCancelled, showAs, sensitivity, responseRequested, onlineMeeting linkage, seriesMasterId, and iCalUId.
  • Calendars and calendar groups — the default calendar, additional calendars, shared calendars, and calendarPermissions.
  • Calendar view — server-expanded occurrences over a bounded window.
  • Free/busy — POST /calendar/getSchedule returning scheduleItems with availability status per interval, plus workingHours.
  • Meeting-time suggestions — POST /findMeetingTimes returning ranked meetingTimeSuggestions with a confidence score and per-attendee availability.
  • Places — /places/microsoft.graph.room and /places/microsoft.graph.roomList with capacity, floor, building, and accessibility attributes.
  • Delta and notifications — /calendarView/delta and /events/delta for incremental sync; subscriptions for push.
Authentication & Scopes
Calendars.ReadBasicCalendars.ReadCalendars.Read.SharedCalendars.ReadWriteCalendars.ReadWrite.SharedPlace.Read.AllMailboxSettings.Read
  • Entra ID app registration, OAuth 2.0. Delegated or application permissions.
  • Calendars.Read, Calendars.ReadBasic (reduced properties), Calendars.ReadWrite. Calendars.Read.Shared / Calendars.ReadWrite.Shared are needed for calendars others have shared or delegated to the signed-in user — the plain scope does not cover them.
  • Place.Read.All for rooms and room lists. Creating or editing places requires Place.ReadWrite.All and an administrative role.
  • Schedule.Read.All is a Teams shifts scope and is not what getSchedule uses; getSchedule runs under Calendars.Read (or Calendars.Read.Shared for other users' calendars).
  • MailboxSettings.Read is required to read a user's configured working hours and time zone independently of getSchedule.
  • Application permission Calendars.Read covers every mailbox in the tenant, including room mailboxes, unless narrowed with an Exchange Online Application Access Policy. The same caveat applies here as to mail.
Granularity

One event per attendee mailbox per meeting — the organiser's copy and each attendee's copy are separate objects with different id values. iCalUId is the cross-mailbox join key; id is not, and (as with mail) default ids change when an item moves, so Prefer: IdType="ImmutableId" matters for anything persisted. Within a series, occurrences share a seriesMasterId; a modified occurrence becomes type: "exception" and a deleted one is simply absent from calendarView rather than present-and-cancelled.

Key Endpoints
  • GET /v1.0/users/{id}/events — masters and singles, no expansion
  • GET /v1.0/users/{id}/calendarView?startDateTime=2026-08-01T00:00:00&endDateTime=2026-08-31T00:00:00 — expanded; range is mandatory
  • GET /v1.0/users/{id}/events/{id}/instances?startDateTime=&endDateTime= — expand one series
  • GET /v1.0/users/{id}/calendars, /calendarGroups, /calendars/{id}/calendarPermissions
  • POST /v1.0/users/{id}/calendar/getSchedule — body carries schedules[], startTime, endTime, availabilityViewInterval
  • POST /v1.0/users/{id}/findMeetingTimes — body carries attendees, timeConstraint, meetingDuration (ISO 8601), minimumAttendeePercentage, maxCandidates
  • GET /v1.0/places/microsoft.graph.roomList, then GET /v1.0/places/{roomList-email}/microsoft.graph.roomList/rooms
  • GET /v1.0/users/{id}/calendarView/delta?startDateTime=&endDateTime=
  • Send Prefer: outlook.timezone="India Standard Time" to have start / end returned in a chosen zone instead of UTC.
Rate Limits
  • Graph throttles per application per tenant; Exchange additionally throttles per mailbox on a resource-cost basis, so an expensive expansion consumes more budget than a cheap metadata read at identical request counts. Both surface as 429 with Retry-After.
  • The documented Outlook ceilings apply here as they do to mail: 10,000 requests per 10 minutes per mailbox per app and 4 concurrent requests per mailbox. Room mailboxes count as mailboxes — a room-utilisation crawl serialises against that same limit per room.
  • POST /$batch accepts at most 20 requests; the constituent requests are still throttled individually, and batching several calendarView reads against the same mailbox does not evade the concurrency cap.
  • findMeetingTimes and getSchedule are computed operations, materially more expensive per call than a read, and getSchedule caps the number of mailboxes per request — chunk the schedules array rather than sending hundreds.
  • $top is capped; follow @odata.nextLink verbatim. calendarView over a long range plus a busy calendar is many sequential pages.
Business Scenarios
  • Meeting-cost modelling — attendee count times duration across calendarView, with showAs and responseStatus used to exclude declines and tentative holds. Scheduled duration is an upper bound, not actual attendance.
  • Room utilisation and right-sizing — booked hours against capacity from /places, and the more useful comparison of booked capacity against actual attendee count.
  • Fragmentation analysis — from getSchedule, measuring how much of a working day is contiguous focus time rather than how many hours are booked.
  • Recurring-meeting hygiene — series with persistently high decline rates or where the organiser has left the organisation.
  • Cross-team collaboration mapping — attendee lists joined to directory attributes, which reveals organisational structure more honestly than the reporting hierarchy does.
Key Restrictions & Gotchas
  • getSchedule returns free/busy only, and cross-tenant detail is a policy outcome. For external attendees you may get availability with no subject or location, or you may get availabilityView populated entirely with 0 (free) because the organisational relationship and sharing policy in Exchange permit nothing more. An external calendar that appears empty is usually a permission result, not an empty calendar. Check the per-schedule error object rather than trusting an all-free view.
  • findMeetingTimes is a suggestion engine, not a booking call. It returns ranked candidates with confidence and organizerAvailability; it reserves nothing, and by the time you create the event the slot may be taken. It also applies defaults you did not set — business hours, a minimum attendee percentage, and a candidate cap — so an empty meetingTimeSuggestions array with emptySuggestionsReason populated is the normal way it says no. Read that field; the HTTP status is still 200.
  • Attendee responseStatus is unreliable for external participants. Cross-organisation responses depend on federation and on the response actually being sent back; a genuine acceptance can persist as none or notResponded indefinitely. Treating none as "did not attend" systematically undercounts external participation.
  • The organiser's copy and the attendee's copy can disagree. Response state, categories, reminders, and even the body differ per mailbox. Attendance and response analytics must state which copy they read; aggregating both double-counts the meeting.
  • Room data requires Exchange-side configuration. /places returns rooms that exist as room mailboxes and, for the room-list traversal, rooms that have been added to a configured room list. Capacity, floor, and building are administrator-entered metadata and are frequently null or stale. An empty room list means nobody configured one — not that the organisation has no rooms.
  • A room booking is not attendance. The resource mailbox auto-accepts under its booking policy, so responseStatus: "accepted" for a room means the policy allowed it, nothing about whether anyone showed up.
  • calendarView requires a bounded range and enforces a maximum window, so multi-year analysis must be chunked and stitched. Chunk boundaries cutting through a long event produce duplicates across chunks — deduplicate on id or iCalUId plus start time.
  • Cancelled and declined meetings behave inconsistently. A cancelled series master may remain with isCancelled: true; individually deleted occurrences vanish from calendarView with no tombstone. Reconstructing "what was on the calendar as of last Tuesday" is not possible after the fact — you need a persisted snapshot.
  • Delta on calendarView is range-bound and its token expires. An expired token returns 410 Gone and forces a full re-read of the window. A rolling window also means events ageing out of the range appear as removals that are not deletions.
  • Time zone handling is a common source of fabricated findings. dateTimeTimeZone carries an explicit zone name, all-day events use midnight boundaries in the event's own zone, and without Prefer: outlook.timezone or a read of mailboxSettings the derived "after-hours meeting" rate is an artefact of UTC.
  • Private events return reduced content. sensitivity: "private" restricts what a delegate sees, and an app-only read may return the time block without subject or attendees. Absent fields are a privacy behaviour, not missing data.
