Smart Scales & Blood Pressure Cuffs BACKLOG

Episodic body-composition and blood-pressure records from connected household devices, retrieved through the Withings cloud API.

Last verified: August 2026

Overview

What It Provides

Withings (formerly Nokia Health) operates the one widely-used public cloud API in this device class. It returns measure groups: one weighing session or one cuff inflation, timestamped, attributed to a user profile, and carrying a set of typed numeric measures. Depending on the device model this covers weight, height, fat ratio, fat-free mass, fat mass, muscle mass, bone mass, hydration, systolic and diastolic blood pressure, pulse, SpO2, temperature and pulse wave velocity, plus activity and sleep series for the vendor's watches and sleep mats.

Most consumer scale and cuff vendors have no public API at all. Omron Connect and Garmin Index are the usual comparison points: Omron's programmatic access has historically run through partner and healthcare-platform arrangements rather than a self-serve public REST surface, and Garmin Index scales publish into Garmin Connect rather than exposing a scale-specific API of their own. For a large fraction of devices on the market the only data path is HealthKit, Health Connect, or the vendor's own app on the user's handset — which means there is no server-to-server pull. You need code running on the user's device, and you inherit that platform's write-provenance and de-duplication problems instead of the vendor's.
Authentication & Scopes

OAuth 2.0 authorization-code flow, per end user, with refresh tokens, against an application registered under a developer or partner account. Scopes are coarse — there is no per-measure-type or per-device consent:

user.info user.metrics user.activity user.sleepevents

user.metrics is the scope that carries body measures and blood pressure. Granting it grants the whole measure history the account holds, for every device on the account, for every type those devices produce. An analysis that only needs weight still receives body-composition estimates it probably should not use.

The API uses an unusual convention for a modern HTTP interface: requests are POSTs to a service endpoint with an action parameter rather than REST verbs against resource paths. The path names the service; action names the operation.

Granularity

Episodic, not continuous. A measure group exists only because someone stood on the scale or inflated the cuff. There is no interpolation, no fixed cadence, and no guarantee of one observation per day — the observation process is entirely user-driven, which is the most consequential single fact about this data.

  • Group level: date (when measured), created and modified (when the record was written and last changed), attrib, category, deviceid, grpid.
  • Measure level: value, type, unit.
  • category separates real measurements from user-set objectives. A target weight is not a measurement and must be filtered out before anything else happens.
Key Endpoints
  • POST /measure?action=getmeas — body measures and blood pressure, filtered by measure type, category, a date window, or lastupdate.
  • POST /v2/measure?action=getactivity — daily activity aggregates.
  • POST /v2/measure?action=getintradayactivity — finer-grained activity series. Access is gated: it is not automatically available to every registered application, and eligibility is decided by the vendor per partner.
  • POST /v2/sleep?action=get and action=getsummary — sleep series and per-night summaries.
  • POST /v2/heart?action=list and action=get — heart and ECG records on ECG-capable devices, including blood-pressure recordings with signal data.
  • POST /v2/user?action=getdevice — the device inventory on the account. Required to interpret anything else, because which measure types can exist is a property of the hardware.
  • POST /notify?action=subscribe — webhook notification subscriptions per data-type code, with matching list and revoke actions.
The getmeas type-code model

This is the technical heart of the API and the single biggest source of parsing bugs. The response contains body.measuregrps, an array of groups; each group holds a measures array; each measure is { value, type, unit }. The actual quantity is:

quantity = value × 10^unit

So {"value": 72500, "unit": -3} on type 1 is 72.5 kg, not 72500. unit is a signed base-10 exponent, not a unit name, and it varies between records for the same type. Ignoring it produces values off by orders of magnitude that still parse as numbers, still load into a table, and still plot — just wrongly. Type codes worth listing:

  • 1 weight (kg)  ·  4 height (m)  ·  12 temperature
  • 5 fat free mass (kg)  ·  6 fat ratio (%)  ·  8 fat mass weight (kg)
  • 76 muscle mass  ·  77 hydration  ·  88 bone mass
  • 9 diastolic blood pressure (mmHg)  ·  10 systolic blood pressure (mmHg)  ·  11 heart pulse (bpm)
  • 91 pulse wave velocity  ·  54 SpO2
  • 71 body temperature  ·  73 skin temperature

Which of these you actually receive depends entirely on the device model on the account. A missing type is usually not a missing measurement — it means the hardware does not produce it. Treat absence as "not instrumented" until getdevice says otherwise.

attrib is the provenance flag, and filtering on it is mandatory. It distinguishes a value the device measured from a value the user typed in by hand, and — critically — from a value the system could not confidently attribute to a specific profile, or that was later reassigned by the user. The enumeration includes device-measured, manually-entered and ambiguous/unattributed states; read the current docs for the exact integer codes rather than hardcoding a guess. The statistical point does not depend on the codes: a column that mixes typed-in numbers with device readings contains two different measurement processes with different error distributions and different missingness mechanisms, and the mixture is not random — people type values in precisely when the device was unavailable or disagreed with them.
Records are mutable, so a date-keyed incremental sync silently loses corrections. A user can reassign a measurement to a different profile, or delete it, months later. That changes modified but not date. An incremental pull that asks for "everything since the latest date I have" will never observe the correction, and your copy of history diverges permanently from the vendor's. This is exactly what the lastupdate parameter exists for: key the sync on lastupdate / modified, and treat every already-stored group as revisable rather than final.
Multi-user attribution on a shared scale is a classifier, and its error rate is correlated with the quantity being studied. A household scale decides who stepped on it by matching the observed weight — sometimes plus impedance — to the nearest stored profile. When two members' weights are close, that assignment has a real and substantial error rate, and it is worst exactly when the profiles converge. Three consequences follow, none cosmetic. (1) Mislabelled observations appear as implausible day-over-day jumps in one series with compensating jumps in another. (2) The label noise is not independent of the outcome: if the analysis is about weight change, convergence of the two users' weights both raises the misassignment probability and is the signal, so the noise is endogenous and will bias any estimate of the effect rather than merely inflating its variance. (3) Retroactive reassignment means the historical series is not immutable. Before modelling: screen for physiologically implausible deltas, apply per-profile plausibility bounds, and treat a shared-scale series as label-noisy data, not clean data. A single-user device, or one with a per-user confirmation step, is a materially different instrument from a shared four-profile scale, and pooling them is unjustified.
Bio-impedance body composition is a model output, not a measurement. What the scale physically measures is electrical impedance across a foot-to-foot current path. Fat ratio, fat-free mass, muscle mass, bone mass and hydration are all produced by a proprietary regression applied to that impedance together with the profile's height, age and sex. Four things follow. First, the foot-to-foot path travels mainly through the lower body and under-samples the trunk and arms, so the estimates are biased, and the bias differs systematically by body shape and composition — it is not a constant offset you can subtract out. Second, impedance is strongly hydration-dependent, so time of day, fluid intake, a meal, or a recent workout move the reported "fat ratio" with no change in adipose tissue whatsoever; within-day variation can exceed weeks of real change, which means any comparison requires the measurement conditions to be fixed and the payload does not tell you whether they were. Third, the regression coefficients are proprietary and can change with a firmware or app update, so a multi-year fat-ratio series can step for purely software reasons with no marker in the data. Fourth, "bone mass" from a foot-to-foot impedance scale is not a densitometric measurement in any meaningful sense. Operational conclusion: weight is a direct measurement on a well-characterised instrument and is usable as an outcome; the body-composition fields are uncalibrated proprietary model output and are not, absent external validation. Do not carry them in the same table at the same status.
Blood pressure specifics

Cuff readings are episodic spot measurements, taken when the user chooses, in conditions the user chooses. That makes the sampling process non-random with respect to the value: people measure more when they feel unwell, after an alarming reading, or when they suspect a problem — so the observed distribution is not the distribution of their blood pressure, and a sample mean estimates the average of the occasions they selected.

  • Each reading typically carries systolic, diastolic and pulse. Consumer cuffs commonly perform several sequential inflations and may report an average, so one API record can already be an aggregate — and whether it is may not be visible in the payload at all.
  • White-coat and masked hypertension effects mean home and clinic readings are not interchangeable measurements of one construct. Pooling them, or validating one against the other as ground truth, is a category error.
  • Posture, cuff placement, cuff size, arm choice, talking during inflation, and time since caffeine or exercise all move the reading materially and are absent from the payload entirely.
  • Position and range context is likewise absent. The API gives you a number without the conditions that make it interpretable.
Sampling interval and derivation are not comparable across devices under a shared label. Two rows labelled "weight" are comparable. Two rows labelled "fat ratio" from different vendors are outputs of different undisclosed regressions over different electrode geometries. Two rows labelled "systolic" may be a single inflation on one device and a three-inflation average on another. The column name is not the measurement definition, and nothing in the response tells you which of the three you have.
Rate Limits

Described qualitatively on purpose. The API applies per-client throttling and returns error codes when a caller exceeds it, and the vendor positions webhook notifications as the intended alternative to polling rather than as an optimisation — which is the right architecture anyway, since measurement events are sparse and irregular and a polling loop spends nearly all its budget on empty responses. Do not design against a specific published requests-per-second figure; treat the limit as a runtime signal to back off.

Business Scenarios
  • Remote patient monitoring and hypertension management, where the cuff series is the clinical object and its self-selected sampling is the central methodological problem.
  • Weight-management and coaching products, which need trend estimation robust both to shared-scale label noise and to hydration-driven composition swings.
  • Employer wellness and insurance programmes — technically feasible, but a self-measured, self-timed metric on a shared device is gameable and identity-ambiguous. An impedance-derived figure has no business in a contract.
  • Clinical trial supplementary endpoints, where weight is defensible, provenance filtering is mandatory, and impedance-derived composition generally is not defensible.
Key Restrictions & Gotchas
  • No raw impedance — only the derived composition estimates. You cannot re-fit the model or substitute a published equation of your own.
  • No raw pressure waveform from the cuff, and no per-inflation breakdown when an average is reported.
  • No access to the composition regression itself, its validation population, or any notification when it changes.
  • No other users' data without their own OAuth grant, even inside one household; and no population aggregates or benchmark distributions.
  • No measurement conditions — posture, time since eating, hydration state, arm used, clothing. The covariates that explain most of the short-run variance are precisely the ones the API omits.
  • Available types vary by device, so one account can change instrument mid-series when hardware is replaced, with no discontinuity marker beyond a changed deviceid.

Two traps are visible above. The last group carries unit: -1 where the first carries unit: -3 for the same type: 1 — the exponent is per measure, not per type, so a hardcoded divisor breaks on real data. And that group has a manual-entry attrib with modified > created: a hand-typed value, subsequently edited. A pipeline that reads value directly and ignores attrib yields a "weight" column containing 72500, 128 and 730.

Shared-scale misattribution — two household members, one scale, 60 days. The scale files each reading under the nearest stored profile. Inside the shaded window the two weights differ by less than the discrimination margin and the assignment starts failing; hollow red markers sit on the profile a reading was filed under, dashed to the profile it belongs to. The misassignment rate is a function of how close the two users' weights are, so the label noise is correlated with the quantity being studied.
