Dropbox BACKLOG

File and folder metadata, revision chains, shared links, file requests, and the team audit log

Last verified: August 2026

Overview

What It Provides

Dropbox API v2 is an RPC-style HTTPS API — every call is a POST, arguments go in a JSON body, and there are no path parameters. Three hosts split the traffic: api.dropboxapi.com for metadata RPC, content.dropboxapi.com for upload/download (arguments move into the Dropbox-API-Arg header), and notify.dropboxapi.com for longpoll.

Surfaces available: folder listings and incremental change cursors, per-file revision chains, shared links and their settings, file requests (inbound upload forms), team member directories, and the team event (audit) log.

Authentication & Scopes

  • OAuth 2.0. Requesting token_access_type=offline yields a short-lived access token plus a refresh token. Long-lived access tokens are no longer issued for new apps.
  • Granular scopes: files.metadata.read, files.content.read, files.content.write, sharing.read, sharing.write, file_requests.read, account_info.read.
  • Team scopes are separate and only issued to Dropbox Business apps: events.read, members.read, team_data.member.
  • Namespace selection: Dropbox-API-Select-User (act as a team member) and Dropbox-API-Path-Root (address team space vs member folder). Getting the path root wrong silently changes what paths resolve to.
files.metadata.read files.content.read files.content.write sharing.read sharing.write file_requests.read account_info.read events.read members.read team_data.member

Orange badges are Dropbox Business team scopes — not obtainable by an individual-account app.

Granularity

Per-file metadata (FileMetadata / FolderMetadata / DeletedMetadata), per-revision metadata, per-shared-link settings, per-event audit records. Content is byte-range downloadable; there is no server-side diff between revisions — you download two revisions and diff them yourself.

Key Endpoints

  • /2/files/list_folder and /list_folder/continue — paged listing that returns a cursor
  • /2/files/list_folder/longpoll — blocks until the cursor is stale
  • /2/files/list_revisions — revision chain for one path or id
  • /2/files/download, /2/files/upload, /2/files/upload_session/start|append_v2|finish
  • /2/files/search_v2 — indexed search
  • /2/sharing/create_shared_link_with_settings, /2/sharing/list_shared_links
  • /2/file_requests/list_v2, /2/file_requests/get
  • /2/team_log/get_events and /get_events/continue

Rate Limits

Dropbox does not publish a fixed requests-per-second figure. It enforces per-user and per-app limits and signals overload with HTTP 429 plus a Retry-After header, and with typed errors too_many_requests and too_many_write_operations. Write contention on the same folder is a distinct failure mode from raw request volume: concurrent writers to one namespace can be rejected even at low request rates. Longpoll additionally returns its own backoff value that must be honoured before reconnecting.

Honour the typed error, not just the status code. too_many_write_operations means "serialise your writes", not "slow down globally". Blind exponential backoff on a write-lock conflict wastes the whole window.

Business Scenarios

  • Sync engines and one-way mirrors driven by list_folder cursors
  • Compliance archival and eDiscovery from team_log
  • Inbound document collection via file requests (vendor onboarding, HR)
  • Content pipelines that watch a drop folder and process new arrivals

Key Restrictions & Gotchas

History outlives the visible file. list_revisions returns prior revisions whose content is still downloadable by rev, and the team event log records the file name, path, and actor for content the user believes they deleted. Both retention windows are plan-tiered, and both are longer than most people assume when they "delete" something. An access-control review that only looks at current files misses the revision and log surfaces entirely.
  • Longpoll tells you nothing about what changed. It returns {"changes": true} — you must then call list_folder/continue with the cursor to learn the delta. It is a wake-up signal, not a change feed.
  • Cursors can be invalidated. A reset flag on the continue response means "discard local state and re-enumerate". Code that assumes cursors are permanently valid drifts silently.
  • Paths are case-preserving but case-insensitive. Metadata carries both name and path_lower; match on path_lower, display name. Better still, use the immutable id (id:...) — paths change on move and rename.
  • content_hash is not a plain SHA-256 of the file. It is a block-based construction (SHA-256 of the concatenated SHA-256s of 4 MB blocks). Comparing it against a naive digest always mismatches.
  • Shared links do not expose analytics. The API returns link settings, expiry, and audience — not view or download counts. Link-level engagement data is not retrievable.
  • Paper is not a separate product surface anymore. The legacy /2/paper/* endpoints are deprecated; Paper documents live in the user's Dropbox as .paper items and are handled through the normal files endpoints, with export rather than raw download.
  • server_modified ≠ client_modified. client_modified is supplied by the uploading client and is untrusted — it can be in the future or the distant past. Only server_modified is monotonic enough to order events.
  • The team event log requires a Dropbox Business team and admin-level scopes; it is not available for individual accounts at any price.
