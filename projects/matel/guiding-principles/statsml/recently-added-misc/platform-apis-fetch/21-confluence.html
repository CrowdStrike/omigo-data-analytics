Confluence BACKLOG

Pages, spaces, version history, comments, labels, attachments, CQL search, and the storage-format body

Last verified: August 2026

Overview

What It Provides

Confluence Cloud exposes content as a hierarchy: a space (identified by a short key such as ENG) contains pages and blogposts, which can nest as parent/child and carry comments (footer and inline), labels, attachments, restrictions, properties, and a full version history. Search is via CQL, a SQL-like query language over content metadata and indexed text.

Two API generations coexist and differ in more than the URL. /wiki/rest/api/* (v1) is the long-standing surface with expand-based response shaping. /wiki/api/v2/* is the current surface with narrower, faster, cursor-paginated endpoints and a different id space for spaces (numeric id rather than key). CQL search remains a v1 endpoint — there is no v2 equivalent — so most real integrations end up using both.

Page bodies are not HTML, and not Markdown. The canonical storage representation is XHTML with Confluence-specific namespaced elements — <ac:structured-macro>, <ac:parameter>, <ri:page>, <ac:link>. Feeding it to a generic HTML parser drops macro content entirely, because macro output does not exist in storage format; it is generated at render time. If you need what a reader sees, request the view representation (rendered HTML) — but that is lossy in the other direction and cannot be written back. Round-tripping view into storage destroys macros.

Authentication & Scopes

  • Basic auth with an API token (Atlassian account email + token) — the standard choice for scripts and internal integrations.
  • OAuth 2.0 (3LO) for apps acting on behalf of users across sites. Granular scopes such as read:page:confluence, write:page:confluence, read:comment:confluence, read:attachment:confluence, read:space:confluence, plus the older classic scopes read:confluence-content.all, write:confluence-content, search:confluence.
  • Forge / Connect apps authenticate as the app with their own permission model declared in the manifest.
  • Cloud requires the /wiki prefix and a site-scoped base URL (https://{site}.atlassian.net/wiki/...); OAuth apps must first resolve the cloudId via /oauth/token/accessible-resources and then call /ex/confluence/{cloudId}/....
read:page:confluence write:page:confluence read:comment:confluence read:attachment:confluence read:space:confluence read:confluence-content.all write:confluence-content search:confluence offline_access

Orange badges are the older classic scopes; granular scopes are the current model and cannot be mixed freely with them in one app.

Permissions are enforced silently. Content the token cannot see is omitted from list and search results rather than returning 403. A CQL query that returns 40 results for an admin and 6 for a service account is behaving correctly — which makes "is my integration seeing everything?" a question you must answer deliberately, not assume.

Granularity

Per-page, per-version, per-comment, per-attachment. In v1, response shaping is via expand (body.storage, version, history, ancestors, children.page, metadata.labels, restrictions.read.restrictions.user) — and almost nothing useful is returned without it. In v2, you request body-format=storage|atlas_doc_format|view and follow separate endpoints for children, labels, and versions.

Key Endpoints

  • GET /wiki/api/v2/pages/{id}?body-format=storage
  • GET /wiki/api/v2/pages/{id}/versions, GET /wiki/api/v2/spaces
  • GET /wiki/api/v2/pages/{id}/labels, /footer-comments, /inline-comments, /attachments
  • PUT /wiki/api/v2/pages/{id} — requires the incremented version.number
  • GET /wiki/rest/api/content/search?cql=... — CQL over content
  • GET /wiki/rest/api/search?cql=... — CQL over content, spaces, and users
  • GET /wiki/rest/api/content/{id}/history, /version/{n}
  • GET /wiki/rest/api/content/{id}/child/page?expand=...
  • POST /wiki/rest/api/content/{id}/child/attachment — multipart

Rate Limits

Atlassian Cloud applies dynamic, cost-based rate limiting rather than a published fixed requests-per-second number: the budget varies by product tier, site size, and current load, and expensive operations consume more of it than cheap ones. The reliable contract is the response: HTTP 429 with Retry-After, and on some endpoints X-RateLimit-* headers indicating remaining budget. Practical cost ordering, which matters more than the number: expand-heavy v1 requests (especially body.storage across many pages) are far more expensive than v2's narrow reads; CQL with text ~ full-text terms is more expensive than metadata-only CQL; and requesting body in a search result set is the classic way to get throttled. Fetch ids by search, then fetch bodies individually.

Business Scenarios

  • Knowledge-base export into a search index or RAG corpus
  • Documentation freshness audits — last-updated, orphaned pages, stale labels
  • Compliance evidence collection: who approved which runbook, and when
  • Bidirectional sync with an external CMS or docs-as-code repo
  • Content governance — enforcing labels, templates, and space conventions

Key Restrictions & Gotchas

Version history is the richest surface on the platform and it outlives the current page. Every save creates a numbered version with its own author, timestamp, and optional message, and each version's full body.storage is independently retrievable via /content/{id}/version/{n} or the v2 versions endpoint. That means content redacted from the current page is still fully readable in version n−1 by anyone with page access — Confluence does not scrub history when you edit a secret out. Deletion is also two-stage: a deleted page moves to the space trash with status: "trashed" and remains fetchable (and restorable) until purged. A secrets scan or DLP review that reads only current page bodies is structurally incomplete.
  • Optimistic locking is mandatory on update. PUT must supply version.number equal to current + 1, or the request fails with a conflict. There is no "just save this" mode; every writer must read first.
  • Macros are opaque in storage format and absent from their own output. A page whose entire content is an include, excerpt-include, or children macro looks nearly empty in storage. Word counts, text extraction, and similarity analysis over storage format systematically undercount macro-heavy pages.
  • atlas_doc_format is a third body format (the JSON ADF document model shared with Jira). Newer editors may produce it; a parser that only handles XHTML storage will fail on those pages.
  • CQL is not SQL. No joins, no aggregation, no GROUP BY. text ~ "phrase" hits the search index, which is eventually consistent — a page created seconds ago may not be findable yet, while GET /pages/{id} returns it immediately. Building a sync on CQL alone loses recent writes.
  • CQL result sets are capped and cursor-paginated. Deep pagination past a few thousand results is unreliable; partition the query by space or date range instead of paging forever.
  • Inline comments carry positional anchors that decay. An inline comment references the text it was attached to; editing that text can orphan the comment. The comment survives with resolutionStatus and its original selection text, but the anchor no longer resolves — so "unresolved comments" counts drift upward over time for reasons unrelated to review activity.
  • No page-view analytics in the REST API. Confluence Analytics (view counts, unique viewers) is a Premium feature surfaced in the UI and not exposed as a documented public REST endpoint. Popularity ranking must come from elsewhere.
  • Labels are flat, global, and unvalidated. There is no label taxonomy, no namespacing beyond the prefix field (global, my, team), and no way to prevent typo variants. Label-driven governance needs its own reconciliation pass.
  • Attachments are versioned content too — an attachment is itself a content object with an id and version chain, so replacing a file leaves the prior binary retrievable.
  • Restrictions are per-page and inherited implicitly. The API returns a page's own read/update restrictions, but effective visibility also depends on ancestor restrictions and space permissions, which are separate calls. There is no single "can user X see page Y" endpoint.
  • Confluence Server / Data Center is a different API. No /wiki prefix, no v2 endpoints, different auth, and some resources (notably v2 pages and granular OAuth scopes) simply do not exist. Code written against Cloud does not port.
  • Webhooks are not part of the core REST API. Event-driven integration requires a Connect or Forge app declaring event modules; there is no POST /webhooks for a plain API-token script.
