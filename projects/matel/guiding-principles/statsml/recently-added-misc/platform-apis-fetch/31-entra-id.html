Microsoft Entra ID Backlog

Microsoft Graph identity telemetry — sign-ins, directory audits, risk detections, conditional access policy, and the directory objects they reference. Retention is gated by licence tier.

Last verified: August 2026

Overview

What It Provides

Entra ID (formerly Azure AD) is the identity control plane for Microsoft 365 and Azure. Its reporting surface is exposed through Microsoft Graph and splits into four families:

  • Sign-in logs — every authentication attempt, with the conditional access policies that were evaluated and what each one decided. Distinguished by signInEventType: interactive user sign-in, non-interactive (token refresh), service principal, and managed identity. Non-interactive events typically dominate volume by an order of magnitude, so a naive count of "sign-ins" is usually measuring token refresh, not people.
  • Directory audits — configuration and lifecycle changes: user created, member added to group, role assigned, application consent granted, credential added to a service principal.
  • Identity Protection — riskDetections (individual signals such as anonymous IP, leaked credentials, impossible travel) and riskyUsers (the aggregated, mutable risk state of a principal).
  • Directory objects and policy — users, groups, servicePrincipals, applications, role assignments, and conditionalAccess/policies. These are current state, not history.
No user content anywhere in this surface. A sign-in event records that a principal authenticated to SharePoint; it does not record which document was opened. Content-level activity lives in a different product (Microsoft Purview / unified audit log), not here.
Authentication & Scopes
  • App registration in the tenant, OAuth 2.0 client credentials (certificate strongly preferred over secret), token from the tenant-specific endpoint.
  • Application permissions, admin-consented: AuditLog.Read.All for signIns and directoryAudits, IdentityRiskEvent.Read.All and IdentityRiskyUser.Read.All for Identity Protection, Policy.Read.All for conditional access, Directory.Read.All or the narrower User.Read.All / Group.Read.All / Application.Read.All for objects.
  • Reading audit logs has historically also required a directory role (Reports Reader or higher) in addition to the Graph permission — grant both rather than assuming the scope alone is sufficient.
Granularity

One row per event. Sign-in records carry a nested appliedConditionalAccessPolicies array — one entry per evaluated policy with its own result — which makes them the only place you can reconstruct why access was allowed. Risk state is deliberately mutable: riskyUsers reflects a current verdict that Microsoft may raise, lower, or dismiss after the fact, so a snapshot taken today will not reproduce the snapshot taken last week even for the same historical sign-in.

Key Endpoints
  • GET /v1.0/auditLogs/signIns — $filter on createdDateTime, userPrincipalName, status/errorCode, signInEventType.
  • GET /v1.0/auditLogs/directoryAudits — $filter on activityDateTime, activityDisplayName, result.
  • GET /v1.0/identityProtection/riskDetections and /riskyUsers.
  • GET /v1.0/identity/conditionalAccess/policies.
  • GET /v1.0/users, /groups, /servicePrincipals, /applications.
  • GET /v1.0/auditLogs/provisioning — outbound SCIM provisioning outcomes to connected apps.
  • Paging is by @odata.nextLink. Do not construct the next URL yourself; follow the returned link verbatim.
Rate Limits
  • Graph throttles per-tenant and per-app with 429 Too Many Requests and a Retry-After header. Honour that header; do not implement a fixed sleep.
  • The reporting endpoints are among the more aggressively throttled in Graph, and the published thresholds change. Design for throttling as a normal condition rather than an error.
  • $top caps well below what a busy tenant produces per hour, so a full day of non-interactive sign-ins is many sequential pages. Narrow with $filter before reaching for parallelism.
Business Scenarios
  • Conditional access blast-radius analysis — before tightening a policy, count from historical sign-ins how many real sessions the new condition would have blocked.
  • Legacy authentication elimination — client app and protocol fields on sign-ins identify which principals still use protocols that cannot do MFA.
  • Service principal and workload identity audit — credential additions in directoryAudits joined to service principal sign-ins reveals machine identities nobody owns.
  • Privileged role change review — who granted which role, when, and whether it was ever used.
  • Guest and B2B collaboration measurement — external tenant identifiers on sign-ins.
Key Restrictions & Gotchas
  • Retention is licence-gated, and this is the single most consequential fact about the product. The free tier keeps a materially shorter window of sign-in and audit history than the paid tiers; Identity Protection risk reporting has its own, separately gated window that is longer on the top tier. Treat the exact number of days as something to verify for your own tenant and current licensing rather than something to hard-code — but plan on the free tier being roughly a week and the paid tiers roughly a month, with Identity Protection extending further only on the highest tier.
  • Sign-in log access via the API has historically required a premium licence at all. On a free tenant the sign-in report may be unavailable through Graph even though sign-ins are obviously happening. This is a licensing gate, not a missing-data bug.
  • Longer history requires a diagnostic setting configured in advance — route sign-ins, audits, provisioning and risk events to Log Analytics, an Event Hub, or a storage account. Retention there is yours to choose. Until that setting exists, nothing is being archived.
  • Ingestion lag is real. These logs are near-real-time but not instant; records appear minutes after the event, and sign-in logs have historically been slower than audit logs. Any query whose window ends at now will undercount. Lag the window and re-read with overlap, deduplicating on the event id.
  • riskyUsers is a view, not a log. Persist your own daily snapshot if you need to reconstruct what the system believed at a point in time.
  • Deleted directory objects leave dangling identifiers in old events; join failures against /users are expected, not corruption.
  • Conditional access policies are versionless in the API — you can read the current definition but not what it said last quarter. The only durable record of a change is the directoryAudits entry, which describes the modification rather than the resulting full policy.
An event not enabled and not exported at the time it occurred is unrecoverable. You cannot backfill an audit log. On Entra ID this failure has two distinct shapes: the retention window silently expiring, and a diagnostic setting that was never created. Both look identical afterwards — an empty result set that is indistinguishable from "nothing happened."
