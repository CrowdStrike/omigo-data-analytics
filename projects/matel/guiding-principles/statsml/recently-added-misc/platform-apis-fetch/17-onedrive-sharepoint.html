OneDrive / SharePoint BACKLOG

Microsoft Graph driveItems, version history, itemAnalytics, sites and lists — and the throttling model that shapes every integration

Last verified: August 2026

Overview

What It Provides

OneDrive and SharePoint document libraries are the same storage engine behind one Microsoft Graph surface. A drive is a document library; a driveItem is a file or folder inside it. A SharePoint site contains drives and lists, and every driveItem in a library has a corresponding listItem that carries the library's custom columns.

Available: file/folder CRUD and content streams, version history, per-item and per-site usage analytics, permissions and sharing links, delta-based change tracking, list items and column definitions, and webhook subscriptions.

driveItem and listItem are two faces of one object. Content, thumbnails, and versions live on the driveItem; custom metadata columns live on driveItem.listItem.fields. Fetching one and expecting the other's data is the single most common source of "the API doesn't return my metadata".

Authentication & Scopes

  • Microsoft Entra ID (Azure AD) OAuth 2.0. Two distinct modes with different permission sets: delegated (acting as a signed-in user) and application (daemon, no user).
  • Delegated: Files.Read, Files.ReadWrite, Files.Read.All, Files.ReadWrite.All, Sites.Read.All, Sites.ReadWrite.All.
  • Application: Files.Read.All, Sites.Read.All, Sites.ReadWrite.All, Sites.FullControl.All — all require admin consent.
  • Sites.Selected is the least-privilege option: the app is granted access to individual sites by an administrator rather than the whole tenant. Prefer it over Sites.Read.All for anything narrowly scoped.
  • Analytics endpoints additionally require Reports.Read.All in some tenant configurations, and site-level analytics is gated on the tenant not having anonymised usage reporting enabled.

Granularity

Addressable by id (/drives/{id}/items/{item-id}) or by path (/drives/{id}/root:/Folder/File.docx:) — the colon syntax is required for path addressing. $select, $expand, $filter, and $orderby are supported unevenly across resources; $filter in particular is unsupported on many driveItem collections. Change tracking is via /delta, which returns an opaque @odata.deltaLink.

Key Endpoints

  • GET /me/drive/root/children, GET /drives/{id}/items/{id}
  • GET /drives/{id}/root/delta — incremental change feed
  • GET /drives/{id}/items/{id}/versions and /versions/{vid}/content
  • GET /drives/{id}/items/{id}/analytics/allTime, /analytics/lastSevenDays, /getActivitiesByInterval
  • GET /drives/{id}/items/{id}/permissions, POST /createLink, POST /invite
  • GET /sites/{site-id}, GET /sites/{site-id}/lists, GET /sites/{site-id}/lists/{list-id}/items?$expand=fields
  • GET /sites/{site-id}/lists/{list-id}/columns
  • POST /subscriptions — change notifications on a drive or list
  • POST /$batch — up to 20 requests in one round trip

Rate Limits & Throttling

Graph does not publish a single fixed quota for SharePoint/OneDrive; the service is throttled dynamically per app, per tenant, and per user, and the effective ceiling moves with overall service load. What is documented and reliable is the protocol:

  • HTTP 429 with a Retry-After header (seconds). Honouring it is mandatory; ignoring it escalates to longer blocks and, for sustained abuse, HTTP 503.
  • Decorated User-Agent earns you headroom. SharePoint Online applies a less aggressive throttling policy to traffic that identifies itself in the documented format — NONISV|CompanyName|AppName/Version for internal apps, ISV|CompanyName|AppName/Version for vendors. Traffic with a generic or missing agent (a bare library default, or nothing) is throttled first.
  • RateLimit-Limit / RateLimit-Remaining / RateLimit-Reset headers surface remaining application-level resource units on SharePoint endpoints, letting you back off before being throttled.
  • $batch reduces round trips but not resource cost — each sub-request is counted, and individual sub-requests can return their own 429 while the batch returns 200.
Do not hard-code a requests-per-second budget. The correct design is a token-bucket driven by observed RateLimit-Remaining plus unconditional obedience to Retry-After. Fixed-rate clients tuned in a quiet tenant fail in a busy one.

Business Scenarios

  • Enterprise content migration and hybrid sync
  • DLP and classification scanning over document libraries
  • Intranet content inventories driven by list items and columns
  • Document engagement reporting from itemAnalytics
  • Records management feeding retention labels back onto listItems

Key Restrictions & Gotchas

Version history is richer, and longer-lived, than the current file. SharePoint libraries version by default, and the per-version lastModifiedBy chain records who touched what even after the content is overwritten. The number of versions kept is a per-library setting (and, with Intelligent Versioning, an automatically trimmed schedule) — not an API constant. Meanwhile a deleted item passes through the site Recycle Bin and then the second-stage Recycle Bin before purge, so "deleted" content remains restorable for a tenant-configured period. An audit that inspects only current items understates exposure on both axes.
  • itemAnalytics is not a full activity log. allTime and lastSevenDays give aggregate view/access counts and unique actors; getActivitiesByInterval gives bucketed counts. You do not get a per-view row with a user and timestamp. Per-user file access forensics requires the Microsoft Purview / unified audit log, which is a different API entirely.
  • lastSevenDays is a rolling window and is frequently empty for low-traffic items — an empty analytics response does not mean the endpoint failed.
  • Delta tokens expire. A stale deltaLink returns 410 Gone with resyncRequired; the client must re-enumerate from scratch. Any sync design without a resync path will eventually diverge.
  • Webhook subscriptions do not carry the change payload. A notification says "something in this drive changed" — you then call /delta. Subscriptions also have a maximum lifetime and must be renewed before expirationDateTime.
  • $filter and $orderby support is patchy. Many driveItem collections reject them outright; list items support filtering on indexed columns only, and unindexed columns fail once the list crosses the list view threshold.
  • Site ids are composite — {hostname},{siteCollectionId},{siteId}. Passing only a GUID fails. /sites/{hostname}:/sites/{path} resolves a friendly URL to the composite id.
  • eTag and cTag differ. eTag changes on metadata or content change; cTag changes only on content change. Sync engines that watch eTag re-download files after a pure metadata edit.
  • Personal (consumer) OneDrive and OneDrive for Business are not feature-equivalent. Analytics, lists, retention labels, and Sites.* scopes are business-only; some consumer-only behaviours (like differing version limits) do not mirror.
  • Checked-out files, and files in a library with required columns, will reject uploads with errors that are about the list schema, not the drive.
