Google Calendar BACKLOG

Calendar API v3: events, attendees and responseStatus, recurrence expansion, freeBusy, working location, and watch channels.

Last verified: August 2026

Overview

Calendar API v3 is a per-calendar event store with a sync protocol bolted on. The data model is genuinely rich — attendee response state, recurrence rules, conferencing, room resources — but two things routinely break analyses built on it: recurring events are not expanded unless you ask, and what you can see about other people's calendars depends on ACLs you do not control. Meeting-load and time-allocation studies frequently measure permission topology rather than behaviour.

What It Provides
  • Events — id, iCalUID, summary, description, location, start/end (either dateTime+timeZone or all-day date), status, created/updated, organizer, creator, transparency, visibility, eventType, conferenceData, recurrence, recurringEventId, originalStartTime.
  • Attendees — array of objects with email, displayName, responseStatus (needsAction, declined, tentative, accepted), and the booleans optional, organizer, self, resource. Room and equipment bookings appear as attendees with resource: true.
  • Recurrence — RFC 5545 RRULE/EXDATE strings in the recurrence array on the parent event. Instances are derived, and modified instances carry recurringEventId plus originalStartTime.
  • freeBusy — busy time ranges for a set of calendars, with no event detail whatsoever.
  • Working location and status events — eventType values beyond default: workingLocation, outOfOffice, focusTime, and birthday/fromGmail derived types.
  • Watch channels — push notification registration for a calendar or the calendar list.
  • Incremental sync — syncToken returned on a completed full listing, replayed later to get only what changed.
Authentication & Scopes
calendar.freebusycalendar.events.readonlycalendar.readonlycalendar.eventscalendarcalendar.settings.readonly
  • OAuth 2.0 user consent, or a service account with domain-wide delegation to impersonate users. Delegation must be authorised by a Workspace super administrator in the Admin console — an application cannot grant it to itself.
  • Scopes, narrowest first: calendar.freebusy (busy intervals only) → calendar.events.readonly → calendar.readonly → calendar.events → calendar (full). calendar.settings.readonly covers user settings such as default timezone.
  • Sensitive/restricted scope usage in a published app triggers Google's OAuth verification review. Broad calendar-content scopes are the reason many internal tools stay in testing mode indefinitely.
  • A service account without delegation has its own empty calendar. Events must be explicitly shared with it, which is a common source of "the API returns nothing."
Granularity
  • Per event, per calendar. There is no cross-calendar or cross-user query — you iterate calendars, impersonating each user in turn.
  • singleEvents=false (the default) gives one row per recurring series. singleEvents=true gives one row per occurrence within the time window.
  • Attendee-level granularity exists but only for events you can read in full. Under limited-visibility ACLs the same meeting collapses to an opaque busy block.
  • freeBusy granularity is interval-only: start and end timestamps, merged into busy ranges.
Key Endpoints
  • GET /calendar/v3/calendars/{calendarId}/events — params timeMin, timeMax, singleEvents, orderBy, showDeleted, updatedMin, syncToken, maxResults, pageToken, eventTypes.
  • GET /calendar/v3/calendars/{calendarId}/events/{eventId}
  • GET /calendar/v3/calendars/{calendarId}/events/{eventId}/instances — expands one series.
  • POST /calendar/v3/calendars/{calendarId}/events/watch
  • POST /calendar/v3/freeBusy
  • GET /calendar/v3/users/me/calendarList — subscribed calendars with per-user accessRole.
  • GET /calendar/v3/users/me/settings
Rate Limits
  • Quota is enforced at two levels: per Cloud project and per authenticated user. Exceeding either returns 403 rateLimitExceeded / userRateLimitExceeded, or 429. The per-user ceiling is the one that bites during domain-wide sweeps, because impersonation spreads load across users but a hot user still throttles.
  • Exponential backoff with jitter is required, not optional — Google's own guidance treats retry behaviour as part of the contract. Quota values are visible and adjustable in the Cloud console for your project, so hard-coding a rate is unsafe; read the console figure and pace against observed 403s.
  • maxResults is capped server-side and the returned page may be smaller than requested. Always loop on nextPageToken and never treat a short page as the end of results — only the absence of nextPageToken means done.
  • singleEvents=true over a wide window is expensive: a daily meeting over three years is one stored event and roughly a thousand returned rows, all paginated.
Business Scenarios
  • Meeting-load analysis: hours in meetings per person per week, recurring vs ad-hoc split, optional-attendee ratio.
  • Room and resource utilisation from resource: true attendees, including booked-but-declined waste.
  • Focus-time erosion: focusTime events created vs subsequently overlapped by meetings.
  • Hybrid-work reporting from workingLocation events (home / office / custom), where licensing permits.
  • Scheduling automation and availability lookup via freeBusy without granting content access.
  • External-collaboration measurement by classifying attendee email domains against your own.
By default events.list does not expand recurrence. A weekly standup returns as a single event carrying recurrence: ["RRULE:FREQ=WEEKLY;..."], and its start is the first occurrence — which may be years before your timeMin. Counting rows without singleEvents=true undercounts recurring meetings to one each, and since recurring meetings are the bulk of most calendars, meeting-load figures come out dramatically low while still looking plausible. Setting singleEvents=true is also required before orderBy=startTime is accepted, and cancelled single instances of a series only appear with showDeleted=true.
Attendee responseStatus is not a reliable attendance signal. It records an RSVP, not presence. External and cross-domain attendees frequently remain needsAction indefinitely because their reply never propagates back to the organiser's copy, and Google Calendar auto-accepts on some configurations — so accepted can mean "a machine said yes." There is no field anywhere in the API stating who actually joined. Treating RSVP as attendance systematically overstates participation for internal attendees and understates it for external ones, which biases exactly the internal-vs-external comparison people most want to make.
Key Restrictions & Gotchas
  • Cross-domain visibility is ACL-dependent and asymmetric. With free/busy-only sharing you get busy blocks with no summary and no attendees; the event may appear titled "busy." Comparing meeting counts across teams or companies compares sharing settings as much as workload.
  • Private events are redacted, not hidden. visibility: "private" on a calendar you can only see partially yields an event object with the timing present and the content stripped — so it silently enters row counts while contributing no attributes.
  • freeBusy returns intervals only. No titles, no attendees, no organiser, no event IDs. For a calendar you lack access to it returns an errors entry (for example notFound) inside that calendar's object rather than data — and a naive parser reads that as "fully free." Absent busy data must be treated as unknown, never as available.
  • syncToken expires. A 410 GONE means the token is dead and you must discard local state and perform a full re-sync. Tokens are also invalidated by parameter changes, so you cannot switch singleEvents or the time window mid-stream. Incremental sync additionally ignores timeMin/timeMax-style narrowing on subsequent calls.
  • Deletions surface as status: "cancelled", not as absent rows, and only with showDeleted=true or during incremental sync. Cancelled rows can be near-empty — sometimes little more than id and status — so any join that assumes summary exists will fail on them.
  • Watch channels tell you nothing about what changed. The notification carries channel and resource identifiers plus a resourceState, and you must re-query with your syncToken to find the delta. Channels also require a verified HTTPS endpoint on a domain you own, they expire and must be renewed before expiry, and notifications may be duplicated or coalesced. Missing a renewal creates a silent gap with no error anywhere.
  • Working location, out-of-office, and focus-time events are edition-gated. They exist as eventType values but are only creatable and populated on qualifying Workspace editions. On other editions the field is simply absent, which is indistinguishable from "the user works from the office every day" unless you check licensing separately.
  • All-day events use date, timed events use dateTime. These are different keys, and all-day end.date is exclusive. Duration arithmetic that ignores this off-by-one inflates every all-day event by a day.
  • Timezones are per-event and per-calendar. An event's start.timeZone may differ from the calendar's default and from the requesting user's. Recurring events expand according to the series timezone, so DST transitions shift wall-clock times of individual instances.
  • Modifying a single instance forks it. The exception instance keeps recurringEventId and originalStartTime; the parent gains an EXDATE. Deduplicating on iCalUID alone will collapse distinct occurrences, because the series shares one iCalUID.
  • There is no meeting-quality or engagement data here. Join times, duration attended, and camera/mic state live in Meet reporting via the Admin SDK Reports API, not in Calendar. Calendar knows intent; it does not know what happened.
