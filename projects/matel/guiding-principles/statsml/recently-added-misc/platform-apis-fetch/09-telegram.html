Telegram BACKLOG

Bot API polling and webhooks, channel posts, and chat member counts — plus the sharp line between the Bot API and the MTProto client API.

Last verified: August 2026

Overview

Telegram exposes two entirely different surfaces. The Bot API is a simple HTTPS/JSON wrapper at https://api.telegram.org/bot{token}/METHOD, designed so a bot can only see what has been deliberately routed to it. The MTProto client API (api_id/api_hash, used via TDLib, Telethon, or similar) authenticates as a real user account and can see everything that user can see. Most disappointment with "the Telegram API" is actually the discovery that the Bot API is narrow by design and the broad alternative carries account-ban risk.

What It Provides
  • Update objects — the single delivery envelope. Carries at most one of message, edited_message, channel_post, edited_channel_post, callback_query, inline_query, my_chat_member, chat_member, chat_join_request, message_reaction, message_reaction_count, plus payment and poll updates.
  • Two mutually exclusive transports — getUpdates long polling, or setWebhook push to an HTTPS endpoint. Setting a webhook makes getUpdates fail; you must deleteWebhook to go back to polling.
  • Channel posts — if the bot is a member (typically an administrator) of a channel, it receives channel_post and edited_channel_post updates for new content going forward.
  • Chat metadata — getChat, getChatMemberCount, getChatMember, getChatAdministrators.
  • File access — getFile returns a file_path which is then fetched from https://api.telegram.org/file/bot{token}/{file_path}.
Authentication & Scopes
  • Bot API: a single bearer-style bot token issued by BotFather, embedded in the URL path. There is no scope system and no per-method permission model — capability is determined entirely by what the bot has been added to and its administrator rights in each chat.
  • There is no OAuth, no user consent screen, and no way for a bot to act on a user's behalf. The bot is always itself.
  • MTProto: api_id and api_hash registered against a Telegram account, then a full user login (phone number, code, optional 2FA password). The resulting session is a user session with that user's full visibility.
  • Group-level behaviour is toggled in BotFather, not in the API: privacy mode, can join groups, and inline mode are account settings on the bot.
Granularity
  • Per update, per message. Each Update has a monotonically increasing update_id, which is the only ordering and de-duplication key you get.
  • getUpdates requires acknowledgement by offset: passing offset = last_update_id + 1 confirms and discards everything earlier. Acknowledgement is destructive and irreversible.
  • Member data is aggregate-only via the Bot API: a count, plus the administrator list. No individual-member enumeration.
  • Reactions arrive as message_reaction (individual, requires the bot to be an administrator) and message_reaction_count (anonymous aggregate), and both must be explicitly requested.
Key Endpoints
  • GET /bot{token}/getUpdates?offset=&timeout=&allowed_updates=
  • POST /bot{token}/setWebhook — url, secret_token, allowed_updates, drop_pending_updates.
  • GET /bot{token}/getWebhookInfo — exposes pending_update_count and last_error_message; the first place to look when updates stop arriving.
  • GET /bot{token}/getChat?chat_id=
  • GET /bot{token}/getChatMemberCount?chat_id=
  • GET /bot{token}/getChatAdministrators?chat_id=
  • GET /bot{token}/getFile?file_id=
  • POST /bot{token}/sendMessage, forwardMessage, copyMessage.
Rate Limits
  • Limits are enforced by response, not published as a contract. On throttling the API returns ok: false with error_code: 429 and a parameters.retry_after value in seconds. Honour retry_after rather than assuming a fixed rate — it is the only authoritative number.
  • Limits differ by target: per-chat message rate is much tighter than global send rate, and broadcast to a large audience is expected to be paced over time rather than burst. Telegram's own guidance for bulk notification is on the order of 30 messages per second across all chats, with a much lower per-group ceiling of roughly 20 messages per minute to the same group chat. Both are advisory guidance rather than a versioned contract and have been revised — treat them as a design budget, not a guarantee.
  • Webhook delivery has its own back-pressure: if your endpoint is slow or erroring, Telegram retries and pending_update_count grows. A persistently failing webhook can have its updates dropped.
  • MTProto enforces FLOOD_WAIT_x errors with a mandatory wait in seconds, and is substantially more aggressive than the Bot API. Repeated violations escalate to session and account restrictions.
Business Scenarios
  • Support and ops bots: ticket intake, alert routing, on-call acknowledgement via callback_query.
  • Own-channel content analytics: post cadence, edit frequency, reaction aggregates, subscriber count trend sampled over time.
  • Community moderation signals from chat_member and chat_join_request updates — joins, leaves, bans, promotion events.
  • Payment and subscription flows using the Bot API payments methods.
  • Notification delivery where email is unreliable, with the hard constraint that the user must opt in by messaging the bot first.
There is no Bot API method to enumerate the members of a group or channel. getChatMemberCount gives you a scalar and getChatAdministrators gives you the admins; that is the entirety of member visibility. You cannot list subscribers, cannot build an audience roster, and cannot compute per-member activity coverage. Any tool that appears to do this is running an MTProto user session, not a bot. This is an intentional anti-scraping design decision, not a gap awaiting a new endpoint.
A bot has no history and a short memory. It cannot read messages sent before it joined a chat, and getUpdates only serves updates from roughly the last 24 hours — unacknowledged updates older than that are discarded. If your consumer is down for a day, that window is gone permanently; there is no replay, no cursor into the past, and no backfill endpoint. Telegram is a push transport that you must persist yourself, not a queryable message store.
Key Restrictions & Gotchas
  • Privacy mode is on by default. In a group, a bot receives only messages that are commands addressed to it, replies to its own messages, or messages mentioning it — plus service messages. Seeing all group traffic requires explicitly disabling privacy mode via BotFather, and the change takes effect on re-add for existing groups. Analytics built assuming full group visibility will silently sample a biased subset: command-issuing users only.
  • Bots cannot initiate contact. The user must message the bot, or add it to a group, before the bot can send them anything. There is no way to message a user by phone number or username. This makes bot-based outbound campaigns structurally impossible.
  • allowed_updates is an opt-in filter with a non-empty default. Update types added after your integration was written — message_reaction most notably — are not delivered unless you list them explicitly. Omitting the parameter does not mean "send me everything."
  • Per-post view counts are not exposed. Channel view counters are visible in the client but the Bot API does not return them for arbitrary channels. Reach and impression metrics that Telegram itself displays are not available programmatically through the Bot API.
  • File size limits are asymmetric and low. A bot can download files up to roughly 20 MB and upload up to roughly 50 MB through the cloud Bot API. Running a local Bot API server removes several of these limits and gives direct filesystem access to files, but that is additional infrastructure you must operate.
  • file_path from getFile is short-lived. Treat it as a one-shot download URL, not a stable reference. The durable identifier is file_id — and even that is only stable for the same bot.
  • Webhook and polling cannot coexist, and switching between them under load loses updates unless you drain first. drop_pending_updates: true is a deliberate data-loss flag.
  • MTProto is a Terms of Service question, not a technical one. A user session can read full history, enumerate members, and download large media — but automating a user account for data collection is a bannable use, and the ban lands on a real phone number. Flood control is aggressive and escalating. Treat MTProto as a last resort with legal review, not as "the API with fewer limits."
  • Deleted messages produce no update. The Bot API does not notify you when a message is deleted, so a locally persisted mirror of a chat will drift permanently out of sync with what users actually see.
