SharePoint Lists via Microsoft Graph BACKLOG

Lists as typed tables — column definitions, list items with field values, per-item version snapshots, and delta sync

Last verified: August 2026

Overview

What It Provides

A SharePoint list is a schema-bearing table: columnDefinition objects describe the typed columns, and listItem objects carry the row values inside an open fields bag. Every document library is also a list, which is why a library can be read either as a drive (file-centric) or as a list (metadata-centric) — the same underlying rows, two projections.

  • Schema — columnDefinition per column: text, number, boolean, dateTime, choice, currency, lookup, personOrGroup, hyperlinkOrPicture, calculated, geolocation, term (managed metadata), thumbnail, contentApprovalStatus.
  • Rows — listItem with fields, contentType, createdBy/lastModifiedBy, and a sharepointIds facet linking back to classic SharePoint identifiers.
  • History — listItemVersion gives a full snapshot of fields at each version, not a diff.
  • Sync — items/delta for incremental change tracking with a durable-ish token.

Authentication & Scopes

  • Delegated — the app is bounded by the signed-in user's effective list permissions, including item-level security trimming.
  • Application (app-only) — Sites.Read.All / Sites.ReadWrite.All are tenant-wide and see every list in every site. Sites.Selected grants nothing until an admin authorises the app on named site collections, and is the only sane choice for a daemon.
  • Site id resolution — you almost always start from a URL, so GET /sites/{hostname}:/sites/{path} is the first call in any script.

Graph vs SharePoint REST

These are two different surfaces over one engine, not two spellings of the same call. Choose deliberately:

  • Graph (/sites/{id}/lists/{id}/items) — Entra ID auth, consistent OData v4, @odata.nextLink paging, delta support, Sites.Selected least-privilege scoping, and one token that also reaches Mail, Teams, and Drive. The recommended surface for new work. But it exposes a subset of SharePoint.
  • SharePoint REST (/_api/web/lists/getByTitle('X')/items, and the newer /_api/v2.1/) — the full surface. CAML queries via POST .../GetItems, list views and their filters, RenderListDataAsStream for view-shaped output with lookup expansion, field schema XML, and item attachments. Costs: an older OData dialect, Accept: application/json;odata=nometadata ceremony, form digests for writes on some auth paths, and no cross-service token.
  • Only in REST: CAML, view definitions as executable queries, AttachmentFiles, field schema XML, ItemCount as a cheap property.
  • Only in Graph: delta, Sites.Selected, subscriptions in the standard Graph webhook model.
  • Practical rule: Graph for reading and writing item data; REST when you need CAML, views, or attachments. Many production integrations run both against the same list, which means two auth paths and two throttling stories to reason about.

Granularity

Per list, per column, per item, per item-version. Field values are not returned by default on a list-items query — you must ask for them: GET /sites/{id}/lists/{lid}/items?$expand=fields, optionally narrowed with $expand=fields($select=Title,Status). Field keys are the column's internal name, not its display name, and internal names encode illegal characters — a column shown as "Due Date" is keyed Due_x0020_Date. Reading columns first and building a display-to-internal map is the only reliable approach.

Rate Limits

Two throttling layers stack here. Graph throttles per app and per tenant; the SharePoint Online backend applies its own per-app, per-site-collection budget underneath, and list queries are charged against it. Both answer with HTTP 429 plus Retry-After; SharePoint-backed responses additionally carry RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset, which let a client self-throttle before it is throttled. Microsoft documents that traffic sent with an identifiable User-Agent is treated more favourably than anonymous traffic. Rather than a fixed rate, budget by cost: an $expand=fields page is meaningfully more expensive than a bare item listing, and a $filter on an unindexed column can be dramatically more expensive still.

Concurrency does not buy throughput here. The SharePoint per-site budget is shared across every thread you run, so eight parallel workers against one site simply reach 429 eight times faster. Serial with Retry-After and jitter finishes sooner in wall-clock time than an aggressive fan-out that keeps getting rejected.

Business Scenarios

  • Lists as lightweight operational databases — request trackers, asset registers, approval queues — read into a warehouse via delta
  • Reverse ETL: push reference data from a system of record into a list users can browse
  • Governance reporting on document libraries by reading them as lists (retention labels, classification columns) instead of walking drives
  • Change auditing at the field level using listItemVersion snapshots to reconstruct who changed which column
  • Migration off legacy list workflows, where the schema must be read before the rows

Key Restrictions & Gotchas

Item version history holds field values the current item no longer shows. Where versioning is on — the default for libraries, and common for lists — /items/{id}/versions returns each prior version with its own full fields snapshot, author, and timestamp. Overwriting a field does not remove the previous value; it stays retrievable by anyone who can read the item. How many versions survive is a per-list setting rather than an API constant, and deletion is separately buffered through the site Recycle Bin and then a second-stage admin Recycle Bin on a tenant-configured schedule. A data-minimisation review that inspects only current items understates retention on both axes.
Internal names are frozen at creation. A column created as "Due Date" is keyed Due_x0020_Date forever. Renaming it in the UI changes only displayName. Every filter, select, and write uses the internal name — building requests from what the UI shows is the most common source of "field not recognised".
The list view threshold is the defining constraint. SharePoint Online caps how many items a single query may evaluate — the long-documented figure is 5,000 items, and it is a limit on the scan, not on the result set. A list with a hundred thousand rows paginates fine, but a $filter or $orderby on a column that is not indexed fails once the list crosses the threshold, because the engine would have to inspect more rows than it is allowed to. Adding an index to the filtered column is the fix; retrying is not. The exact figure is a service limit and may change.
  • Query support is narrower than OData implies. Only some column types are filterable and sortable through Graph, and $filter on a field inside the fields bag has documented restrictions. Discover what works against a realistic list; do not assume full OData because the URL accepts it.
  • Attachments are not exposed. Classic list-item attachments have no Graph representation. Reaching them means dropping to the SharePoint REST endpoint (/_api/web/lists(...)/items(n)/AttachmentFiles) with a separate permission story. This surprises almost every list-migration project.
  • Item-level permissions are not exposed. Graph will not tell you that row 47 has unique permissions or who they are broken to. Security-trimmed delegated reads simply omit the row, which looks identical to the row not existing.
  • Lookup and person columns return references, not objects. You get a LookupId plus a display value, and person fields return a LookupId into the site user information list — resolving to a real Entra ID identity requires a second call, and the display value can be stale.
  • Calculated and read-only columns cannot be written. A PATCH that includes them fails the whole request rather than ignoring them, so update payloads must be filtered against the schema.
  • Version history depth is a list setting. Versioning can be off entirely, in which case versions returns only the current state. Where it is on, the retained count is bounded by the library or list configuration, and trimmed versions are gone — the API never had a copy.
  • Delta can require a full resync. An invalidated token returns 410 Gone with resyncRequired. Delta is also eventually consistent and may repeat an item, so apply changes idempotently keyed on item id.
  • The systemFacet marks non-user edits. Items touched by system processes carry it, and treating those as human activity inflates every "who is active" metric built on list history.
  • Recycle bin is invisible. A deleted item disappears from Graph while remaining recoverable in SharePoint's two-stage recycle bin, which Graph does not expose. "Permanently deleted" from the API's point of view is not permanent.
  • Not retrievable: list-item attachments, unique per-item permissions, view definitions and their filters as executable queries, workflow/Power Automate run history attached to items, and any field value from a version already trimmed by the list's versioning settings.
