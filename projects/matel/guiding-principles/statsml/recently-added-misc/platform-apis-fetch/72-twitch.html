Twitch BACKLOG

Helix REST API, EventSub, and IRC chat. Everything is a snapshot of now — there is no historical viewership or chat-history endpoint, so all longitudinal series are self-collected.

Last verified: August 2026

Overview

What It Provides

Twitch's current public surface is the Helix REST API plus two event/chat transports (EventSub and IRC). Helix is organised around present-tense reads of live platform state and broadcaster-scoped writes. There is no analytics warehouse behind it.

  • Get Streams — currently live channels, filterable by game, language, user id/login; cursor-paginated
  • Get Videos — VODs by type: archive, highlight, upload
  • Get Clips — by broadcaster or by game, with a start/end date range
  • Get Games / Get Top Games — category metadata and current category ranking
  • Get Users, Get Channel Information — profile and current title/category/language
  • Search Channels / Search Categories — name-based discovery
  • Get Followed Streams — live channels the authenticated user follows
  • Get Channel Followers — a follower count is broadly available; the follower list requires broadcaster or moderator authorization

Channel Points, Subscriptions, Engagement

  • Custom Rewards — create, update, delete rewards on your own channel; read and update Redemptions
  • Get Broadcaster Subscriptions (tier and count, broadcaster token required), Check User Subscription
  • Bits leaderboard, Get Cheermotes
  • Hype Train, Polls, Predictions, Goals — all scoped to your own channel
Channel-point redemptions are an unusually clean behavioural signal. Unlike a view or a follow, a redemption is deliberate and priced — the viewer spent an accumulated balance to trigger it, and the price is set by the broadcaster. That gives you a revealed-preference observation with a known cost attached, which is rare in social telemetry. The catch is that the price is a broadcaster-chosen design parameter, so redemption rates are not comparable across channels without conditioning on the reward's cost and availability window.

Moderation Surface

Banned users, AutoMod status checks (test a message before sending), moderators, VIPs, shield mode, blocked terms. All broadcaster- or moderator-scoped — there is no cross-platform moderation feed.

Chat: Two Distinct Mechanisms

  • IRC over TMI — connect as a bot with an OAuth token and receive PRIVMSG lines carrying IRCv3 tags: user id, display name, badges, emotes with positions, colour, message id, room id, timestamp. You also see USERNOTICE (subs, resubs, gift subs, raids), and CLEARCHAT / CLEARMSG for moderation actions.
  • EventSub — structured events over one of two transports. Webhooks: an HTTP callback where Twitch signs each request (you must verify the signature) and performs a challenge handshake on subscribe. WebSockets: a session-based transport with keepalive messages and session reconnect, appropriate for client apps that cannot host a public endpoint.

EventSub subscription types cover stream.online / stream.offline, follows, subscriptions, cheers, raids, channel point redemptions, moderation events, and chat messages.

Authentication & Scopes

OAuth 2.0. Authorization code grant for user context, client credentials for app-only public reads, and a device code flow for input-constrained clients. Every request carries both a Client-Id header and a Bearer token — a token alone is not sufficient. Scopes are granular and named per capability:

channel:read:subscriptions channel:manage:redemptions moderator:read:followers

The practical consequence is that most of the interesting data is gated behind a token issued by the broadcaster whose channel you want to study. Consent is per-channel, not per-dataset.

Granularity

  • Stream objects are current-state snapshots: one viewer_count at the moment of the call, no history attached
  • VOD and clip objects are per-asset records with duration, view count and creation time
  • Redemptions, subs, cheers and raids are per-event records with an id and timestamp
  • Chat is a per-message live stream with no retrieval endpoint

Rate Limits & Pricing

Access is free; the constraint is throughput. Helix uses a token-bucket points budget per client id — each request consumes points from a refilling bucket, and some endpoints cost more than the baseline. The current state is surfaced on every response in Ratelimit-Limit, Ratelimit-Remaining and Ratelimit-Reset headers, so a correct client reads those rather than hardcoding an interval. EventSub applies separate limits: a per-client cost budget across subscriptions and a cap on total enabled subscriptions. Design polling loops against the headers, and prefer EventSub over polling wherever an event type exists — a push subscription is cheaper than a poll that discovers nothing changed.

Business Scenarios

  • Creator analytics tools (growth, category performance, redemption economics)
  • Stream alerts and on-stream overlays driven by EventSub
  • Loyalty and channel-point mechanics, minigames, viewer rewards
  • Esports and category trend tracking from Top Games and Get Streams
  • Brand sponsorship measurement on channels that have granted a token
  • Chat moderation tooling and toxicity research on live chat

Insights Export for Broadcasters

The Creator Dashboard provides viewership, unique viewers, chat and follower trends, and revenue, with CSV export. Separately there are game and extension analytics report endpoints that return time-limited download URLs for a report file.

This is broadcaster-scoped and partly dashboard-only — it is not a research dataset. The richer analytics live behind a human logging into their own dashboard, and the report endpoints only cover assets you own. Aggregate viewership history for a channel you do not own is not exposed anywhere in the API.

Key Restrictions & Gotchas

There is no historical concurrent-viewership endpoint. Get Streams returns the current viewer_count. Every channel-popularity history that exists was produced by someone polling and storing it, which means the series' time resolution is an artifact of their polling interval, not a property of Twitch. It also means the well-known third-party Twitch stats sites are reconstructions — independently sampled estimates with their own gaps and cadence — not authoritative records. Two such sites can legitimately disagree about the same stream.
Access-shaped discontinuities (analytical point 3). Because all Twitch history is self-collected, any break in your own collection — a rate-limit change, a scope revocation, a redeploy, a token expiry, or a migration from polling to EventSub — inserts a discontinuity into the series that looks exactly like a real change in viewer behaviour. A drop in observed concurrents after switching instrumentation is a measurement artifact until proven otherwise. Version-stamp and interval-stamp every stored sample.
  • VODs expire. Archives are retained for a limited period that depends on account type, so a design that plans to fetch VODs retrospectively will find holes in the record. Clips persist under different rules than archives, so clip coverage and archive coverage decay at different rates.
  • Chat has no history endpoint. IRC is a live tail only. Chat that was not being recorded at the moment it happened is unrecoverable — there is no backfill.
  • viewer_count is a vendor metric. Treat it as a platform-computed figure with an undisclosed definition. Embeds, autoplay, background tabs and multi-tab viewing all bear on it in ways Twitch does not publish. It is not a count of humans and it is not stable across product changes on Twitch's side.
  • Survivorship bias on re-query. Deleted VODs, banned channels and deleted messages vanish from results. Re-running the same historical query later returns a smaller, cleaner, systematically different set — the surviving population, not the original one. Cache the raw response at collection time if the population matters.
  • Follower lists, subscriber lists and redemption histories all require the broadcaster's authorization, so any cross-channel study is a sample of channels that agreed to participate.
