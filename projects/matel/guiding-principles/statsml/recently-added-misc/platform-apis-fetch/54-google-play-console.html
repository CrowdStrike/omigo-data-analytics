Google Play Console BACKLOG

Play Developer API for purchases and subscriptions, Reporting API for vitals, Pub/Sub notifications, and bulk report exports to Cloud Storage.

Last verified: August 2026

Overview

What It Provides

Four separable surfaces, with different auth, different shapes, and different privacy behaviour:

  • Google Play Developer API (androidpublisher) — release management (edits, bundles, tracks), purchases.subscriptionsv2.get, purchases.products.get, purchases.voidedpurchases.list, orders, and reviews.list / reviews.reply.
  • Real-time Developer Notifications (RTDN) — subscription and voided-purchase events delivered to a Cloud Pub/Sub topic you own, base64-encoded in the message data.
  • Play Developer Reporting API — programmatic access to Android vitals and related metric sets: crash rate, ANR rate, excessive wakeups, stuck partial wake locks, slow rendering, error-report counts. Queried as metric sets with dimensions and time granularity, plus freshness metadata.
  • Bulk report exports — Play Console can write CSV reports (installs, ratings, reviews, crashes, financial) to a Cloud Storage bucket assigned to your developer account. This is the path for historical backfill.
Authentication & Scopes
  • Service account in a Google Cloud project, linked to the Play Console developer account, with per-app or account-level permissions granted inside Play Console. Linking in Cloud alone is not sufficient — the grant inside Play Console is a separate, easily forgotten step.
  • OAuth scope https://www.googleapis.com/auth/androidpublisher for the Developer API; the Reporting API is a distinct service with its own enablement.
  • RTDN requires the Pub/Sub topic to grant publish rights to Google's Play notification service account, and your subscriber needs its own credentials.
  • Bulk exports are read via Cloud Storage IAM on the assigned bucket, not via the Play APIs.

Granularity — the crux
  • Purchase-level and identified (your customers only): subscriptionsv2.get keyed by purchase token returns full subscription state — line items, expiry, acknowledgement state, obfuscatedExternalAccountId if you set it, linkedPurchaseToken on upgrade/resubscribe. RTDN is event-level. This is the identified path.
  • Aggregate only, thresholded: everything statistical — installs, acquisition funnels, ratings, and vitals. Reported as counts and rates over dimensions (country, device model, Android version, app version), never per user.

Vitals metrics arrive as rate-plus-denominator pairs (for example a crash rate together with a count of distinct users in the denominator), which is what makes them usable — a rate without its denominator cannot be pooled across dimensions correctly, and Play does give you the denominator. Use it.

What people assume and do not get. No per-user install/uninstall timeline. No per-user session or engagement stream (that is your own analytics SDK's job). Play Install Referrer gives an attribution string to your app on the device, not a console report. Reviews API surfaces reviews with a reply channel but is not a complete historical corpus — use the bulk export for history. Vitals only cover devices with Play services reporting enabled and consented, so the vitals denominator is a subset of your install base, not all of it.
Key Endpoints
  • GET purchases.subscriptionsv2.get — packageName + token
  • POST purchases.subscriptions.acknowledge — mandatory; unacknowledged purchases are refunded automatically
  • GET purchases.voidedpurchases.list — refunds/chargebacks/revocations, paged, bounded lookback
  • GET reviews.list, POST reviews.reply
  • Reporting API: vitals.errors.counts, vitals.crashrate, vitals.anrrate, vitals.excessivewakeuprate, vitals.stuckbackgroundwakelockrate, vitals.slowrenderingrate, each with a :query method and a :get for freshness
  • anomalies.list — Play's own flagged metric anomalies
Rate Limits

Standard Google API quota model: per-project per-minute request quotas visible and adjustable in the Cloud console, 429/RESOURCE_EXHAUSTED on breach, exponential backoff expected. Do not hard-code a number — read it from your project's quota page, since defaults differ by API and change. Additional practical bounds:

  • voidedpurchases.list has a bounded lookback window; a gap in polling past that window is unrecoverable.
  • Reporting API responses carry freshness metadata (latest available day per granularity). Recent days are incomplete and will be restated — always read freshness rather than assuming "yesterday is final".
  • RTDN delivery is at-least-once and out-of-order; dedupe on message ID and re-fetch canonical state with subscriptionsv2.get rather than trusting event ordering.
Business Scenarios
  • Subscription lifecycle: entitlement grant/revoke, churn, grace-period and hold-state recovery
  • Refund and chargeback reconciliation
  • Release health gating: block a staged rollout on ANR/crash rate regression
  • Review sentiment monitoring and response SLAs
  • Device/OS fragmentation analysis for support-matrix decisions
Key Restrictions & Gotchas
  • Thresholding and aggregation floors. Console and API aggregate views withhold or coarsen small cells. Narrow slices — a rare device model in a small country on one app version — return nothing rather than a small number.
  • Vitals denominators are consent-gated. Crash rate is computed over reporting-enabled devices. If reporting consent correlates with device tier or region (it does), the rate is not a population rate.
  • Restatement is normal. The last several days of any vitals or install series move. Snapshot with an as_of date or your dashboards will disagree with themselves.
  • The newest day is partial, and a naive comparison invents a decline. The freshness metadata exists precisely because the latest period has not finished filling in. Putting it on a chart beside closed days, or comparing "today" against last week without excluding the open period, produces a drop that reflects delivery lag rather than user behaviour — and it disappears on re-query the next day, which then reads as a recovery. Read freshnessInfo and truncate the series to the latest complete period.
  • Purchase token churn. Upgrades, downgrades and resubscribes mint new tokens with linkedPurchaseToken chaining; treating tokens as stable user keys double-counts subscribers.
  • Test purchases from license-test accounts appear in the purchase APIs and must be filtered out of revenue analysis.
  • Uninstalls are not events. There is no uninstall webhook; you infer it from aggregate install/uninstall report deltas.
The statistical caveat that matters most. As on the App Store, aggregate reporting suppresses low-volume rows, which means missingness is a deterministic function of the count in the cell — missing because small. The consequence is directional, not merely a loss of precision: any unweighted average over surviving cells is an average over high-volume cells. For vitals this bites hardest exactly where you care, because a crash confined to one uncommon device model is both the most actionable finding and the most likely to be suppressed. Two habits help. First, always pool using the reported denominators (sum numerators, sum denominators) instead of averaging rates, so cell size enters the estimate correctly. Second, when cells are suppressed, reconcile against the unsuppressed total and treat the residual as a bounded unknown rather than zero. Assuming a suppressed cell is zero is the same error as assuming an unobserved crash did not happen.
