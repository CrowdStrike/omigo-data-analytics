Microsoft Office / Excel BACKLOG

Graph Excel workbook ranges, tables, charts and worksheetFunctions — plus OOXML for files the API cannot reach

Last verified: August 2026

Overview

What It Provides

Microsoft Graph exposes a live, calculating Excel engine over workbooks stored in OneDrive or SharePoint. This is materially different from parsing a spreadsheet file: writing a formula through the API causes the service to recalculate, and reading a range returns both what was typed and what it evaluated to.

Object model under /workbook: worksheets, range (by address, or via usedRange / entireRow / resizedRange and other derived-range functions), tables with columns and rows, charts, names (named items), pivotTables (limited), comments, and functions — a callable surface for the built-in worksheet function library.

There is no Graph API for Word or PowerPoint content. Graph treats .docx and .pptx as opaque driveItems: you can list, download, upload, version, and share them, but there is no /workbook-equivalent object model for paragraphs or slides. Editing their content server-side means downloading the file and manipulating OOXML, or running an Office Add-in with the client-side Word.run / PowerPoint.run JavaScript API — which is a different execution model entirely, not a REST API.

Authentication & Scopes

  • Entra ID (Azure AD) OAuth 2.0. The Excel API rides the files permissions, not a dedicated Excel scope.
  • Delegated: Files.ReadWrite, Files.ReadWrite.All; read-only work needs Files.Read / Files.Read.All.
  • SharePoint-hosted workbooks additionally need Sites.Read.All / Sites.ReadWrite.All, or the narrower Sites.Selected.
  • Application-permission support is limited. The Excel workbook API has historically been oriented at delegated flows; daemon scenarios are the ones most likely to hit unexpected accessDenied and are worth validating early rather than assumed.

There is no Excel-specific scope — the workbook API is authorised entirely through file and site permissions.

Granularity

Range-level read and write, keyed by A1 address (/range(address='A1:D50')) or by table structure. usedRange lets you discover extent without knowing it. Table rows are addressable by index and appendable without computing an address — the safest way to add data.

Every response distinguishes four parallel 2-D arrays for the same range: values (typed, computed), text (display strings), formulas (A1-style), formulasLocal (localised function names and separators), and numberFormat.

Sessions — persistent vs non-persistent

The workbook-session-id header selects one of three behaviours, and this is the most consequential design decision in the API:

  • Persistent session (persistChanges: true): changes are written back to the stored file. Required for anything that must survive.
  • Non-persistent session (persistChanges: false): the workbook is loaded into a sandbox, edits apply only inside the session, and nothing is saved. Ideal for what-if calculation, using Excel purely as a formula engine.
  • No session header at all: each request is handled independently; writes still persist, but there is no shared calculation state and per-call overhead is highest.
Sessions expire on idle and can be evicted. A session that has gone stale returns an error telling you the session is invalid; a robust client creates sessions lazily, caches the id, and transparently re-creates on failure. Long analytical loops that assume one session lives for hours will break. There is also no way to convert a non-persistent session into a persistent one — you choose at creation, and a non-persistent session's work is unrecoverable once it ends.

Key Endpoints

  • POST /me/drive/items/{id}/workbook/createSession, /closeSession, /refreshSession
  • GET /workbook/worksheets/{name}/range(address='A1:D50')
  • PATCH the same range with { "values": [[…]] } or { "formulas": [[…]] }
  • GET /workbook/worksheets/{name}/usedRange
  • GET|POST /workbook/tables, /workbook/tables/{id}/rows/add
  • GET /workbook/tables/{id}/columns, POST /workbook/tables/{id}/sort/apply
  • GET /workbook/worksheets/{name}/charts, POST /charts/add, GET /charts/{id}/image(width=600)
  • POST /workbook/functions/vlookup, /functions/npv, … (one endpoint per worksheet function)
  • POST /workbook/application/calculate — force recalculation
  • GET /workbook/names — named items, workbook and worksheet scoped

Rate Limits

The Excel endpoints share Microsoft Graph's dynamic throttling with the rest of the SharePoint/OneDrive surface — per app, per tenant, per user, and load-sensitive rather than a fixed published number. Expect HTTP 429 with Retry-After and treat that header as authoritative. Two Excel-specific cost notes: reading a very large range in one call is far cheaper than the equivalent cell-by-cell traversal, and each /workbook/functions/* call is a full server-side calculation round trip — building a loop of them is the classic way to get throttled. $batch (20 sub-requests) helps with round trips but each sub-request still carries its own cost.

Business Scenarios

  • Financial models kept in Excel but driven by a service — write inputs, read outputs
  • Using Excel as a calculation engine for logic already encoded in formulas nobody wants to port
  • Automated report population into a formatted, branded workbook
  • Server-rendered chart images for email digests and PDFs
  • Bulk offline transformation of archived .xlsx / .docx via OOXML where no live service exists

OOXML for Offline Files

An Office file is a ZIP container of XML parts described by ECMA-376 / ISO 29500. Practical structure: [Content_Types].xml at the root, _rels/.rels and per-part _rels for relationships, then xl/workbook.xml + xl/worksheets/sheet1.xml + xl/sharedStrings.xml for a workbook, or word/document.xml for a document, or ppt/slides/slideN.xml for a deck.

  • Cell text is usually not in the sheet. Strings are pooled in sharedStrings.xml and the cell holds t="s" with an index. A parser that reads <v> literally reports integers where text should be.
  • Cached values are stale by construction. A formula cell stores <f> (the formula) and <v> (the last value Excel computed). Nothing recalculates on open unless the application does it — so OOXML parsing gives you the value as of the last save by a real Excel, which may be wrong or absent.
  • Dates are serial numbers against either the 1900 or the 1904 epoch, selected by workbookPr/@date1904. Guessing the epoch produces a four-year error.
  • Word runs split unpredictably. A single sentence is often several <w:r> runs because of spell-check state, revision marks, or formatting; naive text extraction must concatenate runs, and search-and-replace across run boundaries is genuinely hard.
  • Tracked changes and comments persist in the file. <w:ins>, <w:del>, and word/comments.xml retain content and author names that the rendered document does not show. Same theme as the API side: the file remembers more than the page displays.
  • .xls (BIFF) and .doc are not OOXML — they are legacy binary formats and need entirely different tooling.

Key Restrictions & Gotchas

Version history sits outside the Excel API but is richer than the current workbook. Prior versions are reachable through the driveItem's /versions collection with per-version author and timestamp, and SharePoint libraries version by default — so a workbook's earlier inputs, formulas, and results remain retrievable after being overwritten, for a window set by library policy rather than by the API. The Excel object model itself has no concept of history at all.
  • Not every Excel feature is exposed. Pivot table support is partial, Power Query / data model (Get & Transform) refresh is not exposed, and macros cannot be executed — a .xlsm is readable but its VBA is inert through the API.
  • Files above the service's workbook size limits are rejected. Very large workbooks fail to open in the Excel service even though the same file downloads fine as a driveItem. The failure is an open error, not a size warning.
  • formulas vs formulasLocal. formulasLocal uses the user's locale — localised function names and, critically, a semicolon argument separator in many locales. Writing formulasLocal built for one locale into another user's session produces parse errors.
  • Writing values over a formula destroys the formula. There is no "write value but keep formula" mode; choose the field you PATCH deliberately.
  • Chart images are rasterised server-side and reflect current data — but only after calculation has settled. Requesting an image immediately after a write can capture the pre-recalculation state; force application/calculate first.
  • Concurrent editing is a real hazard. A human editing the workbook in Excel Online while your persistent session writes can produce merge behaviour you did not design for. There is no optimistic-concurrency token on ranges.
  • Password-protected and IRM-protected files cannot be opened by either the workbook API or an OOXML parser — the ZIP itself is encrypted.
