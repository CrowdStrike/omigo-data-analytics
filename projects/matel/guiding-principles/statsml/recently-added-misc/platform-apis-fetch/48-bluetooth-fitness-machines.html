Bluetooth Fitness Machines BACKLOG

Reading speed, cadence, power and heart rate directly off exercise equipment over an open Bluetooth SIG GATT standard, with no vendor cloud in the path.

Last verified: August 2026

Overview

What It Provides

This page is different in kind from every other platform API in this collection. The Fitness Machine Service and its neighbours are open, published Bluetooth SIG specifications, not vendor products. Anyone can implement a client. There is no partner programme, no application review, no OAuth, no API key, no rate limit, no terms of service constraining what you may compute, and no vendor server anywhere in the data path. The bytes come off the machine over a local radio link into your process.

Open standard, but no persistence — the trade is total. Because there is no vendor cloud, there is also no cloud storage, no history endpoint, no user account, no cross-session identity, no backfill, and nothing at all unless you are physically within radio range with a connected client at the moment the exercise happens. Capture is entirely your responsibility. What you do not record is gone permanently, and no retrospective request can recover it. Compare a vendor cloud API, where you authorise once and can then pull months of history that accumulated without you.

What is available while connected: instantaneous and average speed, cadence and stride rate, power, resistance level, inclination, total distance, elapsed and remaining time, expended energy, heart rate, machine-declared capability bitfields, supported target ranges, and — for machines that permit it — control writes to set target resistance, power, speed or inclination, which is the mechanism behind ERG mode and simulated gradient.

Access Model

There is no authentication in the API sense. Pairing and bonding exist at the link layer, but the fitness services themselves are generally open to any connected client that discovers them. Access surfaces:

  • Native BLE stacks — Core Bluetooth on Apple platforms, BluetoothGatt on Android.
  • Web Bluetooth in Chromium-based browsers. It requires a user gesture, shows a device-chooser prompt as its consent model, requires a secure context, and requires the service UUID to appear either in the requestDevice filter or in optionalServices — a service you did not declare is invisible even after connecting. It is not available in all browsers; notably absent from Safari and Firefox.
One central at a time is a real operational constraint. For these profiles BLE typically permits a single central connection per peripheral. If the vendor's own app is connected to the trainer, your client cannot be — you are not rate-limited, you are excluded. Some devices additionally broadcast over ANT+, which does allow multiple simultaneous listeners; where available that is the standard workaround for concurrent capture, and it is worth checking for before designing around exclusive BLE access.
Key Characteristics

A peripheral exposes Services (16-bit UUIDs in the SIG-assigned range), each containing Characteristics. A client discovers them, then either reads a characteristic or subscribes to Notify/Indicate and receives a stream of small binary packets.

0x1826 Fitness Machine 0x1818 Cycling Power 0x1816 Cycling Speed and Cadence 0x180D Heart Rate 0x1814 Running Speed and Cadence 0x180F Battery 0x180A Device Information
  • 0x1826 Fitness Machine Service (FTMS) — Indoor Bike Data, Treadmill Data, Rower Data, Cross Trainer Data, Stair Climber Data, Fitness Machine Feature, Fitness Machine Control Point, Fitness Machine Status, Supported Resistance Level Range, Supported Power Range, Training Status. Read Fitness Machine Feature first: it declares which data fields and which control targets the machine actually supports, and everything else is conditional on it.
  • 0x1818 Cycling Power — Cycling Power Measurement, Cycling Power Feature, Sensor Location, Cycling Power Vector, Cycling Power Control Point.
  • 0x1816 Cycling Speed and Cadence (CSC) — CSC Measurement (cumulative wheel revolutions plus last wheel event time, cumulative crank revolutions plus last crank event time) and CSC Feature.
  • 0x180D Heart Rate — Heart Rate Measurement, carrying an Energy Expended field and an RR-Interval field when the flags say they are present, plus Body Sensor Location and Heart Rate Control Point.
  • 0x1814 Running Speed and Cadence, 0x180F Battery Service, 0x180A Device Information for completeness.
Flags-field parsing is the number-one implementation bug. Most of these characteristics begin with a flags bitfield that determines which optional fields are present — and therefore the byte offset of every field after it. The packet is variable-length and position-dependent on the flags; there is no fixed struct to cast onto. Two consequences. A parser with hardcoded offsets works perfectly against the one trainer it was written for and silently misreads a different model that sets a different flag combination. And the misread values are usually plausible-looking numbers rather than obvious garbage, because a uint16 read one byte off is still a uint16. Decode the flags first, walk the fields in spec order, and validate the total packet length against the length you computed from the flags.
Cumulative counters mean the client computes the metric, not the device. CSC and Cycling Power report cumulative revolution counts plus a 16-bit event-time value in units of 1/1024 second. Cadence and speed are never transmitted — the client derives them as a difference of counts over a difference of event times. Both fields wrap: the 16-bit event time rolls over roughly every 64 seconds, and the revolution counters roll over too, so correct decoding requires explicit wrap-around handling. Two consequences worth stating precisely. First, two apps reading the same sensor can legitimately report different cadence, because they use different smoothing windows, different zero-cadence timeouts, and different wrap and dropout handling — the "measurement" is partly the client's arithmetic and the client is part of the instrument. Second, a dropped notification silently changes the denominator, so packet loss produces a wrong-but-plausible rate rather than a visible gap. Missing data here does not look like missing data.
Power is a derived quantity on most hardware, and three different instruments publish through one characteristic. A direct-force power meter measures strain and angular velocity and computes watts from physics. A smart trainer commonly estimates power from a speed-and-resistance model. Some devices report "virtual" power from a published speed-to-power curve for a specific wheel-on trainer at a specific setting. All three transmit through the same Cycling Power Measurement characteristic, under the same field name, in the same unit. A power column pooled across those three sources is three instruments in one variable, and pooling them without a source indicator is unjustified. The practical asymmetry compounds it: direct-force meters are calibratable and support a zero offset via the Cycling Power Control Point; estimate-based sources are not, and trainer power drifts with drivetrain wear, tyre pressure and roller tension. So the bias is not only different across sources — it is stationary in one and drifting in the others.
Throughput & Connection Limits

There is no rate limit because there is no server. The analogous constraint is the link layer, and it works in the opposite direction: the device, not the client, decides how often data arrives.

  • Notification rate is governed by the connection interval negotiated at the link layer, typically landing somewhere around 1–4 Hz per characteristic. This is device-dependent and not a spec-guaranteed rate — do not build a fixed-cadence assumption on it, and measure the actual arrival rate per device rather than assuming one.
  • ATT MTU limits keep packets small, which is why the optional-field-plus-flags encoding exists at all.
  • Notify is unacknowledged: packets can be lost with no retransmission and no indication that anything was lost. Indicate is acknowledged but slower, so the high-rate data characteristics use Notify.
  • You cannot request a higher sampling rate. Polling a characteristic with reads does not increase the underlying update rate; it just re-reads the same last value.
There are no timestamps. Most of these characteristics carry no absolute time at all — your client's receive clock is the timestamp. That makes clock skew, OS scheduling delay, BLE stack buffering and application-layer queueing yours to manage, and it means the inter-sample intervals you record are arrival intervals rather than measurement intervals. If your capture process is briefly starved, several notifications arrive in a burst carrying timestamps that are all wrong in the same direction. Record a monotonic receive time alongside wall-clock time, and treat the sequence order as more trustworthy than the intervals.
Business Scenarios
  • Indoor training platforms and virtual racing — the reason FTMS control writes exist.
  • Gym equipment telemetry and fleet utilisation, where a local gateway per machine captures sessions that no vendor cloud would expose.
  • Physiotherapy and rehabilitation session capture, where the exercise happens on commodity equipment and the clinic needs the raw series.
  • Research-grade capture without vendor dependency. This is a genuine methodological advantage: an open, published standard is auditable and reproducible in a way a proprietary cloud API with an undisclosed post-processing pipeline is not. You can state exactly what the bytes meant and exactly what arithmetic you applied.
Key Restrictions & Gotchas
  • No history. Live notifications only, while connected.
  • No user identity, no account, no cross-session continuity. The peripheral does not know who is exercising, and a session is anonymous unless your client attaches identity itself.
  • No cloud storage and no recovery of an uncaptured session.
  • No timestamps in most characteristics.
  • No guarantee a vendor implements the optional fields, or the standard service at all. Many trainers historically exposed proprietary services and required a vendor-specific protocol, and a device can advertise FTMS while implementing only a subset of it. Read Fitness Machine Feature rather than assuming.
  • Field resolution is encoded, not implicit — cadence in half-rpm units, speed in hundredths of km/h. Forgetting the divisor gives you a plausible number in the wrong unit.

A frame with speed, instantaneous cadence, instantaneous power, heart rate and elapsed time present — and nothing else:

raw (11 bytes):  44 0A A8 0C B0 00 D6 00 8E F4 04

flags  = 0x0A44
         bit 0  clear  -> Instantaneous Speed IS present
         bit 2  set    -> Instantaneous Cadence present
         bit 6  set    -> Instantaneous Power present
         bit 9  set    -> Heart Rate present
         bit 11 set    -> Elapsed Time present
         all other bits clear -> those fields absent,
         so no bytes are reserved for them

offset 2-3   A8 0C  -> 0x0CA8 = 3240   / 100 = 32.40 km/h
offset 4-5   B0 00  -> 0x00B0 =  176   /   2 = 88 rpm
offset 6-7   D6 00  -> 0x00D6 =  214          = 214 W
offset 8     8E     -> 142                    = 142 bpm
offset 9-10  F4 04  -> 0x04F4 = 1268          = 1268 s

decoded = {
  speed_kph:      32.40,
  cadence_rpm:    88,
  power_watts:    214,
  heart_rate_bpm: 142,
  elapsed_time_s: 1268
}

Change one flag and every offset after it moves. Set Average Speed as well and cadence shifts from offset 4 to offset 6; a parser holding offset 4 then reads the low half of the average-speed field and reports a cadence that is wrong but entirely believable. Note also that power_watts here is whatever the machine chose to publish — a strain measurement on some hardware, a resistance-model estimate on others, indistinguishable in this frame.

Four "power" series, one minute of riding — arrival times of the same underlying effort as seen through four different surfaces. All four are labelled power. Only the top two exist without a vendor in the path, and only the top two exist at all if nobody captured the session live.
