Google Workspace Admin Backlog

Admin SDK — Reports API activity streams per application, usage reports for customer/user/entity, Directory API objects and devices, and Alert Center notifications.

Last verified: August 2026

Overview

What It Provides

The Admin SDK is split into three genuinely different things that are easy to conflate:

  • Reports API — Activities. An event stream, but partitioned by applicationName rather than served as one unified log. You request login, admin, drive, token, meet, groups, calendar, mobile, user_accounts, saml, chat and others as separate calls. There is no single "give me everything" endpoint, so a collector's completeness is defined by the list of applications it happens to iterate — omit one and you will never know it was missing.
  • Reports API — Usage reports. Pre-aggregated daily counters at three levels: customerUsageReports (whole tenant), userUsageReport (per user), entityUsageReport (per object, in practice Drive documents and shared drives). These are daily rollups, not events, and are published on a lag.
  • Directory API. Current state: users, groups and members, orgunits, roles and role assignments, mobiledevices, chromeosdevices. No history — a read tells you today's org unit, not last quarter's.
  • Alert Center API. Security and policy alerts Google itself raised (suspicious login, government-backed attack warning, data-loss-prevention rule match, device compromise), each with a typed payload and an optional feedback record.
These APIs contain no user content. A Drive activity says a document with a given id and title was shared with an external address; it does not contain the document. Reading content requires the separate Drive/Gmail APIs with their own, far broader consent — a distinction that matters both for privacy review and for how large the extract is.
Authentication & Scopes
  • A service account with domain-wide delegation, impersonating a super admin, is the standard pattern for tenant-wide collection. The delegation is authorised in the Admin console by client id plus explicit scope list.
  • https://www.googleapis.com/auth/admin.reports.audit.readonly — activities.
  • https://www.googleapis.com/auth/admin.reports.usage.readonly — usage reports.
  • .../auth/admin.directory.user.readonly, .../admin.directory.group.readonly, .../admin.directory.orgunit.readonly, .../admin.directory.device.chromeos.readonly, .../admin.directory.device.mobile.readonly.
  • https://www.googleapis.com/auth/apps.alerts — Alert Center.
  • Delegated scopes are all-or-nothing per scope string: there is no way to grant reports access for one org unit only.
Granularity

An activity record wraps an actor, an id block (containing time, uniqueQualifier, applicationName, customerId), and an events array — so one HTTP record can contain multiple logical events, each with its own name and a parameters list of loosely-typed name/value pairs. Flattening blindly to one row per record loses events; flattening to one row per event is usually what you want.

Key Endpoints
  • GET /admin/reports/v1/activity/users/{userKey|all}/applications/{applicationName} — startTime, endTime, eventName, filters, actorIpAddress, maxResults, pageToken.
  • GET /admin/reports/v1/usage/dates/{date} — customer usage.
  • GET /admin/reports/v1/usage/users/{userKey|all}/dates/{date} — per-user usage.
  • GET /admin/reports/v1/usage/{entityType}/{entityKey|all}/dates/{date} — entity usage.
  • GET /admin/directory/v1/users, /groups, /customer/{id}/orgunits, /customer/{id}/devices/chromeos, /customer/{id}/devices/mobile.
  • POST /v1beta1/alerts/{-}:list — Alert Center, filtered by createTime and alert type.
  • Activities also support push notifications via a watch channel, which avoids polling but still inherits the same ingestion lag.
Rate Limits
  • Per-project quotas expressed as queries per second and per day, visible and adjustable in the Google Cloud console for the project holding the credentials. The number depends on the project, so read it there rather than assuming a documented default.
  • 403 with reason rateLimitExceeded / userRateLimitExceeded, or 429. Exponential backoff with jitter is the documented remedy.
  • Because activities are fetched per application, a tenant-wide backfill multiplies the request count by the number of applications you care about — the quota constraint is on total pages, not on days.
  • maxResults is capped well below a busy tenant's daily Drive volume; expect long pageToken chains for drive and token in particular.
Business Scenarios
  • External sharing exposure — Drive activity events for link-visibility changes and external ACL grants, joined to org unit, answer "which teams leak documents outside the domain."
  • Third-party OAuth app risk — the token application records which users authorised which client id against which scopes. This is the only practical way to inventory shadow SaaS attached to corporate identity.
  • Admin change review — the admin application is the tenant's configuration audit trail: setting changes, role grants, delegation, retention rule edits.
  • Licence and adoption measurement — usage reports give per-user daily activity counters without touching content, which makes them the defensible basis for reclaiming seats.
  • Meeting-load analysis — meet activity gives per-participant join/leave with duration and network quality, enough to quantify meeting hours per team.
  • Device fleet posture — ChromeOS and mobile device records for OS version, enrolment state, and last sync.
Key Restrictions & Gotchas
  • Activity retention varies by application and is not uniform. Some streams are retained for around six months, others materially less. Do not assume one number covers every applicationName; check the per-application data-retention table for the streams you depend on, and archive anything you need beyond that window.
  • Some streams are edition-gated. Certain audit and investigation capabilities — and the deeper security-centre reporting — are only available on higher Workspace editions. On a lower edition the API answers successfully with fewer or no events, which is indistinguishable from an uneventful day.
  • Ingestion lag is significant and differs per application. Some activity types appear within minutes; others are documented as taking hours. Usage reports are daily and are typically not final until a day or two after the date they describe. A dashboard querying "today" will look like a collapse in activity that recovers by itself — a pure artefact.
  • Usage report data can be revised. Re-fetching an older date may return different numbers than the first fetch. If you snapshot once and never re-fetch, your history is subtly wrong; if you always re-fetch, your totals are not stable. Pick deliberately and record which you did.
  • parameters is loosely typed and application-specific. The same conceptual field is named differently across applications, values arrive as value, boolValue, intValue or multiValue, and parameters can be added or dropped. Store the raw array alongside any parsed columns.
  • Deduplicate on id.uniqueQualifier plus id.time. Overlapping windows are necessary given the lag, so records will be re-delivered.
  • Directory reads reflect the present only. A user moved between org units, renamed, or deleted breaks joins from historical activity, and no API will reconstruct the old value.
  • Alert Center is a separate API with its own retention and its own scope; alerts are not duplicated into the activities stream.
An event not captured while it was still inside the retention window is unrecoverable — an audit log cannot be backfilled. Google Workspace adds a specific trap on top of that: because activities are fetched per application, the gap is usually not "we lost a week" but "we never collected the token stream at all," and nothing in the API surface will tell you. The completeness of the dataset is a property of your collector's configuration, not of the platform.
