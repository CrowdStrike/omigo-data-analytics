Asana & monday.com APIs Backlog

Tasks, projects, boards and custom fields from two work-management platforms — one REST with field masks, one GraphQL with a complexity budget.

Last verified: August 2026

Overview

What It Provides

Both platforms model the same domain — a container of work items with user-defined columns — but expose it through opposite API styles.

  • Asana — REST at https://app.asana.com/api/1.0/. Resources: workspaces, teams, projects, sections, tasks, subtasks, stories (the activity feed), custom fields, tags, portfolios, goals, attachments, time-tracking entries. Every object has a gid string id and a resource_type.
  • monday.com — GraphQL only, single endpoint https://api.monday.com/v2. Objects: boards, groups, items, subitems, column_values, updates, users, teams, workspaces, activity logs.

In both, the interesting business data is not in the built-in fields — it is in the customer-defined columns, which are typed, per-container, and renameable.

Authentication & Scopes
  • Asana: Personal Access Token as Authorization: Bearer, or OAuth 2.0 for multi-tenant apps. Asana's OAuth historically granted broad access on behalf of the user; a finer-grained scope model is available on newer apps, so check what your app registration actually requested rather than assuming.
  • monday.com: a personal API token, or OAuth for marketplace apps, sent in the Authorization header. Scopes are explicit and coarse-grained per object family.
asana: default (full user access) asana: openid / email / profile monday: boards:read monday: boards:write monday: users:read monday: workspaces:read monday: updates:read monday: account:read monday: webhooks:write
Granularity
  • Asana task — one record with created_at, modified_at, completed_at, due_on, assignee, memberships (project + section), and custom_fields as an array of typed field objects carrying both the definition and the value.
  • Asana story — one record per comment or system event on a task ("changed the assignee to …"). This is the closest thing to a per-task history.
  • monday item — one record whose column_values is an array of { id, type, text, value }, where value is a JSON string that must be parsed again, and text is a display rendering.
  • monday activity log — per-board event stream with the changed column, before/after payload, user and timestamp.
Key Endpoints
  • Asana: GET /tasks (requires project, section, tag, or assignee+workspace), GET /tasks/{task_gid}, GET /tasks/{task_gid}/stories, GET /tasks/{task_gid}/subtasks.
  • Asana: POST /workspaces/{workspace_gid}/tasks/search — the only server-side filtered search; results are not guaranteed complete for very large result sets and cannot be sorted arbitrarily.
  • Asana: GET /projects/{project_gid}/custom_field_settings — the column definitions for a project.
  • Asana: GET /events?resource={gid}&sync={token} — a sync-token change stream. The token expires if not polled often enough, and recovery means a full re-read.
  • Asana: GET /workspaces/{gid}/audit_log_events — admin/security events, available on higher enterprise tiers only.
  • monday: query { boards(ids: [...]) { items_page(limit: 100, cursor: $c) { cursor items { id name column_values { id type text value } } } } }.
  • monday: items_page_by_column_values for filtered reads; activity_logs(from:, to:) for board history; next_items_page(cursor:) to continue.
Rate Limits
  • Asana — per-token limits on requests per minute, with a separate and much tighter budget for search and for write-heavy operations. Cost is also shaped by response size, so wide opt_fields requests count for more. Honour Retry-After on 429.
  • monday.com — two independent budgets: a complexity budget consumed by the estimated cost of each GraphQL query, and a conventional per-minute request cap. Complexity is charged whether or not the query returns rows, so a badly shaped query with an empty result still spends budget.
  • monday returns remaining complexity inside the response when you ask for it (complexity { before after query reset_in_x_seconds }) — instrument this rather than guessing.
  • Published numbers differ by plan and have changed more than once. Read the limit from headers or the complexity block instead of hard-coding.
Business Scenarios
  • Cross-tool portfolio roll-up — normalising tasks from both platforms into one status vocabulary.
  • Throughput and ageing — completions per period, and open-item age distribution.
  • Intake analytics — request forms feed items whose custom fields encode request type, priority and requesting team.
  • Workload balance — assignee counts weighted by a custom effort column.
  • Process compliance — items that skipped a required status, detectable only from the activity log / stories feed.
Restrictions & Gotchas
  • Asana returns a minimal representation by default. Omit opt_fields and you get little more than gid, name and resource_type — silently, with no hint that the field you wanted exists. Many "the API doesn't expose that" reports are missing field masks.
  • Asana tasks cannot be listed workspace-wide. GET /tasks demands a narrowing parameter, so a full extract means iterating projects — and a task in several projects will be fetched several times, while a task in none is unreachable that way.
  • monday's column_values.value is JSON-in-a-string whose inner shape depends on the column type. text is a locale- and format-dependent rendering, not a parseable value. Type on type, parse value, and never sum text.
  • Column and field identity is unstable across containers. The same business concept ("Priority") is a different column id on every board and a different custom-field gid in every project, and either can be renamed while keeping its id. Build an explicit mapping table; do not join on display names.
  • History coverage is asymmetric and bounded. monday's activity_logs serves a rolling window whose length depends on plan; Asana's stories feed is per-task and mixes human comments with system events, and Asana's audit log is gated to top enterprise tiers. Neither gives a cheap account-wide "everything that changed yesterday".
  • GraphQL nesting multiplies cost, not convenience. Fetching boards → items → column_values → updates in one query is elegant and will exhaust the complexity budget. Flatten into several cheaper queries.
  • Deleted and archived objects vanish from normal reads. Archived monday boards and deleted Asana tasks disappear, so a recomputed historical total can shrink between runs. Snapshot, or accept drift.
  • Status columns are free text underneath. Anyone can add a label, so a status taxonomy learned from last quarter's data will encounter unseen categories.
These feeds record declared state, not performed work. A task moved to Done means somebody clicked Done — the timing reflects when they got round to updating the board, which is often batched at the end of a day or a sprint. Duration metrics built on these timestamps measure bookkeeping latency plus real work, mixed together and not separable.
