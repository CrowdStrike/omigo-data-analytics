MDM / Device Management BACKLOG

Apple MDM and Declarative Device Management, Android Management API, Intune via Graph, Jamf Pro. Visibility is a function of who owns the hardware.

Last verified: August 2026

Overview

What It Provides

MDM is the one route to device-level inventory that the consumer APIs deliberately withhold — installed application lists, hardware identifiers, OS build, compliance state, and on supervised Apple hardware, location while in Lost Mode. It is also the route with the strongest consent and governance requirements, because the enrolment act is the consent.

  • Apple MDM protocol — the server sends commands over APNs-triggered check-ins; the device polls and replies with plist payloads. Inventory commands include DeviceInformation, InstalledApplicationList, ProfileList, CertificateList, SecurityInfo, ProvisioningProfileList, RestrictionsList, OSUpdateStatus. Action commands include InstallApplication, InstallProfile, EraseDevice, DeviceLock, EnableLostMode, DeviceLocation.
  • Declarative Device Management (DDM) — the newer model. Instead of the server polling, the device holds declarations (configurations, assets, activations, management) and proactively pushes status items and status subscriptions when things change. Reduces round-trips and closes the drift window between what the server believes and what is true.
  • Android Management API — enterprises.devices (hardware info, software info, memory, applicationReports, policyCompliance, nonComplianceDetails), enterprises.policies, enterprises.enrollmentTokens, enterprises.webApps; Pub/Sub notifications for enrolment, status report and command events.
  • Microsoft Intune via Graph — deviceManagement/managedDevices, managedDevices/{id}/detectedApps, detectedApps/{id}/managedDevices, deviceCompliancePolicyStates, deviceHealthScripts, plus device and app-protection (MAM) configuration.
  • Jamf Pro API — classic and modern (v1/v2) endpoints for computer and mobile-device inventory, extension attributes, smart groups, policies. Extension attributes are the escape hatch for anything the inventory schema does not model.
Authentication & Scopes
  • Apple MDM: APNs certificate obtained through the Apple Push Certificates Portal (annual renewal — a lapsed cert silently kills all management); SCEP/ACME device identity certificates; enrolment via Automated Device Enrolment (ABM/ASM) for corporate hardware or user-initiated / account-driven enrolment for BYOD.
  • Android Management API: Google Cloud service account + an enterprise binding created through the signup flow; policies applied by name; scope https://www.googleapis.com/auth/androidmanagement.
  • Intune: Entra ID app registration, DeviceManagementManagedDevices.Read.All and related Graph permissions, admin consent required. detectedApps requires the device-inventory permissions specifically.
  • Jamf Pro: bearer token from /api/v1/auth/token (or an API client with role-scoped privileges); privileges are granular per object type.

Granularity — aggregate vs event-level

This is the one section in the group where device-level, identified data is the norm rather than the exception. You get a row per device with a durable identifier, and you can join it to a directory user. But:

  • Inventory is a snapshot, not a stream. DeviceInformation and applicationReports reflect the last successful check-in. Between check-ins you hold stale state and cannot tell staleness from stability unless you record the check-in timestamp alongside every field. Always persist lastSyncTime / lastStatusReportTime with the payload.
  • Event-level exists only where the platform emits it — Android Management Pub/Sub notifications, DDM status subscriptions, Intune audit logs. Classic Apple MDM has no change feed; you poll or you re-query on push wake.
  • Installed-app inventory is not usage. Every one of these APIs tells you an app is present, its version, and sometimes its install source. None of them tells you how long it was used. That is the Screen Time / UsageStatsManager problem again, and MDM does not solve it either — with the narrow exception of device-owner Android deployments where a managed app can hold usage-access permission granted by policy.
Ownership model is the real access-control axis. Supervised or corporate-owned devices expose far more: full installed-app list including personal apps, hardware serials and IMEI, activation lock bypass, Lost Mode with location, non-removable management. BYOD is deliberately narrowed — an Android work profile reports only work-profile apps, iOS user-enrolment issues a per-enrolment identifier rather than a hardware UDID and blocks device-wide inventory and erase, and Intune app-protection policies manage the app without managing the device at all. The same MDM product yields a structurally different dataset on the two populations.
Key Endpoints / Commands
  • Apple: DeviceInformation (with a Queries array), InstalledApplicationList, SecurityInfo, EnableLostMode → DeviceLocation
  • DDM: declaration/configuration/..., StatusSubscriptions, tokens, declaration-items
  • Android: GET enterprises/{e}/devices/{d}, PATCH .../devices/{d} (state), POST .../devices/{d}:issueCommand, PATCH enterprises/{e}/policies/{p}
  • Intune: GET /deviceManagement/managedDevices, GET /deviceManagement/managedDevices/{id}/detectedApps, GET /deviceManagement/detectedApps/{id}/managedDevices
  • Jamf: GET /api/v1/computers-inventory?section=APPLICATIONS, GET /api/v2/mobile-devices/{id}/detail
Rate Limits

Qualitatively different from web APIs, and worth stating plainly rather than numerically:

  • Apple MDM has no request quota because you do not poll the device — you send an APNs wake and the device checks in when it can. Throughput is bounded by APNs delivery, device connectivity, and per-device command queue depth. A locked, offline or low-battery device simply does not answer, indefinitely.
  • Google APIs apply per-project per-minute quotas visible in the Cloud console; batch and back off.
  • Microsoft Graph throttles per-app per-tenant and returns 429 with Retry-After; honour the header rather than guessing an interval. Use delta queries where available instead of full re-enumeration.
  • Jamf Pro quotas are deployment-dependent (self-hosted vs cloud); inventory endpoints are expensive and paged.
Business Scenarios
  • Software asset inventory, license true-up, and unauthorized-app detection
  • Patch and OS-version compliance reporting, CVE exposure by build
  • Zero-touch provisioning and app deployment at scale
  • Lost/stolen device response: lock, locate, wipe corporate data
  • Conditional access — device posture gating resource access
Key Restrictions & Gotchas — what it does NOT give you
  • No app usage duration on iOS at all, and on Android only via a policy-granted usage-access permission in a fully managed deployment. MDM inventory answers "installed?", never "used how much?".
  • No continuous location. Apple exposes DeviceLocation in the Lost Mode flow on supervised devices, not as an ambient tracking feed. Android location reporting depends on management mode and policy, and is visible to the user.
  • No message, browsing or keystroke content. MDM configures; it does not intercept. Anything resembling content capture is a separate agent with separate consent, and in many jurisdictions separate legality.
  • Removability. BYOD enrolments can be removed by the user, and removal is a censoring event in your panel: the device stops reporting for reasons that correlate with what it was about to report.
  • Personal-app invisibility on work profiles is not a bug to engineer around. It is the contract that makes BYOD enrolment acceptable.
  • Certificate and token expiry — APNs MDM cert, ABM/ASM server tokens, VPP content tokens — each silently degrades management on lapse and shows up in data as a cohort going quiet.
Methodological consequence. An MDM-derived fleet dataset is not a random sample of devices, and the missingness is doubly structured: which fields you see depends on ownership model, and which devices report at all depends on connectivity and continued enrolment. Pooling supervised and BYOD devices into one "installed apps per device" statistic compares a full inventory against a work-profile-only inventory and will show corporate-owned devices carrying more apps — an artefact of the reporting contract, not of user behaviour. Stratify by ownership model before computing anything, and carry last_check_in into every analysis so that "no change" and "no contact" stay distinguishable. Devices that stop checking in are censored, not compliant.
