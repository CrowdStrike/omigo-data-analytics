Shopify BACKLOG

Orders and line items, customers, abandoned checkouts, fulfillments, refunds, products and variants with inventory — under a cost-based GraphQL leaky bucket, with bulk operations for anything large.

Last verified: August 2026

Overview

What It Provides
  • Orders — header with financial and fulfillment status, plus lineItems carrying product/variant references, quantity, price, discount allocations, and tax lines. Also shippingLines, transactions, and note attributes.
  • Customers — contact detail, addresses, marketing consent state, order count, total spent, and tags.
  • Abandoned checkouts — carts that reached checkout and did not convert, with line items and, where captured, an email.
  • Fulfillments & fulfillment orders — what shipped, from which location, with tracking. The modern model splits an order into fulfillment orders per location.
  • Refunds & returns — refund line items, restocking behaviour, and the transactions that moved money back.
  • Products, variants, inventory — variant-level pricing and inventoryLevels per location.
  • Webhooks for order, fulfillment, refund, product, and inventory events; shop/redact and customers/redact for mandatory GDPR handling.
Authentication & Scopes
  • Admin API access token in the X-Shopify-Access-Token header. Custom apps get a token directly; public apps go through OAuth per shop.
  • Granular scopes — read_orders, read_all_orders, read_customers, read_products, read_inventory, read_fulfillments, and so on.
  • read_all_orders is separately gated. With only read_orders, the Admin API returns orders from roughly the last 60 days. Older orders are simply absent — not an error, just missing rows. This is the most commonly misdiagnosed gap in Shopify extraction.
  • Protected customer data requires explicit approval for apps handling PII fields; without it, fields like email and address are redacted from responses.
  • Per-shop tokens. One token, one shop. There is no cross-shop query for a multi-store merchant.
A historical order backfill that "works" but returns nothing before 60 days ago is almost always a missing read_all_orders grant, not a pagination bug. The API does not tell you rows were withheld.
Granularity

Order and line item, timestamped to the second with timezone. Money fields use MoneyBag in GraphQL, giving both shopMoney and presentmentMoney — the shop's currency and the currency the buyer saw. Mixing them across a multi-currency store produces totals that reconcile to nothing.

API Surfaces
  • GraphQL Admin API — the primary and actively developed surface. Versioned quarterly (/admin/api/2026-07/graphql.json); each version is supported for about a year.
  • REST Admin API — legacy. Shopify has been moving new capability to GraphQL only, and some newer objects have no REST equivalent.
  • Bulk Operations — asynchronous GraphQL queries whose results land as a JSONL file. This is the correct tool for full extracts.
Rate Limits — the Leaky Bucket

GraphQL Admin uses a cost-based leaky bucket rather than a request count:

  • Each query is assigned a calculated cost before execution, driven by the number of fields and the connection page sizes you requested.
  • The cost is deducted from a per-shop bucket. The bucket refills at a constant leak rate, and its capacity and leak rate scale with the shop's plan tier (Plus and Enterprise get materially more).
  • Every response carries extensions.cost, including requestedQueryCost, actualQueryCost, and throttleStatus with currentlyAvailable, maximumAvailable, and restoreRate.
  • If requestedQueryCost exceeds the bucket's maximum capacity, the query is rejected outright and no amount of waiting helps — you must reduce page size or field depth.
  • actualQueryCost is usually lower than requested, because Shopify refunds the difference when a connection returns fewer nodes than the first: argument allowed for.
This changes the shape of a correct client. Instead of counting requests, read throttleStatus.currentlyAvailable from every response and pace the next request against restoreRate. Requesting first: 250 everywhere maximises requested cost and therefore throttling — a smaller page size often yields higher sustained throughput because the bucket stays out of the floor.

REST Admin uses a simpler request-count bucket per shop, also scaling with plan, and returns the X-Shopify-Shop-Api-Call-Limit header. The two surfaces have independent budgets.

Bulk Operations

Submit a query via bulkOperationRunQuery, poll the returned operation (or wait for the bulk_operations/finish webhook), then download a JSONL file from the signed URL. Constraints worth knowing:

  • One bulk operation at a time per shop. A second submission fails while one is running.
  • The JSONL is flattened, not nested. Parent and child objects appear as separate lines, with children carrying a __parentId. You reassemble the hierarchy yourself, and children are not guaranteed to appear adjacent to their parent — you cannot stream-parse assuming locality without buffering.
  • The download URL expires. Fetch it promptly.
  • Bulk operations bypass the leaky bucket, which is the whole reason to use them for backfill.
Business Scenarios
  • Cohort and LTV analysis — first-order date by customer, repeat purchase intervals.
  • Cart abandonment funnels — abandoned checkouts joined against subsequent orders.
  • Inventory and demand planning — variant-level sell-through against inventory levels per location.
  • Discount and promotion effectiveness — discountAllocations at the line level, which is the only place per-item discount attribution exists.
  • Return-rate analysis by product and variant.
  • Multi-channel attribution — order sourceName and customerJourneySummary where available.
Key Restrictions & Gotchas
  • Orders are mutable after creation. Refunds, edits, and cancellations rewrite totals. An order pulled at creation and the same order pulled a month later are different rows. Re-sync on updated_at, not just created_at.
  • Financial status is current state, not history. displayFinancialStatus tells you the order is PARTIALLY_REFUNDED now. It does not tell you when it was paid, when the refund happened, or in what order. The transactions array is closer to a history and should be the basis for any revenue timeline — the status field is a summary.
  • Test orders exist. The test flag marks orders created by payment-gateway test mode. Filter them or your revenue is wrong.
  • Abandoned checkout is not a full funnel. Shopify records checkouts that reached the checkout step, not add-to-cart, and not sessions. It cannot answer "what fraction of visitors added to cart" — that is storefront analytics, a different data source entirely.
  • Deleted orders are gone. There is no tombstone endpoint listing deleted order IDs. If you do not capture the orders/delete webhook, your warehouse keeps rows Shopify no longer has.
  • No historical inventory series. inventoryLevel.quantities is the level now. Stockout history must be sampled going forward; it cannot be reconstructed.
  • Deprecation is on a clock. Quarterly API versions with roughly a year of support means an unmaintained integration breaks on a known schedule. Shopify's ongoing REST-to-GraphQL migration has already removed some REST capability.
  • GIDs, not integers. GraphQL identifiers are gid://shopify/Order/5502.... They do not equal REST numeric IDs textually, so a warehouse fed from both surfaces will fail to join without normalisation.
  • Webhooks are at-least-once and can be missed. A reconciliation sweep on updated_at is not optional; webhook delivery alone will drift.
