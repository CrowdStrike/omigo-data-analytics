Google Docs & Sheets BACKLOG

Structural document content, suggestions, cell values versus formulas, named ranges, and atomic batchUpdate

Last verified: August 2026

Overview

What It Provides

Two separate APIs over two separate content models, both keyed by the same Drive file id.

Docs API (v1) exposes a document as an ordered structural tree: body.content is a list of structuralElements (paragraph, table, tableOfContents, sectionBreak), and a paragraph is a list of paragraphElements — most commonly textRun, plus inlineObjectElement, footnoteReference, pageBreak, and person. Every element carries startIndex/endIndex in a single UTF-16 index space, and edits are expressed as index-based mutations. Suggestions (tracked changes) are surfaced as suggestedInsertionIds, suggestedDeletionRanges, and per-property suggestion maps.

Sheets API (v4) exposes a spreadsheet as sheets → grids → rows → cells. Each cell has an effectiveValue (the computed result), a userEnteredValue (what was typed, including the formula), a formattedValue (the display string), and layered formatting. Also: named ranges, conditional formats, data validation, charts, filters, protected ranges, and developer metadata.

The Docs API has no "get me the plain text" call. There is no text field on the document. Extracting readable prose means walking body.content, descending into paragraphs, tables, and footnotes, and concatenating textRun.content yourself. Naive walkers routinely drop table cell text, footnotes, and headers.

Authentication & Scopes

  • OAuth 2.0 user tokens, or service accounts with domain-wide delegation for Workspace tenants.
  • Docs: documents, documents.readonly.
  • Sheets: spreadsheets, spreadsheets.readonly.
  • Also usable: drive.file — restricted to files the app created or the user picked, and the least-privilege choice. Broad drive scope triggers Google's restricted-scope verification and (for public apps) annual security assessment.
  • A service account with no delegation can only touch files explicitly shared with its own address — the same trap as any service-identity model.

Granularity

Docs reads are whole-document — you cannot request a page or a range. Writes are surgical via documents.batchUpdate with a request list (insertText, deleteContentRange, updateTextStyle, replaceAllText, insertTableRow, …), applied atomically in order.

Sheets reads come in two flavours: values.get / values.batchGet (A1 or R1C1 ranges, flat arrays, cheap) and spreadsheets.get with includeGridData=true and a fields mask (full cell objects, expensive). Writes are values.update, values.append, or the full spreadsheets.batchUpdate for structural change.

Key Endpoints

  • GET /v1/documents/{documentId} — optional suggestionsViewMode
  • POST /v1/documents/{documentId}:batchUpdate
  • GET /v4/spreadsheets/{id}/values/{range} — valueRenderOption, dateTimeRenderOption
  • GET /v4/spreadsheets/{id}/values:batchGet?ranges=…
  • PUT /v4/spreadsheets/{id}/values/{range}?valueInputOption=USER_ENTERED|RAW
  • POST /v4/spreadsheets/{id}/values/{range}:append
  • POST /v4/spreadsheets/{id}:batchUpdate — addNamedRange, updateCells, addChart, …
  • GET /v4/spreadsheets/{id}?fields=namedRanges,sheets.properties

Rate Limits

  • Sheets API: the published per-project and per-user-per-project read and write quotas are separate counters, measured per 60 seconds, and refill continuously. Read and write quotas do not share a pool — a heavy writer does not starve reads.
  • Docs API: per-project and per-user write quotas are considerably tighter than read quotas. Rewriting a large document one insertText at a time will exhaust write quota long before it finishes.
  • Both return HTTP 429 with RESOURCE_EXHAUSTED. Google's documented guidance is exponential backoff with jitter; there is no Retry-After to lean on, so the client owns the schedule.
  • Batching is the real remedy. One batchUpdate with 200 requests costs one quota unit; 200 individual calls cost 200. This is the single highest-leverage optimisation in both APIs.

Business Scenarios

  • Templated document generation — merge fields via replaceAllText
  • Contract and policy redlining pipelines that read and resolve suggestions
  • Sheets as a lightweight operational database or config store
  • Reporting write-back: pipeline output rendered into a shared workbook
  • Formula auditing and spreadsheet-risk analysis via userEnteredValue

Key Restrictions & Gotchas

Neither API exposes revision history or per-edit attribution. Google Docs' named-versions and "see edit history" UI has no public API counterpart: drive.revisions.list for a Workspace file returns revision records but not the editable diff or per-character authorship, and the granular edit chain the UI shows is not retrievable. Suggestions are the one exception — an unresolved suggestion carries a suggestionId and, via Drive, an author — which means the document object can contain proposed text that no reader ever sees, plus deletion ranges marking text the author believes is gone. A DLP scan that reads suggestionsViewMode=PREVIEW_WITHOUT_SUGGESTIONS will miss content that is genuinely present in the file.
  • Index invalidation. Docs indices shift after every insertion or deletion. Within a single batchUpdate the requests are applied in order, so later requests must account for earlier ones — the usual fix is to apply edits in descending index order.
  • Indices are UTF-16 code units. Emoji and other astral-plane characters occupy two units. Byte or code-point arithmetic corrupts ranges.
  • values.get hides formulas by default. The default valueRenderOption=FORMATTED_VALUE returns display strings; use UNFORMATTED_VALUE for typed values and FORMULA to see the formula text. Locale affects FORMATTED_VALUE, so the same sheet returns different strings for different users.
  • values.get trims trailing empty cells and rows. A request for A1:Z1000 returns a ragged array with short rows and possibly fewer rows than asked. Code that assumes a rectangular result throws on the first sparse sheet.
  • Dates are serial numbers. With dateTimeRenderOption=SERIAL_NUMBER you get a Lotus-1-2-3-epoch float (day 0 = 1899-12-30), not an ISO string.
  • valueInputOption changes semantics, not just parsing. USER_ENTERED lets the string =SUM(A1:A9) become a live formula and 01/02 become a date; RAW stores both literally. Injecting user-supplied text with USER_ENTERED is a formula-injection vector.
  • Named ranges are not stable references in the values API. values.get accepts a named range, but a named range whose underlying grid was deleted resolves to an error rather than an empty set. There is also no API to list "which formulas reference this named range".
  • Sheets has hard structural ceilings — a workbook is capped at 10 million cells and 18,278 columns per sheet, which the API enforces at write time rather than warning about in advance.
  • append appends after the last row of a detected table, not after the last row of the sheet. A stray value far below the data block silently changes where appends land.
  • Apps Script custom functions do not evaluate for API reads. A cell whose value depends on a custom function may return a cached value, an error, or nothing.
  • No push notifications on either API. Change detection requires either polling, Drive's changes.list (which only tells you the file changed, not what), or an Apps Script trigger — none of which give you an edit-level feed.
