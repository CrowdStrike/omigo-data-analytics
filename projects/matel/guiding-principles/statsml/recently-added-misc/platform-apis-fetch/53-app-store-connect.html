App Store Connect BACKLOG

Sales and finance reports, analytics reports, and subscription lifecycle events. Aggregate by construction, with privacy thresholding on small rows.

Last verified: August 2026

Overview

What It Provides

Three distinct API families, often conflated:

  • App Store Connect API — app metadata, versions, builds, TestFlight, users, plus reporting: salesReports, financeReports, and the newer analyticsReportRequests family.
  • App Store Server API — per-transaction and per-subscription state for your own customers: transaction history, subscription status, consumption info, refund lookup, notification history/test.
  • App Store Server Notifications V2 — signed JWS push callbacks for subscription and refund lifecycle events.

Analytics reports cover the funnel and quality surface: impressions, product page views, downloads/installs (first-time vs redownload), sessions, active devices, crashes, and retention by cohort — delivered as downloadable report files requested by report type and granularity, not as a live JSON query endpoint.

Authentication & Scopes
  • App Store Connect API: JWT signed ES256 with a downloaded .p8 private key; header carries kid, payload carries iss (issuer ID) and short-lived exp. Keys are role-scoped (Admin, Finance, Sales, Developer, Customer Support). Finance and sales reports require the corresponding role — a Developer key silently lacks them.
  • App Store Server API: separate in-app-purchase key, also ES256 JWT, with bid (bundle ID) in the payload. Distinct key type from the Connect key; they are not interchangeable.
  • Server Notifications V2: no inbound auth for you to configure — verify the JWS signature chain against Apple's root CA. Sandbox and production endpoints are configured separately.

Granularity — the crux

The split is clean and it matters:

  • Aggregate, anonymized: everything in analytics and sales reports. Rows are counts by date, territory, device, source type, platform version, and so on. There is no user identifier, and no way to join two report dimensions back to the same individual.
  • Transaction-level, identified: the App Store Server API, but only for your purchasers, keyed by originalTransactionId and appAccountToken (a UUID you supplied at purchase). This is the only identified data path, and it exists for entitlement management, not analytics.
What people assume and do not get. There is no endpoint returning per-user acquisition-to-retention journeys. Impressions cannot be joined to the installs they caused at the individual level. There is no per-user session log. Attribution beyond the coarse source-type dimension requires SKAdNetwork / AdAttributionKit, which is itself deliberately aggregated and delayed. And App Store Connect does not report on installs from other stores or alternative distribution channels.
Key Endpoints
  • GET /v1/salesReports — filter by reportType, reportSubType, frequency (DAILY/WEEKLY/MONTHLY/YEARLY), vendorNumber, reportDate; returns a gzipped TSV
  • GET /v1/financeReports — regionCode + fiscal reportDate
  • POST /v1/analyticsReportRequests → GET .../reports → reportInstances → reportSegments (a request/poll/download chain, ONE_TIME_SNAPSHOT or ONGOING)
  • GET /v1/apps/{id}/appStoreVersions, /builds, /customerReviews
  • Server API: GET /inApps/v1/subscriptions/{originalTransactionId}, /history/{id}, /lookup/{orderId}, /refund/lookup/{id}, /notifications/history
Rate Limits

Apple documents a per-hour request budget per team for the App Store Connect API and returns 429 with a rate-limit header describing remaining budget; treat the specific number as something to read from the response header rather than hard-code, since it has changed over time and differs by endpoint class. Practical notes:

  • Report generation is asynchronous — polling loops are the usual way teams burn their budget.
  • Sales reports for a given day are not available immediately; expect a lag of roughly a day, and expect late-arriving corrections.
  • Reports have finite availability windows (older dailies age out), so a backfill has a hard horizon. Archive on ingest.
  • Server Notifications V2 retries on non-2xx, so your handler must be idempotent on notificationUUID.
Business Scenarios
  • Revenue and proceeds reconciliation against internal billing
  • Subscription churn, trial conversion, and refund monitoring (Server API + notifications)
  • Store-listing conversion analysis: impressions → product page views → downloads
  • Release quality tracking via crash counts per version
  • Territory-level pricing and market-entry analysis
Key Restrictions & Gotchas
  • Privacy thresholding. Analytics rows below a minimum volume are suppressed or omitted entirely. Small territories, rare device models, and thin cohorts simply do not appear.
  • Units are not people. Sales report units, active devices, and installs count different things; summing across report types double-counts.
  • Proceeds ≠ revenue. Finance reports are in the payout currency after commission and tax, on Apple's fiscal calendar, which does not align with the Gregorian month used in sales reports. The two will never tie exactly, and that is expected.
  • Restatements. Yesterday's numbers change. A pipeline that treats a daily report as immutable will drift from the console.
  • The most recent period is always partial. Because generation is asynchronous and corrections arrive late, the newest available day is still filling in. Charting it next to closed days, or comparing "today" against last week, manufactures a decline that is a property of the pipeline rather than the product — and the same query re-run later shows the drop gone, which then gets narrated as a recovery. Exclude the open period, or compare on elapsed time since the report date rather than on calendar position.
  • Sandbox differs. Sandbox subscription renewal is time-compressed; sandbox behaviour is not a model of production timing.
  • No customer identity. There is no email, no name, no cross-app identity. appAccountToken only works if you set it, prospectively — you cannot backfill it.
The statistical caveat that matters most. Privacy thresholding produces missingness that is correlated with the quantity being measured: a row is absent because it is small. This is not missing-at-random, and no imputation conditioned only on observed rows fixes it. Concretely, if you drop suppressed rows and compute a mean conversion rate across territories, you have computed the mean over high-volume territories and labelled it a global figure — the estimate is biased toward whatever the large markets do, and the bias grows as you slice finer. Worse, totals and slices become mutually inconsistent: the sum of visible per-territory installs is less than the reported global total, and the residual is not noise but the entire small-market tail. Two defensible responses: (a) keep the aggregate total as the denominator and treat the suppressed set as a known-size bucket with unknown composition, bounding your estimate rather than point-estimating it; or (b) pre-aggregate to a granularity coarse enough that no cell is suppressed, and refuse to report finer. Silently filtering nulls is the one thing that is not defensible.
