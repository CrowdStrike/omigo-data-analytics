Google Forms BACKLOG

Form structure and items, responses with per-answer values and timestamps, quiz grading, and watches for new submissions

Last verified: August 2026

Overview

What It Provides

Google Forms API (v1) exposes two things: the form definition and the responses collected against it.

A form is an ordered list of items. Each item is exactly one of: questionItem (a single question), questionGroupItem (a grid — several questions sharing one set of options), pageBreakItem (a section, and the anchor for branching), textItem, imageItem, or videoItem. A question carries a questionId and a typed body: choiceQuestion (RADIO / CHECKBOX / DROP_DOWN), textQuestion (paragraph: true|false), scaleQuestion, dateQuestion, timeQuestion, fileUploadQuestion, rowQuestion, or ratingQuestion. Quiz behaviour lives in question.grading with pointValue, correctAnswers, and per-outcome feedback.

A response is keyed by responseId and holds an answers map from questionId to an answer object, plus createTime, lastSubmittedTime, totalScore for quizzes, and respondentEmail when collection is enabled.

The API cannot create a quiz from scratch in one step, and it cannot read or write branching logic. Quiz mode is enabled by a updateSettings request setting quizSettings.isQuiz; grading is then attached per question. Section navigation — "if they answer X, jump to section 3" — is authored in the UI and is not represented in the item objects the API returns. Round-tripping a branching form through the API silently flattens its logic.

Authentication & Scopes

  • OAuth 2.0, or a service account with domain-wide delegation in a Workspace tenant.
  • forms.body / forms.body.readonly — form structure, settings, items.
  • forms.responses.readonly — responses. There is no write scope: the API cannot submit a response.
  • drive.file is also accepted for forms the app created or the user selected — the least-privilege option.
  • Watches additionally require a Cloud Pub/Sub topic in your project, with the Forms service account granted publish rights on it.
forms.body forms.body.readonly forms.responses.readonly drive.file

Note the absence of a responses write scope — no scope exists that lets an app submit a response.

Granularity

Whole-form reads (forms.get) — there is no per-item fetch. Responses are listable in pages with an optional filter on timestamp (timestamp > "2026-08-01T00:00:00Z"), which is the only supported filter expression; you cannot filter by answer content, respondent, or score. Single responses are fetchable by responseId.

Structural edits go through forms.batchUpdate with a request list — createItem, updateItem, deleteItem, moveItem, updateFormInfo, updateSettings — applied atomically, with an optional writeControl.requiredRevisionId for optimistic concurrency.

Key Endpoints

  • POST /v1/forms — create (only info.title is accepted at creation)
  • GET /v1/forms/{formId}
  • POST /v1/forms/{formId}:batchUpdate
  • GET /v1/forms/{formId}/responses — filter, pageSize, pageToken
  • GET /v1/forms/{formId}/responses/{responseId}
  • POST /v1/forms/{formId}/watches — eventType: RESPONSES or SCHEMA
  • GET /v1/forms/{formId}/watches, DELETE .../watches/{watchId}, POST .../watches/{watchId}:renew

Rate Limits

Forms API quotas are set per Google Cloud project and per user in the Cloud console, and are modest — this is a low-volume API by design, not a bulk export channel. Rather than quote a figure that varies by project, treat it operationally: read the form definition once and cache it (the schema changes rarely), poll responses incrementally with a timestamp filter rather than re-listing everything, and use watches instead of tight polling. Exceeding quota returns HTTP 429 / RESOURCE_EXHAUSTED with no Retry-After, so exponential backoff with jitter is the client's responsibility. Watches have a per-form limit on concurrent watches per event type, and each watch has a bounded lifetime that must be renewed.

Business Scenarios

  • Survey and intake pipelines that land responses in a warehouse rather than a spreadsheet
  • Programmatic form generation from a question bank or template
  • Assessment scoring and gradebook sync from quiz totalScore
  • Event-driven workflows — a new response triggers ticket creation or approval routing
  • Response-latency and drop-off analysis from createTime vs lastSubmittedTime

Key Restrictions & Gotchas

Responses retain answers to questions the form no longer contains. Deleting an item from a live form does not delete the collected answers keyed by its questionId — the response objects still carry them, but the current form definition no longer explains what the question was. This is the Forms-specific version of the recurring theme: history holds more than the visible artifact. Any pipeline that joins responses to the current schema will encounter orphan questionIds and must either archive form snapshots alongside responses or accept unlabelled data. Conversely, updateItem on a question can change its wording while keeping the same id, so old and new answers merge under one label with no marker that the question changed.
  • Two timestamps, and both are submission-side. createTime is when the response was first submitted, lastSubmittedTime when it was last edited (if response editing is enabled). Neither is when the respondent opened the form — there is no per-question dwell time, no partial-response record, and no abandonment data. Drop-off analysis is not possible from this API; incomplete forms are simply never sent.
  • Answer values are always strings. textAnswers.answers[].value is a string even for scale, date, and numeric questions. Type recovery requires looking up the question type in the form definition.
  • Multi-select answers are multiple entries in one answers array, not a delimited string — and grid (questionGroupItem) answers appear as separate top-level entries in the response answers map, one per row's questionId, not nested under the group.
  • respondentEmail is present only if the form collects it. For an anonymous form there is no respondent identifier of any kind — not even a stable pseudonymous one — so deduplicating repeat submitters is impossible from the API alone.
  • File upload answers return Drive file ids, not content. fileUploadAnswers.answers[] gives fileId, fileName, and mimeType; fetching the bytes is a separate Drive call with its own permissions, and the files are owned by the form owner's Drive and count against their quota.
  • Watches are notification-only. A Pub/Sub message says "this form has new responses" — it carries no response payload, so you then call responses.list. Delivery is at-least-once, so handlers must be idempotent. Watches also expire and must be renewed before expireTime; a lapsed watch silently stops delivering.
  • Deleting a form is not in the API. Use the Drive API (files.delete / trash) — Forms has no delete method.
  • No response-level write. You cannot submit, amend, or delete a response programmatically. Load-testing a form or migrating historical answers into it is not possible.
  • Grading is not re-run retroactively. Changing correctAnswers after responses arrive does not rescore existing responses; totalScore on old responses reflects the rubric in force at submission time.
  • The linked spreadsheet is not part of this API. A form's "responses destination" sheet is reached through the Sheets API, and its column layout drifts from the form's item order once items are moved or deleted — the two views disagree.
  • Item ordering is by array position, not by an index field. moveItem requires the current location; concurrent structural edits without requiredRevisionId reorder unpredictably.
