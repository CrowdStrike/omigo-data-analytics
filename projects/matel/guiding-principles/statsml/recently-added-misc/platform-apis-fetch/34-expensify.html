Expensify BACKLOG

Expense reports, receipt images, SmartScan-extracted fields, policy categories and tags, violations, and the approval chain — retrieved through a template-driven export job rather than a conventional resource API.

Last verified: August 2026

Overview

What It Provides

Expensify's Integration Server exposes expense reports and the individual expenses (transactions) inside them, plus policy configuration: category lists, tag lists, employee lists, and the approval workflow. Receipt images are retrievable as URLs or as downloadable files, and each expense carries the fields SmartScan extracted from the receipt.

The API is job-oriented, not resource-oriented. You POST a requestJobDescription describing a job type — reportExport, create, get, download, update — and the server executes it. For exports, the output shape is defined by a Freemarker template you supply, so the same job can emit CSV, JSON, or an accounting-package-specific format.

Authentication & Scopes
  • partnerUserID / partnerUserSecret — a credential pair generated from Expensify account settings, sent inside the JSON job description, not as an HTTP header.
  • No OAuth flow and no per-scope grants. The credential inherits whatever the owning user can see, which for a policy admin is every report on that policy.
  • Because access is coarse, the practical scoping mechanism is the job's filters block (date range, policy ID list, report ID list, export state).
There is no read-only credential tier. The same secret that runs reportExport can run create and update. Treat it as a write credential in any threat model, and keep extraction jobs in a separate service from anything that mutates.
Granularity

Report-level and expense-level. Each report has a status, a total, a submitter, and a policy; each expense has a merchant, amount, currency, date, category, tag set, comment, receipt reference, and reimbursable/billable flags. Violations attach to individual expenses and, in aggregate, to the report.

Key Endpoints
  • POST /Integration-Server/ExpensifyIntegrations — single endpoint; behaviour selected by job type.
  • type: "file" + inputSettings.type: "combinedReportData" — the export job that returns reports with nested expenses.
  • type: "download" — second call that fetches the file the export job generated.
  • type: "get" + inputSettings.type: "policy" — categories, tags, employee list, approval configuration.
  • type: "create" — push expenses in from an external source.
Export is asynchronous in two steps. The first call returns a generated filename (via onReceive.immediateResponse: ["returnRandomFileName"]); a second download call retrieves the content. Any client that assumes one request returns data will appear to succeed and return nothing useful.
Rate Limits

Expensify does not publish a numeric request quota for the Integration Server. What is documented in practice is a constraint on concurrency and job size: large exports are slow, overlapping jobs from the same credential can be rejected or serialised, and the guidance is to run exports sequentially with generous timeouts rather than fanning out in parallel. Chunk by date range or policy rather than by trying to raise throughput.

Business Scenarios
  • Accounting sync — export approved reports on a schedule and mark them exported so the next run does not re-emit them.
  • Spend analytics — category and tag rollups, merchant concentration, per-department burn.
  • Policy compliance monitoring — which violations fire most, which are routinely overridden by approvers.
  • Approval cycle-time measurement — how long reports sit at each approver, subject to the timestamp limits noted below.
  • Receipt archival — pull receipt images for audit or for independent re-extraction.
Key Restrictions & Gotchas
  • SmartScan fields are model output. merchant, amount, and created as first captured are OCR inferences. When a user corrects them, Expensify stores the correction in a parallel field — modifiedMerchant, modifiedAmount, modifiedCreated — and leaves the original intact.
  • The export is report-centric. combinedReportData walks reports and then their expenses. Expenses that have never been attached to a report are not reliably reachable this way.
  • The export state filter is stateful. Filtering on markedAsExported and then marking rows exported makes your pipeline non-idempotent: a failed downstream load cannot simply be re-run.
  • Only current status is on the report. There is no per-transition history object giving the timestamp of every submit, reject, resubmit, and approve.
  • Custom template = custom schema. Two teams exporting the same data with different Freemarker templates produce incomparable files. The template is part of your data contract and belongs in version control.
  • Currency. Reports mix currencies; the converted amount depends on the exchange rate captured at report time, so re-deriving totals later with today's rates will not reconcile.
Treating the raw SmartScan value as observed fact imports Expensify's OCR error rate into your spend analysis, silently. The correct read of an expense amount is "modified value if present, else scanned value", and the presence of a modification is itself a signal — it is a human flagging that the model was wrong. Count those corrections; they are your only in-band estimate of extraction error.

Request — POST /Integration-Server/ExpensifyIntegrations, requestJobDescription parameter.

{
  "type": "file",
  "credentials": {
    "partnerUserID": "acme_integration",
    "partnerUserSecret": "••••••••••••••••"
  },
  "onReceive": {
    "immediateResponse": ["returnRandomFileName"]
  },
  "inputSettings": {
    "type": "combinedReportData",
    "filters": {
      "startDate": "2026-07-01",
      "endDate": "2026-07-31",
      "markedAsExported": "Exported to warehouse",
      "policyIDList": "A1B2C3D4E5F6A7B8",
      "limit": "1000"
    }
  },
  "outputSettings": {
    "fileExtension": "json",
    "fileBasename": "expensify_2026_07_"
  }
}
