Google Maps Platform BACKLOG

Places, Geocoding, Routes, Distance Matrix, Roads, plus the newer environment APIs. Place-level and route-level data — not individual mobility.

Last verified: August 2026

Overview

What It Provides

Google Maps Platform is a family of independently billed HTTP services over Google's map, place and routing corpus. It is not a single API and it is not a dataset you subscribe to — each request is a metered lookup against Google's index, and the terms of service constrain what you may keep afterwards.

The unit of identity is the place ID: an opaque, stable-ish string that names a business, address or point of interest. Almost every workflow reduces to (a) resolve some input to a place ID, then (b) fetch fields about that place ID.

Authentication & Scopes

API key or OAuth token on a Google Cloud project, with per-API enablement and key restrictions (referrer, IP, or bundle/package). There is no end-user OAuth consent involved — this is your project's quota against Google's public corpus, not access to a user's account. Consequently there are no user scopes to request and no user-specific data to receive.

Granularity

  • Place — one row per place ID; attributes, geometry, hours, rating aggregate, a capped sample of reviews
  • Coordinate — geocode/reverse-geocode between free-text address and lat/lng, with a result type and a match-quality indicator
  • Route — a polyline plus legs/steps and duration, optionally traffic-aware for a departure time
  • Origin x destination element — the Distance Matrix billing and response unit
  • Tile / area — the environment APIs (air quality, solar, pollen) are keyed by location or region, not by place ID

Nothing here is keyed to a person. The finest resolution available is a place or a coordinate at a point in time.

Key Endpoints or Capabilities

  • Places API — Place Details (by place ID), Nearby Search (radius + type), Text Search (free-text query), plus autocomplete for input resolution. Responses are shaped by a field mask: you declare which fields you want, and you get only those
  • Geocoding API — address to lat/lng and reverse; returns structured address components and a location type indicating whether the point is a rooftop, an interpolation along a range, or a centroid
  • Routes API / Directions — routes between waypoints by travel mode, with traffic-aware duration when a departure time is supplied. The newer Routes API also computes matrices
  • Distance Matrix — durations and distances for every origin-destination pair
  • Roads API — snap-to-road for noisy GPS traces and nearest-road lookup; the speed-limit capability is access-restricted rather than generally available
  • Air Quality API — current and forecast indices and pollutant breakdowns by location
  • Solar API — building-level roof geometry, segment orientation and modelled insolation for photovoltaic siting
  • Pollen API — pollen indices and plant-type breakdowns by location

Rate Limits & Pricing

The model, not the numbers, is what matters for design:

  • Per-call, SKU-based. Billing attaches to a SKU, and the SKU is determined by the endpoint and by what you asked for. A Place Details call requesting only basic identity/location fields is a different SKU from the same call requesting atmosphere or contact fields
  • Volume-tiered. Unit price steps down as monthly volume rises, so a cost estimate built from a pilot's per-call rate will not extrapolate linearly
  • Quotas are per-project and expressed as requests per minute; they are separate from cost and are the thing that breaks a batch job at 2am
  • Pricing and free-tier structure have been revised repeatedly. Any figure written into a document goes stale — model the shape, then read the current SKU table at build time
The usual budget surprise: Distance Matrix scales as origins x destinations. Billing is per element, not per request. 300 stores against 5,000 customer postcodes is 1.5 million elements, and it is trivially easy to write that loop without noticing. The same trap applies to field masks: adding one "nice to have" field can move every call in a nightly job into a costlier SKU.

Business Scenarios

  • Site selection and catchment analysis — competitor density and category mix by area
  • Address hygiene and de-duplication via place ID as a join key
  • Delivery and field-service routing, drive-time isochrone approximation
  • GPS trace cleaning with snap-to-road before any speed or dwell inference
  • Rooftop solar feasibility screening and environmental exposure covariates for health or real-estate models

Key Restrictions & Gotchas

"Popular Times" / busyness is not in the public API. Google surfaces a busyness histogram in its own Search and Maps surfaces, but that aggregate is a first-party UI feature — it is not a documented field of the Places API. Teams routinely design a footfall study around it and discover the gap only after the proposal is approved. Any dataset claiming to supply it is scraped, and scraping the Maps surfaces is prohibited by the terms.
Reviews are capped, not exhaustive. Place Details returns a small, selected set of reviews alongside the numeric rating aggregate and a review count. There is no paging to the full corpus. So the rating is a population statistic while the review text is a non-random sample of unknown selection rule — you cannot treat the returned reviews as a sample from which to estimate anything about the whole, and sentiment computed over them is not comparable across places.
Caching is contractually limited. The Maps Platform terms sharply restrict storing or caching returned content; place IDs are the notable exception permitted to be retained for longer-term use as identifiers. The practical consequence for analytics: you generally cannot build a private mirror of Places data. A longitudinal place-level panel therefore has to be reconstructed by re-querying on every observation date, and you pay for each wave. Panel length is a line item, not an engineering choice.
  • Place IDs can be retired or merged as Google's corpus changes; a panel keyed on place ID needs a reconciliation step, and unresolvable IDs are informative attrition rather than noise to drop
  • Geocoder results are not all equal — a rooftop match and a range-interpolated match differ by tens of metres, and the location-type field is the only signal of that. Ignoring it silently mixes two measurement precisions
  • Traffic-aware durations depend on the departure timestamp you pass; a matrix built without one is a free-flow estimate and is not comparable to one built with a rush-hour timestamp
  • Nearby/Text Search return a bounded page count, so "all restaurants in this city" is a tiling problem, and tiles overlap — deduplicate on place ID before counting
  • Solar and air-quality outputs are modelled, not measured at the point queried. They carry model error and coverage gaps that vary geographically; treating them as observations understates uncertainty and can correlate the error with region
What remains is place-level, not personal. Everything above describes places, roads and areas. Individual longitudinal mobility — where a given person was over months — is not obtainable here, and since both major platforms moved personal location history to on-device storage, there is no server-side API that returns it. The only sanctioned route is a user-initiated export the person chooses to hand over, which is a consent-gated donation rather than a queryable endpoint. Location analytics has effectively been pushed up to the aggregate and place level; study designs still assuming a per-user trace pulled on demand are designing against an interface that no longer exists.
Methodological note: SKU restructurings, field deprecations and quota changes land as step changes in what your pipeline collected. A discontinuity dated to a Maps Platform policy change is an artifact of data availability, not evidence that the world changed. Stamp every record with the API version and field mask that produced it.
