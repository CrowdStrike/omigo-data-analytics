Microsoft Teams BACKLOG

Microsoft Graph surface for channel messages, chats, online meetings, call records and presence — four families with four different access models.

Last verified: August 2026

Overview

Teams has no product-specific API of its own; everything is reached through Microsoft Graph. The consequence is that "the Teams API" is really four unrelated data families sharing a hostname — collaboration content (channel and chat messages), meeting objects, telephony and call-quality records, and presence — each with its own permission model, its own retention behaviour, and its own enumeration pattern. Treating them as one API is the most common planning error.

The second planning error is assuming message content is available because a documented endpoint exists. It exists, but reading it at organisational scale is gated behind an approval process, not just a consent prompt.

What It Provides
  • Channel messages — chatMessage objects per channel, with body, from, mentions, attachments, reactions, and replyToId. Channel threading is exactly one level deep: a root message and its /replies. There is no arbitrary nesting to reconstruct.
  • Chat messages — the same chatMessage shape for one-to-one, group, and meeting chats, reached through /chats/{id}/messages.
  • Teams and channels metadata — team, channel (with membershipType: standard, private, shared), members, tabs, apps.
  • Online meetings — the onlineMeeting object (join URL, organiser, lobby and recording settings), plus attendanceReports for who joined and for how long, and transcripts / recordings where licensing permits.
  • Call records — /communications/callRecords: sessions, segments, and media streams with jitter, packet loss, round-trip time, codec, and endpoint details. This is call-quality and call-detail data.
  • Presence — availability and activity for a user, right now.
Message content at tenant scale is not a consent decision, it is an application-review decision. getAllMessages and the application-permission read of chat and channel message bodies fall under the Teams protected APIs. The app must be submitted to and approved by Microsoft, and calls carry a model query parameter selecting a billing model (metered per-message consumption, or seeded capacity). Without approval you are limited to an evaluation mode with a deliberately low monthly call allowance — enough to prototype, not enough to run a pipeline. Budget approval lead time as a project dependency, not a formality.
Authentication & Scopes

  • Entra ID app registration; OAuth 2.0. Delegated flows act as a signed-in user and see only what that user can see. Application (app-only) flows with admin consent are the only route to tenant-wide reads.
  • Messages: delegated ChannelMessage.Read.All, Chat.Read / Chat.Read.All. Application-permission equivalents plus Chat.Read.All and ChannelMessage.Read.All are the protected-API path. ChannelMessage.Read.Group is the resource-specific-consent variant, scoped to a single team rather than the tenant.
  • Call records: CallRecords.Read.All, application permission only. There is no delegated equivalent — a user cannot read their own call records through this API.
  • Meetings: OnlineMeetings.Read.All, OnlineMeetingArtifact.Read.All, OnlineMeetingTranscript.Read.All, OnlineMeetingRecording.Read.All. App-only access to a specific user's meetings additionally requires a Teams application access policy configured in PowerShell (New-CsApplicationAccessPolicy / Grant-CsApplicationAccessPolicy) — the Graph permission alone returns an authorisation failure.
  • Presence: Presence.Read (self), Presence.Read.All (others).
Granularity

One row per message, per call session, per meeting, per attendance record. Messages are soft-deleted rather than removed: a deleted message continues to appear with deletedDateTime set and an emptied body, so deletion is observable but content is not recoverable. Edits are visible only as lastEditedDateTime — there is no revision history, so you cannot reconstruct what a message said before it was edited. Call records decompose into a session per participant pair and a stream per media direction, which means a five-person meeting produces far more than five rows.

Key Endpoints
  • GET /v1.0/teams/{team-id}/channels/{channel-id}/messages and /messages/{id}/replies
  • GET /v1.0/chats/{chat-id}/messages, GET /v1.0/users/{id}/chats
  • GET /v1.0/teams/{team-id}/channels/getAllMessages and GET /v1.0/users/{id}/chats/getAllMessages — the bulk export paths, protected-API gated, ?model=A or ?model=B
  • GET /v1.0/users/{id}/onlineMeetings?$filter=JoinWebUrl eq '...'; GET /v1.0/users/{id}/onlineMeetings/{id}/attendanceReports, /transcripts, /recordings
  • GET /v1.0/communications/callRecords/{id}?$expand=sessions($expand=segments)
  • GET /v1.0/communications/callRecords/getPstnCalls(fromDateTime=...,toDateTime=...) and getDirectRoutingCalls(...)
  • GET /v1.0/users/{id}/presence; POST /v1.0/communications/getPresencesByUserId for a batch of ids
  • Change notifications: POST /v1.0/subscriptions on /teams/{id}/channels/{id}/messages, /chats/{id}/messages, or /communications/callRecords. Resource-data (payload-included) notifications require an encryption certificate and, for messages, the same protected-API approval.
Rate Limits
  • Graph throttles per application per tenant and, for some resources, per user or per mailbox. Exhausting a bucket returns 429 Too Many Requests with a Retry-After header. Honour the header; a fixed sleep either wastes throughput or keeps you throttled.
  • Teams resources have their own service-specific limits distinct from the general Graph limits, and the protected-API paths carry consumption metering on top of throttling — you can be within the rate limit and still be accumulating billable message volume.
  • POST /$batch accepts at most 20 requests per batch, and the individual requests inside a batch are still throttled individually. Batching reduces round trips, not quota consumption.
  • Page sizes on message collections are small (tens of items) regardless of what you ask for, so a busy channel is many sequential pages. Follow @odata.nextLink verbatim rather than constructing skip tokens.
Business Scenarios
  • Collaboration network analysis — who talks to whom, across which teams, at what latency. Message metadata alone is often sufficient and avoids the content-approval path entirely.
  • Meeting load and cost measurement — attendance reports give real joined-duration rather than scheduled duration, which is the only honest input to a meeting-cost model.
  • Call quality regression detection — media stream jitter and packet loss by network, subnet, or device, isolating whether a complaint is the client, the site, or the carrier.
  • Compliance and eDiscovery feeds — the documented reason the protected APIs exist, and the scenario Microsoft's review process expects.
  • Channel abandonment — teams and channels created and never used again, using last-message timestamps rather than membership counts.
Key Restrictions & Gotchas
  • callRecords is not the meeting transcript. It contains no words, no speakers-by-utterance, no content — it is CDR and quality telemetry. Transcripts are a separate, separately licensed artifact under the meeting object. Confusing the two produces a project plan that cannot deliver.
  • callRecords has a 30-day retention window and is unrecoverable after that. If you want history you must ingest continuously; there is no backfill.
  • You cannot list call records. The collection does not support enumeration — you either already hold the record id (from a change-notification subscription) or you use the getPstnCalls / getDirectRoutingCalls functions, which cover telephony legs only, require an explicit date range, and cap the range per call. A pipeline that was not subscribed at the time of the call has no route to that call.
  • Presence is point-in-time only. There is no historical presence series and no presence audit log. "How much time did this team spend Available last quarter" is not answerable through Graph — if you need it, you must poll and persist, and polling frequently across a large tenant is exactly the pattern throttling is designed to stop.
  • There is no tenant-wide "list all meetings" endpoint. onlineMeetings is looked up per organiser and normally by joinWebUrl filter. Discovering the meeting population in practice means walking calendar events and extracting the online-meeting linkage — a different API family with different permissions.
  • Private and shared channels do not behave like standard channels. Coverage differs by endpoint, shared channels can include members from other tenants, and a bulk export validated against standard channels can silently omit them. Verify each channel membershipType against your extraction path rather than assuming uniformity.
  • Transcripts and recordings depend on the meeting having been configured to produce them, on licensing, and on the artifact not having aged out under the tenant's retention policy. Absence of a transcript is usually a configuration fact, not an API fault.
  • Message retention is governed by Purview retention policies, not by the API. Two tenants running identical code will return different history depths for the same query.
  • Attendance reports exist only for meetings where the report was generated, and identify external or anonymous participants weakly — identity may be absent with only a display name present.
