Okta Backlog

Identity provider telemetry — System Log events, users, groups, app assignments, MFA factor enrolment, sessions and provisioning outcomes.

Last verified: August 2026

Overview

What It Provides

Okta sits in front of the applications an organisation uses, so its logs record who attempted to reach what, from where, and whether it succeeded. Two distinct kinds of surface:

  • System Log (/api/v1/logs) — an append-only event stream: authentication attempts, MFA challenges, session start/end, admin configuration changes, group membership changes, app assignment changes, provisioning results, policy evaluations.
  • Current-state resources (/api/v1/users, /groups, /apps, factors) — the directory as it is right now. These have no history: reading a user tells you their present status and profile, not the sequence of states that produced it.
These APIs carry no user content — no mail, no files, no messages. Only metadata about actions: actor, target, client, outcome, timestamp. That is the defining characteristic of the audit-log category and it is what makes these feeds legally and analytically easier to work with than content APIs.
Authentication & Scopes
  • API token (SSWS) — a static token bound to the permissions of the admin who created it. Simple, but inherits that admin's full privilege and dies if the account is deactivated.
  • OAuth 2.0 for Okta — a service app authenticating with a private-key JWT (client credentials), granted narrow scopes. Preferred for scheduled collectors.
  • Relevant scopes: okta.logs.read, okta.users.read, okta.groups.read, okta.apps.read, okta.sessions.read, okta.eventHooks.read.
Granularity

One record per event, typed by a dotted eventType (for example user.session.start, user.authentication.auth_via_mfa, application.user_membership.add, system.api_token.create). Every record carries an outcome.result, an actor, zero or more target objects, a client/geo block, and an authenticationContext.externalSessionId that lets separate events be stitched into one login session.

Key Endpoints
  • GET /api/v1/logs — since, until, filter (SCIM-style expression), q (free text), sortOrder, cursor pagination via the Link: rel="next" header.
  • GET /api/v1/users, GET /api/v1/users/{id} — profile, status, lifecycle timestamps.
  • GET /api/v1/groups, /groups/{id}/users — membership snapshots.
  • GET /api/v1/apps, /apps/{id}/users, /apps/{id}/groups — assignment graph.
  • GET /api/v1/users/{id}/factors — enrolled MFA factors and their status.
  • GET /api/v1/sessions/{sessionId} — a single session by id.
  • Event Hooks / Log Streaming — push delivery to an HTTPS endpoint or to AWS EventBridge / Splunk, as an alternative to polling.
Rate Limits
  • Limits are per endpoint, per minute, per org, and the budget depends on the org's plan and size. There is no single global number worth memorising.
  • Read the response headers rather than hard-coding: X-Rate-Limit-Limit, X-Rate-Limit-Remaining, X-Rate-Limit-Reset. Exceeding the budget returns 429.
  • The System Log endpoint is one of the tighter budgets, and it is the one a collector hits most often — a backfill that pages aggressively will throttle itself.
  • Concurrent-request limits apply independently of the per-minute limit, so parallelising a backfill can fail while still under the rate budget.
Business Scenarios
  • Access review / joiner-mover-leaver — reconstruct when entitlements were granted and by whom, rather than trusting the current snapshot.
  • MFA coverage measurement — enrolled factors per user, and the rate at which challenges are satisfied versus abandoned.
  • Impossible-travel and credential-stuffing detection — geo/ASN fields plus outcome on authentication events.
  • Application rationalisation — which SSO apps are actually being authenticated into, versus merely assigned.
  • Dormant-account and orphan-token hygiene — last successful authentication per user; API token creation and use.
Key Restrictions & Gotchas
  • Retention is bounded and plan-dependent. The System Log API serves a rolling window (commonly documented as 90 days; confirm for your own org and plan). Anything older is gone from the API — the only way to have a longer history is to have been streaming or exporting it continuously all along.
  • Ingestion is near-real-time, not instant, and not strictly ordered. Records can land slightly after the event time they carry. A query for "the last few minutes" will systematically undercount. Poll with a deliberate lag behind now and re-read an overlapping window, keyed on the event uuid for idempotency.
  • There is no "list all active sessions" endpoint. Sessions can be fetched by id or revoked, but the population of live sessions has to be inferred from session start/end events in the System Log.
  • Current-state APIs cannot be backfilled. If you want yesterday's group membership, you needed yesterday's snapshot; the API only answers "now."
  • Outbound SCIM provisioning has no separate history API. Okta acts as the SCIM client to downstream apps, and the evidence of what it pushed is only in System Log application.provision.* events.
  • debugContext.debugData is not a stable contract. It is genuinely useful (policy names, request ids, threat signals) but its keys vary by event type and change over time. Do not build a schema that requires a given key to exist.
  • Deleting a user removes the current-state record but not the historical events that reference them, so joins from log to directory will produce misses.
The sharpest constraint in this whole category: an event that was not captured at the time it occurred is unrecoverable. You cannot backfill an audit log. Every retention or export decision is therefore a decision about which questions will still be answerable in six months — made before you know what the questions are.
