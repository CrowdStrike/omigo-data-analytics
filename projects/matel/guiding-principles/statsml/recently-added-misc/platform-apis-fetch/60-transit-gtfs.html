Transit GTFS BACKLOG

A zip of CSVs for the timetable and a Protocol Buffers feed for reality. Open by convention rather than mandate, which is exactly where the methodological problems come from.

Last verified: August 2026

Overview

What It Provides — Static GTFS

A GTFS feed is a zip archive of plain CSV text files. There is no server, no query language and no pagination: you download the whole thing and load it into whatever store you like. The core tables:

  • agency.txt — the operator(s), timezone, URL
  • stops.txt — stop_id, name, lat/lon, optional parent station hierarchy
  • routes.txt — route_id, short/long name, route type (bus, tram, subway, rail, ferry…)
  • trips.txt — trip_id per scheduled vehicle journey, tied to a route_id and a service_id
  • stop_times.txt — one row per (trip, stop) with arrival and departure times and stop_sequence
  • calendar.txt / calendar_dates.txt — which days each service_id runs, plus exceptions (holidays, added/removed service)

Commonly present optional tables: shapes.txt (the drawn path), transfers.txt, frequencies.txt (headway-based service instead of explicit times), fare_attributes.txt / fare_rules.txt, feed_info.txt.

Granularity — the relational spine

The join path is the whole data model:

route_id → trip_id → stop_times rows → stop_id

stop_times is by far the largest table — it is the scheduled timetable itself, and its row count is roughly trips multiplied by stops per trip. For a mid-size agency it dwarfs everything else in the archive combined. Any GTFS pipeline's performance characteristics are essentially stop_times' performance characteristics.

What It Provides — GTFS-Realtime

GTFS-Realtime is a separate, binary interface: Protocol Buffers over HTTP. Three message types, usually published at three distinct URLs:

  • TripUpdate — predicted arrival/departure per stop, delay against schedule, cancellations, added trips; keyed to a trip_id via a TripDescriptor
  • VehiclePosition — latitude/longitude, bearing, speed, occupancy status, current_stop_sequence and current_status (in transit to / stopped at)
  • ServiceAlert — disruptions, each scoped by an informed_entity list to specific routes, stops, trips or whole agencies, with an active period

All three arrive wrapped identically: a FeedMessage with a FeedHeader (version, timestamp, incrementality) and a repeated list of FeedEntity records, each carrying one of the three payloads.

incrementality is nominally FULL_DATASET or DIFFERENTIAL. In practice DIFFERENTIAL is rarely used — treat almost every real feed as a complete snapshot replacing the previous one, and design the consumer around snapshot diffing rather than applying deltas.

Authentication & Access

  • Many feeds are plain unauthenticated public URLs
  • Some require a free API key, passed as a query parameter or header
  • A few sit behind registration or a developer agreement
  • There is no OAuth model, no scopes, and no per-user data — GTFS describes service, not riders

Rate Limits & Etiquette

Access control is mostly polling etiquette rather than enforced quota. The FeedHeader.timestamp tells you when the publisher generated the snapshot: polling faster than the feed regenerates returns identical bytes and wastes both sides' bandwidth. Read the timestamp, and set your poll interval from the observed regeneration cadence rather than from a guess.

Publishing Model — open by convention, not by mandate

No central authority compels publication or conformance. Each agency publishes at its own URL, on its own schedule, with its own choices about optional fields. Aggregators and community catalogues exist and are useful, but there is no single authoritative registry, and a URL that worked last year may be gone or renamed.

Discovery is a manual, curated problem. Building a multi-agency dataset means maintaining a hand-checked list of feed URLs, keys and quirks — and that list is itself research infrastructure that decays. Budget for it.

Feed Quality Variance — the headline caveat

Conformance across agencies is uneven enough that it dominates most cross-agency analysis. Observed patterns:

  • Realtime cadence spans a very wide range — some feeds regenerate every few seconds, others every few minutes
  • Message coverage differs — some agencies publish VehiclePosition but no TripUpdate; some publish alerts only; some publish all three but with one of them effectively stale
  • Optional fields are inconsistently populated — shapes.txt, occupancy_status, wheelchair_accessible, bikes_allowed may be absent, partially filled, or filled with a default that is indistinguishable from unknown
  • Static feeds refresh on wildly different schedules — and sometimes go stale relative to the service actually being operated, so the "schedule" you compare against is not the schedule the drivers had
  • Validators exist precisely because conformance is uneven — the ecosystem's tooling is an admission of the problem, not a solution to it

Analytical Consequence: cadence is an estimator property

An on-time-performance metric computed from a 10-second feed and from a 60-second feed are not the same estimator. The coarser feed cannot resolve short dwell or short delay events at all — they occur and resolve entirely between samples. Whether that biases delay upward or downward depends on how you interpolate between samples and on how you define an event, which means two agencies can differ on your dashboard purely because of their publisher's cron interval.

This is the general principle in its cleanest form: a measurement's resolution is bounded by the pipeline that produced it. No amount of downstream modelling recovers a delay event shorter than the sampling interval. So:

  • Do not pool agencies without normalizing cadence — downsample everything to the coarsest feed in the panel, or model the sampling process explicitly
  • Document field coverage per agency and carry it as a column, not as a footnote. An agency missing occupancy_status is not an agency with empty vehicles.
  • Treat a change in an agency's publishing cadence or field coverage as a break in the series. A feed that moves from 60s to 15s will show an apparent jump in short-delay frequency on the changeover date. That is an artifact of data availability, not a change in operations.
  • Rank-ordering agencies by any delay statistic is close to meaningless without cadence adjustment, because cadence correlates with agency size and budget — the same things that plausibly correlate with actual punctuality. The confound is structural, not incidental.

No Backfill: the history does not exist unless you make it

Realtime feeds are usually not archived by the agency. The feed is a live snapshot; yesterday's snapshot is simply gone. If you do not capture and store it yourself, you cannot reconstruct it later — there is no historical endpoint to query. Some third parties archive feeds, with partial and inconsistent coverage.

The practical implication is that GTFS-Realtime research is capture-first: the collection infrastructure has to be running before the question is asked. A study designed in March cannot examine last January. And a capture pipeline that had an outage leaves a hole no vendor can fill, so gaps in your own archive need to be recorded as first-class metadata rather than silently interpolated over.

Business Scenarios

  • Trip planning and multi-modal routing over the scheduled network
  • On-time performance and reliability measurement (with the cadence caveats above)
  • Accessibility and service-coverage analysis: what fraction of a population is within a headway threshold of service
  • Headway regularity and bus-bunching detection from VehiclePosition traces
  • Disruption-impact studies from ServiceAlert histories
  • Schedule-vs-actual travel-time modelling as an input to demand models

Key Restrictions & Gotchas

  • GTFS times may exceed 24:00:00 — a trip past midnight is expressed as 25:10:00 on the prior service day, so naive time parsing silently drops overnight service
  • Service days are not calendar days; the service_id plus calendar_dates.txt exceptions are the authority, not the date
  • IDs are only unique within a feed. Merging agencies requires namespacing every stop_id, route_id and trip_id, or you will silently collide.
  • Static feeds are versioned by replacement — an ID may be reused for a different real-world entity after a schedule change, which corrupts longitudinal joins
  • Realtime trip_id references can point at trips absent from the currently published static feed, especially around schedule changeovers
  • frequencies.txt trips have no explicit per-stop times; they must be expanded before any timetable join
  • Feeds can disappear, move, or change key requirements with no notice and no deprecation window

GTFS-Realtime protobuf — abridged schema (protobuf is the real interface)

// Abridged from the GTFS-Realtime .proto.
// Field numbers and optional/repeated markers
// omitted where not load-bearing here.

message FeedMessage {
  FeedHeader          header = 1;
  repeated FeedEntity entity = 2;
}

message FeedHeader {
  string gtfs_realtime_version = 1;   // "2.0"
  enum Incrementality {
    FULL_DATASET  = 0;   // in practice: this one
    DIFFERENTIAL  = 1;   // rarely used
  }
  Incrementality incrementality = 2;
  uint64         timestamp      = 3;  // POSIX, publisher-side
}

message FeedEntity {
  string          id         = 1;
  bool            is_deleted = 2;
  TripUpdate      trip_update      = 3;
  VehiclePosition vehicle          = 4;
  Alert           alert            = 5;
}

message TripUpdate {
  TripDescriptor    trip     = 1;
  VehicleDescriptor vehicle  = 3;
  repeated StopTimeUpdate stop_time_update = 2;
  uint64            timestamp = 4;
  int32             delay     = 5;

  message StopTimeEvent {
    int32  delay       = 1;   // seconds vs schedule
    int64  time        = 2;   // POSIX
    int32  uncertainty = 3;
  }
  message StopTimeUpdate {
    uint32        stop_sequence = 1;
    string        stop_id       = 4;
    StopTimeEvent arrival       = 2;
    StopTimeEvent departure     = 3;
    enum ScheduleRelationship {
      SCHEDULED = 0; SKIPPED = 1; NO_DATA = 2;
    }
    ScheduleRelationship schedule_relationship = 5;
  }
}

message VehiclePosition {
  TripDescriptor    trip     = 1;
  VehicleDescriptor vehicle  = 8;
  Position          position = 2;
  uint32            current_stop_sequence = 3;
  string            stop_id  = 7;
  enum VehicleStopStatus {
    INCOMING_AT = 0; STOPPED_AT = 1; IN_TRANSIT_TO = 2;
  }
  VehicleStopStatus current_status = 4;
  uint64            timestamp      = 5;
  enum OccupancyStatus {
    EMPTY = 0; MANY_SEATS_AVAILABLE = 1;
    FEW_SEATS_AVAILABLE = 2; STANDING_ROOM_ONLY = 3;
    CRUSHED_STANDING_ROOM_ONLY = 4; FULL = 5;
    NOT_ACCEPTING_PASSENGERS = 6;
  }
  OccupancyStatus occupancy_status = 9;
}

message Position {
  float latitude = 1; float longitude = 2;
  float bearing  = 3; float speed     = 5;
}

message Alert {
  repeated TimeRange     active_period   = 1;
  repeated EntitySelector informed_entity = 5;
  TranslatedString header_text     = 10;
  TranslatedString description_text = 11;
}

message TripDescriptor {
  string trip_id   = 1;
  string route_id  = 5;
  string start_date = 3;   // YYYYMMDD
  string start_time = 2;   // HH:MM:SS
}
