Garmin & Polar BACKLOG

Approval-gated partner APIs over sports watches and chest straps, mixing per-second sensor samples with proprietary composite scores.

Last verified: August 2026

Overview

What It Provides

Garmin does not have one API. It has several distinct developer surfaces, and conflating them is the most common scoping mistake:

  • Health API — consumer wellness data: daily summaries, epoch summaries, sleep, stress, body composition, pulse ox, respiration, HRV. Delivered primarily by push to a partner-registered webhook endpoint, with ping and push notification variants, plus separate backfill request endpoints for historical data.
  • Activity API — activity summaries, activity details with per-second samples, and retrieval of the original FIT file for an activity.
  • Connect IQ — on-watch apps, widgets and data fields written in Monkey C. An on-device surface, not a cloud data API; it shares nothing with the two above.
  • Consumer-side export — a user manually exporting from Garmin Connect. Different shape, no automation, no consent flow.

Garmin data types worth naming individually, because their availability differs: daily summaries (steps, distance, calories, intensity minutes, floors); epoch summaries (the roughly 15-minute activity buckets); sleep summaries with stage durations for deep, light, REM and awake, plus sleep levels; stress details; Body Battery; pulse ox (spot readings and all-day acclimatisation readings); respiration; HRV (nightly, on supported devices); body composition from compatible scales; and training load, training status and VO2max estimates.

Polar exposes the AccessLink API (v3): REST over Polar Flow, covering training sessions (summary), exercise samples, heart-rate zones per session, physical information (weight, HR max and rest, VO2max), daily activity summaries, continuous heart rate, and nightly recharge / sleep. Availability of the recovery-oriented resources depends on device model and Polar product tier, so two participants on different watches will not yield the same columns. Polar has also historically been the more research-friendly vendor, publishing a fairly open ecosystem around its sensors — Polar Sensor Logger and the Polar SDK expose raw ECG and R-R intervals on some chest straps.

Authentication & Access

Garmin partner APIs require enrolment in the Garmin Developer Program. This is an application-and-approval process, not a self-serve sign-up: you apply, describe the use case, sign an agreement, and are approved for specific data families — or not. Per-user access is then granted by OAuth user consent through the user's Garmin Connect account. Historically Garmin used OAuth 1.0a for these partner APIs; newer onboarding uses OAuth 2.0 with PKCE. Both have existed, so which applies to you is a property of when and how you were onboarded — confirm against your own partner documentation rather than assuming either is "current".

garmin: dailies garmin: epochs garmin: sleeps garmin: stressDetails garmin: pulseOx garmin: respiration garmin: hrv garmin: bodyComps garmin: activities garmin: activityDetails garmin: activityFiles polar: accesslink.read_all

Garmin expresses entitlement largely as which data families your agreement enables, rather than as a long user-facing scope string; the tags above follow the data-type vocabulary in the partner documentation.

Polar AccessLink uses OAuth 2.0 authorization-code flow with a client registered on Polar's developer portal. Registration is materially lighter than Garmin's, but commercial use is still governed by an agreement. The asymmetry matters for planning: with Garmin there is no self-serve route to production wellness data at all, so the commercial and legal cycle precedes any engineering estimate, and you should design assuming the data families you are approved for may be narrower than what the public documentation describes in aggregate.

Granularity

Garmin spans four very different fidelities under one brand name:

  • FIT file — the highest fidelity. FIT (Flexible and Interoperable Data Transfer) is Garmin's binary record format with a published SDK, so parsing it is a supported path rather than reverse engineering. It carries per-record samples, commonly at 1 Hz, of timestamp, position (encoded as semicircles), heart rate, cadence, power, speed, altitude and temperature, plus lap, session and event messages, device_info, and developer fields written by Connect IQ apps. This is the highest-fidelity consumer sports data generally available, and a completely different object from a daily summary JSON.
  • Activity details — a JSON samples array, effectively a decoded subset of the same per-second series.
  • Epoch summaries — roughly 15-minute activity buckets.
  • Daily summaries — one row per day.
Sampling interval is a per-activity property, not a constant. "Smart recording" on many Garmin devices records at variable intervals rather than 1 Hz, writing a sample when a value changes materially instead of every second — and auto-pause creates real gaps in the timeline. Code that assumes one record per second will silently compress time, mis-estimate duration, and produce wrong integrals for work and training load. Read the timestamps and derive the interval per activity. Never infer elapsed time by counting records.

Polar exposes exercise samples per training session — per-sample heart rate, speed, cadence, distance, altitude and power, each channel carrying a declared recording-rate. The same caution applies, but Polar at least states the rate in the payload rather than leaving you to infer it.

Key Endpoints

Garmin Health API — the mental model is inverted from a normal REST integration. You do not poll a collection; Garmin pushes to an endpoint you register. You register a callback per data type and receive dailies, epochs, sleeps, stressDetails, bodyComps, pulseOx, respiration and hrv payloads as devices sync, and you use the separate backfill endpoints to request a historical window. User registration and deregistration endpoints manage consent lifecycle.

Garmin Activity API — activity summaries, activity details (with the samples array), and an activity-file endpoint returning the original FIT binary.

Polar AccessLink — under /v3/, and the sequence matters:

  • Register the user after OAuth consent.
  • Poll for available data, then create a transaction for a resource class — exercises, daily activity, or physical information.
  • List the items the transaction captured, fetch each one, then fetch its samples and heart-rate-zones sub-resources.
  • Commit the transaction.
  • Sleep, nightly recharge and continuous heart rate are fetched directly, without the transaction lifecycle.
Polar's transactional pull is not a cursor, and it is easy to lose data with. New data is exposed only inside a transaction you create. While the transaction is uncommitted you can re-read it, which makes retries safe. Once you commit, those items are never re-delivered. So a process that commits before the payload is durably stored — or commits in the same block that just failed to write to your database — has destroyed the data with no re-fetch available. Commit only after a confirmed durable write, keep fetch-then-store idempotent, and treat an expired uncommitted transaction as the safe failure mode rather than something to rush past.
Rate Limits

Backfill is a request, not a fetch. Anyone expecting GET /history?from=… to return rows will conclude the API is broken. There is no guaranteed historical depth available synchronously: you ask for a window, the request may be throttled, how far back you may ask is a function of your agreement, and the historical records land on your callback interleaved with live data and possibly out of order — a late-syncing device can deliver Monday after Wednesday. Store raw callback payloads before processing, key on the record identifier and time range, and design for unordered, duplicate-capable arrivals.

  • Garmin applies per-partner limits configured at onboarding rather than a single published public number, and throttles backfill requests separately from live push.
  • Garmin backfill is asynchronous. The HTTP response to a backfill request is an acknowledgement, not the data. The data arrives later, by push, on the same webhook as live traffic.
  • Because delivery is push, your endpoint is the constraint. It must absorb bursts — a watch left in a drawer for a week uploads everything at once — and it must be idempotent, because Garmin can and does re-send.
  • Polar applies per-client limits and returns HTTP 429. The transaction model is itself a load-bounding mechanism: a correct client never re-reads the same exercise.
  • No figures are quoted here deliberately. Published quotas differ by partner tier and have changed across versions; the authoritative numbers are in your partner portal and agreement. A large cohort backfill spreads over a long window and cannot be accelerated by firing more requests.
Business Scenarios
  • Endurance coaching platforms — the FIT file is the reason to integrate. Per-second power, heart rate, altitude and cadence support interval detection, critical-power modelling, cardiac drift and pacing analysis; a daily summary supports none of it.
  • Cardiac autonomic research — Polar chest straps, not watches. Beat-to-beat R-R is the requirement and only the strap delivers it.
  • Corporate wellness — Garmin daily summaries and epochs suffice, and deliberately so: pulling sample-level data you do not need enlarges the consent and retention problem for no analytical gain.
  • Population activity research — epoch summaries give a defensible intensity-minutes series without FIT's fidelity and storage cost.
  • Team load monitoring and return-to-play — workable, but a load model built on Garmin Training Load inherits Garmin's algorithm revisions as unexplained variance in your own model. The operational difficulty is roster churn and shared devices, not the API.
Key Restrictions & Gotchas

Two different instruments under one label. Polar chest straps (H10 and comparable) measure via single-lead ECG and emit beat-to-beat R-R intervals — the reference-grade consumer source for heart rate and HRV. Garmin wrist heart rate is optical PPG: sampled periodically and duty-cycled at rest, sampled more densely during activity, and degraded by motion, cold, strap fit and skin tone. Garmin's HRV is a nightly aggregate computed on-device, not an R-R series you can reanalyse.

Pooling "heart rate" or "HRV" across a Polar strap and a Garmin watch pools two different instruments. An ECG-derived R-R series, a duty-cycled optical wrist reading, and a spot reading do not share a measurement process, an error distribution, or a sampling interval. Device type is not a nuisance covariate to be averaged away — it is part of the variable definition. If a cohort mixes device classes, stratify by instrument or restrict to one. The same holds for sleep: Garmin's wrist-based staging is actigraphy plus PPG inference, not polysomnography, so its stage boundaries are model output rather than scored epochs.
Composite scores are proprietary model outputs, not measurements. Body Battery, Training Status, Training Load, the VO2max estimate, Stress Score and Sleep Score are vendor algorithms — several originally licensed from Firstbeat Analytics, which Garmin acquired — and they change between firmware and app releases. A longitudinal series of such a score is therefore not a stable measurement: a level shift in it can reflect an algorithm update rather than any physiological change, and the historical series is not re-versioned when the model changes. These fields are unsuitable as a dependent variable across long time windows unless you record firmware and app version with every record and can test for step changes at update boundaries. Prefer the closest-to-raw field the API exposes.

The FIT file and the API summary can disagree. Summaries are recomputed server-side, sometimes with different smoothing, gap handling or pause treatment than the on-device totals in the session message. Small distance and calorie discrepancies are expected, not a bug to chase — but pick one source per metric and stay with it.

Other operational traps: a device reports only after it syncs, so any "yesterday's data by 6am" SLA is a promise about user behaviour rather than about the API. Multi-device accounts (watch plus bike computer plus scale) produce concurrent activities and duplicated daily aggregates, so deduplicate on device identifier and time interval, not on date. Garmin supplies UTC start time and local offset as separate fields; bucketing on the UTC field alone shifts whole days for users away from the meridian. And users edit or delete activities in the vendor app after the fact — treat a fetched record as a version, not as final.

Not available from either partner API:

  • Raw PPG waveform.
  • Raw accelerometer from Garmin's partner APIs. Step and intensity counts are derived on-device; the underlying signal stays there.
  • R-R interval series from Garmin wrist devices. Nightly HRV aggregates are not a substitute.
  • Other users' data, and any population aggregate or benchmark. Access is strictly per-consenting-user.
  • Guaranteed historical depth without an explicit, throttled, asynchronous backfill request.
  • All-day pulse ox is opt-in and battery-costly, so its presence reflects a user setting rather than device capability. Absence is a configuration fact, not a physiological one, and treating those users as missing-at-random biases any SpO2 analysis toward people who tolerate poor battery life.
