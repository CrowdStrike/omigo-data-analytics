Amazon Selling Partner & Ads BACKLOG

SP-API orders, inventory, settlements, fees and returns via an asynchronous Reports pattern; Ads API campaigns, search-term reports, and Amazon Attribution — two separately authorised APIs that must be joined manually.

Last verified: August 2026

Overview

What It Provides

Selling Partner API (SP-API) — the seller-side operational record:

  • Orders — getOrders and getOrderItems: order status, fulfillment channel (AFN/MFN), item ASIN/SKU, quantity, item price, promotion discount.
  • Inventory — FBA Inventory API for fulfillable/reserved/inbound quantities; Listings and Catalog Items for the listing itself.
  • Finances — listFinancialEvents for shipment events, refund events, service fees, adjustments. The settlement report is the authoritative reconciliation to a bank deposit.
  • Fees — getMyFeesEstimateForSKU returns an estimate of referral and fulfillment fees. Actual fees appear only in financial events after the fact.
  • Returns & reimbursements — via FBA returns and reimbursements reports rather than a live endpoint.
  • Reports API — the bulk surface. Hundreds of report types covering sales, traffic, inventory ledger, storage fees, and returns.
  • Notifications — event subscriptions delivered through Amazon SQS or EventBridge, not plain HTTP webhooks.

Amazon Ads API — a separate product with separate credentials:

  • Sponsored Products / Brands / Display — campaigns, ad groups, keywords, product targets, negative targets, and their bids.
  • Reporting v3 — asynchronous performance reports by campaign, ad group, keyword, target, or advertised product.
  • Search-term reports — the actual customer query that matched a keyword. This is the highest-value ad dataset Amazon exposes.
  • Amazon Attribution — measures off-Amazon media driving on-Amazon conversions, via tagged click-through URLs.
  • Amazon Marketing Stream — near-real-time hourly ad metrics pushed to your queue, as an alternative to pulling reports.
Authentication & Scopes
  • SP-API — Login with Amazon (LWA) OAuth. You exchange a long-lived refresh token for a short-lived access token, and the app must be registered in Seller Central's developer console. Restricted operations touching buyer PII require a Restricted Data Token (RDT), obtained per call set; the ordinary access token will not return that data.
  • SP-API roles are declared per data category (Product Listing, Inventory, Pricing, Buyer Information, Finance) and approved by Amazon, not self-granted.
  • Regional endpoints and marketplace IDs. SP-API is partitioned into NA, EU, and FE endpoints, and within each you pass marketplaceIds. A US seller and their UK listings are not one query.
  • Ads API — its own LWA client, its own consent flow, and a profileId header selecting the advertiser account and marketplace. An SP-API token does not work against Ads, and vice versa.
There is no shared identifier binding an Ads profile to a Selling Partner account in either API. Joining ad spend to orders is done by you, on ASIN and date, in your warehouse. Any "ad efficiency by product" metric is therefore a join you constructed, with your own assumptions about attribution window and marketplace mapping — not something Amazon returned.
Granularity

SP-API orders are per-order and per-order-item, timestamped. Financial events are per-transaction with itemised fee components. Ads reporting is per-day per-entity; Marketing Stream is hourly. Search-term data is aggregated per day per keyword-and-query pair, and Amazon suppresses low-volume rows.

The Async Report Pattern

Both APIs use the same four-step shape, and it is the single most important operational fact about them:

  • 1. Request — POST /reports/2021-06-30/reports (SP-API) or POST /reporting/reports (Ads v3) with type, date range, and options. Returns a report ID immediately.
  • 2. Poll — check status until DONE / SUCCESS. Latency ranges from seconds to tens of minutes depending on type and date span; large report types are markedly slower.
  • 3. Fetch the document — you get a document ID or a pre-signed URL, valid for a limited window.
  • 4. Decompress and parse — SP-API documents are frequently GZIP-compressed and are tab-separated text or flat JSON, not the JSON shape of the operational endpoints. Some report types are encrypted.
Reports are not idempotent across time. Requesting the same report type for the same date range a week later can return different numbers, because Amazon restates: returns post late, refunds land after the fact, fees are adjusted, and attributed conversions accrue for the length of the attribution window. This is expected behaviour, not a defect — but it means an unversioned report table is not reproducible. Store the generation timestamp alongside every row, and never overwrite a prior extract in place.
Rate Limits

SP-API applies a per-operation token bucket: each operation has its own rate and burst, published per endpoint in the documentation, and the current state is returned in the x-amzn-RateLimit-Limit response header. Two consequences: a global "requests per second" budget for your app does not exist, and one hot operation being throttled says nothing about the others. Some operations are deliberately slow — this is why Reports exists for anything at volume. Amazon can also apply dynamic usage plans that differ from the documented defaults for a given seller.

The Ads API rate-limits per profile and returns 429 with a Retry-After; report generation is additionally constrained by how many reports you may have pending. Marketing Stream sidesteps both by pushing rather than being polled.

Both should be treated as: read the rate-limit headers, back off exponentially with jitter, and make the pipeline resumable. Fixed sleeps tuned by trial and error break when Amazon adjusts your plan.

Business Scenarios
  • True unit economics — net proceeds per unit after referral fee, FBA fee, storage, returns, and ad spend. Requires SP-API finances plus Ads reporting plus your own COGS.
  • Inventory and restock planning — velocity from orders against FBA fulfillable and inbound quantities.
  • Keyword harvesting — promoting converting search terms out of the search-term report into exact-match keywords, and negating the rest.
  • Buy Box and pricing monitoring — competitive pricing signals.
  • Settlement reconciliation — tying settlement reports to deposits, which is the only way to detect fee errors.
  • Off-Amazon media measurement — Attribution for social and search traffic driving Amazon sales.
Key Restrictions & Gotchas
  • No buyer identity by default. Buyer name, address, and email require restricted-data approval and an RDT, and even then are constrained. Cohort or LTV analysis of the kind that is trivial on Shopify is largely not available — Amazon owns the customer relationship, and the API reflects that. This is the most common false assumption about SP-API.
  • Fee estimates are not fees. getMyFeesEstimateForSKU is a calculator. Margin models built on it will disagree with the settlement report, and the settlement report is what you were actually charged.
  • Ad attribution is Amazon's model, not an observation. Sponsored Products conversions are credited within an attribution window (commonly 7 or 14 days depending on report and ad type) using Amazon's own rules. Two reports with different windows will both be "correct" and will not agree. Attributed sales are not a count of causal conversions, and adding attributed sales across ad types double-counts.
  • Search-term data is suppressed at low volume for privacy. Your search-term report does not sum to your campaign totals, and the residual is not an error.
  • Report type semantics vary in ways the names hide. Some report types are date-of-order, others date-of-shipment; some are marketplace-local time, others UTC. Sales figures from two report types for "the same week" routinely differ for this reason alone.
  • No cross-marketplace aggregation. You loop marketplaces and sum yourself, handling currency.
  • Notifications require AWS infrastructure. There is no simple HTTP callback; you stand up SQS or EventBridge.
  • Order status is current state. getOrders gives you where an order is now. Reconstructing pending to shipped to returned requires either repeated sampling or stitching financial events — there is no per-order transition log.
  • Historical windows are bounded. Report date ranges are capped per type, and some data is only retained for a limited period. Backfill windows must be chunked, and beyond a certain age the data is simply unavailable.
Why Orders and Settlements Never Tie Out

Amazon answers two different accounting questions on two different clocks, and the gap between them is definitional rather than a data-quality problem.

  • An order is stamped at purchase. Revenue attributed to it belongs to the purchase date.
  • A financial event posts when the shipment, refund, fee, or adjustment actually occurs — after the order date, sometimes long after.
  • A settlement aggregates whatever posted inside a fixed settlement window and pays out at the window's close, less reserves.

So a single order can have its principal in one settlement, its refund in the next, and a reimbursement adjustment two settlements later. Aggregating financial events by order date reproduces revenue; aggregating by posted date reproduces cash. They will not be equal in the same calendar month, and no query makes them equal.

Do not reconcile order-date revenue against settlement-date cash for the same period — that comparison has no correct answer. Run two reconciliations instead, each internally closed: settlement total against the bank deposit, and separately, order-date revenue against the sum of financial events attributable to those orders regardless of when they posted. Teams that insist on one number spend quarters chasing a difference that is definitional.
The right-censoring consequence. Refunds, A-to-Z claims, chargebacks, and reimbursements arrive after the order, so a cohort's net revenue declines as it ages and a recent cohort always looks better than a mature one. Comparing this month's contribution margin against last quarter's compares an immature cohort against a settled one. Compare cohorts at equal age, or model the maturation curve and discount young cohorts explicitly. Ad spend has the mirror problem: cost is known immediately while attributed conversions accrue over the attribution window, so ACOS on a recent window is biased high — all the cost, only some of the credit.
