GitLab & Bitbucket APIs Backlog

Repositories, merge and pull requests, reviews, and CI pipelines — the same DevOps domain under two different pagination and identity models.

Last verified: August 2026

Overview

What It Provides
  • GitLab REST API v4 — https://gitlab.com/api/v4/ or your self-managed host. Projects, groups, branches, tags, commits, merge requests, notes and discussions, approvals, issues, milestones, pipelines, jobs, job traces, artifacts, environments, deployments, releases. GitLab also ships GraphQL at /api/graphql, where newer features land first.
  • Bitbucket Cloud API 2.0 — https://api.bitbucket.org/2.0/. Workspaces, projects, repositories, refs, commits, pull requests, activity, comments, diffstat, pipelines, deployments. Bitbucket Data Center is a separate product with a separate API (/rest/api/1.0/); the two are not interchangeable.

Together they cover the delivery pipeline end to end: what changed, who reviewed it, how long it waited, and whether it built.

Authentication & Scopes
  • GitLab — Personal, Project or Group Access Token via PRIVATE-TOKEN or Authorization: Bearer; OAuth 2.0 for apps; CI_JOB_TOKEN inside pipelines, scoped to that job. Project and group tokens suit collectors because they expire with the project rather than with an employee.
  • Bitbucket Cloud — Repository / Project / Workspace Access Tokens (bearer), OAuth 2.0 consumers, or App Passwords with per-capability permissions. Account-password basic auth is not supported.

Granularity
  • One record per merge/pull request, with the timestamps flow analysis needs: created_at, updated_at, merged_at, closed_at.
  • One record per note / comment / activity entry. GitLab flags machine-generated ones with system: true — that is how label, assignee and approval changes appear. Bitbucket exposes the equivalent via /pullrequests/{id}/activity.
  • One record per pipeline, one per job beneath it, each with status, duration, and (GitLab) queued_duration.
  • One record per commit, with author and committer as separate identity/timestamp pairs.
Key Endpoints
  • GET /api/v4/projects/:id/merge_requests?state=merged&updated_after=…&order_by=updated_at
  • GET /api/v4/projects/:id/merge_requests/:iid/notes, /discussions, /approvals, /changes, /commits
  • GET /api/v4/projects/:id/merge_requests/:iid/resource_state_events and /resource_label_events — typed history instead of prose notes
  • GET /api/v4/projects/:id/pipelines, /pipelines/:pipeline_id/jobs, /jobs/:job_id/trace
  • GET /api/v4/projects/:id/repository/commits, /repository/compare, /deployments
  • GET /api/v4/audit_events, /groups/:id/audit_events — administrative trail, higher tiers only
  • GET /2.0/repositories/{workspace}/{repo_slug}/pullrequests?state=MERGED&q=…
  • GET /2.0/repositories/{workspace}/{repo_slug}/pullrequests/{id}/activity, /comments, /diffstat, /statuses
  • GET /2.0/repositories/{workspace}/{repo_slug}/pipelines/, /pipelines/{uuid}/steps/
  • GET /2.0/workspaces/{workspace}/permissions — who can reach what
Rate Limits
  • GitLab.com throttles per endpoint family, per authenticated user and per IP, and hits unauthenticated traffic much harder. Self-managed instances have whatever the administrator configured — possibly nothing. Read RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset, Retry-After; the published SaaS figures differ per endpoint group and have changed repeatedly.
  • Bitbucket Cloud applies hourly limits that vary by endpoint class and by caller type, with lower budgets for anonymous access. Same rule: read the headers rather than hard-coding.
  • Both punish the same anti-pattern — one request per merge request to fetch notes. Filter with updated_after / q so each incremental run touches only what moved.
Business Scenarios
  • DORA-style delivery metrics — lead time from first commit to deploy, deployment frequency from /deployments, change-failure rate from pipeline outcomes plus revert detection.
  • Review latency — time to first substantive review comment, and approval-to-merge gap.
  • CI reliability and cost — flake rate from repeated jobs on one commit; queue time versus run time separates a slow build from a starved runner pool.
  • Bus-factor and ownership — commit and review concentration per path.
  • Compliance evidence — that every merge to a protected branch carried an approval from someone other than the author.
Restrictions & Gotchas
  • GitLab has two id namespaces. Every object carries a global id and a per-project iid. URLs and humans use iid; cross-project joins need id. Mixing them returns data about the wrong merge request with no error.
  • Bitbucket paginates with an opaque next URL, and size/pagelen are not reliably populated on large collections. Follow next until absent; never compute page counts.
  • Cloud and Data Center are different APIs. Code written for api.bitbucket.org/2.0 will not run against a self-hosted /rest/api/1.0 instance. Establish the product first.
  • Tier gating is invisible until it isn't. GitLab approval rules, audit events and some merge-request metrics are paid-tier features; on a Free namespace the endpoint returns 403 or an empty structure. An analysis that works on one group silently degrades on another.
  • Git identity is not platform identity. author_email comes from local git config and may match no account. Reconcile through platform user objects, and expect an unattributable residue.
  • Force-push, rebase and squash rewrite history. A squash merge collapses many commits into one new SHA with a new timestamp, destroying the original authoring times that lead-time metrics depend on. Capture the pre-merge commit list at merge time or lose it permanently.
  • Pipelines are not one per commit. Retries, schedules, parent/child and multi-project pipelines all attach to the same ref. Counting pipelines as builds overstates activity; deduplicate on sha plus source.
  • Job logs and artifacts expire on a configurable schedule, so failure evidence has a shorter life than the pipeline record pointing at it. The metadata outlives the diagnosis.
  • System notes are prose, not fields. "changed target branch from x to y" is a rendered sentence. Prefer GitLab's resource_state_events / resource_label_events over regex on note bodies.
  • Deleted source branches break provenance — the merge request then references the branch by name only.
Merge-request and pipeline records are metadata about a change, not the reasoning behind it. They show an approval landed eleven minutes after the request; whether the diff was read is not in the data. Review-latency metrics measure elapsed clock time between events — any reading of them as diligence is an assumption added afterwards, not a measurement.
