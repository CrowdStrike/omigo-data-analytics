Outlook / Exchange Online BACKLOG

Microsoft Graph mail surface — messages, mail folders, delta synchronisation, inbox rules, MAPI extended properties, and the app-only access model that grants far more than most teams intend.

Last verified: August 2026

Overview

Graph's mail surface reads Exchange Online mailboxes as a tree of mailFolder objects containing message objects. It is one of the oldest and most complete parts of Graph, with mature paging, filtering, and incremental sync. The difficulty is not capability; it is that the same code path can mean "one user's inbox" or "every mailbox in the organisation" depending on a single choice in the token request, and nothing in the response tells you which one you picked.

Underneath, the data model is still MAPI. Most of the friction — identifier instability, extended properties, single-value vs multi-value property access — comes from that inheritance rather than from Graph itself.

Application permission Mail.Read means every mailbox in the tenant, including the CEO's, with no per-user consent and no per-user audit prompt. The only supported way to narrow it is an Application Access Policy configured in Exchange Online PowerShell (New-ApplicationAccessPolicy scoped to a mail-enabled security group), which is a mailbox-side control invisible from the Graph app registration. Teams routinely ship an app-only integration believing the app registration defines its blast radius. It does not. Verify with Test-ApplicationAccessPolicy against a mailbox that should be out of scope, and treat a successful read as a finding.
What It Provides
  • Messages — subject, from, toRecipients / ccRecipients / bccRecipients, body and bodyPreview, hasAttachments, isRead, importance, internetMessageId, conversationId, conversationIndex, categories, flag, and the full internetMessageHeaders collection when explicitly selected.
  • Mail folders — hierarchical, with totalItemCount and unreadItemCount, plus well-known aliases (inbox, sentitems, drafts, deleteditems, archive, junkemail) usable in place of an id.
  • Attachments — fileAttachment, itemAttachment (a nested message or event), and referenceAttachment (a link to cloud storage, which contains no bytes at all).
  • Delta queries — /delta on messages and mailFolders, returning an opaque @odata.deltaLink to resume from.
  • Inbox rules — messageRules under mailFolders/inbox, with conditions, actions, exceptions, and sequence.
  • Mailbox settings — time zone, working hours, language, and automatic-reply configuration.
  • Extended properties — named or tagged MAPI properties, reachable via singleValueExtendedProperties and multiValueExtendedProperties.
Authentication & Scopes
Mail.ReadBasicMail.ReadMail.ReadWriteMail.SendMailboxSettings.ReadUser.Read
  • Entra ID app registration, OAuth 2.0. Certificate credentials preferred over secrets for app-only.
  • Mail.ReadBasic — metadata and headers, but not body, bodyPreview, or uniqueBody. This is the correct scope for network, volume, and response-time analytics, and requesting it instead of Mail.Read is the single cheapest way to make a review pass.
  • Mail.Read — full read including bodies and attachments. Mail.ReadWrite adds create, update, move, delete. Mail.Send is separate and is not implied by ReadWrite.
  • MailboxSettings.Read is a distinct scope; mailbox settings are not covered by any Mail.* permission.
  • Delegated flows are bounded by the signed-in user and honour delegate and shared-mailbox rights. Application flows require admin consent and are tenant-wide by default — see the callout above.
  • Exchange Online has retired Basic authentication; there is no username-and-password path. Legacy EWS integrations must move to OAuth, and EWS itself is deprecated for Exchange Online in favour of Graph.
Granularity

One row per message per mailbox — which means an internal email to twelve colleagues is thirteen distinct message objects with thirteen different id values. internetMessageId is the stable cross-mailbox join key; id is not. Threading is via conversationId, which is Exchange's own grouping and does not always agree with the RFC 5322 References / In-Reply-To chain, particularly once external participants and subject-line edits are involved.

Key Endpoints
  • GET /v1.0/me/messages or GET /v1.0/users/{id|upn}/messages
  • GET /v1.0/users/{id}/mailFolders, /mailFolders/{id}/childFolders, /mailFolders/inbox/messages
  • GET /v1.0/users/{id}/mailFolders/{id}/messages/delta — incremental sync per folder
  • GET /v1.0/users/{id}/messages/{id}/attachments
  • GET /v1.0/users/{id}/mailFolders/inbox/messageRules
  • GET /v1.0/users/{id}/mailboxSettings
  • GET /v1.0/me/messages?$search="from:vendor@example.com" — note $search and $orderby cannot be combined on messages, and $search uses KQL semantics rather than OData
  • POST /v1.0/$batch — at most 20 requests per batch
  • POST /v1.0/subscriptions — change notifications on a folder; payload-included notifications require an encryption certificate
Rate Limits
  • Two independent mechanisms apply. Graph enforces per-application per-tenant limits; Exchange additionally enforces per-mailbox limits based on the resource cost of each request, so an expensive query consumes more budget than a cheap one even at the same request count.
  • Exceeding either returns 429 Too Many Requests with Retry-After. Honour the header. Repeated abuse can escalate to longer back-off.
  • Documented Outlook-specific limits worth designing against: 10,000 requests per 10 minutes per mailbox per app, and 4 concurrent requests per mailbox. The concurrency cap is the one that catches parallel-fetch designs — scale by fanning out across mailboxes, never by fanning out within one.
  • $top is capped (commonly 1,000 for message collections, lower in practice for wide $select). Follow @odata.nextLink verbatim.
  • Requesting internetMessageHeaders or full bodies substantially raises per-item cost. $select is a throughput control, not just a bandwidth one.
Business Scenarios
  • Response-time and SLA measurement — first-reply latency on a shared or support mailbox, derived from conversationId and receivedDateTime, with no body access needed.
  • Organisational network analysis — communication graph from recipient lists; Mail.ReadBasic is sufficient and materially easier to get approved.
  • Data-exfiltration and rule-abuse detection — inbox rules that forward externally or silently move mail to a rarely-opened folder are a well-known compromise indicator, and are only visible per mailbox through messageRules.
  • Vendor and invoice extraction — attachment harvesting scoped by sender domain and folder.
  • Mailbox hygiene and storage forecasting — folder item counts and attachment sizes by age.
Key Restrictions & Gotchas
  • Delta tokens expire, and the only recovery is a full resynchronisation. A stale or invalid deltaLink returns 410 Gone with syncStateNotFound; you must restart from /delta with no token and re-walk the folder. Any pipeline that pauses for longer than the token's life — an outage, a long weekend, a migration — pays full-fetch cost on resume. Size your infrastructure for the resync, not the steady state.
  • Default message ids are not immutable. Moving a message between folders changes its id, so a stored id can 404 even though the message still exists. Opt into immutable ids by sending Prefer: IdType="ImmutableId" on every request in the session — including the initial one that created the stored id. Mixing id types in one dataset produces joins that are wrong rather than empty.
  • Delta reports removals as tombstones, not deletions you can interpret. A removed entry (@removed with reason: "changed" or "deleted") is emitted both when a message is genuinely deleted and when it moves out of the synced folder. Folder-scoped delta cannot distinguish the two; a move looks like a delete in the source folder and a create in the destination.
  • Delta does not return every property. The delta payload is a reduced projection, and $select support on delta is limited. Practical designs use delta to learn which items changed, then fetch those items individually — which doubles the request count relative to the naive estimate.
  • Mail.ReadBasic silently omits the body rather than failing. body comes back empty or absent instead of returning an authorisation error, so a downstream text pipeline degrades quietly into producing nothing.
  • Inbox rules are strictly per-mailbox. There is no tenant-wide rule inventory endpoint; auditing rules across an organisation means iterating every mailbox, which collides directly with the per-mailbox throttle.
  • Extended properties are reachable but awkward. They must be requested by explicit property identifier via $expand=singleValueExtendedProperties($filter=id eq 'String {guid} Name propname'), one property specification at a time, with no discovery mechanism — you cannot list what extended properties an item has. They are not returned by default and are not covered by delta.
  • referenceAttachment contains no content. It is a pointer to OneDrive or SharePoint; retrieving the bytes is a different API with different permissions, and the link may resolve to something the calling app cannot read.
  • $filter on some message properties is unsupported or silently ignored, and combining certain filters with $orderby returns an error demanding Prefer: HxMailboxTimeZone-style hints or a different ordering. Test each filter combination rather than assuming OData generality.
  • Archive mailboxes and recoverable-items are not exposed as ordinary folders. Compliance-grade retrieval of deleted or archived mail is a Purview eDiscovery scenario, not a Graph mail scenario.
  • Datetimes are UTC unless you send Prefer: outlook.timezone. Deriving "business hours" behaviour without setting this, or without reading mailboxSettings for the user's actual working hours, produces a timezone artefact that looks like a real behavioural finding.
