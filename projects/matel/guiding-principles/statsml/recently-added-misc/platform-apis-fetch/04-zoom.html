Zoom BACKLOG

Meeting and webinar metadata, per-participant join/leave records, cloud recordings and audio transcripts, and the Dashboard quality-of-service surface.

Last verified: August 2026

Overview

Zoom exposes conferencing data through several distinct API families that look similar but answer different questions: configuration endpoints describe meetings as scheduled, /past_meetings and /report describe meetings as they actually happened, and /metrics (Dashboard) describes connection quality. They disagree with each other often enough that choosing the wrong family is the most common source of wrong numbers.

What It Provides
  • Scheduled state — meetings and webinars as configured: topic, host, start time, duration, settings, join URL, recurrence.
  • Occurred state — past meeting instances keyed by uuid, with per-participant join_time, leave_time and duration.
  • Reports — aggregated usage per user, per meeting, per day; poll and Q&A results; webinar registrant and attendee reports.
  • Dashboard / QoS — bitrate, latency, jitter, packet loss, CPU, resolution, per participant, per media stream (audio / video / screen share).
  • Cloud recordings — file inventory per recording (MP4, M4A, chat file, and TRANSCRIPT VTT when enabled), with download URLs.
  • Webinars — sessions, registrants, panelists, absentees, tracking sources.
Authentication & Scopes
meeting:read:adminreport:read:admindashboard_meetings:read:adminrecording:read:adminwebinar:read:adminuser:read:admin
  • Server-to-Server OAuth is the mechanism for unattended collectors. It replaced the old JWT app type, which Zoom deprecated and then removed — any integration still described as "JWT" is dead and must be rebuilt.
  • User-level OAuth for acting on behalf of an individual host; account-level for org-wide reads.
  • Scopes are granular and split by actor: meeting:read:admin, report:read:admin, dashboard_meetings:read:admin, recording:read:admin, webinar:read:admin, plus the cloud_recording family. An admin-suffixed scope requires the app to be authorised at account level and, for published apps, admin consent.
Granularity

The finest analytic grain is one row per participant per join, not per participant per meeting. Below that, Dashboard QoS is one row per participant per media stream per sampling interval. Above it, reports aggregate to meeting, user, and day.

The rejoin trap. /report/meetings/{meetingId}/participants returns the same person multiple times if they dropped and rejoined — one row per join interval, each with its own join_time, leave_time and duration. Counting rows gives an inflated attendance figure, and summing duration gives connected time, not wall-clock presence: overlapping rows from two devices double-count, and gaps between rows are invisible. Deduplicate on id/user_id (falling back to user_email, which can be blank for guests) and merge intervals before you compute anything.
Key Endpoints
  • GET /v2/users/{userId}/meetings — scheduled/upcoming/previous meetings for a host.
  • GET /v2/past_meetings/{meetingUUID} and /past_meetings/{meetingUUID}/participants — what actually occurred.
  • GET /v2/report/meetings/{meetingId} and /report/meetings/{meetingId}/participants — the reporting view, with more fields than the past_meetings variant.
  • GET /v2/report/users/{userId}/meetings, GET /v2/report/daily, GET /v2/report/users — usage rollups.
  • GET /v2/metrics/meetings, /metrics/meetings/{meetingId}/participants, /metrics/meetings/{meetingId}/participants/qos — Dashboard; type=live or type=past.
  • GET /v2/users/{userId}/recordings, GET /v2/meetings/{meetingId}/recordings — recording file inventory.
  • GET /v2/webinars/{webinarId}/registrants, /panelists, GET /v2/report/webinars/{webinarId}/participants.
  • Event Subscriptions (webhooks) — meeting.started, meeting.ended, meeting.participant_joined, meeting.participant_left, recording.completed, recording.transcript_completed.
Rate Limits
  • Limits are assigned per endpoint category, not per API as a whole: Light, Medium, Heavy and Resource-intensive. Each category has its own per-second request allowance, and the Heavy category additionally carries a daily request cap.
  • Report and Dashboard endpoints — exactly the ones a backfill hammers — sit in the heavier categories. A naive per-meeting loop over a quarter of history will exhaust the daily budget rather than the per-second one, and the daily budget does not recover until it resets.
  • Treat the published per-category numbers as account- and plan-dependent and read the 429 response plus Retry-After rather than hard-coding a rate. Design collectors to prefer one wide report call over many narrow ones.
Business Scenarios
  • Meeting-load and licence utilisation — how many licensed hosts actually host, and concurrency peaks by hour.
  • Attendance measurement — genuine presence per attendee after interval merging, for training compliance or billable time.
  • Network quality triage — correlate packet loss and jitter from QoS with site, ISP, or device type to locate the bad segment.
  • Webinar funnel — registrants versus attendees versus watch-time, by tracking source.
  • Recording governance — what exists in cloud storage, how old it is, and whether transcripts were produced.
Key Restrictions & Gotchas
  • Dashboard requires a higher plan than people expect. Dashboard/metrics endpoints are gated to Business, Education and Enterprise-tier accounts; a Pro plan is not sufficient. Reporting endpoints have their own plan requirement. A collector that works in one tenant can return 4xx in another purely because of plan.
  • Meeting UUID encoding. Past-meeting endpoints are keyed by uuid, not the numeric meeting id. If a UUID begins with / or contains //, it must be double URL-encoded before being placed in the path. Skipping this produces confusing 404s on a subset of meetings only, so it survives testing.
  • Numeric meeting id is not unique over time. Recurring meetings and Personal Meeting IDs reuse the same id across many instances. Only uuid identifies an instance.
  • Query windows are bounded. Report and Dashboard endpoints accept a from/to range limited to roughly one month per request, and their historical depth is a small number of months — not unlimited. Long history must be paged month by month and archived locally.
  • QoS has a much shorter horizon than the meeting record. Detailed per-stream quality data is retained for only a limited window after a meeting ends; the meeting and participant rows outlive it. If QoS is not pulled promptly it is gone while the meeting still appears in reports.
  • Transcripts cannot be produced retroactively. An audio transcript exists only if cloud recording was on and the "Create audio transcript" setting was enabled before the meeting started. There is no API to transcribe an existing recording. Failing to set this in advance is unrecoverable.
  • Webinar endpoints require the Webinar add-on licence on the host. Registrant and panelist data exists only if registration was actually enabled — otherwise those collections are legitimately empty, not broken.
  • Recording retention is an account setting, not an API guarantee. Admins configure auto-delete after N days; deleted recordings sit in Trash for a limited period and then vanish. Download URLs require a bearer token or download token — they are not public links.
  • No in-meeting content. Chat messages, reactions, and shared screens are not retrievable as structured data; in-meeting chat surfaces only as a file inside a cloud recording, if that was enabled.
  • Participant identity is weak for guests. External joiners often have no user_id and a self-typed name; the same human across two meetings is not reliably the same key.
