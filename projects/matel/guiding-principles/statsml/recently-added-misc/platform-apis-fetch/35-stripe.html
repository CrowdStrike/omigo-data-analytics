Stripe BACKLOG

Charges and PaymentIntents, subscriptions and schedules, invoices, disputes, payouts and balance transactions, Radar risk assessments, the Events log, and Sigma SQL over the same data.

Last verified: August 2026

Overview

What It Provides

Stripe is unusually complete as an analytical source because it stores the money movement and the lifecycle events that produced it. The core objects:

  • PaymentIntent — the modern payment lifecycle object. Tracks a payment attempt through requires_payment_method, requires_confirmation, requires_action, processing, succeeded or canceled.
  • Charge — the older object, still created underneath a PaymentIntent. Carries outcome, including the Radar assessment.
  • Subscription and SubscriptionSchedule — recurring state; the schedule holds planned future phases (price changes, trial ends, term commitments).
  • Invoice and InvoiceItem — what was billed, with line items, proration entries, discounts, and tax.
  • Dispute — chargebacks with reason codes and an evidence submission deadline.
  • Payout and BalanceTransaction — the bank-reconciliation layer: gross, fee, net, and the payout each transaction settled into.
  • Event — an append-only log of state changes, also the payload delivered to webhooks.
Authentication & Scopes
  • Secret API keys (sk_live_ / sk_test_) as HTTP Basic username. Test and live modes are entirely separate datasets.
  • Restricted keys (rk_live_) — per-resource read or write grants. This is what an analytics pipeline should use: read-only on the handful of resources it needs.
  • Stripe Connect — platforms act on connected accounts via the Stripe-Account header. Data is partitioned per connected account; there is no single query spanning all of them in the REST API.
  • OAuth for third-party apps operating on someone else's account.
Granularity

Individual transaction and individual state change. Amounts are integers in the currency's smallest unit — cents for USD, but yen are already whole units, so a blanket divide-by-100 is wrong for zero-decimal currencies. Every object has a metadata map you control, which is the join key back to your own domain model.

Key Endpoints
  • GET /v1/payment_intents, GET /v1/charges
  • GET /v1/subscriptions, GET /v1/subscription_schedules
  • GET /v1/invoices, GET /v1/invoices/:id/lines
  • GET /v1/disputes
  • GET /v1/balance_transactions, GET /v1/payouts
  • GET /v1/events — the change log
  • Sigma — scheduled SQL over Stripe-managed tables, no pagination required
Rate Limits

Stripe applies a per-account request-rate limit that is higher in live mode than in test mode, and separately throttles concurrent long-running requests. Rather than fixing a number, treat the mechanism as: read endpoints are generous for paginated backfill at moderate concurrency, list requests cap at 100 objects per page, and 429 responses are expected under burst and must be retried with exponential backoff and jitter. Deep expand[] chains cost more server work and are throttled sooner than flat requests.

For any backfill beyond a few hundred thousand objects, Sigma is the right tool, not the REST API. Paginating a year of balance_transactions at 100 per page is a rate-limit problem you have chosen to have.
Business Scenarios
  • Revenue recognition — invoice lines with period start/end are the only sound basis for MRR; summing successful charges conflates annual prepayment with monthly revenue.
  • Churn and expansion analysis — reconstructed from subscription events, not from the current subscription row.
  • Payment failure and recovery — decline codes on failed PaymentIntents, retry outcomes via Smart Retries.
  • Dispute and fraud-loss modelling — dispute rate by cohort, geography, card brand.
  • Bank reconciliation — balance_transactions grouped by payout is the only view that ties to the bank statement.
Key Restrictions & Gotchas
  • Radar scores are model output. outcome.risk_level and outcome.risk_score are Stripe's fraud model's estimates, with false positives and false negatives. A high-risk label is not evidence of fraud, and a low-risk label is not evidence of legitimacy. Using them as a target variable in your own model trains you to reproduce Stripe's errors; using them as a feature is defensible if you also record that they are correlated with Stripe's blocking decision, which censors your outcome data.
  • Radar scores are not returned on every account or every charge. risk_score availability depends on the Radar plan; do not assume the field exists.
  • Events are retained for a limited window (on the order of a month, not forever). The Events API is a catch-up mechanism for missed webhooks, not a permanent audit log. If you need the history, persist it yourself as it arrives.
  • Webhooks are at-least-once and unordered. Duplicates arrive; a customer.subscription.updated can land before the created for the same object. Deduplicate on event ID and reconcile against object state rather than trusting arrival order.
  • No revenue report endpoint. There is no GET /v1/mrr. The Dashboard's revenue figures are computed, and reproducing them requires re-implementing the same accounting rules.
  • Deleted customers lose most fields; the charges survive but the identity attached to them degrades.
  • Sigma is not real-time and its schema is versioned separately from the API. Queries can break across schema revisions.
  • Disputes move. A dispute's status changes over weeks. A snapshot taken today will disagree with one taken next month, so dispute rate is not a stable metric until the window has fully aged.
Payment data is mutable after the fact, and this is the single most common analytics mistake with it. A charge that succeeded today can be refunded next week, disputed next month, and charged back after that — network dispute windows run to months, not days. So revenue computed from a recent window is biased upward, not noisy: the deductions have not arrived yet. Formally this is right-censoring. Every cohort's net revenue only ever moves downward as it matures, so a recent period always outperforms a settled one for purely mechanical reasons.

The fix is not a better query. Either compare cohorts at equal age since transaction rather than at equal calendar label, or estimate the maturation curve from settled cohorts and discount young ones explicitly. Label anything inside the dispute window as provisional. A dashboard showing month-to-date net revenue beside closed months is comparing a partially observed period against fully observed ones, and will overstate the recent one every single time.

A Subscription object tells you the plan a customer is on right now. It does not tell you that they downgraded in March, churned in May, and were won back in July. That story exists only in the event stream and in subscription_schedule phases. Any churn analysis built from the current subscription table will systematically undercount both churn and recovery, because it can only see net position.
