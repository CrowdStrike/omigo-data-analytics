Fitbit Web API BACKLOG

Cloud REST API over activity, sleep, heart rate, HRV and body data synced from Fitbit trackers.

Last verified: August 2026

Overview

What It Provides

A server-to-server REST API over the Fitbit cloud. The tracker syncs to a phone, the phone syncs to Fitbit's servers, and your backend reads from those servers using a stored refresh token. There is no client app in the read path, which is the practical difference from an on-device store like HealthKit or Health Connect.

  • Activity: daily summaries, per-resource daily time series, logged exercises
  • Sleep: logs by date or date range, with per-stage segments where available
  • Cardio: heart rate zones and resting HR, nightly HRV, breathing rate, SpO2
  • Body: weight and fat logs, skin and core temperature
  • Devices: model, battery level, last sync timestamp

Every value returned is a processed quantity. The device computes steps from accelerometry, heart rate from optical PPG, and stages from a proprietary classifier. None of the inputs to those computations are exposed.

Authentication & Scopes

OAuth 2.0 Authorization Code Grant with PKCE, per end user. Access tokens are short-lived; refresh tokens rotate on use, so a stored refresh token must be written back atomically or the user's connection breaks. Scopes are coarse — one scope per data family, not per field.

Granularity
  • Default: daily aggregates for every family, plus 30-second stage segments inside a sleep log.
  • Intraday (1-second and 1-minute series) is not one of the scopes above. It requires a separate application to Fitbit and their approval, and is granted for personal or research use rather than general commercial redistribution.
  • HRV is a nightly aggregate computed over a sleep window, reported as dailyRmssd and deepRmssd. It is not a waking measure and not a continuous one.
  • SpO2 and breathing rate are likewise sleep-window estimates surfaced as daily averages; SpO2 also has a minute-level form under intraday access.
Intraday is an approval, not a scope — and the failure is silent. Your own developer account has intraday access to its own data, so code written and tested against your own account works. Point it at any other consented user without the approval and you get coarse data with no error raised. Anything that claims to measure short-lived events — a stress spike, an interval workout, a sleep-onset transition — is measuring something else entirely under default access.
Key Endpoints
  • GET /1/user/-/activities/date/{date}.json — daily activity summary
  • GET /1/user/-/activities/steps/date/{start}/{end}.json — daily time series per resource
  • GET /1.2/user/-/sleep/date/{start}/{end}.json — sleep logs with stage levels
  • GET /1/user/-/activities/heart/date/{date}/1d.json — HR zones and resting HR
  • GET /1/user/-/activities/heart/date/{date}/1d/1sec.json and .../1min.json — intraday HR (approval-gated)
  • GET /1/user/-/hrv/date/{start}/{end}.json — nightly RMSSD
  • GET /1/user/-/spo2/date/{date}.json, GET /1/user/-/br/date/{date}.json
  • GET /1/user/-/temp/skin/date/{date}.json and /temp/core/
  • GET /1/user/-/body/log/weight/date/...
  • GET /1/user/-/profile.json, GET /1/user/-/devices.json
  • POST /1/user/-/{collection}/apiSubscriptions/{id}.json — subscribe to change notifications for activities, sleep, body, foods

Subscriptions are webhooks in the delivery sense only. Fitbit posts a pointer — owner id, collection type, changed date — and carries no measurement payload. You then pull that date yourself. The notification is a change signal, not data delivery, and the pull still costs quota.

Rate Limits
  • 150 requests per hour per user for user-authorized endpoints, resetting at the top of the clock hour. Responses expose remaining-quota headers, and exhaustion returns HTTP 429 with Retry-After.
  • Quota is charged per request, not per day of data returned, so range endpoints are dramatically cheaper than day-at-a-time loops.
  • Because the cap is per user rather than per application, cohort size scales fine but any single user's historical backfill is throughput-bound. A multi-year backfill for one participant takes hours of wall-clock time regardless of how much infrastructure you have. This is exactly why the subscription design exists: fetch the changed date, not the whole history.
Business Scenarios
  • Research cohorts and trials — consented participants, server-side pull, no participant-facing app. The intraday approval route exists largely for this case.
  • Insurance and employer wellness — credits against step or sleep targets. Any incentive attached to a sensor-derived metric creates pressure to game the sensor.
  • Digital therapeutics adherence — passive activity and sleep as an engagement signal alongside in-app behaviour.
  • Sleep coaching — stage architecture and efficiency trends feeding a recommendation loop.
  • Corporate step challenges — leaderboards over daily summaries; friend graphs via social.

For all of these the analytically defensible unit is user-day with known wear-time, not user-day.

Key Restrictions & Gotchas
The sleep-log schema is not guaranteed per night. A log carries type: "stages" or type: "classic". Stages logs have levels.summary with deep/light/rem/wake, each with count, minutes and thirtyDayAvgMinutes. Classic logs — older devices, or nights where insufficient heart rate data was captured — contain only asleep/restless/awake and no stage breakdown at all. A parser that assumes the stages shape produces wrong nightly totals rather than an exception, and the shape can change mid-panel for the same user. Branch on type before touching levels. Separately, levels.data holds 30-second segments while levels.shortData holds brief wake episodes (typically under three minutes) reported separately — summing only levels.data silently discards them and inflates continuous sleep.
Heart rate zone minutes are a threshold model, not a measurement. Out of Range / Fat Burn / Cardio / Peak boundaries are derived from an estimated maximum heart rate — an age-based formula — unless the user has set custom zones. So "minutes in Cardio zone" is the convolution of a measured HR series with a vendor default that has wide individual error and that the user can silently override. Two users with identical HR traces can report different zone minutes; one user can shift zone minutes on their birthday. Use the HR series where you have it, and treat zone minutes as a vendor construct.
Composite scores are model output, not measurement. Fitbit's Sleep Score and similar composites are proprietary algorithms that change between firmware and app releases. A level shift in a long score series can reflect a software update rather than anything physiological, so a score is a poor dependent variable across long windows without version controls. Prefer the components — stage durations, resting HR, RMSSD — which are far more stable across releases.
  • Never available: raw PPG waveform, raw accelerometer samples, beat-to-beat R-R interval series, other users' data, population aggregates. Nightly RMSSD is therefore not comparable to a chest-strap R-R series or a lab HRV measurement — same label, different measurement.
  • Approval-gated: all intraday second- and minute-level series.
  • Data exists only after sync. "Today" is always partial and yesterday can arrive days late. Re-read a trailing window; never treat a day as final on first read.
  • Battery and last-sync from /devices.json are the only fields that distinguish "slept badly" from "was on the charger". Non-wear correlates with exactly the disrupted nights you care about, so it is informative missingness and complete-case averages overstate.
  • Timezone is a per-user profile setting and sleep straddles midnight. dateOfSleep is the wake date, not the bed date.
  • Platform continuity is not assumable. Fitbit accounts have been migrating to Google accounts and several consumer surfaces have been retired over time. Treat long historical continuity of any given field as something to verify, not assume.
