Evolution of System Architectures

Where the computation happens, and where the state lives — a pendulum that has swung between centralised and distributed four times.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
1995 – 2010s
The browser as the client
Three-tier: web, application, database
Separating presentation, business logic and storage let each tier scale independently, and putting the interface in a browser eliminated client installation entirely. This was the dominant enterprise pattern for well over a decade and is still perfectly adequate for a great many systems.
2001 onward
One machine pretends to be many
VMware, hypervisors, then containers
Virtualisation decoupled the operating system from the hardware, making machines allocatable in minutes rather than procured in months. Containers later did the same for the application, packaging dependencies so the same image ran identically everywhere — the precondition for everything after.
2006 onward
Infrastructure as a rented API
AWS EC2/S3, elastic capacity
Compute and storage became on-demand services, converting capital expenditure into operating expenditure and removing capacity planning as a gate on starting anything. Provisioning a hundred machines for an hour became a normal thing to do.
2013 onward
Small services, orchestrated
Docker, Kubernetes, service mesh, gRPC
Systems decomposed into independently deployable services with their own datastores, coordinated by an orchestrator that handled placement, scaling and restarts. Teams gained autonomy; the cost was that a single request now crossed many network boundaries, and understanding system behaviour required distributed tracing.
2015 onward
No server to think about
Lambda, managed databases, platform services
Execution became per-request with capacity managed by the provider, and databases, queues and search became services rather than software to operate. The operational burden fell substantially, and portability fell with it — architecture became coupled to a specific vendor's primitives.
2017 onward
Pushing outward again, and specialised compute
Edge functions, CDN logic, GPU clusters
Latency-sensitive work moved to points of presence near users, partially reversing the centralising trend. Simultaneously, model training concentrated in the opposite direction: tightly coupled GPU clusters with high-bandwidth interconnects, which is closer to supercomputing than to distributed web architecture.
1960s – 1980s
Everything in one machine
Mainframes, time-sharing, terminals
Computation and data lived in a single central system; terminals only displayed output and captured keystrokes. Expensive and inflexible, but with properties later architectures had to rediscover: one place to secure, one place to back up, and no state anywhere else.
1980s – 1990s
Intelligence moves to the deskgone
PCs, LAN file shares, fat clients
Cheap workstations pulled processing outward. Applications installed on each machine talked to a shared database, which distributed capability and created the deployment problem — every upgrade meant touching every desk, and versions drifted apart.
2000s
Buses and shared middlewaregone
SOA, enterprise service bus, message brokers
Integration was centralised into a bus that routed and transformed messages between systems. In practice the bus became both a bottleneck and a single point of failure, and the coordination cost of changing a shared contract slowed everything that touched it.

What Disappeared

Ended as mainstream practice:
  • Fat clients installed on every desktop — the deployment and version-drift problem the browser eliminated
  • The enterprise service bus — centralised integration middleware, abandoned as a bottleneck
  • Physical server procurement per project — lead times measured in months as a normal constraint on starting work
  • The application server as a deployment target — deploying an archive into a long-running container
  • Manual capacity planning for peak load — buying for the busiest hour of the year and idling the rest of the time
  • Pets rather than cattle — individually named, hand-configured, irreplaceable servers
Alive, but only in niches:
  • Mainframes — still processing a large share of financial transactions, with reliability characteristics that are hard to reproduce
  • Three-tier monoliths — entirely appropriate for most applications, and several teams have moved back to them from microservices
  • On-premise data centres — retained where data residency, regulation or sustained heavy load makes cloud economics unfavourable
  • Thin clients — the model returned in a new form as browser-based applications and virtual desktops
