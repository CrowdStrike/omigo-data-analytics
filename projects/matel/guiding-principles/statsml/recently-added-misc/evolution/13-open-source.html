Evolution of Open Source & Shared Resources

From sharing code by default, to a licensing movement, to foundations and platforms that hold the industry's shared code, data, models and benchmarks.

Dates are approximate and mark mainstream adoption rather than first release. Bars in red ended as mainstream practice; orange survives in specific niches only.

The Eras

EraWhat changed
1983 onward
Freedom asserted through licensing
GNU project, GPL, copyleft
The GNU project set out to build a complete free operating system, and its licence introduced copyleft: derivative works must carry the same terms. This was a legal mechanism rather than a technical one, using copyright law to compel openness downstream, and it is arguably the single most consequential idea in the movement's history.
1988 onward
Permissive licensing as the alternative
BSD, MIT, Apache 2.0
A parallel tradition allowed use in proprietary products without requiring the result be shared. The practical consequence became clear over time: permissive licences saw far wider corporate adoption precisely because they imposed no obligation, and most widely-used libraries today carry them rather than copyleft terms.
1991 onward
A kernel arrives, and the collaboration model with it
Linux, distributed contribution, mailing lists
The missing kernel appeared from an unrelated project and combined with the GNU tools into a complete system. What proved as significant as the software was the demonstration that a large, complex, reliable artefact could be produced by geographically dispersed volunteers with no employment relationship — a claim widely doubted at the time.
1999 onward
Foundations as neutral custodians
Apache Software Foundation, later Linux Foundation, CNCF
Vendor-neutral non-profits took ownership of projects, holding trademarks and copyrights so no single company controlled them. Apache's contribution was as much organisational as technical — a governance model of meritocratic committees, mandatory public discussion and a defined path from contributor to committer, reproducible across hundreds of projects. This is what allowed competing companies to collaborate on shared infrastructure: Hadoop, Kafka, Spark, Cassandra and much more sit under that umbrella, and Kubernetes under the CNCF.
1999 – 2010s
Hosting, then social coding
SourceForge, then GitHub and GitLab
Centralised hosting made projects discoverable and downloadable at a time when both were obstacles. GitHub then combined distributed version control with a social layer — forks, pull requests, visible profiles — which reduced the cost of a first contribution to a few clicks and changed contribution from a request for permission into a routine mechanical act.
2002 onward
Selling support rather than licences
Red Hat Enterprise Linux, subscriptions, dual licensing
A commercial model formed around free software: charge for support, certification, long-term maintenance and indemnity rather than for the code. This made open source procurable by risk-averse enterprises that needed a contract and an accountable vendor, and it is what moved Linux into regulated industries.
2008 onward
Companies become the main contributors
Corporate-employed maintainers, strategic open sourcing
Large technology firms became the largest contributors to major projects, and releasing infrastructure openly became a deliberate strategy — commoditising a competitor's advantage, attracting talent, establishing a standard. Most work on major projects is now done by paid employees, which is a substantial change from the volunteer model, with different incentives and different failure modes.
2009 onward
Sharing extends beyond code
ImageNet, open datasets, Kaggle, Papers with Code, arXiv preprints
The open-source model was applied to things that are not source code. Public labelled datasets became shared research infrastructure — ImageNet mattered as much for the dataset and its benchmark as for any algorithm, since a common evaluation let competing methods be compared directly. Kaggle then made method shareable: competitions with a fixed dataset and metric, where strong approaches were published as runnable notebooks, compressing the spread of a new technique from a conference cycle to days. Preprint servers did the same for papers, decoupling publication from journal timelines.
2018 onward
Model hubs as shared infrastructure
Hugging Face, model and dataset registries
Trained weights became distributable artefacts with the conventions needed to use them: a standard library interface, versioned repositories, model cards stating intended use and limitations, and hosted datasets alongside. This matters because training a large model from scratch is beyond most budgets, so a hub of pretrained starting points is what lets small teams work at all — a package registry for capability rather than code. It also concentrates much of the field's practical infrastructure in one commercial platform, which is the same dependence question SourceForge and GitHub each raised in their turn.
2018 onward
Cloud tension, security scrutiny, and open weights
Source-available licences, supply-chain initiatives, model releases
Cloud providers offering managed versions of open-source databases without contributing back prompted several projects to adopt licences restricting that use — commonly called source-available, and not open source by the standard definition. In parallel, incidents involving widely-depended-upon and thinly-maintained components moved attention to supply-chain security, dependency provenance and the sustainability of unpaid maintenance. Most recently, downloadable model weights created a parallel ecosystem, though the terminology deserves care: released weights usually come without training data and often under licences with usage restrictions, so they are not open source in the sense the rest of this page describes.
1960s – 1970s
Code circulated because it had togone
Academic and lab software, user groups
Software was shared informally among researchers and customers, often distributed with the source because the hardware vendor made the money and the software was an accessory to it. This was not a philosophical position, it was a practical default — which is what made its removal a shock rather than a continuation.
Late 1970s – 1980s
Software becomes a licensed product
Binary-only distribution, restrictive licences
As software separated from hardware commercially, source code became a trade secret and users received binaries under terms restricting copying and modification. This is the change that prompted an organised response rather than the other way round.

What Disappeared

Ended as mainstream practice:
  • Software shipped with source as a matter of course — the pre-licensing default, ended by software becoming a product
  • SourceForge as the centre of open source — the dominant hosting platform, lost to GitHub after bundling adware into downloads
  • "Open source is not enterprise-ready" — a standard procurement objection through the 1990s, now hard to state seriously
  • The purely volunteer major project — still exists, but most significant infrastructure is now maintained by paid employees
  • Shipping physical distribution media — Linux distributed on CDs by post and on magazine covers
  • Publishing a method without runnable code — once normal in research papers, now often treated as insufficient
  • Free software versus open source as a live schism — the terminological dispute has largely faded from practice
Alive, but only in niches:
  • Copyleft licences — still central to Linux and much system software, but permissive terms dominate new libraries
  • Community distributions — Debian and others continue as volunteer-governed alternatives to commercial offerings
  • Mailing-list development — the Linux kernel still works this way, having declined to move to a hosting platform's workflow
  • Self-hosted forges — a deliberate choice for projects avoiding dependence on a single commercial platform
