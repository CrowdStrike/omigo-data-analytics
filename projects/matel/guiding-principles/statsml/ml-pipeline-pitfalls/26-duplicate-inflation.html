Pitfall: Duplicate Inflation in ETL

ETL joins or retry logic create duplicate rows that inflate counts and skew statistical analysis

The Problem

Many-to-many joins create fanout, retry logic generates multiple records for the same event, or window functions duplicate rows. Aggregations count duplicates multiple times, making metrics like conversion rate or average value incorrect.

  • User joins session joins event creates M × N × P fanout
  • Kafka retry logic writes duplicate messages with same event_id
  • Window function over partitions duplicates base rows
  • Incremental append without deduplication accumulates duplicates
Impact: Counts are inflated by 2x-10x. Averages are biased if duplicates aren't random. Downstream models trained on inflated counts learn wrong distributions. Fix: Add explicit deduplication step after joins and before aggregation.

Example: A conversion funnel joins users × sessions × events. For 100 users with 3 sessions and 10 events each, naive join produces 3,000 rows instead of 100 users. Conversion rate appears 30x higher than reality.

Why It Happens / Detection / Common Sources

SQL joins default to Cartesian product behavior. Retry logic prioritizes delivery over idempotency. Teams forget that join fanout requires explicit deduplication before counting.

  • Many-to-many joins without awareness of fanout consequences
  • At-least-once delivery semantics in event streams (Kafka, SQS)
  • Multiple systems writing to same table without unique constraints
  • Window functions used before understanding their duplication behavior
Detection: Compare count(*) vs count(distinct primary_key). If ratio > 1.0, you have duplicates. Profile join cardinality: for A JOIN B, check if |A × B| > |A| + |B| by orders of magnitude. Track row count deltas across pipeline stages.

Example: An ad pipeline joins impressions × clicks × conversions. Impressions table has 1M rows, clicks 10K, conversions 500. Naive join yields 5B rows (fanout of 5000x). Correct result should be 500 attributed conversions.

Prevention / Correct Approach

Add explicit deduplication after every join and before every aggregation. Use distinct or group by on primary key. Profile join cardinality to catch unexpected fanout.

  • After every join: SELECT DISTINCT ON (primary_key) to collapse fanout
  • Before aggregation: GROUP BY primary_key, then aggregate
  • Use LEFT JOIN instead of INNER JOIN when possible to avoid fanout
  • Add unique constraints or row_number() = 1 filters in window functions
Best practice: Profile every join: log input cardinality |A|, |B| and output |A JOIN B|. Alert if output > max(|A|, |B|) × expected_multiplier. Always include count(*) vs count(distinct id) in pipeline metrics dashboard.

Example: Instead of SELECT COUNT(*) FROM users JOIN sessions JOIN events, use SELECT COUNT(DISTINCT user_id) FROM (deduplicated result). Or pre-aggregate: count events per session, then sessions per user.
