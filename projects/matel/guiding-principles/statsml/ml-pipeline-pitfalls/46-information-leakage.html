Pitfall: Information Leakage (Comprehensive)

Umbrella category for any information crossing a boundary it shouldn't—temporal, train-test, or entity.

The Problem

Information that wouldn't be available at prediction time leaks into training, inflating offline metrics while guaranteeing production failure. Includes future data, test set signals, or cross-entity contamination. The model learns shortcuts that don't exist in reality.

  • Temporal boundaries: Feature uses data from after the prediction timestamp—e.g., "user churned 30 days later" as feature when predicting churn; model sees the answer
  • Train-test boundaries: Normalization or imputation computed on full dataset including test set, leaking test distribution into training preprocessing
  • Entity boundaries: User-level features include aggregates from other users in same test batch, leaking cross-user signals that won't be available for isolated predictions
  • Target encoding leakage: Categorical feature encoded with target mean computed on full dataset, directly embedding label information into feature
Impact: Artificially perfect offline metrics (AUC > 0.99) collapse to random performance (AUC ~ 0.5) in production. Model has memorized patterns that don't generalize because they violate causality. Fix: Enforce strict temporal ordering—features use only data from before prediction time. Compute preprocessing statistics only on training set. Isolate entity-level computations. Simulate production data availability during training.

Example: Predicting loan default. Feature "account_closed_within_90_days" computed from future data (loans approved today, account status checked 90 days later). Training AUC = 0.97; production AUC = 0.52. Model learned that closed accounts default (true) but can't predict closures in advance (leakage).

Why It Happens

Information leakage is an umbrella term covering many distinct failure modes. Each has different mechanics but the same symptom: unrealistically good offline metrics.

  • Temporal leakage: Using future data to predict past events—features computed from data that didn't exist at prediction time
  • Split leakage: Same entity appears in train and test (grouped data not split by group)—e.g., multiple visits from one patient in both sets
  • Deployment leakage: Features available offline but not at prediction time—batch-computed fields unavailable in real-time serving
  • Label leakage: Target variable encoded into features (e.g., "cancelled_reason" predicting churn)—direct or indirect label exposure
  • Population leakage: Training population differs from deployment population—selection bias in who enters the dataset
  • Knowledge leakage: Domain knowledge about label inadvertently encoded during feature engineering
Root cause: Leakage is an umbrella term covering many distinct failure modes. Each has different mechanics but the same symptom: unrealistically good offline metrics. Recognizing which type you have determines the fix.

Example: A hospital readmission model uses "discharge_summary_text" which contains phrases like "patient likely to return." The model achieves 98% AUC offline but the field isn't populated until after the readmission decision is made.

The Correct Approach

The universal test for leakage: "Is this feature available at prediction time?" Every feature must pass this test before inclusion in the training pipeline.

  • Feature availability audit: Apply the universal test—"Is this feature available at prediction time?"
  • Feature parity: Ensure feature parity between training and serving environments—no offline-only features
  • Entity-aware splits: Split by entity (patient, user, session) not by row—all rows from one entity stay together
  • Time-based splits: For temporal data, train on past, validate on future—never shuffle time series
  • Feature registry: Document when each feature becomes available relative to prediction time
Best practice: For every feature, document when it becomes available relative to prediction time. Build a feature availability timeline. Any feature filled after the prediction moment is leakage.

Example: Feature registry has columns: feature_name, available_at (e.g., "T-0", "T+1h", "T+1d"). Training pipeline automatically excludes any feature where available_at > prediction_time.
