Pitfall: Silent Join Fanout (Row Multiplication)

When a many-to-many join silently multiplies rows, inflating counts, metrics, and statistical results without warning.

The Problem

A join between two tables produces more output rows than input rows because both sides have duplicate keys. The query succeeds without error, but every metric downstream is inflated by the fanout factor.

  • Occurs when: Joining users to events, orders to items, features to labels without proper cardinality checks
  • Silent: SQL returns results; no warning that 1,000 users became 10,000 rows
  • Cascades: Aggregations (COUNT, SUM, AVG) all become wrong; joins downstream multiply again
Impact: 10x inflated conversion rates, training data with duplicated labels, models that see the same example weighted 5x. Detection: assert row counts before/after joins; use INNER JOIN DISTINCT or window functions to deduplicate.

Example: User table (1,000 users) joined to events table (each user has 5 events) without aggregation yields 5,000 rows. A COUNT DISTINCT users still works, but COUNT(*) or AVG(revenue) is now 5x inflated.

Why It Happens

  • 1-to-many joins without pre-aggregation: Joining directly to a detail table without rolling it up first
  • No row count assertions before/after joins: Pipeline code never checks if output rows exceed input rows
  • Assumption that join keys are unique on both sides: No DISTINCT or cardinality check on the key column
  • Multiple tables at different granularities: Mixing user-level and user-event-level tables without explicit grain documentation
Root cause: The database does exactly what you asked — it matches every row on the left to every matching row on the right. It has no concept of "expected" output size.

The Correct Approach

  • COUNT DISTINCT before/after join: Verify row count stability — if users in = users out, no fanout occurred
  • Aggregate the many-side first: GROUP BY user_id on the events table before joining to users
  • Assert expected cardinality in pipeline code: assert len(df_joined) == len(df_users)
  • Use window functions instead of joins: Compute per-user aggregates with OVER(PARTITION BY user_id) to avoid row multiplication
Rule: Every join should have a documented expected grain and an assertion that verifies it. If the output grain differs from the input grain, the join is wrong or undocumented.
