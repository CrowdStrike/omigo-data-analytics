Pitfall: Wrong Missing Data Assumptions

Treating all missing data the same when 'why it's missing' matters.

The Problem

You apply a blanket missing data strategy—mean imputation, median fill, forward fill—without considering why the data is missing. But missingness is often informative. The fact that a value is absent IS the signal, and imputing it destroys predictive power.

  • Medical test not ordered = patient not sick enough to warrant it (healthier)
  • Income field blank = applicant unemployed or hiding something (riskier)
  • Product review missing = customer didn't engage enough to review (less loyal)
  • Sensor reading NULL = equipment failure or abnormal condition (critical event)
Impact: Missing data carries information about the target. Imputing with mean/median/mode replaces this signal with noise. The model loses predictive power because you've told it "missing = average" when missing actually means "high risk" or "unusual condition."

Example: Loan default model. "Second income" is missing for 30% of applicants. These have 2.4x higher default rate. You impute with median income. Model now sees everyone as dual-income. Default signal destroyed.

Why It Happens

Most ML tutorials and libraries treat missing data as a technical nuisance to be "fixed" before modeling. But missing data has three distinct mechanisms, each requiring different treatment.

  • MCAR (Missing Completely At Random): Missingness is unrelated to anything. Rare in real data. Safe to impute.
  • MAR (Missing At Random): Missingness depends on observed variables. Can model and impute if you understand the mechanism.
  • MNAR (Missing Not At Random): Missingness depends on the unobserved value itself. Cannot be safely imputed. Missingness IS the feature.
Mechanism: You assume MCAR and impute. Reality is MNAR. Patients with missing cholesterol tests are healthier (test not needed). You impute population median. Now model thinks they have average cholesterol when absence signals low risk.

Example: E-commerce. "Time on product page" is NULL for 15% of users. These are drive-by visitors (very low conversion). Impute with mean time. Model now sees them as engaged users. Conversion predictions completely wrong.

Detection & Mitigation

Before imputing, test whether missingness is informative. Create an indicator variable. Compare target rates. Only impute if missingness is truly uninformative.

  • For each feature with missing data, create "feature_is_missing" binary indicator
  • Compare target rate for missing vs. non-missing groups. If difference > 10%, missingness is informative.
  • Add the indicator as a feature. Let the model learn that "missing" is distinct from any imputed value.
  • If missingness is informative, consider NOT imputing. Use models that handle missing natively (XGBoost, LightGBM).
  • If you must impute, use sophisticated methods: model-based imputation, multiple imputation, or domain-specific rules.
Fix: Test if missingness predicts the target. If it does, create a "missing" indicator and either don't impute (use tree models) or impute + keep indicator so the model knows this value was fabricated.

Example: "Previous purchase amount" missing for 40% (new customers). Default rate: 8% for existing, 18% for new. Create "is_new_customer" binary. Keep it as feature. Model learns new customers are riskier. Accuracy improves 7%.
