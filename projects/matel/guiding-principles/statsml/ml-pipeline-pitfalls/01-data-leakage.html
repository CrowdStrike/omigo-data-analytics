Pitfall: Data Leakage (Future Info in Training)

Model uses information not available at prediction time

The Problem

Your model achieves near-perfect accuracy in training and testing but collapses in production. The gap reveals that training data included information that would not be available at prediction time.

  • Feature computed from future events leaks into training (e.g., "total_purchases_lifetime" when predicting churn at day 30)
  • Model gets 99% accuracy in training, 55% in production — the gap IS the leakage
  • Subtle forms: aggregates computed over full time range, features derived from other rows (global mean), join keys that shouldn't exist yet

Example: Predicting hospital readmission using "discharge diagnosis code" — but that code was assigned AFTER the outcome was known. At prediction time (admission), you don't have it.

Defense: For every feature, ask: "would I have this value at the moment I need to make the prediction?" If no → remove it.

Why It Happens

Features are computed without timestamp discipline. Aggregates are calculated over the full time range instead of being restricted to data available before the prediction point. Join operations pull in records from the future because no temporal filter is applied.

  • Features computed without timestamp discipline — aggregates span full time range
  • No "available at prediction time?" audit during feature engineering
  • Join keys pull future records because no temporal filter is applied
  • Convenient but deadly: computing rolling stats using pandas without explicit cutoff dates

Example: "avg_spending_30d" computed as average over the entire dataset including future months. At prediction time (Jan 1), the feature includes spending from Feb-Dec. Nobody noticed because the code runs correctly — it just answers the wrong question.

Root Cause: The feature engineering pipeline treats all data as a single static snapshot. There is no concept of "when this row was created" baked into the computation graph.

The Correct Approach

For every feature, apply the "available at prediction time?" test. Implement temporal feature auditing: each feature computation must take a cutoff timestamp parameter. No feature should access any row with timestamp > cutoff.

  • Temporal feature audit: every feature computation takes a cutoff timestamp parameter
  • "Available at prediction time?" test applied to every single feature before model training
  • Use point-in-time joins: filter all joined tables to records existing before the prediction timestamp
  • Automate: build a feature registry that enforces temporal constraints at computation time
  • Validate: compare feature distributions at different time cutoffs — sudden jumps indicate leakage

Example: Correct "avg_spending_30d" for a Jan 1 prediction uses only Dec data (30 days back from prediction point). The feature store query: SELECT AVG(amount) FROM transactions WHERE user_id=X AND txn_date BETWEEN '2023-12-01' AND '2023-12-31'.

Fix: Build a point-in-time feature store. Each feature is computed with an explicit timestamp boundary. The system physically cannot access future data because the query enforces WHERE event_time < prediction_time.
