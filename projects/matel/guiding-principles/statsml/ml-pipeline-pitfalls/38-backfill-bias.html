Pitfall: Backfill Bias (Data Filled Retroactively)

When historical data is corrected or enriched with information that was not available at the time, creating unrealistic training data.

The Problem

A data backfill operation updates historical records with information learned in the future. The updated records are used for training, but production sees the original noisy data without the corrections.

  • Corrections: Missing geocodes filled in 2024 for 2022 addresses, but geocoding service had 30% failure rate in 2022
  • Schema changes: New field "customer_segment" backfilled to 2020 using 2024 segmentation logic; logic didn't exist in 2020
  • Enrichments: Third-party vendor data appended retroactively; coverage and accuracy differ from real-time
Impact: Model trained on clean backfilled data achieves 90% AUC, but production data has 20% missing values and drops to 75%. Training-serving skew is structural. Solution: Use point-in-time snapshots; never train on backfilled data unless production pipeline will have identical backfill.

Example: Training a credit model on 2020-2022 data. In 2023, a bug-fix updates all 2020 income fields that were NULL to correct values from a recovered database. Model trains on this corrected data but production sees 15% NULL incomes (same rate as original 2020). Feature importance and imputation strategy are now misaligned.

Why It Happens

  • Data revisions and retroactive corrections applied to historical records
  • Using "final revised" data for training instead of "preliminary as-published" data
  • Bug fixes that update old records with information unavailable at the time
  • Schema migrations that backfill new columns using current (not historical) logic
Root cause: The database looks like a single clean table, but it has been silently improved over time. The current snapshot does not represent what the data looked like when it was first collected.

The Correct Approach

  • Use point-in-time queries: query data as it existed on the prediction date
  • Store data snapshots (e.g., daily table partitions, slowly changing dimensions)
  • "As-of" data access patterns: get_features(entity_id, as_of_date)
  • Never train on data that was corrected after the prediction window
Principle: Training data must reflect the same data quality and completeness that the model will encounter in production.
