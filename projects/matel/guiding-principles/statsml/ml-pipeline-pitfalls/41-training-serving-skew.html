Pitfall: Batch vs Online Feature Mismatch (Training-Serving Skew)

Features computed differently in batch training vs real-time serving create systematic prediction errors.

The Problem

Training uses batch-computed features with one aggregation window, but serving recomputes them in real-time with different logic or time boundaries. The model learns patterns from the batch version that don't hold in production.

  • Time aggregation windows: Training uses "last 30 days" computed at midnight; serving uses "last 30 days" from request timestamp, creating boundary mismatches
  • Feature computation logic: Training runs SQL with full table scans; serving uses cached lookups or approximate streaming aggregates that drift from exact values
  • Data freshness: Training features reflect complete, backfilled data; serving features use whatever arrived by request time, missing late events
  • Timezone and rounding: Batch jobs run in UTC with date truncation; serving uses local timezone or millisecond precision, shifting boundaries
Impact: Model degrades in production despite good offline metrics. Features that were predictive in training are systematically different at serving time. Fix: Use identical feature computation logic in training and serving—same code, same libraries, same time boundaries. Log actual serving features and compare distributions against training features.

Example: A model trained on "user activity in last 7 days" (computed at midnight) sees values like 15, 23, 8 during training. At serving time, the same feature is computed from request timestamp (e.g., 3:42 PM), producing values like 12, 19, 6—systematically lower because fewer complete days. Accuracy drops 8% in production.

Why It Happens

  • Different code paths: Batch training uses SQL/Spark; streaming serving uses Flink/Redis — different implementations of "the same" logic
  • Time boundary mismatch: Training computes features at midnight with complete data; serving computes mid-day with partial data
  • Library version drift: Training environment pins library v2.1; serving container upgraded to v2.3 with subtle behavioral changes
  • Timezone handling: Batch jobs truncate to UTC date; real-time systems use local timezone or raw timestamps
Root cause: Training and serving are built by different teams, at different times, with different priorities (throughput vs latency). The "same feature" is actually two implementations that happen to share a name.

The Correct Approach

  • Unified feature pipeline: Same code computes features for both training AND serving — one implementation, two execution modes
  • Log and compare: Log actual online features at serving time; compare with batch-computed versions to detect drift
  • Distribution monitoring: Compare training vs serving feature distributions daily; alert on KL-divergence spikes
  • Feature store consistency: Use a feature store that guarantees identical values across batch and online retrieval
Principle: One definition, one computation, verified daily. If training and serving can't share code, they must share validation.
