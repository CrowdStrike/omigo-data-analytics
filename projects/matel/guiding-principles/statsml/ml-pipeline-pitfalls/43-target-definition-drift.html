Pitfall: Target Definition Drift

What "positive" means changes over time, invalidating the label and model objective.

The Problem

Business rules or product requirements evolve, silently redefining what constitutes a positive outcome. Historical training data uses the old definition; production evaluates the new one, creating a fundamental mismatch between learned objective and actual objective.

  • Business rule changes: "Purchase" originally meant any completed transaction; now excludes refunded orders within 7 days—training labels don't reflect this
  • Label definition evolution: Fraud definition expands to include new attack vectors, but historical negative class doesn't contain these patterns
  • Consistency across time: Six months of training data uses three different versions of "churn" definition due to incremental product changes—model learns a blurred concept
  • Documentation lag: Code defines the label, but specification doc is outdated; no one knows which definition is authoritative
Impact: Model optimizes for the wrong objective. Offline metrics look fine (measured against old definition), but business metrics degrade (measured against new definition). Fix: Version target definitions explicitly. Backfill historical labels when definition changes or segment training data by definition version. Document every label change with effective date and relabel policy.

Example: "High-value customer" defined as >$500 annual spend in 2024 data. Definition changes to >$800 in Q2 2025. Model trained on mixed data learns confused boundary, predicting "high-value" for $600 customers. Targeting campaign wastes 40% of budget on misclassified users.

Why It Happens

Target definition drift is fundamentally an organizational problem. The business evolves continuously, but the ML pipeline is treated as a static artifact that only needs retraining on "more data."

  • Business evolves silently: Label criteria change without model retraining—stakeholders assume the model adapts automatically
  • Product teams update success criteria: New KPIs or thresholds are adopted without informing the ML team
  • Definition changes buried in ETL: A SQL WHERE clause changes what counts as "converted"—no documentation, no alert
  • Multiple teams, multiple definitions: Marketing, product, and finance each define "active user" differently—model trains on one, evaluates on another
Root cause: No formal coupling between business definition changes and model lifecycle. The label is not treated as a versioned artifact—it lives implicitly in code, not explicitly in a contract.

Example: Marketing redefines "engaged user" from 3 logins/week to 5 actions/week. ETL updates. Model keeps predicting the old concept. Engagement scores diverge from actual business metric by 30% before anyone notices.

The Correct Approach

Treat the target definition as a first-class versioned artifact. Gate every retraining on definition consistency and never mix definition versions in a single training set.

  • Version definitions explicitly: Use semantic versioning (target_def_v1, v2, v3) with effective dates and changelogs
  • Retrain from scratch on definition change: No incremental training on mixed labels—the concept itself changed
  • Backfill labels before retraining: Apply new definition to historical data, or exclude pre-change data entirely
  • Document every change: Effective date, rationale, impact on label distribution, relabel policy
Best practice: Treat label definition as a first-class artifact. Version it, gate retraining on it, and never mix definition versions in a single training set. The pipeline should fail loudly if definition version mismatches are detected.

Example: Team uses target_def_v3.yaml with effective_date=2025-06-01. Training pipeline rejects data before that date unless relabeled under v3 rules. Model registry tags every model with its definition version.
