Pitfall: Positive-Only Data Collection (No Negative Class Design)

Pipeline collects rich positives but has no negative class strategy, crippling model training.

The Problem

Data collection focuses on positive outcomes (conversions, clicks, purchases) with full feature instrumentation. Negative class is afterthought—unlabeled, incomplete features, or sampled haphazardly. Model can't learn decision boundary because negative class is undefined or unrepresentative.

  • Negative sampling strategy: No principled approach—use "everything else" as negatives, creating massive imbalance and class definition incoherence (negatives include irrelevant cases, missing data, early exits)
  • Class design: Positive class well-defined ("completed checkout"), negative class vague ("didn't complete checkout" includes: never saw product, added to cart then left, payment failed, bot traffic—semantically different)
  • Feature completeness: Positive examples have full feature vectors; negatives missing features because tracking only fires on positive path (e.g., "checkout_started" feature only exists for converters)
  • Retrospective labeling: Collecting positives prospectively (as they happen) but negatives retrospectively (querying who didn't convert), introducing temporal misalignment and survivorship bias
Impact: Model learns to classify "has complete data" vs "has incomplete data," not true positive vs negative. Decision boundary is artifact of data collection, not meaningful pattern. Serving data doesn't match training negative distribution. Fix: Design negative class first—define what "true negative" means, not just "not positive." Sample negatives deliberately (time-matched, feature-complete). Instrument negative paths with same rigor as positive paths.

Example: Recommendation click prediction. Positive: user clicked item (logged with full context—item features, user history, session data). Negative: "random sample of not-clicked items" with no session context, no view logging, missing features. Model achieves 95% accuracy by predicting "has session data = positive," "missing session data = negative." Production accuracy 58%—all served examples have full features.

Why It Happens

Data collection follows intervention: you only record what happened, not what didn't happen. Negative cases equal nothing happened, which equals nothing was recorded.

  • Event-driven logging: Systems log actions (clicks, purchases, complaints) but not non-actions
  • Survivorship bias: Only successful cases reach the data warehouse
  • No non-event signal: Negative cases generate no events, so they leave no trace in event-driven systems
  • Selection by prior system: Historical gatekeeping (previous model, human review) filters who enters the observable population
Root cause: Most data systems are event-driven—they record occurrences. Non-occurrences don't generate events. If your positive class IS the event, you have no natural negative class.

Example: A loan default model trained on approved loans only. All data points are people who received loans. The model never sees "would have defaulted if approved"—the rejected applicants who were denied by the previous system.

The Correct Approach

Design the negative class BEFORE modeling—define what constitutes a true negative. Use the "eligible population" concept: who could have been positive but wasn't?

  • Define inclusion criteria: Explicitly specify what constitutes a true negative
  • Eligible population: Identify who could have been positive but wasn't
  • Reject inference: Consider propensity weighting for historical selection bias
  • Excluded class: Separate "unknown outcome" from "true negative"—rejected applicants are neither positive nor negative
Best practice: Before collecting data, define both classes. Positive = event occurred. Negative = event could have occurred (eligible) but didn't. If you can't define eligibility, you can't build a valid classifier.

Example: For loan default: eligible population = all applicants. Positive = approved AND defaulted. Negative = approved AND did NOT default. Excluded = rejected (unknown outcome). This gives a clean binary problem on the observable population.
