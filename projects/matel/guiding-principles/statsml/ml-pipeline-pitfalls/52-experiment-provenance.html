Pitfall: Experiment Provenance Ignored (A/B Test Data Mixed Into Training)

Training data pools A/B test variants without tracking provenance, confounding learned patterns.

The Problem

Training data spans period with active A/B tests that alter features, labels, or user experience. Data from multiple experiment arms pooled without tagging provenance, mixing samples where ground truth or feature semantics differ due to experimental manipulation.

  • Confounding effects: Treatment arm shows 20% higher conversion; model trained on pooled data learns spurious correlation between "users who happened to be in treatment" and conversion, not true causal features
  • Experiment tracking: No experiment_id or variant column logged; impossible to separate organic behavior from experimentally induced behavior in training data
  • Data lineage: Experiment ended, logs archived without experiment metadata; six months later, retraining includes experiment period—no way to filter or stratify by experiment arm
  • Feature meaning shifts: Experiment changes "relevance_score" computation; data from control uses old formula, treatment uses new formula, both populate same column—model sees bimodal distribution, learns incoherent patterns
Impact: Model learns from heterogeneous data distributions created by experiments, not stable production patterns. Predictions degrade post-experiment when all users experience single variant. Simpson's paradox: pooled data shows opposite trend from within-experiment trend. Fix: Log experiment_id and variant with every data point. Filter training data to single experiment arm or control-only. Analyze experiment effects on features and labels before pooling. Use experiment-aware training (explicit variant features or stratified models).

Example: Ranking model trained during pricing experiment (50% users see 10% discount). Pooled data: discounted users convert 25% more. Model learns "user_id in this set = high conversion," not "discount drives conversion." Post-experiment (no discount), model still predicts high conversion for those user_ids, false positive rate 18%. True discount feature (if tracked) would generalize, but provenance was lost.

Why It Happens

  • Data warehouse pools all A/B test variants without tracking experiment origin
  • ETL pipelines strip experiment metadata as "non-essential"
  • Multiple concurrent experiments interact — user in experiment A and B simultaneously
  • Historical data mixes control and treatment without labels
Root cause: Experimentation metadata is treated as operational logging, not as a critical data lineage attribute. Once it's stripped, you cannot reconstruct which behavior generated which outcome.

Example: Company runs 5 concurrent A/B tests affecting checkout flow. Training data includes all users regardless of variant. Model learns the average effect across all variants — which matches no single production configuration.

The Correct Approach

  • Tag every row with experiment_id and variant (control/treatment)
  • Train on control-only data or post-settled data (after experiment concluded)
  • If training on mixed data, include experiment_id as a feature so model can condition on it
  • Document which experiments were active during each training data window
Best practice: The training pipeline should filter to rows where experiment_status='control' OR experiment_status='concluded_winner'. Never train on in-flight treatment variants unless the model explicitly conditions on variant assignment.

Example: Training query: SELECT * FROM events WHERE (experiment_id IS NULL) OR (experiment_id IS NOT NULL AND variant='control') OR (experiment_concluded=true AND variant=winning_variant). Ensures model learns stable, production-representative behavior.
