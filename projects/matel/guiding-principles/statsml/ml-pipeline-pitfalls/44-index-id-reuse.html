Pitfall: Index / ID Reuse

IDs get recycled or reset, causing joins to match wrong records and corrupt training labels.

The Problem

System reuses IDs after deletion, reset, or partition boundary, breaking the assumption that ID uniquely identifies an entity. Joins across tables or time periods match unrelated records, silently corrupting training data with mislabeled examples.

  • ID collision: Auto-increment counter resets after migration or per-partition, creating duplicate IDs across time—session_id=42 in Jan is different entity from session_id=42 in Feb
  • Temporal boundaries: Join uses ID alone without timestamp constraint, merging data from deleted user_id=1234 (2024) with new user_id=1234 (2025)
  • Foreign key integrity: Parent record deleted and ID recycled before child records cleaned up—orphaned child data now points to wrong parent
  • Partition-scoped IDs: ID unique within partition but not globally; cross-partition joins create many-to-many matches instead of one-to-one
Impact: Training examples contaminated with features from unrelated entities. Model learns spurious correlations from mismatched data. Silent correctness violation—looks like valid data. Fix: Use UUIDs or composite keys (ID + timestamp + partition). Add temporal constraints to all joins. Validate key uniqueness in actual data, not just schema. Log when IDs are recycled.

Example: Session IDs are 32-bit auto-increment, reset monthly. Training job joins January sessions (id=1-50K) to February events using bare session_id, matching January's session 1234 (mobile user) to February's session 1234 (desktop user). Model learns desktop features predict mobile behavior, accuracy drops 22% on real mobile traffic.

Why It Happens

ID reuse is rarely intentional—it emerges from system design choices that assume local uniqueness implies global uniqueness.

  • Auto-increment resets: IDs reset when tables are recreated or databases migrated
  • Session recycling: Session IDs recycle after TTL expires
  • Shared namespaces: Test and production environments share ID namespace
  • Uncoordinated generation: Microservices generate IDs independently without coordination
Root cause: Assuming IDs are globally unique across time and systems when they're only locally unique within one context.

Example: user_id=12345 in prod DB refers to Alice. After a migration, user_id=12345 now refers to Bob. Joins across pre/post migration data silently merge two different people.

The Correct Approach

Design join keys to be collision-proof across time, environment, and source system.

  • UUIDs: Use UUIDs or globally unique identifiers
  • Composite keys: Include source system + timestamp in composite keys
  • No bare auto-increment joins: Never join across systems on auto-increment IDs alone
  • Row provenance: Add source_id and ingestion_date to every row
Best practice: Design join keys to be collision-proof across time, environment, and source system. If you can't guarantee uniqueness, add qualifying dimensions.

Example: Instead of JOIN ON user_id, use JOIN ON user_id AND source='prod_v2' AND created_date >= '2025-01-01'. Eliminates cross-migration collisions.
