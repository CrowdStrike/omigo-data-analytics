Pitfall: Off-By-One in Windowing / Aggregation

When inclusive vs exclusive time boundaries cause features to leak future data or miss critical information.

The Problem

Computing features using time windows with unclear boundary semantics. "Last 7 days" could mean [t-7, t), [t-7, t], (t-7, t), or (t-7, t]. One bracket difference leaks the target event or excludes the most recent data point.

  • Leakage form: Feature computed as "activity in [label_date - 7d, label_date]" includes the day of the target event itself
  • Miss form: Feature computed as "activity in (label_date - 7d, label_date)" excludes both endpoints, losing signal
  • Language ambiguity: SQL BETWEEN is inclusive on both ends; pandas iloc is half-open; numpy is half-open by default
Impact: 10-20% AUC inflation from leakage (feature sees outcome); or 15% AUC drop from exclusion (feature misses most recent behavior). Fix: Standardize on [t-7, t) for "up to but not including today" and document in code.

Example: Predicting churn on day T. Feature "purchases_last_7d" computed as COUNT(*) WHERE date BETWEEN T-7 AND T includes purchases on day T (post-churn), leaking the label. Correct: WHERE date >= T-7 AND date < T.

Why It Happens

  • Inclusive vs exclusive conventions differ across languages: No universal standard — each tool picks its own default
  • SQL BETWEEN is inclusive on both ends: BETWEEN T-7 AND T includes T (often unexpected by Python devs)
  • pandas .loc is inclusive, .iloc is exclusive on end: Same library, two different boundary conventions
  • No team-wide convention documented: Each engineer picks their own interpretation; code reviews miss the boundary semantics
Root cause: The difference between [a, b] and [a, b) is invisible in code review. A single bracket character is the difference between leakage and correctness. Without explicit tests, it passes silently.

The Correct Approach

  • Standardize on exclusive upper bound: [start, end) everywhere — all features, all languages, all pipelines
  • Write boundary tests: assert max(feature_timestamp) < prediction_timestamp
  • Document boundary convention: In feature engineering code, explicitly comment the bracket notation
  • Use helper functions that enforce the convention: get_window(start, end_exclusive) — the API makes it hard to get wrong
Rule: Every feature window must have an automated test that proves max(feature_ts) < label_ts. If this test fails, you have leakage. No exceptions.
