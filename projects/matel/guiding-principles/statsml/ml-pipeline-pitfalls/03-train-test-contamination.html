Pitfall: Train/Test Contamination

Information from test set leaks into training process

The Problem

Same patient appears in both train and test (different visits) — model memorizes patient, not pattern. Feature engineering uses statistics from full dataset (including test) — mean/std include test rows.

  • Same patient appears in both train and test (different visits) → model memorizes patient, not pattern
  • Feature engineering uses statistics from full dataset (including test) → mean/std include test rows
  • Oversampling/SMOTE applied before train/test split → synthetic points in test set resemble training points

Example: Patient has 5 hospital visits. 3 in train, 2 in test. Model learns "patient_id_12345 → positive" — it's memorizing, not generalizing. On new patients: accuracy drops 20%.

Defense: Split by ENTITY (patient, user, household), not by row. All rows from one entity must be in the same split.

Why It Happens

Random row-level splits ignore entity grouping. When the same patient/user/household appears in both train and test, the model memorizes entities rather than learning generalizable patterns. Applying SMOTE or oversampling before splitting creates synthetic test points that are near-copies of training data.

  • Random row-level splits ignore entity grouping (patient, user, household, device)
  • Same entity in both splits → model memorizes entity-specific patterns, not generalizable signal
  • SMOTE/oversampling applied before split → synthetic minority samples leak into test set
  • Feature engineering on full data → statistics (mean, count) include test entity information

Example: 1000 patients, 5 visits each = 5000 rows. Random 80/20 split: each patient has ~4 train rows and ~1 test row. Model achieves 92% accuracy. Entity-level split (800 patients train, 200 test): accuracy drops to 74%. The 18% gap was memorization.

Root Cause: sklearn's train_test_split operates on rows, not entities. If a patient has 10 visits and 7 go to train, the model learns "patient X → outcome Y" which trivially generalizes to the 3 test visits of the same patient. This is memorization, not learning.

The Correct Approach

Use entity-level splitting with GroupKFold or GroupShuffleSplit. All records from one entity must be in the same split. Apply oversampling only after splitting, on the training set only.

  • Use GroupKFold or GroupShuffleSplit: split by entity (patient_id, user_id, household_id)
  • All records from one entity go to the SAME split — no entity spans train and test
  • Apply SMOTE/oversampling AFTER splitting, on training set only
  • Feature engineering: compute statistics only from training entities
  • Validate: check that no entity ID appears in both train and test sets

Example: GroupKFold with groups=patient_id. 1000 patients → 800 in train (all their visits), 200 in test (all their visits). No patient appears in both. Model accuracy: 74% — honest and reproducible in production.

Fix: Replace train_test_split(X, y) with GroupShuffleSplit(groups=patient_id). This guarantees zero overlap. For SMOTE: split first, then oversample only the training partition. Test set must reflect real-world entity distribution.
