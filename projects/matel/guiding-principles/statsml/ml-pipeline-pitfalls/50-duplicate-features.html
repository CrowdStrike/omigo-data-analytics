Pitfall: Duplicate / Highly Correlated Features (Semantic Incoherence)

Near-identical features destroy interpretability and split importance across redundant variables.

The Problem

Features are semantically identical or nearly so (correlation > 0.95), often due to multiple derivations of same concept or renamed columns from different sources. Tree models split importance arbitrarily, linear models have unstable coefficients, interpretation becomes meaningless.

  • Feature correlation: "revenue_usd" and "revenue_dollars" are same data, different names; model treats as two features, splits importance 50/50 randomly
  • Importance splitting: True signal strength is 0.4, but split across 3 correlated features (0.15, 0.12, 0.13); all rank below threshold, erroneously dropped in feature selection
  • Semantic duplication: "age" and "birth_year" (perfectly correlated given constant reference year); "price" and "log_price" (monotonic transform, nearly redundant for tree models)
  • Multicollinearity: Linear models: coefficients unstable, change dramatically with small data perturbations; regularization arbitrarily zeros one of the pair
Impact: Feature importance uninterpretable—can't determine which features matter because importance is fractured. Model explanation contradictory. Feature selection drops important predictors because importance diluted below threshold. Coefficients unstable across retraining. Fix: Compute pairwise correlation matrix, drop features with r > 0.95. Use variance inflation factor (VIF) to detect multicollinearity. Deduplicate at feature engineering stage—one canonical feature per concept.

Example: User engagement model has "total_clicks," "click_count," and "num_clicks" from three different logging sources—all identical. True importance: 0.42. Measured importance split: 0.16, 0.14, 0.12. Feature selection drops all three because each individually below 0.20 threshold. Retrained model without click features loses 18% AUC. Post-mortem discovers they were duplicates of critical signal.

Why It Happens

  • Collecting all available features without deduplication
  • Same signal appears under different names from different source systems
  • Feature engineering creates correlated variants (amount, log_amount, amount_zscore)
  • Teams independently create similar features without cross-team visibility
Root cause: The "more features = better" assumption combined with siloed feature development. Without a central registry, the same information enters the model through multiple correlated paths.

Example: Three teams contribute features: "revenue_30d", "monthly_revenue", "rev_last_month" — all computed slightly differently but 0.98 correlated. Tree model splits on all three, appearing to use diverse signals when it's one signal three times.

The Correct Approach

  • Correlation clustering: group features with correlation > 0.95
  • Keep one representative per cluster (most interpretable or most stable)
  • Post-hoc path audit in tree models: check if multiple splits use the same underlying signal
  • Central feature registry with lineage tracking
Best practice: Before training, compute pairwise correlation matrix. Cluster features above threshold. Select one per cluster. After training, audit feature importance — if removed "duplicates" would change predictions, the dedup threshold was too aggressive.

Example: 200 features clustered into 85 groups. Keep 85 representatives. Model performance unchanged (0.1% AUC difference) but interpretability and stability improve dramatically.
