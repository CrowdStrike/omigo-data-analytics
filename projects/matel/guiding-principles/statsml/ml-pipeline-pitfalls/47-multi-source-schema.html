Pitfall: Multi-Source Schema Inconsistency

Multiple sources fit same schema but encode values differently, creating semantic confusion.

The Problem

Data sources conform to same column schema but use different conventions for encoding, units, or semantics. Pipeline unions them without normalization, treating semantically different values as comparable. Model learns patterns that don't transfer across sources.

  • Semantic differences: "status=active" means "currently logged in" in source A, "account not suspended" in source B—same field, different concept
  • Encoding variations: Dates in ISO-8601 from source A, Unix timestamps from source B, "YYYY-MM-DD" strings from source C—all land in same column
  • Source-specific quirks: Source A logs revenue in cents (4500 = $45), source B in dollars (45.00); both populate "revenue" column without conversion
  • Missing value semantics: NULL means "not applicable" in source A, "unknown" in source B, "still processing" in source C—same representation, different meanings
Impact: Model sees heterogeneous distributions for "same" feature, learns incoherent patterns. Predictions biased by which source user came from. Silent corruption—data types match, logic doesn't. Fix: Add source_id column and analyze per-source distributions. Normalize encoding and units explicitly before union. Document semantic differences; use separate features or source-specific models when meanings diverge.

Example: User engagement score from web (0-100 scale) and mobile (0-5 stars, converted to 0-100 by multiplying by 20). Model sees web scores uniformly distributed 0-100, mobile scores clustered at 0, 20, 40, 60, 80, 100. Learns that mobile users are "binary" and web users "continuous," predicting differently for same engagement level. Mobile retention predictions off by 35%.

Why It Happens

Schema validation passes (types match) but semantics differ across sources. The root problem is confusing structural compatibility with semantic compatibility.

  • "amount" in system A is in cents, in system B it's in dollars—both are INTEGER/FLOAT, both pass type checks
  • "timestamp" in one source is UTC, in another it's local time—both are TIMESTAMP type, but represent different instants
  • "status" codes mean different things across vendors—status=1 means "active" in vendor A, "pending" in vendor B
Root cause: Schema validation only checks syntax (column name, data type, nullability) — not semantics (units, timezone, encoding, meaning). Two sources can be schema-compatible but semantically incompatible.

Example: Merging clickstream from web (timestamps in UTC) and mobile (timestamps in device-local time). Schema check passes — both are TIMESTAMP type. But feature engineering computes wrong session durations, mixing timezones silently.

The Correct Approach

Defend against semantic drift by treating each source as a separate entity until explicitly normalized.

  • Tag every row with source_id to enable per-source analysis
  • Profile each source separately before merging
  • Define semantic data contracts (not just schema contracts)
  • Include units, timezone, encoding in metadata
Best practice: A data contract specifies not just types but semantics — units, timezone, value ranges, null meaning, and update frequency. Validate contracts per-source before union.

Example: Contract specifies: source=web → amount_unit=cents, tz=UTC. source=mobile → amount_unit=dollars, tz=device_local. ETL normalizes both to dollars/UTC before merge, with source_id preserved for auditing.
