Pitfall: Unit Mismatch (Dollars vs Cents, Seconds vs Milliseconds)

When the same column name is stored in different units across sources or time, causing silent 100x or 1000x errors.

The Problem

A column called "amount" or "duration" exists in multiple tables or data sources, but one stores dollars while another stores cents; one stores seconds while another stores milliseconds. No schema enforcement, no unit metadata, no validation.

  • Currency: Payment API returns cents (2500), internal DB stores dollars (25.00), join mixes both
  • Time: Unix timestamps in seconds (1609459200) vs milliseconds (1609459200000); "duration" in seconds vs minutes
  • Distance: Meters vs kilometers; inches vs centimeters; longitude in degrees vs radians
Impact: Revenue calculations off by 100x, latency metrics off by 1000x, models train on garbage features. Detection: Statistical outlier checks (revenue spike from $50 to $5000), unit tests on representative samples, schema-level unit annotations.

Example: Merging transaction data from Stripe (amounts in cents: 4500) with internal analytics table (amounts in dollars: 45.00). A naive join treats 4500 as $4500, inflating revenue by 100x. Model sees nonsensical features: "average purchase $2000" when true value is $20.

Why It Happens

  • Undocumented conventions: Different teams choose different unit conventions independently, with no central registry
  • System migrations: A platform migration changes units (e.g., cents to dollars) without updating column names or documentation
  • API vs DB mismatch: External APIs return amounts in cents while internal databases store dollars — both land in the same column
  • No schema-level metadata: Column definitions lack unit annotations, validation ranges, or semantic types
Root cause: The column name "amount" carries no unit semantics. Without explicit unit metadata, every consumer must guess — and guesses diverge across teams and time.

The Correct Approach

  • Units in column names: amount_cents, latency_ms, distance_km — self-documenting and prevents mix-ups
  • Range validation rules: amount_cents > 0 AND < 10000000 catches 100x errors immediately
  • Schema-level unit annotations: Data catalog entries include unit, valid range, and source system
  • Conversion at ingestion boundary: Normalize units at the point of entry, not downstream in queries or models
Principle: Make the unit impossible to ignore. If the column name forces you to acknowledge the unit, you cannot accidentally mix dollars with cents.
