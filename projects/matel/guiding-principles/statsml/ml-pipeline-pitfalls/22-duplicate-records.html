Pitfall: Duplicate / Near-Duplicate Records

Same or nearly identical record appearing in both train and test sets causes memorization leakage and inflated performance

The Problem

When the same record (or near-duplicates differing only in irrelevant fields) appears in both train and test sets, the model simply memorizes it. Test accuracy becomes artificially high because the model has seen these exact examples before.

  • ETL bugs create duplicate rows from joins or retries
  • Data collection systems capture same event multiple times
  • Splitting before deduplication spreads copies across train/test
  • Near-duplicates (same content, different timestamp) are harder to detect
Impact: Test performance vastly overstates production performance. Models fail in the wild because they memorized duplicates rather than learning patterns. Fix: Deduplicate before splitting. Use entity-level splits where possible.

Example: A text classifier has 15% duplicate documents. Test accuracy is 94%, but production accuracy is 78%. The model memorized duplicates instead of learning features.

Detection Strategies

Detecting duplicates requires checking across the train/test boundary. Exact duplicates are easy; near-duplicates require content hashing or similarity measures.

  • Hash all rows and check for collisions across train/test
  • For text: use MinHash or SimHash to find near-duplicates
  • For images: perceptual hashing (pHash, dHash)
  • For time-series: compare windowed subsequences
  • Check for suspiciously high test accuracy on specific subsets
Detection signal: Large gap between in-sample and out-of-sample error, or test accuracy that seems "too good" for the problem difficulty. Inspect high-confidence predictions for memorization.

Example: A fraud model has 99.5% test accuracy but 87% production accuracy. Investigating shows 20% of test set has exact matches in training data due to retry logic creating duplicate transactions.

Prevention and Mitigation

The safest approach is to deduplicate the entire dataset before any splitting. Use entity-level or temporal splits to prevent information leakage through near-duplicates.

  • Deduplicate globally before train/test split
  • Use entity-based splitting (one user or account entirely in train or test)
  • For time-series, use temporal splits with guardbands
  • Monitor for duplicate creation in ETL pipelines
  • Track unique IDs and flag when same ID appears in multiple sets
Best practice: Always deduplicate before splitting. Use content-based deduplication (not just ID-based) to catch near-duplicates. For high-stakes applications, implement automated checks that fail the pipeline if cross-set duplicates are detected.

Example: An e-commerce recommendation system switched from random split to user-level split. Test accuracy dropped from 91% to 78%, revealing that the model had been memorizing duplicate product views from the same users.
