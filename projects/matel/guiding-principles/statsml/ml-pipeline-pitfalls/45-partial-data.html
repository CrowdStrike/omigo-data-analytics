Pitfall: Partial Data (Incomplete ETL Window)

Analysis runs before all data arrives, creating systematically biased training sets.

The Problem

Training job queries data for day D but runs before all day D data has arrived. The incomplete snapshot is systematically biased—missing late events, missing certain sources, or truncated at arbitrary cutoff. Model learns patterns from partial view, fails on complete data.

  • Completeness checks: No validation that all expected sources delivered data; job proceeds with whoever arrived by deadline, silently omitting stragglers
  • Late-arriving data: Events timestamped for day D arrive hours later due to processing lag, timezone conversion, or batch delay—training snapshots miss them every time
  • ETL timing: Training job scheduled for 2 AM UTC to process "yesterday," but some sources don't finish loading until 4 AM—training sees only 60% of data
  • Backfill vs real-time: Historical data is complete (backfilled); recent data is partial (streaming with lag)—model trained on heterogeneous completeness
Impact: Training data systematically underrepresents certain events, regions, or sources. Model learns skewed distributions. Serving data is complete, triggering distributional shift. Fix: Add explicit completeness checks—count records per source, compare to historical baseline. Delay training until all sources confirm delivery. Use watermarks or heartbeat signals. Separate complete historical data from incomplete recent data.

Example: Daily training job for fraud model runs at 3 AM, processing previous day. International transactions arrive with 4-hour lag due to timezone batch windows. Model trained on data missing 35% of EU transactions. At serving time, full data arrives; model predicts "legitimate" for fraud patterns it never saw, false negative rate 2.8x higher on EU traffic.

Why It Happens

  • Queries run before all data for a time window has arrived
  • Timezone differences cause late-arriving events
  • Batch pipelines trigger on schedule, not on data completeness
  • Upstream systems have variable latency (some events arrive hours late)
Root cause: Conflating "query returned results" with "all data for this period is present." Schedule-based triggers don't verify completeness.

Example: Daily pipeline runs at 2am UTC. Events from US West Coast (UTC-8) for 11pm local time arrive at 7am UTC — 5 hours after pipeline already consumed "yesterday's" data. Those events are permanently lost from training.

The Correct Approach

  • Implement completeness SLA checks before processing
  • Don't process until event count matches expected (watermarks)
  • Use event-time windowing, not processing-time
  • Add late-arrival buffers (grace periods)
Best practice: Gate pipeline execution on data completeness signals, not wall-clock time. Use high-watermarks and expected row counts to verify all sources have flushed.

Example: Pipeline checks: expected_events >= 95% of trailing 7-day average for this hour. If not met, pipeline waits (with timeout alert). Late data is reprocessed in next window.
