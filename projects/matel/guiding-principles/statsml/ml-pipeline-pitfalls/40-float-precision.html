Pitfall: Floating Point / Precision Loss

When numerical precision issues create silent errors in aggregations, comparisons, and financial calculations.

The Problem

Floating point arithmetic is inexact. Repeated operations accumulate rounding errors. Equality checks fail. Currency stored as float loses cents. Large integers stored as float lose precision beyond 2^53.

  • Accumulation: Summing 1M small floats (0.01) yields 9999.999743 instead of 10000.00
  • Comparison: 0.1 + 0.2 != 0.3 in float; WHERE revenue = 0.3 matches nothing
  • Currency: $19.99 stored as float becomes 19.989999771; multiply by 1M transactions = $100k error
  • Large IDs: User ID 9007199254740993 (> 2^53) stored as float64 becomes 9007199254740992 (collision)
Impact: Financial reports off by thousands due to rounding; user IDs collide; model features drift because 0.33333 rounded differently in batch vs online. Solution: Use DECIMAL/NUMERIC for currency, INTEGER for IDs, round-to-even for aggregations, epsilon tolerance for comparisons.

Example: E-commerce pipeline aggregates revenue as SUM(price * quantity) using float. For 1M transactions averaging $25, accumulated rounding error is $3,200. Daily P&L report is wrong. Auditors notice $1.2M annual discrepancy; takes 6 months to find root cause.

Why It Happens

  • float32 aggregations: Using float32 for SUM/AVG where float64 is needed — error accumulates with every row
  • Equality comparisons: WHERE price = 19.99 matches nothing because stored value is 19.989999...
  • Division by near-zero: 1.0 / 0.0000001 produces Inf/NaN that propagates silently through entire pipeline
  • Serialization round-trips: JSON/CSV export truncates precision; re-import produces different values than original
Root cause: IEEE 754 floating point represents numbers in binary fractions. Most decimal fractions (0.1, 0.01, 19.99) have no exact binary representation. Each operation adds a small error; millions of operations compound into visible discrepancies.

The Correct Approach

  • Aggregations: Use float64 for all SUM/AVG operations; DECIMAL/NUMERIC for currency
  • Comparisons: Never join or filter on float columns; use epsilon tolerance (abs(a-b) < 1e-9)
  • Post-operation checks: Explicit NaN/Inf validation after every division or log operation
  • Currency: Store as integers (cents) not floats — $19.99 becomes 1999
Principle: Defensive numerical programming — assume every float operation can lose precision, and design systems that detect and prevent accumulation of error.
