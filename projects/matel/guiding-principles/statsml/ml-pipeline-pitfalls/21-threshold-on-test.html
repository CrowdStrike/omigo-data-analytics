Pitfall: Threshold Selection on Test Set

Choosing classification threshold that maximizes test set performance leads to overly optimistic evaluation

The Problem

Many practitioners tune their classification threshold (the decision boundary converting probabilities to binary predictions) by testing multiple values and selecting the one that maximizes performance on the test set. This is a subtle form of overfitting.

  • The test set is supposed to be a simulation of unseen data
  • Using it to pick the threshold means test performance is no longer unbiased
  • The threshold has effectively been trained on test data
  • Real-world performance will be lower than the reported test metrics
Impact: Test metrics become optimistically biased. The gap between reported performance and production reality widens. Fix: Use a separate validation set or nested cross-validation for threshold selection, then evaluate once on held-out test data.

Example: A fraud model reports 92% F1 on test after trying 50 thresholds. Production F1 is 87%. The 5-point gap is partly from threshold overfitting to test quirks.

Why It Happens

The confusion stems from treating threshold selection differently from other hyperparameters. It feels like "post-processing" rather than training, so people don't realize they're fitting to the test set.

  • Threshold feels like a simple decision rule, not a learned parameter
  • Many tutorials show "grid search over thresholds on test set"
  • The data science workflow often lacks a proper validation set
  • Small datasets make holding out more data painful
Root cause: Misunderstanding that any tuning based on test set performance invalidates the test set as an unbiased estimator. The threshold is a hyperparameter like any other.

Example: A team with 10,000 samples uses 8,000/2,000 split. They don't want to sacrifice more for validation, so they tune threshold on the 2,000-row test set directly.

The Correct Approach

Threshold selection must happen before the test set is touched. Use train/validation/test split or nested cross-validation.

  • Train model on training set
  • Tune threshold on validation set (or inner CV fold)
  • Evaluate final model + chosen threshold on test set exactly once
  • Report test metrics as unbiased estimate of production performance
Best practice: Treat threshold as a hyperparameter. Include it in cross-validation. If you must use the test set, commit to the threshold choice before looking at test metrics, or accept that your numbers are upper bounds.

Example: An 80/10/10 split (train/val/test) allows threshold tuning on validation, then one final honest evaluation on test. With 10k samples, that's 1k held out for unbiased reporting.
