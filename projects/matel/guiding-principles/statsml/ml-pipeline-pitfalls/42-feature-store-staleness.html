Pitfall: Feature Store Staleness

Feature store serves outdated values with no monitoring, silently degrading model performance.

The Problem

Feature store caches values for performance but fails to monitor freshness. Updates pause or lag without alerting, causing models to make decisions on hours-old or day-old features while believing they are current.

  • Cache expiry: TTL set to "reasonable" values (e.g., 1 hour) without checking actual update frequency—upstream job now runs every 6 hours, cache serves 5-hour-old data
  • Update frequency drift: Feature pipeline originally refreshed every 15 minutes, now runs hourly due to load or failures, but no alerts fire
  • Staleness detection: No timestamp comparison at read time—application assumes if value exists, it's fresh enough
  • Silent degradation: Model accuracy erodes gradually as features age; no single event triggers investigation
Impact: Models make decisions on outdated context, systematically missing recent events. Gradual accuracy drop is invisible until major incident. Fix: Store and expose feature timestamp at write time. Alert when age exceeds threshold. Monitor staleness percentiles across all features. Reject reads when staleness exceeds policy.

Example: Feature store caches "user session count in last 10 minutes" with 5-minute TTL. Upstream streaming job fails silently at 2 PM, cache continues serving 2 PM values until 8 PM when manual investigation starts. Model predicts "inactive" for users with recent activity, blocking 14% of legitimate traffic.

Why It Happens

  • Unmonitored pipelines: Refresh pipelines have no SLA enforcement — failures are silent and undetected for hours
  • No per-feature freshness SLA: No defined or tracked maximum age per feature; all features treated identically
  • Generic cache TTLs: Cache expiry set to "1 hour" generically without matching actual upstream update cadence
  • No alert propagation: Upstream pipeline failures don't propagate alerts downstream to consumers
Root cause: Feature stores are built for performance (low-latency reads) but freshness monitoring is an afterthought. The system optimizes for speed of retrieval without tracking age of data.

The Correct Approach

  • Per-feature timestamps: Store last_updated timestamp per feature per entity in the feature store
  • Defined SLAs: Define max_age SLA per feature (e.g., user_activity: 15 min, demographics: 24 hours)
  • Alert on breach: Alert when any feature exceeds its freshness SLA
  • Reject stale predictions: Return uncertainty flag instead of prediction when critical features are stale
Principle: Every feature read should carry its age. The model serving layer must know whether it is making a decision on fresh data or stale data — and act accordingly.
