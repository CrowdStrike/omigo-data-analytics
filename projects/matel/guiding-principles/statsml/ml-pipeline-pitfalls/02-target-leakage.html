Pitfall: Target Leakage (Label Encoded in Features)

A feature is a direct proxy or consequence of the label

The Problem

"treatment_given=chemo" perfectly predicts "has_cancer" — but treatment was assigned BECAUSE of cancer diagnosis. The feature doesn't predict the target; it IS the target wearing a disguise.

  • "treatment_given=chemo" perfectly predicts "has_cancer" — but treatment was assigned BECAUSE of cancer diagnosis
  • The feature doesn't predict the target; it IS the target wearing a disguise
  • Symptoms: perfect accuracy on train, feature importance dominated by one variable, model useless on new data where proxy is absent

Example: Predicting loan default. Feature "collection_calls_made" = 0 for good loans, >0 for defaults. But calls happen AFTER default — it's a consequence, not a predictor.

Defense: Check causal direction. Does the feature CAUSE the outcome, or does the outcome CAUSE the feature? If the latter → leakage.

Why It Happens

Teams confuse correlation with causation. A feature that is perfectly correlated with the target seems like a great predictor — but it is actually a consequence of the target, not a cause. These proxy features are set AFTER the outcome is known.

  • Confusing correlation with causation: high correlation does not imply predictive utility
  • Features that are consequences of the target (set AFTER the outcome is determined)
  • Data pipelines that join tables without checking temporal ordering of events
  • "Worked in the lab" syndrome: feature exists in historical data but not at prediction time

Example: Predicting customer churn. Feature "account_closed_date" is non-null only for churned customers. AUC = 0.99. But account closure IS churn — you cannot know this feature at prediction time.

Root Cause: The team does not ask "which direction does causation flow?" A feature perfectly correlated with the target is suspicious, not impressive. If removing the feature drops accuracy from 99% to 75%, it was doing the target's job.

The Correct Approach

Apply a causal direction check to every feature. Ask: "Does this feature exist BEFORE the outcome is determined?" Remove any feature that is set after the outcome. When in doubt, trace the data generation process step by step.

  • Causal direction check: for each feature, ask "is this set before or after the outcome?"
  • Remove any feature whose value is determined by the target (consequence, not cause)
  • Trace the data generation process: draw a timeline of when each column gets its value
  • Suspicion trigger: any feature with AUC > 0.95 by itself deserves manual causal review
  • Use domain experts to validate that features are genuinely available pre-outcome

Example: After removing "collection_calls_made" (a consequence of default), loan default model drops from 98% to 76% AUC. The 76% is the real performance. The model now uses legitimate predictors: income, credit score, debt-to-income ratio.

Fix: For every feature with high univariate predictive power, trace the causal chain. If target → feature (not feature → target), it is leakage regardless of correlation strength. Remove it and accept the accuracy drop.
