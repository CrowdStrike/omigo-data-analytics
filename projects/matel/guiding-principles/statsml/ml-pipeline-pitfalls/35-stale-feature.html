Pitfall: Stale Feature (Cached / Not Updated)

When a cached feature value becomes outdated because the refresh pipeline failed, but the model keeps serving predictions with stale data.

The Problem

Features are precomputed and cached (in a feature store, Redis, or materialized view) for fast serving. The refresh job fails or lags, but the serving system continues using the stale cached values without alerting.

  • Silent staleness: Feature says "user logged in 2 days ago" when they actually logged in 5 minutes ago
  • Drift: Model trained on fresh features (computed at training time) but served with 24-hour-old features; performance degrades
  • Detection gap: Monitoring tracks model performance (which decays slowly), not feature freshness (which breaks instantly)
Impact: 10-30% AUC drop when features lag by 1 day in a real-time prediction task; churn models fail because "last_activity" is 24 hours stale. Solution: TTL on cached features, freshness monitoring (last_updated timestamp), fallback to recompute on cache miss.

Example: A fraud detection model uses "transactions_last_hour" computed every 5 minutes. The batch job fails at 2pm but no alert fires. Predictions from 2pm to midnight use 2pm data, missing 10 hours of new transactions. A fraudster exploits this window.

Why It Happens

  • Silent pipeline failures: ETL jobs fail without alerting — no one notices until model performance degrades days later
  • Cache TTL misconfiguration: TTLs set arbitrarily (24h) without considering how frequently the underlying data actually changes
  • No freshness monitoring: Teams monitor model output metrics (AUC, precision) but not feature freshness — a leading indicator of failure
  • Upstream schedule changes: The source system changes its update cadence without notifying downstream feature pipelines
Core issue: The serving layer has no concept of "too old." It serves whatever is cached, regardless of age, because freshness was never made a first-class concern.

The Correct Approach

  • Track last_updated per feature: Every cached feature carries a timestamp of when it was last computed
  • Alert on age threshold: If feature_age exceeds configured SLA (e.g., 30 min for real-time features), fire alert immediately
  • Feature age as input signal: Pass feature_age_minutes to the model — let it learn to discount stale signals
  • TTL with fallback: If stale, either recompute on-demand or return an uncertainty flag so the serving layer can fall back to a safe default
Principle: Freshness is a feature property, not an operational afterthought. Monitor it like you monitor latency — with SLAs, alerts, and fallbacks.
