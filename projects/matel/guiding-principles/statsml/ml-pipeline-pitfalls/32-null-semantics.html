Pitfall: NULL Semantics Mismatch

When NULL means different things in different columns or contexts, creating silent misinterpretation of missing data.

The Problem

A NULL value has no inherent meaning. In one column it might mean "not applicable", in another "not yet collected", in another "unknown", and in another "explicitly declined to answer". Without documentation, models treat them all identically.

  • Ambiguity: NULL in phone_number (no phone) vs NULL in last_purchase_date (never purchased) vs NULL in survey_response (skipped question)
  • Treatment: Imputation strategies that work for one type (mean imputation for MCAR) catastrophically fail for another (MNAR)
  • Joins: NULL != NULL in SQL; filters on NULL columns silently drop rows
Impact: Models misinterpret signal as noise, imputation destroys information, joins drop 20% of data silently. Solution: Encode NULL reasons as separate columns or sentinel values (e.g., -1 for "never", -2 for "declined").

Example: In a customer dataset, NULL in "last_login_date" means "never logged in" (strong negative signal), but NULL in "preferred_language" means "not asked yet" (neutral). Treating both as missing at random destroys the churn prediction signal.

Why It Happens

  • No column-level NULL documentation: Data dictionaries rarely specify what NULL means per column — just "nullable: yes/no"
  • Treating all NULLs as "unknown": Default mental model conflates absence of data with absence of signal
  • Different upstream systems encode missingness differently: One system sends NULL, another sends empty string, another sends -1
  • Schema evolution adds nullable columns: New columns appear with NULLs for historical rows without documenting why those rows have no value
Root cause: NULL is overloaded — it's a single database concept forced to represent 4+ distinct real-world meanings. Without metadata, the context is lost.

The Correct Approach

  • Document NULL meaning per column: Data dictionary must state: "NULL in X means Y"
  • Create explicit is_missing indicator features: Boolean columns that encode the fact of missingness as signal
  • Use different imputation per NULL type: MCAR → mean/median; MNAR → model-based or indicator; MAR → conditional imputation
  • Encode reason codes: -1 = not applicable, -2 = not collected, -3 = declined — preserve semantics numerically
Rule: Every NULL column should expand into at least two columns: the value (when present) and the reason for absence. The reason IS the feature.
