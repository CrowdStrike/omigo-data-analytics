Pitfall: Sampling Rate Changes

When data collection frequency changes over time, creating fake trends that look like real behavior shifts.

The Problem

The rate at which events are logged or sampled changes between time periods. Analytics interpret the volume change as user behavior when it's actually a measurement artifact.

  • Log sampling: Errors logged at 100% until March, then downsampled to 10%; error "drop" is illusory
  • Instrumentation changes: New SDK version logs every click; old version logged every 5th click; "engagement spike" is fake
  • Retention policy: Changed from "keep 7 days" to "keep 30 days"; older data now available, looks like volume increased
Impact: False trend detection, models train on inconsistent densities, time-series forecasts break at sampling discontinuities. Detection: Plot event counts over time with annotations for instrumentation changes; normalize by sampling rate metadata if available.

Example: Mobile app logs clicks at 100% rate through 2023, then switches to 1% sampling in Jan 2024 to reduce costs. A model trained on 2023-2024 data sees a "cliff" in click volume and learns "post-Jan users are less engaged" when true engagement is unchanged. Feature drift alarms fire falsely.

Why It Happens

  • SDK upgrades that change default logging rates
  • Cost-reduction decisions that downsample without notifying ML teams
  • A/B test instrumentation that logs differently per variant
  • Infrastructure changes (new data center, different sampling config)
Root cause: Sampling rate is an infrastructure decision made independently of ML teams. Volume changes look identical to behavior changes in raw event counts.

The Correct Approach

  • Track sampling rate as metadata alongside event counts
  • Normalize all counts by sampling rate before use as features
  • Segment model training into pre/post sampling change periods
  • Store sampling_rate column in event tables; divide raw counts by it
Principle: Raw counts are meaningless without knowing the sampling denominator. Always normalize: adjusted_count = raw_count / sampling_rate.
