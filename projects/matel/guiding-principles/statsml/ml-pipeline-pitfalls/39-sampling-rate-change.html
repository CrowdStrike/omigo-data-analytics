Pitfall: Sampling Rate Changes

When data collection frequency changes over time, creating fake trends that look like real behavior shifts.

The Problem

the trapsampling
  • The trap — logging or sampling rate changes between periods, shifting event volume
  • Misread signal — analytics read the volume change as user behavior, not measurement
  • Log sampling — errors logged at 100% then downsampled to 10% show an illusory drop
  • Instrumentation — a new SDK logs every click where the old logged every 5th, faking a spike
  • Retention policy — extending "keep 7 days" to 30 days looks like a real volume increase

A mobile app cuts click logging from 100% to 10% in Jan 2024, and the model learns a fake 90% engagement cliff.

Impact: False trends fire drift alarms, models train on inconsistent event densities, and forecasts break at each discontinuity.

Why It Happens

root causesampling
  • Infra ownership — sampling rates live in configs owned by teams optimizing for cost
  • Last to know — downstream data consumers usually hear about a change after the fact
  • SDK upgrades — new SDK versions ship with different default logging rates
  • Cost cuts — downsampling decisions cut storage bills without notifying ML teams
  • A/B instrumentation — test variants can log at different rates, confounding comparisons
  • Silent changes — a new data center or sampling config alters volume with no announcement
Root Cause: Sampling rate is an infrastructure decision made independently of ML teams, and in raw counts a volume change looks identical to a behavior change.

The Correct Approach

the fixnormalization
  • Carry the denominator — make the sampling rate part of the data every count travels with
  • Metadata — store the sampling rate as a column beside event counts in every table
  • Normalization — divide raw counts by the rate: adjusted_count = raw_count / sampling_rate
  • Segmentation — if old rates are unrecoverable, train separately on pre- and post-change data
  • Detection — plot counts annotated with releases; aligned jumps are measurement artifacts
Fix: Raw counts are meaningless without the sampling denominator — always normalize as raw_count / sampling_rate.
