Pitfall: Non-Representative Training Data

Model trained on one population but deployed on a different population with different characteristics

The Problem

Training data comes from a subset (power users, one region, one time period) but production serves the full population. The model learns patterns that don't generalize, causing poor performance on underrepresented groups.

  • Trained on power users, deployed to all users including novices
  • Trained on US data, deployed globally with different cultural patterns
  • Trained on summer months, fails during winter seasonal shifts
  • Trained on complete records, but production has sparse/missing data
Impact: Aggregate metrics look acceptable but hide severe performance gaps in subgroups. Model is biased toward overrepresented segments. Fix: Stratified sampling, representation analysis, per-segment evaluation.

Example: A loan approval model trained on prime borrowers (FICO > 700) is deployed to all applicants. Performance on subprime segment (FICO < 650) is 40% worse than reported test metrics.

Why It Happens / Detection / Common Sources

Data collection is often biased by availability, convenience, or historical precedent. Teams don't realize their training data is a biased sample until production reveals gaps.

  • Data from early adopters or beta testers (not typical users)
  • Survivorship bias: only have data from successful outcomes
  • Convenience sampling: using whatever data is easy to collect
  • Historical bias: past data reflects old product/policies
Detection: Compare training distribution to production distribution across key segments (demographics, geographies, time periods, device types). Track performance by segment. Large gaps signal non-representativeness.

Example: A mobile app model trained on iPhone users (80% of training data) but deployed to Android majority market (60% of production users). Android performance is 25% lower.

Prevention / Correct Approach

Explicitly analyze representation before training. Use stratified sampling to ensure all production segments are adequately represented. Evaluate performance by segment, not just aggregate.

  • Profile production population across key dimensions
  • Use stratified sampling to match production distribution
  • If minority segments lack data, collect targeted samples or use weighting
  • Report performance metrics broken down by segment
Best practice: Maintain a representation matrix showing training vs production distribution. Ensure minority segments have sufficient samples (minimum 100-1000 depending on complexity). Flag segments with performance deltas > 10%.

Example: A fraud model stratifies by transaction amount (small/medium/large). Each stratum gets proportional samples. Per-segment evaluation reveals the model needs more features for high-value transactions.
