Pitfall: Character Encoding / Locale Issues

Text data corrupted by encoding mismatches, causing silent data loss and incorrect feature extraction

The Problem

Text data encoded in UTF-8 but parsed as Latin-1 (or vice versa) produces mojibake. Non-ASCII characters corrupt silently. Names, addresses, and text features become unusable. Models trained on corrupted text learn garbage patterns.

  • UTF-8 vs Latin-1 mismatches turn "José" into "JosÃ©" (mojibake)
  • Locale-dependent operations (case folding, collation) produce inconsistent results
  • Byte order marks (BOM) break CSV parsers and JSON decoders
  • Windows-1252 vs UTF-8 creates "smart quotes" and em-dash corruption
Impact: Text features are silently corrupted. String matching fails. Names and addresses become unparseable. Models see corrupted tokens and learn wrong associations. Detection is hard because corrupted text looks "almost right."

Example: A customer name table has 10% non-ASCII names. Data exported as UTF-8, imported as Latin-1. "François" becomes "FranÃ§ois". Matching fails. Model sees two different customers.

Why It Happens / Detection / Common Sources

Systems default to different encodings. Windows uses Windows-1252, Linux defaults to UTF-8, databases may use Latin-1. Excel exports CSV with BOM. Locale settings change string operations invisibly.

  • Excel saves CSV with UTF-8 BOM by default (breaks many parsers)
  • Database client libraries default to Latin-1 unless explicitly configured
  • Python 2 treated strings as bytes; Python 3 requires explicit encoding
  • Locale-dependent case folding: Turkish "i".upper() → "İ" not "I"
Detection: Check for replacement characters (U+FFFD �). Scan for mojibake patterns like "Ã©" (é as UTF-8 read as Latin-1). Validate that all text is valid UTF-8. Test with international characters in CI.

Example: A pipeline reads CSV exported from Excel. BOM bytes (EF BB BF) are interpreted as text. First column name is "﻿user_id". Joins fail silently because column name doesn't match.

Prevention / Correct Approach

Enforce UTF-8 everywhere. Explicitly declare encoding at every I/O boundary. Use encoding-aware libraries. Validate text on ingestion. Test with non-ASCII data in your test suite.

  • Set database connection encoding to UTF-8 (MySQL: utf8mb4)
  • Explicitly specify encoding in file I/O: open(file, 'r', encoding='utf-8')
  • Strip BOM on CSV read: read_csv(file, encoding='utf-8-sig')
  • Use locale-independent operations: casefold() instead of lower()
Best practice: UTF-8 everywhere. Validate text on ingestion with try/except UnicodeDecodeError. Add test cases with names like "José", "北京", "Москва". Log warnings when non-UTF-8 detected.

Example: A pipeline explicitly sets UTF-8: database connection, file reads, HTTP headers. Validator checks for mojibake patterns on ingestion. Test suite includes international names. Zero encoding issues in production.
