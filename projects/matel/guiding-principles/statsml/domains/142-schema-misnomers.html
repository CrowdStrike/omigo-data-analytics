Schema Misnomers & Semantic Traps

Field names that say one thing and mean another. The schema becomes a source of silent wrong interpretation — not because the data is bad, but because the NAME misleads everyone who reads it.

The core problem: A field named `revenue` might mean gross, net, projected, or recognized — depending on who created it and when. Everyone reads the name, assumes the obvious meaning, and builds analysis on a wrong interpretation. The data is correct. The interpretation is wrong. The name is the bug.

Overloaded Names — Same Word, Different Meaning Per Context

`amount` Means 5 Different Things in 5 Tables
  • Table A: `amount` = USD total (e.g., $42.50)
  • Table B: `amount` = cents integer (e.g., 4250)
  • Table C: `amount` = quantity of items (e.g., 3 units)
  • Table D: `amount` = percentage expressed as decimal (e.g., 0.15 = 15%)
  • Table E: `amount` = delta from previous value (can be negative)
  • The damage: JOIN tables A and B on a shared key, sum the `amount` column → adding dollars to cents. Off by 100×. No error thrown. Dashboard shows "revenue up 9,800%." Nobody questions it for weeks because the number is directionally plausible ("we grew!").
  • Why it persists: Each team named their field reasonably in isolation. No one enforced a global naming standard. By the time you have 200 tables, renaming is a breaking change nobody wants to own.

Temporal Ambiguity — When Did This Number Become True?

`created_at` — When the Event Happened or When We Recorded It?
  • `created_at`: Does it mean when the user performed the action? When the event hit the server? When the row was inserted into the warehouse? These can differ by seconds, hours, or days (batch ingestion).
  • `updated_at`: Last update to the row — but was the update a data correction, a status change, or a reprocessing artifact? If you filter by `updated_at > yesterday` you might get rows whose CONTENT didn't change, just their ETL timestamp.
  • `date`: The most dangerous field name. Date of what? The transaction? The settlement? The reporting period? In finance, transaction_date vs settlement_date can differ by T+2 days. Using the wrong one shifts your entire revenue curve by 2 days.
  • The analysis mistake: "Revenue by day" using `created_at` (ETL insert time) instead of `transaction_date` (when money moved). Monday's batch inserts weekend events → Monday looks 3× higher than Tuesday. Real pattern: uniform. Measured pattern: massive Monday spike.

Status Fields With Undocumented Historical Semantics

`status = 3` — What Does That Mean?
  • The enum graveyard: Status field has values 0-14. Values 0, 1, 2 are documented. Values 3-14 were added over 5 years by different engineers, some no longer at the company. No enum definition exists. Code comments say "// legacy, don't touch."
  • Semantic drift: `status=5` meant "churned" in 2019. In 2021, product added a "paused" state and reused value 5 for existing users who didn't log in for 30 days. Now `status=5` means two different things depending on when the row was created. Filtering by `status=5` mixes churned users (real churn) with paused users (will return). Churn model accuracy: garbage.
  • The "active" trap: "Give me all active users." Which statuses count as active? 1? 1 and 2? 1, 2, and 7 (trial)? Different dashboards use different definitions. Each shows a different "active user count." Leadership sees contradicting numbers. Nobody knows which is right because the field name doesn't encode the semantics.
  • Boolean fields that aren't: `is_deleted = true` but the row still appears in queries because the app uses soft-delete but some pipelines don't filter on it. `is_active` was true when the account was created but never gets set to false — it's a creation flag, not a current-state flag.

Unit Ambiguity — The Number Is Right, the Scale Is Wrong

Dollars vs Cents vs Basis Points vs Percentage
  • The Mars Climate Orbiter problem: One system sends meters, another expects feet. Spacecraft crashes. In data: one pipeline writes milliseconds, downstream reads seconds. Latency looks 1000× worse. Alert fires. On-call wakes up at 3am. Finds: unit mismatch. Not a real incident.
  • Currency fields: `price` = is it USD? EUR? The user's local currency? If local, is it pre- or post-conversion? A global dashboard summing `price` across regions adds JPY (≈150 per USD) to USD to GBP. Total is meaningless. But it's a number, so it gets graphed.
  • Rate fields: `conversion_rate = 0.03` — is that 3% or 0.03%? If it's a probability (0 to 1), then 0.03 = 3%. If it's already a percentage, then 0.03 = 0.03%. Multiply by the wrong factor and your revenue projection is off by 100×.
  • Duration fields: `duration = 3600` — seconds (1 hour)? Milliseconds (3.6 seconds)? Minutes (60 hours)? Name doesn't say. Analyst assumes seconds. Dashboard shows "average session: 1 hour." Real value: 3.6 seconds. Product team panics about "why are users spending an hour on checkout?"

Naming Creates False Equivalence Across Systems

`user_id` in System A ≠ `user_id` in System B
  • Identity fragmentation: Marketing's `user_id` = email hash. Product's `user_id` = account UUID. Analytics' `user_id` = cookie ID. Same name. Different entity. JOIN them → one person becomes three. Three people become one. User count is simultaneously inflated and deflated.
  • The attribution disaster: "User who saw ad also purchased." But marketing's user (cookie) ≠ product's user (account). The cookie saw the ad on a phone. The purchase happened on a laptop with a different cookie. Attribution model says: "ad didn't convert." Reality: it did. The identity stitching failed because both systems call their identifier `user_id` and someone assumed they're the same thing.
  • Granularity mismatch: System A's `transaction_id` is one row per order. System B's `transaction_id` is one row per line item. JOIN them → order with 5 items appears 5× in system B. Revenue looks 5× higher. Or: aggregate system B first, then join — but which aggregation? SUM? MAX? Depends on what `amount` means in each system (see Pitfall 1).
