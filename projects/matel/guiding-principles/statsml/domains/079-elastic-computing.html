Elastic Computing / Auto-Scaling

Auto-scaling reacts in minutes while demand spikes in seconds. The non-representative data collected during scaling events — latency spikes, timeouts, degraded features — silently contaminates your pipeline.

Scale-Up Lag — Traffic Arrives Before Capacity

3-5 Minutes to Scale. Spike Lasts 30 Seconds.
  • The sequence: Detect, provision, boot, deploy, warm up — scaling takes 3-5 minutes while the spike lasts 30 seconds.
  • The data impact: During the lag, latency spikes 10× and timed-out feature computations return defaults/nulls — latency-derived features carry corrupted values.
  • The false signal: The model learns "high latency → low conversion," a correlation caused by infrastructure rather than user behavior, so it misfires during every scaling event.

Scale-Down Oscillation — Hysteresis as Noise Generator

Scale Down → Latency Rises → Scale Up → Latency Drops → Scale Down → Repeat
  • The cycle: Scale down raises latency, which triggers scale up, which lowers latency, which triggers scale down — the system oscillates between states.
  • The data impact: Time-series models read the 50ms/500ms oscillation as a real pattern when it is a control-system artifact.
  • The false seasonality: The model learns "latency spikes every 10 minutes" — then hysteresis settings change, the pattern disappears, and predictions are wrong.

Cold Start Penalty — First Request Data Is Garbage

New Instance: First Request Takes 2-10 Seconds. Subsequent: 50ms.
  • The problem: A cold instance serves its first request in 2-10 seconds versus 50ms warm — a completely different user experience.
  • The data contamination: The bimodal latency distribution makes averages meaningless, and a "winning" A/B variant may simply have fewer cold starts.
  • The model serving problem: Cold-start weight loading makes the first prediction arrive after the user left, so ~5% of users always get NULL scores and the fallback experience.

Spot Eviction — Computation Interrupted Mid-Pipeline

2-Minute Warning → Checkpoint → Lose 5 Min of Work → Reschedule
  • The scenario: A 2-minute eviction warning can't checkpoint 50GB, so the job restarts from the last full checkpoint and loses 30 minutes of compute.
  • The data pipeline impact: An ETL job evicted mid-JOIN writes partial output that downstream jobs read as complete — wrong aggregates, no error.
  • The non-reproducibility: Eviction-retry runs differ through non-deterministic operations (sampling, hash partitioning), so two "identical" training runs yield different weights.

Cost ≠ Utilization — Competing Objectives in Data Collection

10 Instances at 20% CPU: Expensive but Safe. 2 Instances at 90%: Cheap but Fragile.
  • The tradeoff: High utilization is cheap but leaves no headroom, so saturated CPUs compute "real-time" features from stale data.
  • The data quality issue: Features computed with 30-second lag under load but 1-second lag in training create training-serving skew from infrastructure pressure alone.
  • The cost-driven data loss: Event sampling, shorter retention, and less frequent pipelines each cut cost — and each is a data quality degradation in disguise.

Capacity Planning From Non-Stationary Demand

Last Year's Pattern ≠ This Year's. Until It Suddenly Is Again.
  • The problem: Capacity planning extrapolates history, but product launches, viral events, and competitor outages were never in the training data.
  • Under-provisioning: An overwhelmed collection system drops events, so training data has gaps exactly during peak load — where the model matters most.
  • Over-provisioning: Idle capacity invites right-sizing down to "barely enough," which fails at the first unexpected spike — the cycle repeats every quarter.
