Internet Outages / Cascading Infrastructure Failures

Shared infrastructure makes failures correlated, fast, and self-hiding — the monitoring dies with the system, and the mitigations (retries, updates, caches) amplify the damage.

One Cloud Region Takes Down Half the Internet

Shared Dependency = Correlated Failure
  • The blast radius: One region failure takes thousands of companies' services offline simultaneously — streaming, chat apps, smart doorbells, robot vacuums, all at once.
  • Broken assumption: Models assuming "independent failures" between services are wrong — everything sits on the same infrastructure.
  • The lesson: Correlated failure from a shared dependency, not many independent events.

EDR Vendor BSOD (July 2024) — 8.5M Machines Simultaneously

One Bad Push = 8.5M Bricks at Once
  • The event: A faulty update pushed to ALL Windows endpoints at once caused a boot loop on 8.5M machines.
  • No remote fix: A machine that can't boot can't receive the fix — manual recovery required per machine.
  • The impact: Airlines grounded, hospitals dark, banks offline.
  • The irony: The "reliability" of automated updates is a single point of failure at global scale.

BGP Misconfiguration Propagates Globally in Seconds

One Wrong Route Advertisement Black-Holes Worldwide Traffic
  • The weakness: BGP (the routing protocol) has no authentication — one ISP advertising a wrong route pulls the internet's traffic into a black hole.
  • Real case: Pakistan trying to block a video platform (2008) accidentally blocked it globally for 2 hours.
  • The speed: A single misconfiguration in one country has worldwide impact in under 60 seconds — no human can react fast enough.

DNS Failures Are Invisible — Everything Just "Doesn't Work"

One Root Cause, Fifty Different Symptoms
  • No error message: DNS down means the browser just says "cannot resolve" — users blame their WiFi, the website, or their computer.
  • Symptom scatter: EVERY service fails simultaneously but with DIFFERENT symptoms, making debugging impossible for non-experts.
  • The data trap: User reports describe 50 different problems, but the root cause is ONE DNS failure.

Cascading Retry Storms Amplify the Problem

The Retry Designed for Resilience CAUSES the Failure
  • The setup: Service A calls slow Service B and retries 3x — but 1000 instances of A retry simultaneously, so B gets 3000x normal load and crashes.
  • The feedback loop: B's errors make A retry MORE aggressively — load goes 1x → 3x → 9x → 27x in seconds.
  • The lesson: Exponential amplification from a mechanism built for reliability.

Observability Dies WITH the System It Monitors

"No Alerts" Might Mean "Alerting Is Dead"
  • The paradox: The monitoring service runs on the same infrastructure it monitors — cloud provider goes down, CloudWatch goes down, and you can't see that the cloud is down.
  • The trap: "No alerts" doesn't mean "no problem" — the alerting system IS the thing that's broken.
  • The regress: You need monitoring of your monitoring — but where does that run?

Partial Failure Is Worse Than Complete Failure

"99% Success Rate — Healthy!" While Some Users Are 100% Broken
  • The contrast: Complete failure is obvious and gets immediate response; partial failure means some requests succeed, some fail, some are slow.
  • Shifting target: 10% of users affected — a different 10% each minute.
  • Hidden in aggregates: Monitoring reports "99% success rate" while that 1% represents users COMPLETELY unable to use the service.

DNS Poisoning / Cache Corruption

Your Server Sees Zero Traffic — Because It All Went Elsewhere
  • The mechanism: An attacker or bug corrupts a DNS cache — users get the wrong IP and are sent to the wrong server for the TTL duration (minutes to hours).
  • Invisible internally: From your server's perspective nobody is connecting, so nothing looks wrong — the traffic simply went elsewhere.
  • Detection: Requires EXTERNAL probing of your own domain, not internal monitoring.

Malware Propagation Outruns Human Response

By the Time You Detect It, the Network Is Already Compromised
  • Ransomware worm (2017): Spread laterally across networks via an SMB exploit — an infected machine scans the local network and infects ALL vulnerable machines in seconds.
  • Destructive malware: Spread via an accounting software update and destroyed 10,000+ machines at Maersk in 10 minutes.
  • The asymmetry: Propagation speed exceeds human response speed — detection arrives after compromise is total.

Post-Mortem Data Reconstruction Is Forensic Archaeology

The Most Critical 5 Minutes of Data = The 5 Minutes Where Collection Failed
  • Missing logs: After a major outage, the logs are ON the machines that crashed and the metrics service was down.
  • Unreliable time: Timestamps can't be trusted (NTP failed too), and clock skew makes events from different services impossible to correlate.
  • The result: Reconstructing the incident timeline is forensic archaeology, not data analysis.
