Predictive Analytics Pitfalls

Common failure modes in enterprise ML deployment that practitioners encounter repeatedly

Feature Leakage: #1 Cause of "Too Good to Be True"

Feature Leakage: #1 Cause of "Too Good to Be True"
A model at 99% accuracy almost certainly has feature leakage. One of the input features encodes the target variable, either directly or through a proxy that wouldn't exist at prediction time. Classic examples: using "account_status=closed" to predict churn (status IS the outcome), using hospital discharge codes to predict admission diagnosis, or including future timestamps in features. The check: for each feature, ask "would this value exist at the exact moment I need to make the prediction?" If no, it's leakage.

Model Degradation Without Retraining

Model Degradation Without Retraining
Model deployed in January performs well. By June: accuracy has dropped 8%. Nobody noticed because no monitoring was in place. Data distributions drifted, customer behavior changed, a competitor launched a new product, seasonality shifted — but the model is frozen in January's reality. Without performance monitoring and automated alerts, degradation is silent. By the time someone checks, months of degraded predictions have already caused damage. Every model has a shelf life; most teams don't know what theirs is.

Business Metric ≠ Model Metric

Business Metric ≠ Model Metric
Model optimizes AUC. Business cares about revenue. A model with AUC 0.85 that captures high-value customers outperforms a model with AUC 0.92 that captures low-value ones. Metric mismatch leads to technically excellent but commercially useless models. The data science team celebrates improving AUC from 0.88 to 0.91; the business sees no revenue change because the new model just got better at classifying customers who don't matter. Always ask: "if this metric improves by X, how much money does the business make?"

Stakeholder Cherry-Picking

Stakeholder Cherry-Picking
Model shows mixed results overall. Stakeholder selects the ONE segment where it works brilliantly, presents that to leadership. "Model improves conversion by 40%!" — in one segment, for one week, with n=200. Overall effect: +2%. This is post-hoc subgroup analysis without multiple testing correction. The larger the number of segments you examine, the more likely one will show extreme results by chance. When someone presents only the best segment, ask: "How many segments did you look at before finding this one?"

Confidence Miscalibration

Confidence Miscalibration
Model says "80% chance of churn" for 1,000 customers. If calibrated, approximately 800 should actually churn. If miscalibrated, maybe only 500 do. Probability outputs are not actual probabilities without explicit calibration. Most models (especially tree ensembles and neural nets) produce scores that rank correctly but don't correspond to true frequencies. Using raw model scores to set intervention thresholds ("contact everyone above 70%") fails when 70% doesn't mean 70%. Calibration is rarely checked and almost never maintained after deployment.

Deployment Gap (Lab → Production)

Deployment Gap (Lab → Production)
Works in Jupyter notebook on historical data. Deploy to production: different data format, missing features (that column doesn't exist in the real-time feed), different encoding (training used one-hot, production sends integers), latency constraints (model takes 2s but SLA requires 100ms), edge cases never seen in training (nulls, negative values, Unicode). "Works in lab" ≠ "works in prod." The gap between a notebook prototype and a production system is not engineering overhead — it's where most model value is destroyed.

Interpretability Theater

Interpretability Theater
SHAP values are computed, displayed in a colorful plot, and shown to stakeholders who nod approvingly without understanding them. "Feature importance" is used to justify decisions it doesn't actually explain. The explainability checkbox is ticked without real understanding. SHAP shows marginal contribution, not causation. A feature being "important" doesn't mean changing it would change the outcome. Stakeholders hear "age is important" and conclude "target older people" — but SHAP doesn't say that. Interpretability without statistical literacy is theater.

Premature Productionization

Premature Productionization
POC model with n=500 and 3 features gets impressive results in a demo. Stakeholder demands immediate production deployment. Model fails at scale because the POC was a lucky subset with unusually high signal-to-noise that doesn't generalize. The demo dataset was curated (clean data, complete features, recent customers), but production data is messy, incomplete, and includes populations never seen in the POC. The pressure to "just deploy it" skips validation, stability testing, and edge case analysis. Most ML project failures trace back to premature productionization.
