Caching

Statistical pitfalls in caching systems — the false comfort of hit rates, thundering herds, and consistency impossibilities.

Hit Rate ≠ Correctness

Hit Rate ≠ Correctness
Cache hit rate = 99.5% — sounds great. But 0.5% misses + 0.1% stale hits serving WRONG data. High hit rate with stale data = confidently wrong. Hit rate doesn't measure accuracy of cached values. A 99.5% hit rate tells you nothing about whether those hits are returning correct, current data. The metric everyone watches is orthogonal to the metric that matters.

TTL Goldilocks Problem

TTL Goldilocks Problem
TTL too short: constant cache misses, no benefit, backend hammered. TTL too long: serving data minutes/hours stale. There's no universal "right TTL" — it depends on how fast the underlying data changes and how much staleness is tolerable. Every TTL is a tradeoff between freshness and performance, and the optimal value shifts as your data's change rate shifts.

Thundering Herd on Expiry

Thundering Herd on Expiry
Popular key expires → 10,000 simultaneous requests hit backend → backend overwhelmed → timeout → all 10,000 retry → amplified storm. Cache expiry of hot keys = potential outage trigger. The more popular the key, the worse the thundering herd. The very success of caching (concentrating load on few keys) creates the vulnerability.

Cache Poisoning Persists

Cache Poisoning Persists
Attacker poisons DNS cache or CDN cache with wrong response → cached for TTL duration → EVERY user served wrong/malicious content. One successful poison = duration × users affected. Stale malicious data = worse than no cache. The cache amplifies the attack by serving the poisoned response at scale for the entire TTL window.

Cold Start After Deployment

Cold Start After Deployment
Deploy new version → all caches empty → backend absorbs 100% of traffic → backend designed for 5% of traffic (the miss rate) → instant overload → cascade failure. The transition from "warm" to "cold" is a cliff. Your backend's true capacity requirement is hidden by the cache — until the cache disappears and reality arrives all at once.

Write-Through vs Write-Behind Consistency

Write-Through vs Write-Behind Consistency
Write-through: slow writes but cache = source of truth. Write-behind: fast writes but cache can lose data on crash. Read-after-write consistency depends on which you choose. Distributed cache + distributed DB = eventual consistency nightmares. Neither strategy eliminates the consistency problem — they just move it to different failure modes.
