43. ACID, BASE & Eventual Consistency

Consistency models and their implications for data pipelines, profiling correctness, and analytical reproducibility.

Core tension: ACID gives you correctness guarantees but limits throughput and distribution. BASE gives you availability and partition tolerance but means your pipeline might read stale, partial, or out-of-order data. The profiling pipeline must know which consistency model its source data lives under — because "correct" means different things in each.

ACID — Strong Consistency

Atomicity, Consistency, Isolation, Durability. The transactional guarantee model from relational databases.

PropertyWhat It MeansWhat Breaks Without It
AtomicityA transaction either fully completes or fully rolls back. No partial writes.Half-written records, orphaned foreign keys, corrupted state.
ConsistencyEvery transaction moves the database from one valid state to another. Invariants always hold.Negative balances, duplicate keys, violated constraints.
IsolationConcurrent transactions don't see each other's intermediate state.Dirty reads, phantom rows, non-repeatable reads.
DurabilityOnce committed, the data survives crashes, power loss, hardware failure.Acknowledged writes disappear after restart.

BASE — Eventual Consistency

Basically Available, Soft state, Eventually consistent. The availability-first model from distributed NoSQL systems.

PropertyWhat It MeansThe Trade-off
Basically AvailableThe system always returns a response — even if the data is stale or partial.You get an answer, but it might not be the latest truth.
Soft StateState may change over time even without new input, as replicas converge asynchronously.The same read issued twice may return different values (replica lag).
Eventually ConsistentGiven enough time without new writes, all replicas converge to the same value."Enough time" is unbounded — you don't know when convergence has happened.

ACID vs BASE — Side by Side

DimensionACIDBASE
PriorityCorrectness firstAvailability first
CAP theoremCP — sacrifices availability under partitionAP — sacrifices consistency under partition
Failure modeRejects writes it can't guaranteeAccepts writes optimistically, resolves conflicts later
Read guaranteeYou always read committed, consistent stateYou might read stale or partially-converged state
Scale modelVertical (single-node coordination)Horizontal (multi-node, partition-tolerant)
Typical systemsPostgreSQL, MySQL, Oracle, SQL ServerCassandra, DynamoDB, CouchDB, Riak
The chemistry metaphor: Acids and bases are opposites on the pH scale. ACID and BASE are opposites on the CAP theorem spectrum — one maximizes consistency, the other maximizes availability. Neither is universally better; the right choice depends on what failure mode your system can tolerate.

Implications for Data Profiling

1. Profiling an eventually-consistent source mid-convergence produces phantom bimodality (two versions of truth coexist).

2. Distribution shape can flicker between runs if reads hit different replicas.

3. Row counts, null rates, and cardinality estimates are non-deterministic without snapshot isolation.

4. Joins across systems with different consistency models create impossible states silently.

Anti-Patterns

• Assuming ACID when reading from a distributed cache or event stream

• Profiling during active ingestion without watermark/fence

• Comparing two pipeline runs that read from different replica states

• Using row count as a completeness check under eventual consistency
