3. Markdown

Readable as plain text, renderable to anything.

Core trade-off: Human convenience and universal readability — but no single standard exists (CommonMark, GFM, MDX, Pandoc all diverge).
What It Is A lightweight markup language that uses punctuation characters (#, *, -, []) to indicate formatting. Designed so the source text is readable even without rendering. Created by John Gruber in 2004, now the de facto standard for developer documentation.
Structure / Syntax Headings with # prefixes. Paragraphs separated by blank lines. Bold with **text**, italic with *text*. Lists with - or 1.. Code blocks with triple backticks. Links as [text](url). Tables with pipe characters (GFM extension).
Strengths Diffable in version control — changes are meaningful in plain text. Readable without any rendering tool. LLM-native format — models produce and consume it naturally. Converts to HTML, PDF, DOCX, slides. Extremely low friction to write.
Weaknesses No formal spec originally — Gruber's description was ambiguous. Fragmented implementations disagree on edge cases. Limited semantics (no admonitions, no figure captions without extensions). Tables are painful for wide data. No built-in metadata standard.
Business Use Case Documentation (README files, wikis, docs-as-code). Note-taking (Obsidian, Notion export). LLM input/output format. Technical blogging. API documentation. Internal knowledge bases. Anywhere humans write structured text that machines also need to process.
Example 
## Source markdown

- **Bold item** with `inline code`
- A [link](https://example.com)

| Col A | Col B |
|-------|-------|
| 1     | hello |
This renders to: a heading, a bulleted list with bold and code, a hyperlink, and a simple table. The same source is readable as-is in any text editor — that is the design goal.
