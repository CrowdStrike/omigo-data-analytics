10. Avro

Binary format where schema travels with the data.

Core trade-off: Self-describing files that any consumer can decode without external documentation — but schema management becomes its own distributed systems problem at scale.
What It Is A row-oriented binary serialization format from the Hadoop ecosystem. Unlike Protobuf, Avro embeds the writer's schema in the file header, so any reader can decode the data without a separate schema file. Schema evolution is handled through reader/writer schema resolution rules.
Structure / Syntax An Avro file (container) has: a header with the writer's schema (as JSON), a sync marker, and data blocks of serialized records. Schema defines types: null, boolean, int, long, float, double, string, bytes, plus complex types (record, enum, array, map, union, fixed). No field numbers — uses field names.
Strengths Schema in file header — any tool can decode without external documentation. Reader/writer schema resolution handles evolution gracefully. Compact binary encoding. Splittable at block boundaries for parallel processing. Rich type system including unions (nullable fields).
Weaknesses Schema registry (like Confluent's) needed at scale to manage versions. Not human-readable. Less tooling than Parquet for analytics. Row-oriented means no column pruning for analytical queries. Schema resolution rules have subtleties that cause confusion (default values, field ordering).
Business Use Case Kafka message serialization (with Schema Registry). Hadoop data storage (the original use case). Schema evolution across microservices. Data pipelines where producers and consumers evolve independently. Any streaming system where you need guaranteed decode-ability.
Example 
// Writer schema (embedded in file header as JSON):
{
  "type": "record",
  "name": "User",
  "fields": [
    {"name": "id", "type": "long"},
    {"name": "name", "type": "string"},
    {"name": "email", "type": ["null", "string"],
     "default": null}
  ]
}

// Reader schema (what the consumer expects):
// Can ADD fields with defaults — old files still readable
// Can REMOVE fields — reader just ignores them
// Can promote int → long, float → double
// CANNOT change field type incompatibly
// CANNOT remove fields that have no default
The reader/writer resolution means: a file written with schema v1 can be read by code expecting schema v3, as long as the evolution rules were followed. No rewriting of old data needed.
