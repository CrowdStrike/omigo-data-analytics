9. Protocol Buffers / Thrift

Binary schema-first serialization with code generation.

Core trade-off: Compact encoding and safe schema evolution via field numbering — but the data is not human-readable and requires tooling to inspect.
What It Is Schema-defined binary serialization formats. You write a schema file (.proto or .thrift), run a code generator, and get type-safe serialization/deserialization in your target language. The wire format is compact binary — not human-readable. Protocol Buffers (Google) and Thrift (Facebook/Apache) solve the same problem with slightly different designs.
Structure / Syntax Schema defines messages with typed, numbered fields. Each field has: a unique number (wire identifier), a type (int32, string, enum, nested message), and a label (optional/repeated). The binary encoding uses field numbers — not names — so fields can be renamed without breaking compatibility.
Strengths Field numbering enables schema evolution — add fields without breaking old consumers. Compact encoding (5-10x smaller than JSON). Generated code in every major language. gRPC integration for RPC. Strong typing catches errors at compile time. Backward and forward compatible by design.
Weaknesses Not human-readable — cannot inspect data without tooling. Requires .proto/.thrift files to decode. Code generation adds build complexity. Debugging network issues requires protobuf-aware tools. Schema registry/distribution becomes its own problem at scale.
Business Use Case Inter-service RPC (gRPC). Mobile app communication (smaller payloads = faster on cellular). High-throughput event pipelines. Any system where services evolve independently and need backward-compatible wire formats. Google, Facebook, and most large tech companies use these internally for nearly everything.
Example 
// user.proto
syntax = "proto3";

message User {
  string name = 1;       // Field number 1
  int64 user_id = 2;     // Field number 2
  string email = 3;      // Field number 3
  repeated string roles = 4;  // Field number 4

  // Added in v2 — old consumers simply skip it
  optional string department = 5;
}

// On the wire, field NUMBERS are encoded, not names.
// Old code seeing field 5 skips it (unknown field).
// New code not seeing field 5 uses the default value.
// This is why you NEVER reuse or change field numbers.
The key insight: field numbers are the permanent identity. You can rename email to contact_email freely — the wire format only sees "field 3, type string."
