4. JSONL / NDJSON

One JSON object per line.

Core trade-off: Appendable, splittable, and streamable — but there is no root document structure, no way to express file-level metadata.
What It Is A text format where each line is a complete, self-contained JSON object (or value). No wrapping array, no commas between records, no root structure. The newline character is the only record separator. JSONL and NDJSON are effectively the same format with different names.
Structure / Syntax Each line: one valid JSON object terminated by \n. No trailing commas. No enclosing brackets. Each line is independently parseable. Files can be concatenated with cat. Lines can be split across workers at any newline boundary.
Strengths Streamable — process one record at a time without loading the full file. Parallelisable — split at any newline for distributed processing. Appendable — just write a new line. Tail-able while another process writes. Trivial error isolation (bad line doesn't corrupt file).
Weaknesses No schema — fields can vary between lines. Each line must be valid JSON independently (no multi-line pretty-printing). Large numbers still lose precision past 2^53. No file-level metadata or header. No standard way to express relationships between records.
Business Use Case Log shipping (structured logging to files). Event streams and click-stream data. ML training data (one example per line). Incremental ETL pipelines. Kafka consumer output. Any scenario where data arrives continuously and you want to append without rewriting.
Example 
{"event":"click","user_id":12345,"ts":"2024-03-15T10:22:01Z","page":"/pricing"}
{"event":"purchase","user_id":12345,"ts":"2024-03-15T10:24:33Z","amount":49.99}
{"event":"click","user_id":67890,"ts":"2024-03-15T10:25:01Z","page":"/docs"}
{"event":"error","user_id":null,"ts":"2024-03-15T10:25:02Z","code":500}
Each line stands alone. You can grep for errors, wc -l for count, split for parallelism, or tail -f while the file is still being written.
