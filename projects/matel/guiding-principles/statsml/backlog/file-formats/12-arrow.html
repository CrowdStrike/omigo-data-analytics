12. Arrow

In-memory columnar format for zero-copy sharing.

Core trade-off: Zero-copy data sharing between tools and languages eliminates serialization overhead — but the columnar memory layout has overhead for small datasets and Arrow is not a persistence format.
What It Is Apache Arrow is a language-agnostic specification for columnar data in memory. It defines how arrays of typed values should be laid out in RAM so that any tool (Pandas, DuckDB, Spark, Polars, R) can read the same memory without copying or converting. It is a memory format, not a file format — though Arrow IPC and Feather provide serialization.
Structure / Syntax Data is organized as record batches: a schema plus column arrays. Each column is a contiguous buffer of typed values with a separate validity bitmap for nulls. Strings use an offsets buffer + data buffer. Nested types (struct, list, map) compose these primitives. All buffers are aligned for SIMD and cache-line efficiency.
Strengths Zero-copy between tools — DuckDB query result consumed by Pandas with no serialization. Language-agnostic (C, C++, Python, R, Java, Rust, JS all share the same layout). SIMD-friendly memory alignment. Eliminates the "convert to my format" tax. Enables IPC between processes via shared memory.
Weaknesses Memory overhead for small datasets (columnar layout has per-column buffer costs). Not a storage/persistence format by itself. Ecosystem still maturing (some libraries have partial support). The full spec is complex. Does not compress data in memory (that's intentional for compute speed).
Business Use Case Analytics engine interoperability (DuckDB ↔ Pandas ↔ Polars). IPC between Python and R processes. Query engine internals (DataFusion, Velox, Acero). DataFrame libraries (Polars is Arrow-native). Flight RPC for high-speed data transfer. Any pipeline where the serialization tax between tools is the bottleneck.
Example 
Without Arrow (traditional):
  DuckDB query → serialize to bytes → deserialize into
  Pandas numpy arrays → copy strings → rebuild index
  Cost: O(n) copy + O(n) type conversion + memory spike

With Arrow (zero-copy):
  DuckDB query → Arrow record batch (already in memory)
  Pandas reads the SAME memory via Arrow-backed columns
  Cost: O(1) pointer handoff, zero additional memory

Real-world impact:
  10M row query result, 8 columns
  Traditional: 2.1 seconds, 800MB peak memory
  Arrow:       0.003 seconds, 0MB additional memory

The key insight: Arrow eliminates the tax you pay
every time data crosses a library boundary. When your
pipeline is DuckDB → Pandas → scikit-learn → Polars,
that tax was being paid 3 times. Now it is zero.
