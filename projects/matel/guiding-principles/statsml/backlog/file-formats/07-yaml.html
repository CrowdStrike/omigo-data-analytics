7. YAML

Configuration format readable by humans.

Core trade-off: Beautiful readability and comments — but invisible indentation hazards and implicit type coercion create silent bugs that surface in production.
What It Is YAML Ain't Markup Language — a data serialization format that uses indentation instead of braces/brackets. Designed for human readability with support for comments, multi-line strings, and complex nested structures. The spec is surprisingly large (86 pages for YAML 1.2).
Structure / Syntax Key-value pairs with key: value. Nesting via indentation (spaces only, not tabs). Lists with - item. Comments with #. Multi-line strings with | (literal) or > (folded). Anchors (&name) and aliases (*name) for reuse. Multiple documents separated by ---.
Strengths Human-readable without any ceremony. Supports comments (unlike JSON). Complex nested structures are visually clear. Anchors/aliases reduce repetition. Multi-line strings are natural. The format DevOps teams actually want to write by hand.
Weaknesses Indentation-sensitive — one wrong space breaks everything silently. The Norway problem: NO is parsed as boolean false. Implicit typing: version: 3.10 becomes float 3.1. The spec is enormous and few parsers implement it fully. Security issues with arbitrary object instantiation.
Business Use Case Kubernetes manifests. CI/CD pipelines (GitHub Actions, GitLab CI). Ansible playbooks. Docker Compose files. Application configuration. Helm charts. Any infrastructure-as-code where humans write and review the files directly.
Example 
# Gotcha demonstration
countries:
  - US
  - GB
  - NO        # Parsed as boolean false!

python:
  version: 3.10   # Parsed as float 3.1, not string "3.10"

ports:
  - 22
  - 0o77     # Octal 63, not string "0o77"

# Safe version — quote everything ambiguous:
safe_version: "3.10"
safe_country: "NO"
The Norway problem and version truncation have caused real production outages. YAML's implicit type coercion means values silently change type based on content patterns.
