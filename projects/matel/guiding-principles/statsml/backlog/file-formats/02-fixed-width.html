2. Fixed-Width Records

Column positions defined in a separate document.

Core trade-off: Fast positional parsing with zero ambiguity — but the schema lives outside the file, in a document you hope someone maintained.
What It Is A text format where each field occupies a predefined number of characters in every row. No delimiters needed — you extract fields by byte position. The layout specification (which columns start where, how wide each is) is documented separately.
Structure / Syntax Every record is the same length. Fields are padded (usually right-padded with spaces for text, left-padded with zeros for numbers). A separate "record layout" document defines: field name, start position, length, data type, and padding rules.
Strengths O(1) field access — jump directly to byte offset. No parsing ambiguity whatsoever. Fixed record size enables random access to any row. Extremely fast to read in languages like C/COBOL. No quoting issues, no escape characters.
Weaknesses Schema is external documentation that can drift from reality. Wasted space when short values are padded to maximum field width. Cannot represent nested or variable-length data. Adding a field means changing every record. Human-unreadable without the layout doc.
Business Use Case Banking and payroll file transfers (NACHA/ACH format). Mainframe batch processing. Government reporting (IRS, census). Insurance claims interchange. Any domain where COBOL systems still run — which is most of financial infrastructure.
Example 
SMITH   JOHN    19850315NYC 00045000
JONES   ALICE   19901122CHI 00072500
CHEN    BOB     20010830LAX 00031000
Layout: Last name (cols 1-8), First name (cols 9-16), DOB (cols 17-24, YYYYMMDD), City code (cols 25-27), Space (col 28), Salary in cents (cols 29-36, zero-padded). Every row is exactly 36 characters.
