11. Parquet / ORC

Columnar on-disk storage.

Core trade-off: Analytical query speed through column pruning and predicate pushdown — at the cost of expensive row-level updates and write amplification.
What It Is Binary columnar file formats that store data by column rather than by row. Parquet (from the Hadoop ecosystem, now universal) and ORC (Optimized Row Columnar, from Hive) solve the same problem: make analytical queries fast by only reading the columns needed. Both include metadata statistics (min/max/count) per column chunk.
Structure / Syntax Data is organized into row groups (Parquet) or stripes (ORC). Within each row group, data for each column is stored contiguously and compressed independently. Footer contains schema, row group locations, and column statistics (min, max, null count). Encoding is per-column (dictionary, RLE, delta, etc.).
Strengths Column pruning — read only the columns your query touches. Predicate pushdown — skip entire row groups using min/max statistics. Excellent compression (similar values compress well together). Encoding adapts per column. Metadata enables query planning without scanning data.
Weaknesses Expensive row-level updates (must rewrite entire row groups). Write amplification for frequent small inserts. Not streamable — must write complete row groups. Random row access is costly. File size overhead for very small datasets. Tooling for inspection is less intuitive than text formats.
Business Use Case Data lakes (S3 + Parquet is the modern standard). Analytical data warehouses. Any query that reads few columns from wide tables. Time-series analysis. ML feature stores. The format behind most "big data" query engines (Spark, Presto, DuckDB, BigQuery export).
Example 
Scenario: Table with 200 columns, 1 billion rows
Query: SELECT avg(price) FROM sales WHERE region = 'US'

What Parquet reads:
- Column "price": only this column's data (0.5% of file)
- Column "region": only this column's data (0.5% of file)
- Row group stats: skip groups where region min/max
  excludes 'US' (maybe 70% of groups skipped)

Total I/O: ~1% of file size × 30% of row groups
         = 0.3% of total data actually read

What CSV would read: 100% of the file, every time.

This is why a 50GB Parquet file can answer queries
in seconds that would take minutes on the same data
stored as CSV.
The 200-column table reading 2 columns touches roughly 1% of the data. Combined with row group skipping via statistics, the actual I/O can be under 0.5% of file size.
