Turing Complete Languages & Query Systems

Discussion — Computational Theory Applied

Core idea: SQL is intentionally NOT Turing complete (in its pure form) — it's declarative, terminating, and analyzable. Adding UDFs, stored procedures, recursive CTEs without bounds, or embedding queries in general-purpose languages makes the system Turing complete — gaining expressiveness but losing guarantees about termination, resource usage, optimization, and determinism.

The Power / Safety Tradeoff

Declarative (Constrained)
  • Examples: SQL, Datalog, regular expressions, CSS selectors
  • Properties you get: guaranteed termination, predictable resource usage, global optimization possible, can prove correctness properties
  • What you lose: can't express all computations, sometimes awkward to write, limited control flow
  • Key insight: constraints enable reasoning. If the optimizer KNOWS a query terminates, it can rewrite it freely.
Turing Complete (Unconstrained)
  • Examples: Python, Java, PL/pgSQL with loops, recursive CTEs without bounds
  • Properties you get: can express ANY computation, familiar imperative patterns, full generality
  • What you lose: can't guarantee termination (halting problem), can't predict resource usage, optimizer can't reason about opaque code, can't safely cache/parallelize
  • Key insight: freedom prevents reasoning. If the system can't see inside your code, it can't help you.

Where Query Systems Become Turing Complete

Explicit Escapes
  • UDFs in Python/Java — arbitrary code embedded in query execution
  • Stored procedures — PL/pgSQL, T-SQL with WHILE loops and conditionals
  • External function calls — Snowflake external functions, BigQuery remote functions
  • Custom Hive SerDes — arbitrary Java in serialization/deserialization
  • Spark UDFs — Python/Scala closures passed to the executor
Subtle Escapes
  • Recursive CTEs without LIMIT — unbounded recursion = Turing complete
  • dbt Jinja macros — SQL-only by design, but Jinja is Turing complete (loops, conditionals, recursion)
  • Dynamic SQL generation — EXECUTE IMMEDIATE with computed strings
  • Trigger cascades — triggers calling triggers, potentially non-terminating
  • Window functions with complex PARTITION BY — combinatorial explosion in practice if not bounded

What You Lose

When UDFs enter the picture:
  • Optimizer blindness — query planner can't push predicates through UDFs, can't reorder around them, can't eliminate dead columns inside them
  • Parallelization risk — can't safely parallelize if UDF has hidden state or side effects
  • Resource unpredictability — UDF might allocate unbounded memory, loop forever, or call external services
  • Termination uncertainty — halting problem: can't prove a general program terminates
  • Caching invalidation — can't deterministically cache if UDF behavior depends on hidden state

Concrete Examples

SQL → SQL + Python UDF

Pure SQL: optimizer sees the full plan, pushes filters, eliminates columns, chooses join order globally.

Add Python UDF: optimizer treats it as a black box. Can't push a WHERE clause past it. Can't eliminate input columns the UDF doesn't use (it might use them via reflection). Can't predict memory or time.

Result: 10x slower queries because the optimizer gives up.
Spark DataFrame → .mapPartitions

DataFrame API: Catalyst optimizer sees logical plan, fuses operations, predicts shuffle sizes, generates efficient code.

.mapPartitions(arbitrary_python_function): Catalyst stops. Everything after is a black box. No predicate pushdown, no column pruning, no code generation.

Result: Lost all Catalyst optimization for everything downstream of the escape hatch.
dbt: SQL-only → Complex Jinja

dbt philosophy: SQL-only transforms. Analyzable, testable, deterministic.

Complex Jinja macros: loops generating dynamic SQL, conditionals based on runtime variables, recursive macro calls. You've rebuilt a bad programming language on top of SQL.

Result: Lost the simplicity that was the whole point of dbt.
Design Implication for statsml

The statsml pipeline should prefer declarative specifications of transforms (what to compute) over imperative implementations (how to compute it).

This enables: optimization (reorder steps), parallelization (independent steps run concurrently), verification (can prove properties of declarative specs), reproducibility (declarative = deterministic).

Rule: imperative code at the edges, declarative specifications in the core.

The "Just Expressive Enough" Design Space

Sub-Turing Languages That Work
  • SQL (pure) — relational algebra + aggregation, no general recursion
  • Datalog (stratified) — recursive but stratified negation guarantees termination
  • Regular expressions — finite automata, always terminate, O(n) matching
  • Total functional languages — all programs provably terminate (Agda, Idris)
  • Linear types — guarantee resources are used exactly once
Could We Design One for Feature Transforms?
  • Input: column references, arithmetic, aggregations, window functions
  • Control: pattern matching on types (not general conditionals)
  • Composition: pipe outputs of one transform into another
  • No loops, no recursion, no external calls, no mutable state
  • Escape hatch: explicitly marked "custom transform" that opts out of guarantees
Question: Is this just SQL with a different syntax? Or is there a sweet spot between SQL and Python that gives us more expressiveness without losing analyzability?

Handling the Inevitable Escape Hatch

When imperative code is needed (and it will be), isolate it behind well-defined interfaces:
  • Contract: input schema → output schema (typed, validated at boundaries)
  • Guarantee: terminates within timeout (enforced externally)
  • Constraint: no side effects (or declared side effects, verified by sandbox)
  • Testing: property-based tests verifying the contract holds for generated inputs
  • Monitoring: runtime tracking of resource usage, alerting on anomalies

Key Discussion Points

  • How to handle the inevitable escape hatch (custom transforms) while maintaining system properties?
  • Is the Spark DataFrame API the right model? (Declarative until you need .map, then explicit opt-out)
