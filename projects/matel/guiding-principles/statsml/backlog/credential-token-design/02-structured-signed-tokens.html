Structured Signed Tokens

The JWT-family design — carry the claims inside the artifact and sign them, so any server holding the verification key can trust the token without ever phoning home.

Inversion: the database row itself is signed into the token, so verification becomes local math — both the design's power and its hardest problem.

1. What is it?

The JWT-family token carries its own proof.

  • Self-contained: subject, expiry, and scopes ride inside the token
  • Signed whole: the issuer signs the entire package
  • Local check: any key-holding server verifies integrity itself
  • No lookup: claims are trusted without a database round-trip
  • Two promises: signing and encrypting guarantee different things
  • Signed variant: tamper-evident but readable by anyone who sees it
  • Encrypted variant: sealed; only decryption-key holders can read
Root of trust: the verification key replaces the database — portable across services, awkward for pre-expiry takeback.

2. Anatomy of a signed token

  • Header: declares the algorithm and token type
  • Claims: the actual facts the token asserts
  • Signature: computed over the header and claims together
  • Tamper-evident: change one claim character, verification fails
  • Standard claims: subject, issuer, audience, issue time, expiry
  • Custom claims: scopes, roles, and tenant identifiers as needed
  • Bake-in: anything downstream needs is added at issue time
  • Rides along: every added claim travels on every request
  • Bloat habit: "just put it in the token" inflates overhead
Verifier decides: the signature covers the header too, so the verifier must enforce its own algorithm, never obey the token's.

3. Pros / cons

  • Stateless: local cryptography validates each token
  • No round-trip: the per-request database hit disappears
  • No dependency: auth stops relying on database availability
  • Portable: every key-holding service trusts one token
  • Right fit: exactly the shape service-to-service auth needs
  • Size: the token is large and grows with every claim
  • Leak surface: signed-only claims are readable to any viewer
  • Exposure paths: logs, URLs, and proxies all see every claim
  • Algorithm confusion: a threat-model-level verifier failure
  • The trap: obeying the header instead of a fixed expectation
  • The steer: verification weaker than the issuer intended
  • Revocation gap: valid until expiry, no matter what happens
  • Lever 1: short lifetimes shrink the damage window
  • Lever 2: a denylist consulted on every request
  • The irony: the denylist quietly reinstates the lookup

4. Prevalence: current vs historical

  • Dominant in: service-to-service auth and OAuth ecosystems
  • Why: one issuer trusted by many independent verifiers
  • Opaque wins: developer API keys and personal access tokens
  • Long-lived: such credentials prize central control
  • The trade: instant revocation beats saving a lookup
  • Early era: stateless-everything looked like the endgame
  • Push-back: the revocation problem drove practice to hybrids
  • Hybrid shape: a short-lived signed access token
  • Paired with: a long-lived, revocable refresh token
Quiet admission: neither pure design suffices — signed buys minutes of lookup-free checks, opaque keeps the issuer's kill switch.
