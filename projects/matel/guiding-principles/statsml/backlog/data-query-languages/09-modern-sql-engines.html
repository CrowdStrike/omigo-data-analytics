10. SQL on New Engines

The language became the stable layer while engines were replaced underneath
Compatibility with SQL grammar is the main adoption strategy for new systems. The cost of a new language is retraining everyone. So innovate the engine, keep the interface. SQL is the stable API — engines are the implementation detail.
What It Is Modern cloud-native query engines (Trino/Presto, BigQuery, Snowflake, DuckDB, Databricks SQL) that accept standard SQL but execute it on radically different architectures — serverless, separated storage/compute, federated, or embedded.
Core Idea Same SQL grammar, different execution architectures underneath. Separated storage and compute. Serverless scaling. Federated queries across sources. The language is the stable contract — the engine is replaceable.
Strengths Zero retraining cost — anyone who knows SQL is immediately productive. Ecosystem compatibility (BI tools, JDBC/ODBC drivers, notebooks all work). Decades of SQL optimization research inherited by new engines. Competition on performance, not syntax.
Weaknesses Vendor-specific extensions creep back (BigQuery's STRUCT syntax, Snowflake's VARIANT handling). Performance differences hidden behind identical syntax. Migration still has edge cases (date functions, NULL handling, type coercion). Cost models differ dramatically.
Business Use Case Cloud data warehouses, federated queries across heterogeneous sources, serverless analytics for variable workloads, lakehouse architectures, embedded analytics (DuckDB).
Example 
-- The same analytical query runs on all three engines:
-- BigQuery, Snowflake, Trino — same SQL, different execution

SELECT
    region,
    product_category,
    DATE_TRUNC('month', order_date) AS month,
    SUM(revenue) AS total_revenue,
    COUNT(DISTINCT customer_id) AS unique_customers
FROM orders
JOIN products ON orders.product_id = products.id
WHERE order_date >= '2024-01-01'
GROUP BY region, product_category, DATE_TRUNC('month', order_date)
ORDER BY total_revenue DESC;

-- Engine differences are invisible at this level:
-- BigQuery: serverless, slot-based execution
-- Snowflake: warehouse auto-scaling
-- Trino: federated across S3 + PostgreSQL + Kafka
