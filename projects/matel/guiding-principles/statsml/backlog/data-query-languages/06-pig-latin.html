7. Pig Latin

Dataflow DAGs for Hadoop — the transitional language between MapReduce and SQL-on-cluster.
Core trade-off: Higher-level than MapReduce but lower than SQL. You describe dataflow steps and the system compiles to MapReduce jobs. Proved the concept — then was replaced by exactly what it proved.

Bottom-up vs top-down: SQL is top-down — you declare the final result and the optimizer works backward to find the path. Pig Latin is bottom-up — you build the result step by step, each line transforming the previous output. Like Splunk SPL, you think in a pipeline: load → filter → group → project → store. The programmer sees the data flow; in SQL, only the optimizer does.

What It Is

A dataflow language developed at Yahoo (2008) that compiles procedural data transformation scripts into sequences of MapReduce jobs on Hadoop.

You write LOAD, FILTER, GROUP, FOREACH, JOIN, STORE — the compiler plans the MapReduce stages. Explicit data flow, implicit parallelism.

Why it mattered: proved that a higher-level abstraction over MapReduce was viable and necessary — paving the way for SQL-on-Hadoop.
Compilation Pipeline
Each Pig statement becomes one or more MapReduce stages.

Strengths & Weaknesses

Strengths
  • Much easier than raw MapReduce for multi-step pipelines
  • Handles nested data (bags, tuples, maps) naturally
  • Extensible via User Defined Functions (UDFs)
  • Good for ETL where step ordering matters
  • Lazy evaluation enables some optimization
Weaknesses
  • No optimizer in early versions — execution order was literal
  • Another language to learn (neither SQL nor Java)
  • Made redundant by HiveQL and then Spark SQL
  • No interactive queries — batch only
  • Small community; effectively abandoned by 2017
Top-Down vs Bottom-Up
SQL hides the plan → better optimization. Pipeline shows the plan → better debugging.

Business Use Case

Historical context (2008–2014): Hadoop ETL pipelines at Yahoo, where analysts needed to process web-scale data without writing raw Java MapReduce.

What it solved: reduced a 200-line Java MapReduce job to 10 lines of Pig, making data engineers 10× more productive on batch ETL.

Why it died: once SQL itself could compile to distributed plans (Hive, then Spark SQL), there was no reason to learn a separate language that offered less optimization.
Same Task — Three Eras
Lines of code for word-count: MapReduce ~200, Pig ~10, Spark SQL ~3.

Example

Scenario: process web server access logs to find URLs with the most 500-errors.

Each statement transforms the data one step further. The compiler sees the full DAG and can merge stages where possible.

Key operators used:

  • LOAD — read from HDFS
  • FILTER — narrow rows
  • GROUP — collect by key
  • FOREACH...GENERATE — project/transform
  • ORDER — sort output
  • STORE — write back to HDFS
Pig Latin Script
-- Load web server logs
logs = LOAD '/data/access_logs'
    USING PigStorage('\t')
    AS (ip:chararray, ts:chararray,
        method:chararray, url:chararray,
        status:int, bytes:int);

-- Keep only server errors
errors = FILTER logs BY status >= 500;

-- Group by URL
by_url = GROUP errors BY url;

-- Count errors per URL
counts = FOREACH by_url GENERATE
    group AS url,
    COUNT(errors) AS error_count;

-- Top offenders
ranked = ORDER counts BY error_count DESC;
top20 = LIMIT ranked 20;

-- Write output
STORE top20 INTO '/output/error_hotspots';
