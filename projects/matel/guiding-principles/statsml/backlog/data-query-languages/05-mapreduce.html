6. MapReduce

The one reversal — scale required giving up the optimiser
Distribute work by writing explicit map and reduce functions. You become the optimizer. The lesson learned: this approach was wrong — expressing intent declaratively is more valuable than controlling execution manually.
What It Is A programming model (Google, 2004) for processing large datasets across clusters. The programmer writes two functions — map() and reduce() — and the framework handles distribution, fault tolerance, and scheduling.
Core Idea Programmer writes map() to emit key-value pairs and reduce() to aggregate values by key. The framework partitions, shuffles, sorts, and distributes work across commodity nodes. Fault tolerance via re-execution of failed tasks.
Strengths Horizontal scaling on commodity hardware (thousands of nodes). Fault tolerance through deterministic re-execution. Simple mental model — just two functions. Proven at Google/Yahoo scale for batch workloads.
Weaknesses You are the optimizer — no query planner, no automatic join strategies. Verbose Java boilerplate for simple operations. High latency (batch only, no interactive queries). No iterative processing (each step writes to disk). Intermediate shuffle is expensive.
Business Use Case Historical — early Hadoop batch ETL (2004-2012), web indexing at Google, log processing, large-scale text analysis. Largely replaced by higher-level frameworks but the distribution model persists underneath.
Example 
// Word Count — the canonical MapReduce example

map(key: filename, value: file_contents):
    for each word in file_contents:
        emit(word, 1)

reduce(key: word, values: list_of_counts):
    emit(word, sum(values))

// Framework handles: splitting input, distributing map tasks,
// shuffling by key, sorting, distributing reduce tasks,
// writing output, retrying failures
