# Filters and Joins That Cut a Corner

**Page type:** detail page (three card-sections, each a two-column layout table: text left 50%, canvas right 50%)
**HTML title tag:** Filters and Joins That Cut a Corner — Filters That Invent Correlations

**Subtitle:** The everyday SQL and dataframe operations — inner joins, WHERE clauses, drop-nulls, HAVING, LIMIT — that silently act as entry rules and bend the correlation matrix without anyone writing a filter on purpose.

## An Inner Join Is an Entry Rule

**Tags:** `sql` (red), `the mechanism` (blue)

- **Join semantics** — a row survives an inner join only if it is present in BOTH tables
- **Presence is not random** — when a table is written on activity, presence encodes that activity
- **The setup** — customer tenure and monthly spend are independent in the full customer table
- **The enrichment rule** — a profile row is written for long-tenured OR high-spending customers
- **The join becomes a door** — `customers INNER JOIN profiles` keeps only the union-driven rows
- **The deleted corner** — low-tenure and low-spend customers have no profile row, so they vanish
- **The invented link** — inside survivors, short tenure implies high spend, so the two look opposed
- **Seeded figure** — all 500 rows r = +0.038; the 257 joined rows r = -0.501; 243 dropped rows

*Example:* Tenure and spend drawn independently 500 times give r = +0.038, but the 257 rows that survive the inner join give r = -0.501 — a trade-off that exists in no customer's data.

**Key idea:** Nobody wrote `WHERE`, yet the join was a filter — the profile table's write condition is downstream of both columns, so joining to it conditions on a collider.

## The WHERE Clause and the Drop-Nulls Step

**Tags:** `same mechanism` (orange), `costumes` (blue)

- **A WHERE on a shared consequence** — filtering a column both features influence is a collider filter
- **Not a harmless subset** — the surviving rows have a relationship the full table does not have
- **"Active users only"** — the most common instance, because activity sits downstream of everything
- **`dropna()` per row** — its real condition is "was measured", and measurement is rarely random
- **`HAVING` on an aggregate** — the same collider filter applied one level up, at group granularity
- **`LIMIT` with `ORDER BY score`** — selecting on a composite score selects on every feature in it
- **Filtering on a common CAUSE** — controlling a confounder removes spurious correlation, and is fine
- **Filtering on a common EFFECT** — this alone manufactures correlation between independent features
- **Safe by timing** — a column fixed before the features existed (signup month) cannot be a collider

*Example:* `WHERE support_tickets > 0` looks like a data-quality guard, but tickets rise with both tenure and spend, so the filtered table shows the two trading off; `WHERE region = 'west'` touches neither and leaves the relationship intact.

**Key idea:** Cause versus effect decides the sign of the damage — filtering on a common cause removes a spurious link, filtering on a common effect invents one. They are opposite operations that look identical in SQL.

## Auditing a Pipeline for Corner-Cutting Filters

**Tags:** `checklist` (green), `practice` (blue)

- **Log row counts** — record rows before and after every filter step, and keep the ratio in the logs
- **Treat a large drop as risk** — a filter that removes a big share of rows can reshape the matrix
- **Diff the matrix** — recompute the correlation matrix before and after each filter and compare cells
- **Interrogate the filter column** — ask whether the features could have influenced its value
- **Prefer pre-fixed columns** — filter on values determined before the features were generated
- **Keep the rejects** — write refused rows to a side table so the true relationship stays measurable
- **Scope the claim** — if the filter is unavoidable, say the model is valid only inside that population
- **The hardest case** — a filter buried in a view or upstream ETL, because you never wrote it yourself
- **How to find it** — read the view definition, not the query, and compare its row count to the source

*Example:* On the seeded 500 rows, the tenure/spend cell moves from +0.038 to -0.501 after the join, while both cells involving an unrelated control column barely move — the diff points straight at the guilty pair.

**Key idea:** A correlation-matrix diff around every filter is cheap and catches this class of defect automatically — the cells that move are exactly the features the filter column depends on.
