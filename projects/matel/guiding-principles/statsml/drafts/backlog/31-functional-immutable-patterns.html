Functional Programming & Immutability in Data Systems

Discussion — Design Philosophy

Core idea: Data pipelines benefit enormously from functional programming principles — pure functions (same input → same output), immutable data (transforms produce new data, don't modify in place), composition (small functions chained together), and referential transparency (can replace any expression with its value). These aren't academic preferences — they directly prevent classes of bugs that plague data systems.

Why FP Fits Data Pipelines Naturally

A Pipeline IS Function Composition
  • raw → clean → transform → model → output
  • Each stage is a pure function: input DataFrame → output DataFrame, no side effects
  • Composition = can rearrange, parallelize, or skip steps without worrying about hidden state
  • Referential transparency = can cache any intermediate result safely
  • This isn't forcing FP onto data — data pipelines ARE functional by nature. The imperative style fights this.
What Imperative Gets Wrong
  • Mutation: "did step 3 modify what step 2 produced?" — invisible coupling between stages
  • Shared state: global config, database connections, cached values — any of these change and everything breaks
  • Ordering dependence: swap two steps and get different results because of hidden state
  • Testing: need to mock the world to test one function
  • Debugging: "what was the state at step 5?" requires reproducing all prior steps

Immutability in Practice

Code-Level Immutability
  • Don't mutate DataFrames — use .assign() to create new columns, not direct column assignment
  • Don't update rows in place — filter and create new DataFrames
  • Don't share mutable state between pipeline stages — pass immutable snapshots
  • Avoid global mutable state — no module-level variables that change between calls
The pandas trap: df['new_col'] = ... mutates in place. df = df.assign(new_col=...) creates a new DataFrame. The first hides state changes; the second makes them explicit.
Storage-Level Immutability
  • Write-once, read-many — Parquet files are immutable once written
  • Append-only tables — Delta Lake, Iceberg: new versions are appends, old versions stay
  • Event sourcing — every change is an appended event, current state = replay all events
  • Slowly changing dimensions — don't UPDATE rows, add new versions with timestamps
  • Time travel — Delta Lake, LakeFS: query any historical version
Anti-pattern: "Overwrite yesterday's table with today's results." This is a mutability bug at the storage level. You can't audit what yesterday looked like, can't debug regressions, can't replay.

Pure Functions in Practice

What Makes a Function Pure
  • Depends ONLY on its input arguments — not on global state, time, or external calls
  • Produces ONLY its return value — no writing to databases, files, or shared variables
  • Same input always produces same output — deterministic
  • No observable side effects — calling it twice is the same as calling it once and copying
What You Get From Purity
  • Testability: known input → assert known output. No mocking needed.
  • Memoization: cache results freely — output only depends on input
  • Parallelization: run pure functions concurrently without locks — no shared state to corrupt
  • Retry safety: if a step fails, re-run it without worrying about partial side effects
  • Refactoring: replace any expression with its value (referential transparency)
Pure Feature Transform
# Pure: depends only on input columns
def age_bucket(age: int) -> str:
    if age < 25: return "young"
    if age < 65: return "middle"
    return "senior"

# Impure: depends on external state
def age_bucket_v2(age: int) -> str:
    thresholds = db.get("age_thresholds")  # side effect!
    ...

If a function reads from a database → it's not pure → isolate it at the boundary, pass the thresholds as input.
Impurity at the Edges
# Impure boundary: reads config, files
config = load_config("pipeline.yaml")  # IO
raw_data = read_parquet("input.parquet")  # IO

# Pure core: all transforms are pure functions
clean = remove_nulls(raw_data)
features = engineer_features(clean, config)
results = validate(features, config)

# Impure boundary: writes output
write_parquet(results, "output.parquet")  # IO

Functional core, imperative shell.

Composition Patterns

Pipe / Chain
# pandas pipe: each step is independent
result = (
    df
    .pipe(remove_outliers)
    .pipe(normalize_numeric)
    .pipe(encode_categorical)
    .pipe(validate_schema)
)

# Each function: DataFrame → DataFrame
# Can reorder, skip, or add steps freely
# Can test each step in isolation
Higher-Order Functions
# Apply a transform strategy without hardcoding
def apply_normalization(df, strategy):
    """strategy is a function: column → column"""
    return df.assign(**{
        col: strategy(df[col])
        for col in numeric_columns(df)
    })

# Use different strategies
result_z = apply_normalization(df, z_score)
result_mm = apply_normalization(df, min_max)
result_r = apply_normalization(df, robust_scale)

Functions as values: pass, return, compose them.
Map / Filter / Reduce Over Collections
# Instead of loops with accumulators:
results = []
for feature in features:
    if is_numeric(feature):
        result = profile(feature)
        results.append(result)

# Functional:
results = [profile(f) for f in features if is_numeric(f)]

# Or with explicit map/filter:
results = list(map(profile, filter(is_numeric, features)))

No mutable accumulator. No loop variable leaking. Intent is clear from the structure.

Where Pure FP Breaks Down

Practical Limitations
  • Performance: immutable copies of 100M row DataFrames — need structural sharing or lazy evaluation
  • Integration: databases, APIs, file systems are inherently stateful — can't make them pure
  • Team familiarity: most data engineers think imperatively — FP has a learning curve
  • Debugging: long composition chains are hard to inspect mid-flow
  • Libraries: pandas, scikit-learn, numpy all assume mutation — fighting the ecosystem is costly
The Pragmatic Middle

"Functional core, imperative shell" — not "everything must be Haskell" but:

  • Core transforms are pure functions (testable, composable, cacheable)
  • Boundaries handle IO (file reads, database calls, API requests)
  • State is passed explicitly, not hidden in globals
  • Mutation is isolated and documented, not sprinkled throughout

Use immutability where it's cheap (configs, metadata, small DataFrames). Accept controlled mutation where performance demands it (large arrays in numpy). But KNOW which is which.

Immutability at Scale

How much immutability is practical for large-scale data?
  • Arrow/Polars: copy-on-write semantics — looks immutable, shares memory until mutation
  • Spark RDDs: immutable by design — transformations create new RDDs, lineage tracks derivation
  • Dask: lazy evaluation — no copies until .compute(), then only materializes what's needed
  • DuckDB: columnar, vectorized — operates on immutable batches internally
The large-scale systems already chose immutability. It's the small-scale Python scripts that fight it.

Event Sourcing for Data

The Concept
  • Every mutation is an append (never update/delete)
  • Current state = replay all events from the beginning
  • Can reconstruct state at any point in time
  • Natural audit trail — nothing is ever lost
  • Debugging: replay events up to the bug, inspect
Is It Overkill or Essential?
  • Overkill for: exploratory analysis, one-off scripts, prototype pipelines
  • Essential for: production ML models (regulatory audit), financial data (compliance), data with corrections (medical records)
  • Middle ground: snapshot key checkpoints, not every micro-operation
  • Delta Lake / Iceberg: event sourcing for tables — practical, not theoretical
