Hierarchical Data with Implicit Relationships

TO DISCUSS

Many datasets contain columns that form implicit hierarchies — parent/child, part/whole, containment — without explicit foreign keys or tree structure. The pipeline needs to detect these relationships and understand their consequences for profiling and modeling.

Types of Implicit Hierarchy

Containment Hierarchies
  • Geographic: city → state → country → region (each level fully determines levels above)
  • Organizational: employee → team → department → division
  • Temporal: day → week → month → quarter → year
  • Product: SKU → product line → category → department
Detection signal: if column A has N unique values and column B has M where M ≪ N, and every value of A maps to exactly one value of B — that's a functional dependency revealing hierarchy.
Derived/Computed Hierarchies
  • Aggregation: line_item_total is qty × price; order_total is sum of line items
  • Bucketing: age_group is derived from age; income_bracket from income
  • Encoding: first 3 digits of ZIP = region; ICD code prefix = disease category
  • Composite keys: account_id embeds branch_code + customer_seq
These create perfect multicollinearity if both parent and child enter a model. Detection: substring/prefix patterns, exact functional relationships, or suspiciously high correlation with discrete steps.
Semantic Hierarchies (Hardest)
  • Taxonomic: "laptop" is-a "computer" is-a "electronics" — but stored as flat category strings
  • Part-whole: engine is part of car, but the dataset just has component and system columns
  • Role-based: manager is an employee who supervises other employees (self-referential)
Can't detect purely from data distributions — requires either domain metadata, naming conventions, or explicit ontology. How much should the pipeline attempt without external knowledge?
Implicit Graph Structure
  • Referral chains: user_id + referred_by_user_id = hidden tree
  • Supply chain: supplier → manufacturer → distributor → retailer (encoded as separate entity columns)
  • Approval flows: created_by → reviewed_by → approved_by = DAG
These are graph relationships flattened into tabular form. Profiling each column independently misses the structure entirely. What does "feature profiling" even mean here?

Context-Scoped Identifiers (Motivating Example)

Roll Number Problem

A student's roll number (e.g., 15) is meaningful only within the context of their class. Roll number 15 in Class 3-A is a completely different student than roll number 15 in Class 3-B.

  • The identifier looks numeric — type classifier might say int_num
  • It looks low-cardinality — values 1-50 repeat across classes
  • Profiling it alone produces a near-uniform distribution — meaningless
  • It only resolves to an entity when paired with its scoping column (class)
This is a compound key disguised as a single column. The pipeline sees a number; the domain sees an identifier that requires context. How do we detect that a column is scoped?
More Examples of Scoped IDs
  • Seat number — meaningful only within a flight
  • Apartment number — meaningful only within a building
  • Port number — meaningful only within a host IP
  • Question number — meaningful only within an exam
  • Employee ID — sometimes scoped to a subsidiary/branch
  • Version number — meaningful only within a software package
Detection heuristic: if unique(col) is low but unique(col, scope_col) ≈ nrows — the column is scoped. Also: column named *_number, *_id with suspiciously low cardinality relative to row count.

Why This Matters for the Pipeline

Statistical Consequences
  • Redundant information: city + state + zip all encode overlapping location signal → inflated importance
  • Simpson's paradox: aggregating across hierarchy levels hides or reverses effects
  • Non-independence: observations within the same group (same department, same region) are correlated — violates i.i.d. assumption
  • Ecological fallacy: group-level statistics don't apply to individuals within the group
Modeling Consequences
  • Multicollinearity: including both levels of hierarchy inflates variance
  • Leakage: child-level aggregates leak parent-level labels
  • Cardinality explosion: one-hot encoding leaf-level of deep hierarchy creates thousands of sparse features
  • Wrong granularity: model trained at wrong level of hierarchy → predictions don't match decision context

Key Discussion Points

  • What automatic detection is feasible? Functional dependency mining? Cardinality ratios? Prefix/substring patterns?
  • Once detected, should the pipeline recommend which level to use — or present all levels with warnings?
  • How does this interact with the type classifier? (A hierarchy column might be cat at leaf, cat at root, but with very different cardinality profiles)
  • Should hierarchical features get a special encoding strategy (target encoding at group level, embeddings that respect hierarchy)?
  • Mixed-level datasets: some rows at leaf level, others at intermediate nodes — how to detect and handle?
  • When should the pipeline suggest multilevel/hierarchical models instead of flat feature engineering?
