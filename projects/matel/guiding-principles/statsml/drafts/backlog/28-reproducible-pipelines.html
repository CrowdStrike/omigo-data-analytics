Reproducible Data Pipelines & Deterministic Output

Discussion — Design Philosophy

Core idea: A data pipeline should produce identical output given identical input, regardless of when it runs, how many times it retries, or what environment it executes in. This is the broader design philosophy that encompasses query determinism (#27) but goes further — covering the entire pipeline from ingestion to output.

What Breaks Reproducibility

Temporal & Environmental
  • Wall-clock dependencies — NOW(), CURRENT_DATE, time-based partitions that shift
  • Floating-point non-determinism — different hardware (x86 vs ARM, GPU generations) produces different rounding
  • Hash randomization — Python dict ordering pre-3.7, PYTHONHASHSEED changing set iteration order
  • External API calls — third-party services returning different results over time (exchange rates, model endpoints)
Execution & Concurrency
  • Parallel execution non-determinism — reducer order in MapReduce, Spark partition shuffles, thread scheduling
  • Random seeds not fixed — sampling, train/test splits, initialization of models
  • Model training non-determinism — GPU thread scheduling, cuDNN non-deterministic algorithms, gradient accumulation order
  • Dependency drift — unpinned library versions, OS-level differences, transitive dependency updates
The insidious ones: Floating-point non-determinism and parallel execution order are especially dangerous because they produce results that look correct — they're just slightly different each time. You won't catch these with eyeball checks; you need bit-for-bit output comparison.

Design Principles

Referential Transparency
  • Same input → same output — the fundamental contract. If f(x) = y today, then f(x) = y tomorrow.
  • Version everything — code, data, config, dependencies, environment. If any of these change, you have a different pipeline.
  • Snapshots over live queries — read from a frozen snapshot, not a live table that might change mid-execution.
  • Explicit side effects — every write, every external call, every non-deterministic operation must be declared and isolated.
Content-Addressed Storage
  • Hash of input determines output location — if the input hasn't changed, the output shouldn't be recomputed.
  • Enables memoization — skip stages whose inputs haven't changed since last run.
  • Natural deduplication — same data written twice goes to the same location.
  • Audit trail — can always trace output back to the exact inputs and code that produced it.

Practical Techniques

Environment & Dependencies
  • Pinned dependency versions (pip freeze, lockfiles)
  • Containerized execution (Docker with pinned base images)
  • Fixed random seeds at every non-deterministic call site
  • Deterministic serialization (sorted JSON keys, stable Parquet row order)
  • Sorted outputs — don't rely on implicit ordering from databases or hash maps
Data Versioning
  • DVC — git for data, tracks versions of large files
  • LakeFS — git-like branching for data lakes
  • Delta Lake time travel — query any historical version of a table
  • Immutable partitions — write-once, never overwrite (date-partitioned, append-only)
  • Input manifests — record exact file paths, sizes, checksums consumed by each run

The Determinism Spectrum

Not all stages CAN be deterministic
  • Fully deterministic: SQL transforms, feature engineering, aggregations, data cleaning (pure functions on snapshots)
  • Deterministic with effort: Model training (fix all seeds, use deterministic cuDNN, accept perf hit), sampling (fix seed)
  • Inherently non-deterministic: Real-time API calls, user interaction, live sensor data

Strategy: isolate non-deterministic stages, checkpoint around them, and accept that the checkpoint itself becomes the reproducible artifact.
Cost/Benefit Analysis
  • Cost of reproducibility: snapshotting everything is expensive (storage, complexity, slower iteration)
  • Cost of non-reproducibility: can't debug production issues, can't audit model decisions, can't compare experiments, can't satisfy regulatory requirements
  • Pragmatic approach: full reproducibility for model training and evaluation, best-effort for exploratory/ad-hoc work

Relationship to Testing

Critical insight: If a pipeline isn't deterministic, you can't write assertions about its output. Testing requires reproducibility. A non-reproducible pipeline is an untestable pipeline.
  • Unit tests assert exact output for known input — requires determinism
  • Integration tests verify end-to-end behavior — requires reproducibility of the full chain
  • Regression tests catch unintended changes — requires that "unchanged" actually means "same output"
  • If your test passes 99% of the time, you have a non-deterministic pipeline, not a flaky test

Streaming Systems

Open question: How does this interact with streaming systems where input is inherently unbounded?
  • Windowing makes bounded sub-problems — but window boundaries can differ across runs
  • Watermarks are heuristic — late data produces different results
  • Event-time processing helps but doesn't solve non-deterministic arrival order
  • Approach: streaming for freshness, batch replay for correctness — the "lambda architecture" tension

Key Discussion Points

  • Where on the spectrum from "fully deterministic" to "best effort" should each pipeline stage sit?
  • Cost of reproducibility (snapshotting everything) vs cost of non-reproducibility (can't debug, can't audit)
  • How does this interact with streaming systems where input is inherently unbounded?
  • Should reproducibility be a hard gate (pipeline fails if non-determinism detected) or a soft metric?
