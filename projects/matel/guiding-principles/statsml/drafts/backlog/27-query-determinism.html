Query Determinism & Time-Sensitive Queries

TO DISCUSS

Data pipelines that use relative time expressions (last 1 hour, now() - interval 7 days) produce different results every time they run. This is an anti-pattern for any system that needs reproducibility, debugging, or consistent analysis.

The Anti-Pattern: Relative Time in Queries

What Goes Wrong
SELECT * FROM events WHERE ts > NOW() - INTERVAL '1 hour'

Run at 10:00 → gets 9:00–10:00 data.
Run at 10:05 (retry after partial failure) → gets 9:05–10:05 data.
Different results. Same query. No error. Pipeline reports "success."

The most common trigger isn't deliberate reruns — it's automatic recovery from partial failures. Pipeline crashes mid-write, scheduler retries 5 minutes later, the time window silently shifts. Nobody notices because the retry "succeeded." The data is just slightly wrong, forever.

  • Non-deterministic output: pipeline produces different results on retry, rerun, or backfill
  • Silent recovery corruption: automatic retries after partial failures shift the window — the "fix" introduces inconsistency
  • Unreproducible analysis: "I ran this yesterday and got X" — can never reproduce X again
  • Race conditions: two pipeline stages run seconds apart, see different "last 1 hour" windows
  • Late-arriving data: events from 50 minutes ago arrive after the query runs — permanently missed
  • Debugging impossible: can't rerun a failed pipeline step and get the same data it originally saw
The Fix: Pre-Constructed Absolute Ranges

Compute the time range once, store it, pass it as parameters:

  • window_start = '2026-08-03T09:00:00Z'
  • window_end = '2026-08-03T10:00:00Z'
  • SELECT * FROM events WHERE ts >= :window_start AND ts < :window_end

Now:

  • Retry produces identical results
  • Backfill uses the same window boundaries
  • Multiple pipeline stages share the same parameters
  • Audit log records exactly what data was queried
  • Debugging: replay with same parameters = same output
The scheduler or orchestrator computes the window boundaries. The query is a pure function of its parameters. Separate "when to run" from "what time range to query."

Broader Query System Concerns

Other Sources of Non-Determinism
  • Unordered results: SELECT ... LIMIT 100 without ORDER BY — different rows each run depending on storage engine state
  • Concurrent writes: query runs mid-ingestion — partial batch visible, next run sees full batch
  • Snapshot isolation: different database isolation levels give different visibility guarantees
  • Eventual consistency: distributed DBs (Cassandra, DynamoDB) may serve stale reads from replicas
  • Schema evolution: a column added mid-pipeline changes NULLability for historical rows
  • Partition pruning: query planner uses different partitions depending on available statistics at runtime
Time-Related Anti-Patterns Catalog
  • WHERE date = CURDATE(): fails if pipeline runs past midnight; backfill impossible
  • ORDER BY ts DESC LIMIT 1: "latest record" changes every second — non-deterministic join key
  • DATEDIFF(NOW(), created_at) < 30: "active users" definition drifts continuously
  • Cron at :00 queries "last hour": if cron fires at :00:03 due to load, 3 seconds of data from previous window leak in
  • Event time vs processing time: WHERE processed_at > X misses reprocessed events; WHERE event_time > X catches them but duplicates on replay
  • Timezone-naive timestamps: "last 24 hours" crosses DST boundary — actually 23 or 25 hours

Design Principles for Deterministic Queries

Rules
  • Parameterize all time boundaries: no function calls that depend on wall clock inside the query
  • Separate scheduling from windowing: "run every hour" ≠ "query last hour." The scheduler decides WHEN; the config decides WHAT range.
  • Idempotent writes: re-running a pipeline step with same parameters overwrites/upserts same output — no duplicates
  • Watermarks for late data: don't close a window until you're confident no more events will arrive (grace period)
  • Explicit ORDER BY: every query that feeds a pipeline must have deterministic sort order
  • Log the parameters: every pipeline run records its exact window boundaries, query hash, row count
Frameworks That Get This Right
  • Apache Airflow: execution_date is a fixed logical timestamp, not "now." Tasks receive their window as parameters.
  • Apache Flink: event-time processing with watermarks — explicitly handles late data and window closure.
  • dbt: incremental models use this.run_started_at but best practice is explicit var('start_date') parameters.
  • Spark Structured Streaming: watermark-based window triggers — window boundaries are data-driven, not wall-clock.
The common pattern: the system computes a deterministic window boundary, passes it as a value, and the query is a pure function. "When did this run" is metadata, not a query filter.

Key Discussion Points

  • Should the pipeline lint queries for non-deterministic functions (NOW(), CURDATE(), RANDOM()) and warn?
  • How to handle the tension between "freshest possible data" (dashboards) vs "reproducible" (pipelines)?
  • Late-arriving data: close the window and accept gaps, or reprocess? Each has different determinism guarantees.
  • How does this interact with our monitoring (#22) — if the monitoring query itself is non-deterministic, alerts are unreliable
  • Relationship to backfill: a deterministic query can be replayed for any historical window; a relative one cannot
