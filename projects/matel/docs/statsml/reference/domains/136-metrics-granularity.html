Metric Granularity & Denominator Selection

Statistical tests require independent observations. Page-level SRP events within a session are correlated → violate independence. User-level aggregates (total purchases/month per user) are independent → valid for t-tests. Choosing the wrong granularity doesn't just give a different number — it makes the MATH invalid.

Pitfall 1: A/B Test at Session/Page Level Violates i.i.d. Assumption

Page Events Are Correlated Within a Session — Not Independent Samples
  • The mathematical requirement: T-test, z-test, chi-squared — ALL assume each observation is an independent draw from a population. The standard error formula SE = σ/√n relies on this. If observations are correlated, this formula underestimates the true variance.
  • SRP (Search Result Page) events within a session: User searches "shoes" → sees 10 results → clicks result 3 → goes back → clicks result 7. These 10 impressions are NOT independent. They share: the same user intent, the same query, the same session state, the same mood/urgency. Click on result 3 REDUCES probability of clicking result 4 (satisfied). They form a correlated cluster.
  • Sessions within a user: User visits Mon, Tue, Wed. Monday's session outcome predicts Tuesday's (loyal users keep coming, bounced users don't return). Sessions within a user are auto-correlated. Not independent draws.
  • User-level monthly totals ARE independent: User A bought $200 this month. User B bought $50. These are independent observations — different people, no causal connection. One value per user per time period = one independent observation. n = number of users. T-test on these: VALID. The i.i.d. assumption holds.

Pitfall 2: Independence Violation — Why Page-Level Data Can't Use a T-Test

T-Test Requires Independent Observations. Page Events Are NOT Independent.
  • The math requirement: A t-test assumes each data point is drawn independently. x₁, x₂, ..., xₙ are i.i.d. (independent and identically distributed). The formula SE = σ/√n ONLY works when observations are uncorrelated. If observations are correlated (ρ > 0), the true SE is larger: SE_true = σ/√n × √(1 + (m-1)ρ) where m = cluster size, ρ = intra-cluster correlation.
  • Page views within a session are CORRELATED: Same user, same intent, same browsing sequence. If user clicked result 1, they're less likely to click result 2 (satisfied). If they bounced from page 1, they're more likely to bounce from page 2 (frustrated). Each page view is NOT an independent draw — it's a dependent observation within a correlated sequence.
  • User-level totals ARE independent: User A's total purchases this month and User B's total purchases this month are independent. Different people, different decisions, no causal link. One number per user → n independent observations → t-test valid. This is pure math: user-level satisfies the i.i.d. assumption, page-level does not.
  • The inflation: 1000 users × 10 pages each = 10,000 rows. Naive t-test: SE = σ/√10000. Reality: effective n ≈ 1000 (one independent cluster per user). SE is √10 = 3.16× too small. Confidence interval 3× too narrow. p-values 10-100× too small. "Significant" results that are actually noise.

Pitfall 3: Denominator Manipulation (Changing What You Divide By)

The Variant Changes the Denominator, Not the Behavior
  • CTR inflation: Variant B shows fewer items per page (10 vs 20). Same user clicks same 1 item. A: CTR = 1/20 = 5%. B: CTR = 1/10 = 10%. "B doubled CTR!" No — B halved impressions. User behavior unchanged. Clicks per user per day: identical.
  • Conversion rate inflation: Variant B adds a pre-filter page (bounces unqualified users before they reach the product page). Denominator shrinks → conversion rate rises. "B improved conversion!" No — B just excluded low-intent users from the denominator.
  • Revenue per session inflation: B makes the flow longer (more steps = fewer completed sessions). Only high-intent users complete. Revenue/completed session is higher. "B increased monetization!" No — B reduced completed sessions and lost revenue overall.
  • Rule: If your variant can mechanically change the DENOMINATOR (fewer impressions, fewer sessions, fewer qualified users), you MUST use a denominator the variant CANNOT affect: unique users randomized, or user-days. Otherwise you're measuring arithmetic, not behavior.

Pitfall 4: Simpson's Paradox from Mix Shift

Aggregate Goes One Way, Every Segment Goes the Other
  • Classic case: Overall conversion drops 3.5% → 3.4%. Panic. Investigation: Mobile improved 2.0% → 2.2%. Desktop improved 4.0% → 4.3%. BOTH improved. But mobile traffic share grew 40% → 60%. More traffic on the lower-converting channel → aggregate declined.
  • A/B test version: Test shows "no effect" overall. But: for new users, variant B wins +8%. For returning users, B loses -3%. Aggregate: net zero. The real signal: B is great for acquisition, bad for retention. Aggregate hides BOTH insights.
  • Why it happens in metrics: Any time you have heterogeneous sub-populations with different base rates AND the proportion between them changes, the aggregate can move opposite to every sub-group. This is guaranteed when: marketing spend shifts channel mix, seasonality changes device mix, or growth brings a different user demographic.
  • Fix: Never report ONLY aggregate metrics. Always segment by: device, new/returning, geo, acquisition channel. If segments diverge from aggregate → Simpson's is active. The aggregate is lying. Act on segments, not the blended number.

Pitfall 5: Novelty Effect — Testing Too Short

Day 1-3 Results ≠ Steady-State Behavior
  • The pattern: ANY visible UI change shows +10-20% engagement in first 72 hours. Users explore the novelty. By day 14, effect decays to true steady-state (often +0%). If you call the test on day 3, you shipped a novelty artifact that will embarrass you in the monthly review.
  • Compounding trap (reverse): A retention improvement of +2% per day is invisible on day 3 (noise). By day 30, the B cohort is 18% larger than A. Short tests miss the most valuable effects (retention, engagement depth) while amplifying the least valuable (novelty clicks).
  • Weekend/paycheck cycles: A test that runs Mon-Fri sees different users than one including weekends. Payday cycles (1st/15th of month) create 2-week spending patterns. A 7-day test might start after payday and look great, or before payday and look terrible — same variant, different timing.
  • Fix: Minimum 2 full business cycles (14 days consumer, 2 months B2B/subscription). Plot metric by day and look for stabilization. If the effect is still GROWING at test end, it's probably real. If it was huge at start and declining, it's novelty.

Pitfall 6: Wrong Level Hides the Real Problem

Aggregate "Error Rate" Hides Whether It's 1 User or 1000
  • Request-level error rate = 1%: Could mean 1 user hitting an error 100 times (retry loop) out of 10,000 requests from 1,000 users. Or could mean 100 different users each hitting the error once. Same "1% error rate." Completely different severity.
  • User-level error rate: 1 user affected = 0.1% of users. 100 users affected = 10% of users. The REQUEST metric hides this. An SRE alert on "1% request error rate" could be a single broken bot or a widespread outage — you can't tell without user-level decomposition.
  • Revenue version: "Average order value = $45." Is that because everyone spends ~$45? Or because 80% spend $20 and 20% spend $145 (bimodal, nobody near the "average")? The aggregate tells you NOTHING about the distribution. Acting on $45 AOV optimizes for a customer that doesn't exist.
  • Fix: Every metric needs a DISTRIBUTION, not just an average. Histogram of per-user values, or at minimum: p10, p50, p90. "Error rate" should always be reported as both: % of requests AND % of users affected. Different levels surface different problems.

Pitfall 7: Time Window Selection Bias

Monthly Churn 5% Sounds Manageable. Annual = Lost Half Your Customers.
  • The compounding trap: 5% monthly churn → (0.95)^12 = 54% annual retention → lost 46% per year. "Only 5% a month" feels small. Annualized it's catastrophic. Same metric, different timeframe, opposite organizational response.
  • The snapshot trap: DAU/MAU = 25% today. Looks stable. But: the 25% today is a DIFFERENT 25% than last month — you have 100% monthly churn with constant inflow replacing outflow. Ratio looks stable, underlying dynamics are terrible.
  • Reporting window cherry-pick: Q4 revenue always spikes (holiday). Report Q4 and "revenue grew 40%!" Compare Q4-to-Q4 (same-season): grew 3%. The time window you choose IS the story you tell. And everyone picks the window that makes them look best.
  • Fix: Report at MULTIPLE timeframes simultaneously: daily, weekly, monthly, same-period-last-year. If the story changes between timeframes, you've found something real. If daily says "growing" but monthly says "flat" — you have high variance within months but no trend.

Pitfall 8: Per-Impression vs Per-User Economics

Ad Revenue Per Impression Grows While Revenue Per User Falls
  • The ad trap: Revenue per impression (RPM) up 10%. Great! But: you showed 30% more ads → users engage less → daily active users dropped 20%. Net revenue: RPM × impressions × DAU = up 10% × up 30% × down 20% = up 14%. Looks fine in aggregate. But DAU decline is compounding — next quarter you lose more users, and RPM gains can't compensate.
  • Subscription version: ARPU (revenue per user) up 5% because you raised prices. But: churn increased 2% per month (new price pushed marginal subscribers out). ARPU looks great THIS month. In 6 months you have fewer users at higher ARPU, lower total revenue.
  • The metric tells a story about the WRONG timeframe: Per-impression and per-user metrics optimize for THIS moment. Lifetime value (LTV) metrics require waiting months. Companies optimize per-impression/per-user because the feedback is instant. LTV damage shows up 6 months later when it's too late.
  • Fix: Always pair "efficiency" metrics (per-impression, per-user, per-session) with "volume" metrics (total users, total sessions, total revenue). If efficiency up + volume down → you're harvesting, not growing. Pair both with leading indicators of LTV (retention, engagement depth).

Pitfall 9: Geographic / Demographic Aggregation Hiding Inequity

"Average Latency 200ms" When Half Your Users Get 2 Seconds
  • CDN coverage bias: 60% of users near edge servers (50ms latency). 40% in underserved regions (500ms+). Average: 230ms. Looks fine! P95: 1200ms. The "average" user doesn't exist — you have TWO populations with 10× different experience and you're optimizing for neither.
  • A/B test on a global product: Variant B improves speed for US users (60% of traffic): -50ms. Slightly degrades for SEA users (20%): +100ms. Aggregate: net improvement. But you just made things worse for your fastest-growing market.
  • Demographic aggregation: "Model accuracy 92%." Across demographics: majority group 95%, minority group 78%. The aggregate hides that your model actively underperforms for the people who may need it most. "92% accurate" passes legal review. "78% for minority group" does not.
  • Fix: Always report metrics split by: geography, device tier, demographic group, network quality. If any sub-group has 2× worse experience than the best group, the aggregate is hiding a real problem. Set floor constraints: "no group below X" rather than "average above Y."

Pitfall 10: Survivor Bias in Denominator (Who Gets Counted)

Measuring Only Users Who Didn't Leave
  • NPS of active users only: NPS = +45 (great!). But: 30% of users churned last quarter. If you surveyed THEM, NPS would be -60. Your NPS measures "satisfaction among people who haven't rage-quit yet" — of course it's high. The unhappy people already left.
  • Engagement among remaining users: "DAU engagement up 5% this quarter!" But DAU dropped 15%. The least-engaged users left → remaining pool is more engaged by construction. Engagement/user rose because the DENOMINATOR got filtered, not because anyone got more engaged.
  • A/B test survivor bias: Measure "revenue per user" after 30 days. But variant B had higher Day 7 churn. The users left in B at Day 30 are a HIGHER-QUALITY subset than those in A. B looks like it has better revenue/user — but only because it killed off the low-spenders early.
  • Fix: ALWAYS include churned/departed users in the denominator for any metric reported to leadership. Intent-to-treat analysis: once randomized into a group, they stay in the count forever, even if they leave. Revenue per RANDOMIZED user, not per ACTIVE user.
