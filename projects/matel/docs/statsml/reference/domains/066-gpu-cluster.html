GPU Cluster

Statistical pitfalls in GPU computing — occupancy lies, memory bottlenecks, and the tyranny of the slowest node.

1. SM Occupancy ≠ Throughput
GPU shows "95% occupied" but SMs are stalled on memory; actual throughput = 30% of peak. High occupancy with low arithmetic intensity = memory-bound. The utilization metric lies about actual useful work. A kernel can have every warp scheduled yet spend most cycles waiting on global memory fetches. Without measuring arithmetic intensity (FLOPs per byte), occupancy alone is meaningless.
2. Memory Bandwidth Bottleneck
GPU compute capability is 100 TFLOPS but memory can only feed 2TB/s. If your model is memory-bound, doubling compute does nothing — the bottleneck is invisible in GPU utilization metrics. The roofline model reveals the truth: operations with low arithmetic intensity (FLOPs/byte < compute/bandwidth ratio) are always memory-limited regardless of how many CUDA cores you add.
3. Multi-tenant Interference
Shared GPU cluster: your job runs alongside 3 other tenants. NVLink bandwidth is shared; memory contention on shared L2 cache degrades everyone. Your training is 15% slower and you cannot determine why without cluster-wide visibility. Per-job metrics show no anomaly — the interference is systemic and invisible to isolated monitoring.
4. Checkpointing IO Storms
1000-GPU training job checkpoints every 30 minutes. Each checkpoint = 50GB written to shared storage simultaneously. Storage saturates; other jobs on the same storage experience IO latency 100x normal. These periodic storms are invisible in per-GPU metrics — they manifest only in storage-side monitoring that most teams never check.
5. Stragglers from Heterogeneous Hardware
A100 and H100 GPUs in the same cluster. Job scheduled across both: A100 nodes finish 30% slower, becoming stragglers. All-reduce waits for the slowest node, so the entire job is limited by the weakest hardware. "Cluster utilization" reads 95% but effective throughput is only 70% — the fast nodes idle waiting for synchronization barriers.
6. Thermal Throttling Under Sustained Load
Initial performance hits peak. After 15 minutes of sustained compute, the GPU throttles to 85% to manage heat. Benchmarks on a cold GPU do not reflect production performance on a hot GPU. The first 10 minutes of any test are misleading — steady-state performance is always lower than burst performance, yet most benchmarks measure only the initial burst.
