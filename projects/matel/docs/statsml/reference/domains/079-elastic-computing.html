Elastic Computing / Auto-Scaling

Systems that grow and shrink with demand — but the growing takes minutes while the demand spike takes seconds. The data you collect during scale-up events is non-representative: elevated latency, dropped requests, timeout errors, and degraded feature computation all contaminate your pipeline.

Pitfall 1: Scale-Up Lag — Traffic Arrives Before Capacity

3-5 Minutes to Scale. Spike Lasts 30 Seconds.
  • The sequence: Traffic spike arrives → auto-scaler detects (30s) → provisions VM (60s) → boots OS (30s) → deploys app (60s) → warm-up (30s). Total: 3-5 minutes. The spike was 30 seconds.
  • The data impact: During those 3 minutes: requests queue, timeouts increase, latency spikes 10×. Models that use "response_time" as a feature see corrupted values. Features computed server-side return defaults/nulls because the computation timed out.
  • The false signal: ML model sees: "users who experience high latency have lower conversion." Correct, but the CAUSE is infrastructure, not user behavior. Model learns to use latency as a predictor — which works during normal operation but fails during scaling events (latency is high but conversion should be normal once capacity catches up).

Pitfall 2: Scale-Down Oscillation — Hysteresis as Noise Generator

Scale Down → Latency Rises → Scale Up → Latency Drops → Scale Down → Repeat
  • The cycle: Load drops → scale down → reduced capacity → latency rises → health check fails → scale up → load handled → latency drops → scale down → repeat. Oscillating between states.
  • The data impact: Metrics oscillate: latency is 50ms then 500ms then 50ms then 500ms. Time-series models see this as a "pattern" and try to predict it. It's not a pattern — it's a control system artifact. Training on oscillation data teaches the model to expect periodic degradation that shouldn't exist.
  • The false seasonality: Oscillation period happens to align with a time window (e.g., 10-minute cycles). Model learns "every 10 minutes, latency spikes." Deploys. Hysteresis settings change. Pattern disappears. Model predictions wrong.

Pitfall 3: Cold Start Penalty — First Request Data Is Garbage

New Instance: First Request Takes 2-10 Seconds. Subsequent: 50ms.
  • The problem: Serverless/container cold start: first request loads code, initializes connections, warms caches. Response time: 2-10 seconds. All subsequent requests: 50ms. User who hits a cold instance has a completely different experience.
  • The data contamination: Your latency distribution is bimodal: 95% at 50ms, 5% at 3000ms. Average: 195ms (meaningless). If you use average latency in features or A/B test metrics, cold starts pollute the signal. A "winning" variant might just have fewer cold starts due to different traffic routing.
  • The model serving problem: ML model runs in a container. Cold start: model weights load from S3 (4 seconds). First prediction: 4.2 seconds. User already left. Feature "model_score" returns NULL for cold-start users → downstream model sees NULL → treats as missing → fallback logic activates. 5% of users always get the fallback experience.

Pitfall 4: Spot Eviction — Computation Interrupted Mid-Pipeline

2-Minute Warning → Checkpoint → Lose 5 Min of Work → Reschedule
  • The scenario: Training job running on spot instances (70% cheaper). Provider reclaims instance: 2-minute warning. Must checkpoint current state. State is 50GB. Can't transfer 50GB in 2 minutes. Partial checkpoint. Reschedule. Reload from last FULL checkpoint (30 minutes ago). Lost 30 minutes of compute.
  • The data pipeline impact: ETL job running on spot. Evicted mid-JOIN. Partial results written to output table (rows 1-50K of 100K). Downstream job reads the partial table. Aggregates computed on 50% of data. No error — just wrong numbers. Row count check: "expected ~100K, got 50K" — is that an eviction artifact or real data loss? Hard to distinguish.
  • The non-reproducibility: Pipeline ran on spot, got evicted, retried, produced slightly different result (non-deterministic operations like sampling, hash partitioning). Model trained on run A vs run B has different weights. Which one is "correct"? Neither — both are artifacts of infrastructure instability.

Pitfall 5: Cost ≠ Utilization — Competing Objectives in Data Collection

10 Instances at 20% CPU: Expensive but Safe. 2 Instances at 90%: Cheap but Fragile.
  • The tradeoff: High utilization = cost efficient but no headroom. Sudden feature computation request takes 3 seconds instead of 0.3 seconds because CPU is saturated. Data arrives late. Real-time features computed from stale data.
  • The data quality issue: Feature pipeline configured for "real-time" computation. Under high utilization: features computed with 30-second lag instead of 1-second lag. Model trained on 1-second-fresh features, serving gets 30-second-stale features. Training-serving skew from infrastructure pressure.
  • The cost-driven data loss: "Reduce costs by 40%." How: sample incoming events (keep 60%). Or: reduce retention (delete after 7 days instead of 30). Or: reduce compute (run feature pipeline every hour instead of every minute). Each "cost optimization" is a data quality degradation in disguise.

Pitfall 6: Capacity Planning From Non-Stationary Demand

Last Year's Pattern ≠ This Year's. Until It Suddenly Is Again.
  • The problem: Demand prediction for capacity planning uses historical patterns. Product launch → unprecedented traffic. Viral event → 10× normal. Competitor outage → 3× refugee traffic. None of these were in training data.
  • Under-provisioning: Data collection system overwhelmed → drops events → training data has gaps during high-traffic periods. Model never sees peak-load behavior. Deployed model fails precisely during peak load (when it matters most).
  • Over-provisioning: Idle capacity costs money. Pressure to reduce → right-sizing → barely enough for normal → fails at first unexpected spike. Cycle repeats every quarter.
