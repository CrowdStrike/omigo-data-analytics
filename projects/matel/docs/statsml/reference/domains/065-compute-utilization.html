CPU / Resource Utilization

Statistical pitfalls in compute metrics — the lies of averages, invisible overhead, and metrics that miss the actual bottleneck.

1. Average CPU Hides Bimodality
Server shows "50% CPU" but is actually idle for 30 seconds then pegged at 100% for 30 seconds. The average equals 50% but performance is terrible during the pegged phase. The mean tells you nothing about the shape of usage. You need the distribution, not the average. A bimodal workload produces a meaningless single summary number that masks two very different operational states.
2. Steal Time in VMs
VM shows "CPU idle" but the hypervisor is giving cycles to other tenants. Actual available compute is less than what's reported. The "steal%" metric is often ignored in dashboards. Your container thinks it has 4 cores but effectively gets 2.5. What appears as idle time is actually time stolen by the hypervisor for noisy neighbors. Without steal-time awareness, capacity planning is based on fiction.
3. Context Switch Overhead Unmeasured
CPU "utilization" counts work time. Context switch overhead lives in the gaps BETWEEN measurements. At 10,000 context switches per second, you lose 5-10% overhead that is invisible in utilization metrics. High thread counts impose a hidden tax. The CPU appears busy doing useful work, but a significant fraction is spent saving and restoring register state, flushing caches, and TLB invalidations.
4. NUMA Effects
Accessing memory on the wrong NUMA node incurs 2-3x latency. CPU utilization looks identical either way, but performance differs by 40%. "CPU%" cannot tell you whether the memory access pattern is optimal. You need memory controller metrics and NUMA hit/miss ratios. Two workloads with identical CPU% can have radically different throughput based solely on memory topology awareness.
5. GC Pauses as Periodic Spikes
Java GC: every 30 seconds, a 200ms stop-the-world pause. Average latency is 5ms; p99 is 200ms. The GC pause is invisible in the average but devastating for tail latency. The pattern is periodic but not perfectly predictable. Users see intermittent freezes that vanish in dashboards showing mean response time. Only percentile tracking reveals the true impact.
6. Cgroup Limits vs Actual Usage
Container limited to 2 CPU cores; actually uses 1.5. But the LIMIT changes throttling behavior. At 1.9 cores the kernel starts throttling. Throttle events are not visible as "usage" — they manifest as invisible slowdowns. The container never reports exceeding its limit, yet response times degrade. CFS throttling creates latency spikes that no CPU metric captures directly.
