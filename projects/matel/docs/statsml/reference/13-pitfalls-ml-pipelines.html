1. Data Leakage (Future Info in Training)

Model uses information not available at prediction time
  • Feature computed from future events leaks into training: e.g., "total_purchases_lifetime" when predicting churn at day 30
  • Model gets 99% accuracy in training, 55% in production — the gap IS the leakage
  • Subtle forms: aggregates computed over full time range, features derived from other rows (global mean), join keys that shouldn't exist yet

Example: Predicting hospital readmission using "discharge diagnosis code" — but that code was assigned AFTER the outcome was known. At prediction time (admission), you don't have it.

Defense: For every feature, ask: "would I have this value at the moment I need to make the prediction?" If no → remove it.

2. Target Leakage (Label Encoded in Features)

A feature is a direct proxy or consequence of the label
  • "treatment_given=chemo" perfectly predicts "has_cancer" — but treatment was assigned BECAUSE of cancer diagnosis
  • The feature doesn't predict the target; it IS the target wearing a disguise
  • Symptoms: perfect accuracy on train, feature importance dominated by one variable, model useless on new data where proxy is absent

Example: Predicting loan default. Feature "collection_calls_made" = 0 for good loans, >0 for defaults. But calls happen AFTER default — it's a consequence, not a predictor.

Defense: Check causal direction. Does the feature CAUSE the outcome, or does the outcome CAUSE the feature? If the latter → leakage.

3. Train/Test Contamination

Information from test set leaks into training process
  • Same patient appears in both train and test (different visits) → model memorizes patient, not pattern
  • Feature engineering uses statistics from full dataset (including test) → mean/std include test rows
  • Oversampling/SMOTE applied before train/test split → synthetic points in test set resemble training points

Example: Patient has 5 hospital visits. 3 in train, 2 in test. Model learns "patient_id_12345 → positive" — it's memorizing, not generalizing. On new patients: accuracy drops 20%.

Defense: Split by ENTITY (patient, user, household), not by row. All rows from one entity must be in the same split.

4. Temporal Leakage (Shuffling Time Series)

Random train/test split on time-ordered data → model sees the future
  • Stock data: random split puts 2024 data in train, 2023 in test. Model "predicts" the past using future knowledge.
  • Customer behavior: Tuesday's data trains, Monday's data tests. Features from Tuesday leak Tuesday-knowledge into "predicting" Monday.
  • Symptom: 90% accuracy on random split, 60% on proper temporal split

Example: Fraud detection model achieves 95% on random split. Deploy with temporal split (train on past, predict future): 72%. The 23% gap was temporal leakage.

Defense: Always use temporal splits for time-ordered data. Train on [t₀, t₁], test on [t₁, t₂]. Never shuffle across time.

5. Class Imbalance Mishandling

Treating 95/5 class ratio naively → model predicts majority class always
  • "Model is 95% accurate!" — but it just predicts "negative" for everything. Recall on positives = 0%.
  • Oversampling minority in train but evaluating on original distribution → inflated metrics
  • Using accuracy as metric when classes are imbalanced → meaningless number

Example: Fraud (2%). Model predicts "no fraud" always → 98% accuracy, 0% fraud detection. Completely useless. Precision-recall or F1 on the minority class tells the real story.

Defense: Use precision/recall/F1 for rare class. Stratified splits. If oversampling: only on train, never on test. Evaluate at multiple thresholds (PR curve).

6. Scaling Before Splitting

Normalizing with global mean/std → test statistics leak into train
  • StandardScaler on full dataset → mean includes test values → model has seen test distribution
  • The effect is usually small (1-2%) but in competitions or borderline cases, it matters
  • Same issue with any global transform: PCA, feature selection, binning boundaries

Example: Feature ranges from 0-100 in train, 0-150 in test. Global scaling sees 150. Model trained on properly-scaled data would never encounter values > 100. With leaked scaling, it handles the extrapolation — unfairly.

Defense: Fit scaler on TRAIN ONLY. Transform test using train's statistics. Pipeline: split → fit_transform(train) → transform(test).

7. Imputation Leakage

Filling missing values using information from the full dataset
  • Impute with column mean → mean computed over train+test → test info leaks
  • KNN imputation: nearest neighbors may come from the test set → using test values to fill train gaps
  • Imputation strategy itself can leak: "if missing → likely negative" was learned from the full dataset

Example: Income missing for 20% of records. Impute with median=$52k (computed globally). Test set median is actually $48k (different demographic). Leaked the higher train median into test imputation.

Defense: Impute using train-only statistics. Better: encode "missing" as its own signal (a feature "is_missing_income" may be predictive without needing imputation).

8. Multicollinearity Blindness

Correlated features inflate importance and destabilize coefficients
  • height_cm and height_inches: r=1.0. Model gives wild coefficients to both (+500 and -498). Net = sensible but individual importances are garbage.
  • Feature importance splits credit randomly among correlated features → all look weak individually
  • Removing one correlated feature → the other suddenly becomes very important. Instability = collinearity.

Example: 5 blood lipid features are intercorrelated (r>0.8). Random Forest: each gets 4% importance. Drop 4 of them → remaining one gets 18%. The "weak" features were cannibalizing each other's signal.

Defense: VIF check. Cluster correlated features and pick one representative. Or: use regularization (Lasso) that naturally selects among correlated features.

9. Feature Selection on Full Dataset

Selecting features using test data → optimistic performance
  • Run correlation/importance analysis on FULL data → select top 10 features → split into train/test → evaluate
  • Problem: feature selection used test data to decide which features to keep → test is not independent
  • The "top 10" might include features that are only coincidentally good on this specific test fold

Example: 500 features. Univariate selection picks top 20 (p<0.01 against target on full data). Train/test split: 88% accuracy. Proper way (selection inside CV): 79%. The 9% gap was selection bias.

Defense: Feature selection MUST be inside the cross-validation loop. Fit selection on train fold only. Re-select for each fold.

10. Label Shift (Train ≠ Deploy Distribution)

Class proportions in production differ from training
  • Trained on 50/50 balanced data. Production is 99/1. Calibration is wrong — model over-predicts the rare class.
  • Threshold set at 0.5 in training is wrong when base rate is 1% — should be much lower.
  • Even well-calibrated models break when deployed to different prevalence populations.

Example: Disease prediction model trained on case-control (50% disease). Deployed in general population (1% disease). At threshold 0.5: flags 30% of population as positive. Useless. Need threshold recalibration.

Defense: Know your deployment base rate. Recalibrate predictions using Platt scaling or isotonic regression on deployment-representative data.

11. Proxy Variables (Hidden Sensitive Attributes)

Model learns protected attributes through correlated features
  • Remove "race" from model. Zip code remains → zip code correlates 0.85 with race → model still discriminates.
  • Name, language, school, neighborhood — all are proxies for demographics you tried to exclude.
  • Fairness-unaware models will discover ANY available proxy for the strongest signal, including protected ones.

Example: Resume screening model. "Gender" removed. But "lacrosse team captain" and "sorority president" remain → model learns gender through activities. Discrimination persists through proxies.

Defense: Audit model predictions across demographic groups. Use fairness constraints. Remove proxies, not just the protected attribute itself.

12. Silent Data Drift (Schema/Pipeline Changes)

Upstream data changes without notification → model degrades silently
  • A column that was in dollars is now in cents (upstream format change). Model sees 100× values. No error — just wrong predictions.
  • A categorical feature adds a new value (new product category). Model has never seen it → undefined behavior.
  • NULL handling changes upstream: NULLs become 0, or empty strings, or -999. Each encodes differently.

Example: "Transaction amount" switches from USD to local currency after system migration. Model trained on $50 avg now sees ¥7000 avg. No error thrown. Fraud model flags everything as suspicious.

Defense: Data validation layer: schema checks, range checks, distribution checks (PSI/KS) on every input. Alert when distribution shifts beyond threshold.

13. Wrong Missing Data Assumptions

Treating all missing data the same when "why it's missing" matters
  • MCAR (Missing Completely At Random): safe to ignore/impute. Rare.
  • MAR (Missing At Random given observed data): imputable with conditional models.
  • MNAR (Missing Not At Random): the missingness IS informative. "Lab not ordered" = doctor thought patient was fine → healthy signal.
  • Imputing MNAR data with mean destroys the signal that "missing" carries.

Example: Blood glucose missing for 60% of patients. Not random — only ordered for suspected diabetics. "Missing" = healthy. Imputing with population mean (110) gives healthy patients diabetic-range values.

Defense: Create "is_missing" indicator feature. Analyze: do missing and non-missing groups have different outcomes? If yes → missingness is a feature, not noise.

14. Aggregation Destroys Signal

Summarizing into one number loses the pattern that matters
  • "Average purchase amount" = $50. But pattern is: 20 purchases at $10 + 1 purchase at $800. Average hides the anomaly.
  • Mean hides bimodality. Sum hides frequency. Max hides distribution. Count hides value.
  • The RIGHT aggregation depends on what you're predicting — there's no universal "correct" summary.

Example: Customer lifetime value. "Avg order = $45" for two customers. Customer A: steady $45/month × 12. Customer B: one $540 order, never returns. Same average, completely different pattern. Need: frequency, recency, variance — not just mean.

Defense: Generate MULTIPLE aggregates (mean, std, max, min, count, recency, trend). Let the model decide which matters. Or: don't aggregate — use sequence models on raw events.

15. Outlier Handling Before Understanding

Removing outliers because they're "weird" — before asking why they exist
  • Income = $5M removed as outlier. But your TARGET is "high net worth individuals." You just removed your best signal.
  • Outlier in one context = crucial signal in another. Hospital charges >$200k = billing errors? Or = transplant patients (the ones you're trying to predict)?
  • Trimming/winsorizing before understanding compresses the very tail where separation may live.

Example: Capital gain = $99,999 (appears in 159 records). Removed as "clearly a cap value." But those 159 are nearly ALL high-income — removing them eliminates the strongest single predictor in the dataset.

Defense: Investigate before removing. Check: is the outlier group a coherent subpopulation? Does it have high class purity? If yes → it's signal, not noise. Isolate it (make it its own bucket), don't remove it.

16. Rare Category Explosion

One-hot encoding high-cardinality features creates thousands of sparse columns
  • Zip code: 40,000 unique values → 40,000 binary columns, mostly zeros
  • Each column has n=2-5 → unreliable. Model overfits to individual zip codes.
  • New data has unseen zip codes → all zeros → model has no information

Example: Product category with 2000 values. One-hot → 2000 columns. 80% of categories have <10 purchases. Model memorizes "category_1847=1 → buy" from 3 examples. Doesn't generalize.

Defense: Group rare categories into "other." Use target encoding (risky — leakage!) or frequency encoding. Or: embed categories into dense vectors (entity embeddings).

17. Look-Ahead Bias in Feature Engineering

Feature uses information from the same row's future or outcome
  • "Days until next purchase" as a feature for churn prediction — you only know this AFTER the future arrives.
  • "Rolling 30-day average" includes today and tomorrow (for time-series: must be strictly past).
  • Target encoding: category mean computed including the current row's label → direct label leakage.

Example: "Average rating of movies this user will watch" → includes movies they haven't seen yet at prediction time. Accidentally perfect predictor that doesn't exist in production.

Defense: Timestamp everything. For any derived feature: "what is the latest event used in this computation?" Must be before prediction time.

18. Wrong Metric for the Problem

Optimizing a metric that doesn't align with business value
  • Accuracy on imbalanced data → useless (see #5)
  • AUC is threshold-free but hides the actual precision at your operating point
  • RMSE penalizes large errors quadratically — if large errors are acceptable but small errors aren't, use MAE
  • Log-loss rewards confidence but punishes wrong confident predictions catastrophically

Example: Spam filter optimized for precision (few false positives). But: one missed spam costs $0.01, one blocked legitimate email costs $50. Should optimize for recall instead. Metric didn't match cost structure.

Defense: Start from business cost: "what's the cost of a false positive vs false negative?" Build custom metric from the cost matrix. Standard metrics are proxies — know what they proxy for.

19. Overparameterized Models on Small Data

More parameters than data points → memorization, not learning
  • Neural network with 1M parameters on 5000 rows: will memorize training set perfectly, generalize terribly.
  • 500-feature random forest on 200 samples: each tree sees ~10 samples per leaf → noise.
  • Symptom: train accuracy 99%, test accuracy 60%. Gap = overfitting from excess capacity.

Example: Deep learning on 500-patient medical dataset. Training loss → 0. Test AUC: 0.52 (random). Logistic regression on same data: test AUC 0.71. Simpler model wins with insufficient data.

Defense: Match model complexity to data size. n<1000 → logistic regression, shallow trees. n<10,000 → RF, XGBoost. n>100,000 → neural nets viable. (Rough guide — depends on signal-to-noise.)

20. Ensemble Leakage (Stacking on Same Data)

Meta-model trained on base model predictions from the same data → overfitting
  • Train 3 models on train set. Get predictions. Train stacker on those predictions + labels from SAME train set. Stacker overfits to base model errors.
  • Proper stacking: base model predictions must be out-of-fold (cross-validated) for the stacker's training data.
  • Using test set predictions for stacking = direct test leakage.

Example: Model A: 85% train accuracy. Model B: 83%. Stacker trained on same train predictions: 95% train accuracy, 82% test. The stacker learned to exploit base model overfitting patterns.

Defense: K-fold: generate base model predictions via cross-validation. Each row's base prediction comes from a model that didn't see that row. Only then train stacker.

21. Threshold Selection on Test Set

Choosing the classification threshold that maximizes test performance → optimistic
  • Model outputs probabilities. You try thresholds 0.3, 0.4, 0.5, 0.6, 0.7 on test set. Pick 0.42 because it gives best F1.
  • But: you just made 5 comparisons on the test set. The "best" threshold is partly tuned to test noise.
  • On new data: the optimal threshold may be 0.38 or 0.51 — your test-optimized 0.42 was overfit.

Example: At threshold 0.42: test F1=0.78. Deploy: F1=0.71. The 0.07 gap = threshold was tuned to this specific test set. Should have used validation set for threshold selection.

Defense: Select threshold on VALIDATION set. Report test performance at that threshold (no further tuning). Test set is for reporting only.

22. Duplicate / Near-Duplicate Records

Same record in train and test = memorization leakage
  • Exact duplicates: same patient, same visit, duplicated by ETL bug. Model memorizes → inflated accuracy.
  • Near-duplicates: same patient, slightly different timestamps, same values. Splits them across train/test → model recognizes patient.
  • Augmented data that's too similar to original appearing in both splits.

Example: Medical imaging: same scan in train (original) and test (augmented flip). Model recognizes the anatomy, not the pathology. Remove augmentation overlap: accuracy drops 12%.

Defense: Deduplicate before splitting. Hash records. For near-duplicates: cluster similar records and ensure clusters stay within one split.

23. Data Survivorship (Only Recent Records Kept)

Archived/deleted data biases what remains
  • System retains 2 years of data. Churned users deleted after 6 months. Dataset = only current/recent users.
  • Old records with different patterns (different product, different era) are gone → model only knows the current regime.
  • Result: model can't handle rare events it's never seen because historical examples were purged.

Example: Loan dataset only keeps records from last 3 years (post-regulation). Pre-regulation defaults (higher rate, different patterns) are gone. Model doesn't know how to handle economic downturn because those examples were deleted.

Defense: Understand data retention policy. Ask: "what was removed?" If rare events are underrepresented due to retention, note the limitation.

24. Silent Column Semantics Change

Column name stays the same but meaning changes
  • "Revenue" used to be gross, now it's net. Same column name, different numbers. Model trained on gross, deployed on net.
  • "Status" codes: 1=active, 2=inactive. Then a migration: 1=active, 2=pending, 3=inactive. Code 2 means something different.
  • No error thrown — data flows through cleanly. Just produces wrong predictions.

Example: "Days_since_last_login" used to count calendar days. New system counts business days. Model sees "5" and thinks "5 days of inactivity" — actually it's 7 days (weekend excluded). Churn predictions shift systematically.

Defense: Data contracts between teams. Column-level documentation with version. Distribution monitoring catches semantic shifts (mean/std change even if schema doesn't).

25. Non-Representative Training Data

Model trained on one population, deployed on a different one
  • Trained on US data, deployed in India. Feature distributions, correlations, and base rates all differ.
  • Trained on desktop users, deployed to mobile. Behavior patterns are fundamentally different.
  • Trained on 2019 data, deployed in 2024. World changed (COVID, regulation, technology shifts).

Example: Skin cancer detection trained on fair skin images (90% of training data). Deployed globally: fails on darker skin (underrepresented in training). Performance gap = representation gap.

Defense: Profile your training data demographics. Compare to deployment population. Report performance per subgroup. If gaps: collect more representative data or calibrate per group.

26. Duplicate Inflation in ETL

Duplicates from joins/retries/bugs inflate counts and skew analysis
  • A fanout join (1-to-many) silently doubles/triples rows. Counts, sums, averages all wrong.
  • Retry logic in event pipelines: same event recorded 2-3× during transient failures. "Revenue doubled!" No — events duplicated.
  • ETL ran twice (manual re-run after "failure" that actually succeeded). Data doubled.
  • Deduplication not in the pipeline → inflated metrics, wrong distributions, bogus significance tests.

Example: Payments table joined to line items: 1 payment × 3 items = 3 rows. "Average payment" computed on joined table: wrong by 3×. Conversion rate: inflated because same user counted per item, not per session.

Defense: Count distinct before and after every join. Assert row counts. Deduplicate on business key (user_id + timestamp + amount). Monitor "events per entity" distribution — sudden doubling = bug.

27. Unquantified Spikes (Memory / Skew Failures)

Data spikes (extreme concentration) break processing without warning
  • One key has 10M rows, all others have 100. GroupBy on that key: one partition gets 10M, 999 partitions get 100. OOM crash on one worker.
  • A feature with 95% zeros: algorithms that iterate per-unique-value work fine. Algorithms that allocate per-row: 20× memory for the zero bucket.
  • Histogramming: one bin gets 99% of data. Visualization is useless. Statistics on that bin dominate everything.
  • Not quantifying spikes upfront means you discover them at runtime (crash) rather than at profiling time (handled gracefully).

Example: Spark job aggregating by user_id. One bot account: 50M events. Job hangs for 3 hours processing that one partition while 999 other partitions finished in 2 minutes. No error — just extreme data skew.

Defense: Profile top-N cardinality per key column BEFORE processing. Flag any key with >1% of total rows. Meta-distribution Gini (doc 28) detects this automatically. Salt skewed keys or process them separately.

28. No Data Quality Monitoring Over Time

Not measuring trends through regular ETL → data shifts go unnoticed for months
  • Feature mean drifted 20% over 6 months. Nobody noticed because nobody was checking. Model degraded gradually → blamed "model staleness" when the problem was upstream data.
  • New NULL pattern appeared 3 months ago (upstream source changed). 15% of a key feature is now NULL. Pipeline imputes with mean → results are subtly wrong but pass all schema checks.
  • Category distribution shifted: "product_type=X" was 5% of data, now it's 25%. Model never saw this balance — predictions for type X are unreliable.
  • This is NOT about "temporal data" (doc 26) — it's about basic operational hygiene: measuring your data characteristics regularly and alerting on unexpected changes.

Defense: Automated profiling on every ETL run. Store statistics in a time-series table. Alert when any metric crosses ±2σ from rolling baseline.

29. Timezone / Timestamp Ambiguity

Timestamps without locale, precision, or format spec → silent misinterpretation
  • Unix timestamp without locale: Is 1690000000 in UTC or local time? Depends on where the pipeline ran. Server in Virginia → UTC. Pipeline on dev laptop → EST. Same number, 5 hours apart.
  • String timestamps without timezone: "2024-03-10 02:30:00" — in which timezone? During DST transition this time doesn't even exist in some zones.
  • Granularity ambiguity: Is 1690000000 seconds or milliseconds? Seconds → year 2023. Milliseconds → year 2023 but a completely different instant. Some systems use fractional seconds (1690000000.123), others use long integers with millis (1690000000123) or micros (1690000000123456).
  • Mixed granularity: One source writes epoch-seconds, another writes epoch-millis. Joining them: one timestamp is 1000× the other. "Duration" feature: negative 50 years.
  • DST edge cases: Events at 2:30am during spring-forward don't exist. Events at 1:30am during fall-back exist TWICE. Deduplication/ordering breaks.

Example: Event pipeline: service A logs epoch-millis (1690000000000), service B logs epoch-seconds (1690000000). Join on timestamp: off by 1000×. "Time between events" feature: 53 years or -53 years depending on which is subtracted from which. No error — just an impossible value that flows downstream.

Defense: Enforce: all timestamps in UTC epoch-milliseconds (int64). Document granularity in column name (ts_epoch_ms, ts_epoch_s). Validate ranges (a timestamp claiming year 2055 is millis misread as seconds). Add assertion: max(ts) < now + 1 day.

30. Character Encoding / Locale Issues

Text data corrupted by encoding mismatches → silent data loss
  • CSV saved as Latin-1, read as UTF-8: accented characters become garbage (Ã© instead of é). Names break, joins fail silently.
  • Numeric formatting: "1.234,56" (German) vs "1,234.56" (US). Parse as float: either crashes or silently reads 1234.56 vs 1.23456.
  • Dates: "01/02/2024" = Jan 2 (US) or Feb 1 (EU). Silent, unfixable once parsed wrong.
  • JSON with BOM (byte order mark): invisible character at start of file breaks parsing intermittently.

Example: Customer names with umlauts (Müller) parsed as "M\xfcller" in one system, "Müller" in another. Join on name fails. 8% of German customers disappear from analysis. Nobody notices because the join doesn't error — just returns fewer rows.

Defense: Enforce UTF-8 everywhere. Validate row counts after every join. Parse dates with explicit format. Never infer encoding — declare it.

31. Silent Join Fanout (Row Multiplication)

A many-to-many or one-to-many join silently multiplies rows
  • Users table (1 row/user) JOIN Orders table (5 rows/user) = 5× row count. Average computed on joined table → wrong.
  • "Revenue per customer" computed after joining to line items: each customer counted per item, not per order.
  • No error. No warning. Query returns more rows than input. Metrics are inflated by the fanout factor.
  • Particularly insidious when the fanout varies by group (heavy buyers have more rows → over-weighted in averages).

Example: 10,000 users join to 50,000 events. Compute "average age" on joined table: users with more events contribute more to the average. Age of power users dominates. "Average user age = 35" when true average is 28 (power users are older).

Defense: Check row count before and after every join. If count increases: you have fanout. Aggregate BEFORE joining, or use DISTINCT where appropriate.

32. NULL Semantics Mismatch

NULL means different things in different columns and nobody documents which
  • NULL in "income" = refused to answer (could be high OR low → truly unknown)
  • NULL in "second_floor_sf" = doesn't have a second floor (= ZERO, not unknown)
  • NULL in "lab_result" = test not ordered (= doctor thought patient was healthy → informative!)
  • Treating all NULLs the same (impute with mean, or drop) is wrong for all three cases differently.

Example: Hospital data: "HbA1c" NULL for 70% of patients. Impute with mean (5.8). But NULL means "not diabetic enough to test" — true value is probably ~5.0. Imputing 5.8 makes healthy patients look pre-diabetic.

Defense: Document NULL semantics per column. Three categories: "truly unknown" (impute cautiously), "not applicable" (encode as 0 or separate category), "informative absence" (make it a feature).

33. Off-By-One in Windowing / Aggregation

Inclusive vs exclusive boundaries → feature looks ahead or misses data
  • "30-day rolling average" — does it include today? If yes and you're predicting tomorrow: today's data leaks.
  • Window [t-30, t] vs [t-30, t) — one includes the boundary, other doesn't. Off by one day = leakage.
  • "Last 7 days of purchases" — does "last" mean including today or ending yesterday? Different answers in different libraries.
  • Aggregation "by month" — does the month start at day 1 00:00 or day 0 24:00? UTC or local?

Example: "7-day average revenue" feature includes the target day's revenue (the thing you're predicting). Model: 92% accuracy. Fix the off-by-one: 74%. The 18% gap was one day of leakage.

Defense: Always use EXCLUSIVE upper bound (strictly less than prediction time). Write tests: "does this feature's max timestamp exceed the prediction timestamp?" If yes → bug.

34. Unit Mismatch (Dollars vs Cents, Seconds vs Milliseconds)

Same column name, different units across sources or over time
  • System A reports latency in milliseconds, System B in seconds. Join them: "500ms" becomes "500 seconds" in combined view.
  • Billing migrated from dollars to cents. Same column "amount" now 100× larger. No schema change. Model thinks prices exploded.
  • Temperature in Celsius from one source, Fahrenheit from another. Both called "temperature."

Example: Mars Climate Orbiter: one team used pounds-force, another used newtons. Same interface, undocumented unit mismatch. $327M spacecraft crashed. In ML: less dramatic but equally wrong predictions.

Defense: Include units in column names (amount_cents, latency_ms, temp_celsius). Validate value ranges against expected physical bounds. A "latency" of 50,000 should trigger an alert (seconds? or milliseconds?).

35. Stale Feature (Cached / Not Updated)

Feature value is outdated because the refresh pipeline failed or lagged
  • "Customer lifetime value" recomputed weekly. Pipeline fails silently one week. Feature stays at last value for 2 weeks → stale.
  • Real-time features served from cache. Cache TTL = 24 hours. Feature represents "current state" but is actually yesterday's state.
  • Feature depends on upstream table that's refreshed monthly. Model trained on fresh data, deployed with month-old features.

Example: "Account balance" feature refreshed nightly. User deposits $5000 at 9am, applies for loan at 10am. Model sees yesterday's balance ($200). Denies loan based on stale data. Customer complains.

Defense: Track feature freshness (last_updated timestamp). Alert when age > expected refresh interval. In real-time systems: include "feature_age_seconds" as an input — let model learn when features are too stale to trust.

36. Label Noise (Incorrect Ground Truth)

The target variable itself is wrong for 5-20% of records
  • Human-labeled data: annotator disagreement = label noise. 3 annotators disagree on 15% of examples.
  • Proxy labels: "clicked = interested." But bot clicks, accidental clicks, rage clicks ≠ interest.
  • Time-dependent labels: "churned" defined as "no purchase in 30 days." But what about seasonal buyers (every 60 days)?
  • 5% label noise → model ceiling is 95%. No architecture or feature engineering can exceed it.

Example: Email "spam" labels from user reports. Users sometimes report legitimate marketing as spam (10%) and miss actual spam that lands in inbox (5%). Model trained on these labels: ceiling = ~85% even if the actual spam pattern is perfectly learnable.

Defense: Estimate label noise rate (inter-annotator agreement). Clean labels where possible. Use noise-robust loss functions. Accept that reported accuracy includes the label noise floor.

37. Feature Computed After Target Event

Feature uses data generated AFTER the outcome already happened
  • "Total support tickets" for churn prediction — but most tickets are filed DURING the churn process (cancellation flow)
  • "Post-surgery complications" as a feature for predicting surgery outcome — it IS the outcome
  • Subtle: "account_status=closed" available as a feature. But it was set to "closed" as part of the churn event you're trying to predict.

Example: Predicting customer churn. Feature "contacted_retention_team=1" has 95% correlation with churn. But retention is contacted BECAUSE customer initiated churn. The feature is a consequence, not a cause.

Defense: Timeline audit: for each feature, draw when it was generated relative to the target event. Any feature generated at T ≥ T_target must be excluded.

38. Backfill Bias (Data Filled Retroactively)

Historical data "corrected" or filled in with knowledge of the future
  • Company restates revenue for Q1-Q3 after Q4 audit. The Q1 numbers you see NOW are not what was available IN Q1.
  • Diagnosis codes updated retroactively after additional tests. Historical record looks complete — but wasn't at the time.
  • Feature "industry_classification" reassigned after company pivoted. Historical feature reflects TODAY's classification, not the classification at the time of the prediction.

Example: Economic data is revised 3 times (preliminary → revised → final). Model trained on "final" data performs great. In production, it sees "preliminary" data (30% different). Accuracy drops because training used a polished version that doesn't exist at prediction time.

Defense: Use point-in-time data (what was actually available on that date). Store data snapshots, not just latest values. "As-of" queries instead of current-state queries.

39. Sampling Rate Changes

Collection frequency changes → fake trends in aggregated data
  • Sensor sampling 1/sec in v1, 10/sec in v2. "Average readings per hour" jumps 10×. Not because phenomenon changed — sampling did.
  • Logging enabled for 10% of users → 100% of users. Total event counts jump 10×. Interpreted as "engagement spike."
  • A/B test: variant A has heavier instrumentation → more events → appears more "engaged." But it's measurement, not behavior.

Example: Mobile app upgrade adds new event tracking. "Daily active events" triples overnight. PM reports "massive engagement increase!" Actually: same user behavior, more measurement points per action.

Defense: Track sampling rate as metadata. Normalize counts by sampling rate. When rates change, segment analysis into pre/post periods.

40. Floating Point / Precision Loss

Numerical precision issues create silent errors in aggregations and comparisons
  • Sum of 1M float32 values: order of summation changes the result. Parallel sum ≠ sequential sum.
  • Equality comparison on floats: 0.1 + 0.2 ≠ 0.3 in IEEE 754. Joins on float keys fail for "matching" values.
  • Training in float32, serving in float16: model weights lose precision → different predictions (small but systematic).
  • Currency calculations in float: $0.10 × 3 = $0.30000000000000004. Over millions of transactions: significant rounding error.

Example: Feature "ratio = column_a / column_b" produces NaN when column_b=0, Inf when column_b≈0. 0.1% of rows have Inf. Mean of feature: Inf. Model training: NaN propagates silently through gradient computation.

Defense: Use float64 for aggregations. Never join on floats (use integer keys). Handle division by zero explicitly. Check for NaN/Inf after every computation.

41. Batch vs Online Feature Mismatch (Training-Serving Skew)

Features computed differently in training (batch) vs serving (real-time)
  • Training: "avg_last_30_days" computed with full access to 30 days of data (batch SQL query).
  • Serving: same feature computed incrementally (streaming). Slight difference in window boundaries, NULL handling, edge cases.
  • Result: model trained on batch features, served with streaming features. Subtle numerical differences → performance drop.
  • Hardest to debug: predictions are "slightly worse" in prod but no single feature is obviously wrong.

Example: Batch training: "last_login_days_ago" computed from daily snapshot. Online: computed from real-time event stream. Batch version rounds to integer days. Online version: fractional days. Model learned thresholds at integer boundaries → online version crosses them differently.

Defense: Log online features at prediction time. Compare against batch-computed features for same records. Any systematic deviation = training-serving skew. Unified feature pipelines (same code for batch and streaming).

42. Feature Store Staleness

Feature store serves outdated values because refresh pipelines are unmonitored
  • Feature "credit_score" refreshed monthly. It's now 45 days since last refresh. Serving stale data for 15 days — no alert.
  • Feature depends on upstream ML model that was retrained and changed output format. Feature store still serves old-format values.
  • Multiple features with different refresh cadences: some are 1 hour old, some are 30 days old. Model doesn't know which is fresh.

Example: Real-time fraud model uses "merchant risk score" from feature store. Score was last updated 2 weeks ago. Merchant was compromised yesterday. Model sees "low risk" because the store is stale. Fraud goes undetected for the full refresh cycle.

Defense: Store last_updated per feature per entity. Serve feature_age alongside the value. Set SLA per feature (max acceptable age). Alert on SLA violations.

43. Target Definition Drift

What "positive" means changes over time, invalidating the label
  • "Churn" = no purchase in 30 days. Business changes to subscription: now "churn" = cancellation. Same model, incompatible labels.
  • "Fraud" definition expanded to include "friendly fraud" (chargebacks from real customers). Label mix changes without model retraining.
  • Threshold for "high-value customer" changes from $500 to $1000/year. Old labels are wrong by new definition.

Example: Spam classifier trained when spam = "Nigerian prince emails." By 2024: spam includes phishing, scams, promotional abuse. Model's concept of "spam" is 10 years outdated even though it's "retrained on new data" — because the labeling criteria evolved.

Defense: Version your target definition. When it changes: retrain from scratch with new labels on ALL data. Never mix old-definition labels with new-definition labels.

44. Index / ID Reuse

IDs get recycled or reset → joins match wrong records
  • Auto-increment IDs reset after table rebuild. user_id=500 in 2022 ≠ user_id=500 in 2024.
  • Session IDs recycled after expiration. Joining on session_id across months: matches different users.
  • Test environment IDs (1-1000) overlap with production IDs. Join leaks test data into production analysis.

Example: Event tracking uses integer session_id. After 2^31 sessions: ID wraps around to 1. Historical analysis joins old session (id=1, user A from 2019) with new session (id=1, user B from 2024). Features are a mix of two unrelated users.

Defense: Use UUIDs, not sequential integers. If using integers: include source system + date range in join conditions. Never join on bare IDs across time periods without verifying continuity.

45. Partial Data (Incomplete ETL Window)

Analysis runs before all data has arrived → systematically biased toward early arrivals
  • "Yesterday's data" queried at 2am. But late-arriving events (mobile offline, batch uploads) arrive until 6am. Missing 20% of events.
  • "Monthly report" run on the 1st at midnight. West coast data for the 31st hasn't arrived yet (3 hours behind). Report misses those hours.
  • Features computed from incomplete windows are systematically LOWER than truth (missing the late portion).

Example: Daily model retraining at 1am UTC. Events from Asia (UTC+8) for the previous "day" still arriving until 4am UTC. Model trained on systematically incomplete Asian data every day. Predictions for Asian users: biased low forever.

Defense: Define data completeness SLA. Don't process until completeness check passes (e.g., event count within 5% of expected). Or: process with known lag and document the bias.

46. Information Leakage (Comprehensive)

The Umbrella Category: Any Info Crossing a Boundary It Shouldn't

Information leakage is the root cause behind many pitfalls above. It has these forms:

  • Temporal leakage: Future → past (features from after the target event)
  • Split leakage: Test → train (statistics, records, or selections using test data)
  • Deployment leakage: Training → serving (batch features unavailable online)
  • Label leakage: Target → features (a feature that IS the target in disguise)
  • Population leakage: Other entities → this entity (global stats include current row)
  • Knowledge leakage: Human insight about test data → model decisions (domain expert "tuning" after seeing test results)

The universal test: "At prediction time, for this specific entity, would this information ACTUALLY be available?" If the answer is no — even partially, even subtly — it's leakage.

Symptoms: Train/test gap > 5%. One feature dominates with implausible importance. Performance drops dramatically on truly new data. Model "knows things it shouldn't."

Defense: Feature audit with timeline. Strict temporal ordering. Entity-level splitting. Feature parity between training and serving. Regular comparison of offline vs online metrics (gap = leakage somewhere).

47. Multi-Source Schema Inconsistency

Multiple upstream sources fit same schema but encode differently → silent pollution
  • 3 services emit "purchase_event" into the same table. Service A: amount in dollars. Service B: amount in cents. Service C: amount in local currency. Same column name, 3 different meanings.
  • Source X uses status codes [1=active, 2=inactive]. Source Y uses [0=inactive, 1=active]. UNION them: code "1" means opposite things depending on origin.
  • "Category" field: Source A uses "electronics", Source B uses "ELECTRONICS", Source C uses "Electronics & Gadgets". Same concept, 3 representations → treated as 3 separate categories.
  • Timestamps: Source A writes ISO-8601 with timezone, Source B writes epoch-millis, Source C writes "MM/DD/YYYY" strings. All land in one "event_time" column after ETL normalization — but normalization bugs differ per source.
  • The insidious part: each source passes schema validation (right column names, right types). The SEMANTICS are wrong but invisible to automated checks.

Example: Healthcare system aggregates lab results from 4 hospital networks. All report "glucose" as a number. Network A: fasting glucose (mg/dL). Network B: random glucose (mg/dL). Network C: glucose (mmol/L, different unit). Network D: glucose tolerance test result (different test entirely). Same column, 4 incompatible values. "Average glucose" is meaningless. Model trained on this: garbage.

Defense:

  • Tag every row with source_system_id. Profile each source SEPARATELY before combining.
  • Compare distributions per source: if mean/std differs significantly between sources for "same" column → inconsistency.
  • Semantic data contracts: upstream teams must document not just type but MEANING, units, and business rules per column.
  • Periodic reconciliation: compute same metric from each source independently and compare (should agree within tolerance).
  • Never trust that "same schema" = same semantics. Schema is necessary but not sufficient for compatibility.

48. Volatile State in Real-Time Systems

Data changes between API calls → model sees inconsistent state
  • Auction/bidding systems: Price, bid count, time remaining change every second. Feature fetch at T=0, model runs at T=0.5s → data already stale. Two features fetched 200ms apart may reflect different auction states.
  • Inventory/availability: "Items in stock = 3" at feature time, "items in stock = 0" by prediction time. Model recommends out-of-stock item.
  • Competing writes: User A and User B both bidding. Model for User A reads state before User B's bid lands. Prediction based on pre-B state is immediately obsolete.
  • Read inconsistency: Feature 1 (price) read from cache (2s old). Feature 2 (bid count) read from DB (current). They don't correspond to the same moment — price was $50 when there were 3 bids, now there are 5 bids but you still see old price.
  • Training vs serving gap: Training data is a clean snapshot (all features from same instant). Serving: features arrive asynchronously, each from a different timestamp. Model trained on consistent state, deployed on inconsistent state.

Example: E-commerce auction. Model predicts "will user win?" using features [current_bid, time_left, num_bidders]. Feature fetch takes 50ms total (3 calls). During those 50ms: 2 new bids arrive, price jumps $10. Model receives: old price + new bidder count + slightly-old time_left. Prediction based on impossible state that never actually existed.

Defense:

  • Snapshot reads: Read all features from a single consistent snapshot (versioned state, event-time aligned)
  • Timestamp every feature: Include feature_timestamp alongside value. Reject if any feature is older than threshold.
  • Staleness-aware models: Include "feature_age_ms" as an input — model learns when features are too old to trust.
  • Optimistic concurrency: After prediction, verify key state hasn't changed before acting. If it has → re-predict or abort.
  • Train on realistic serving conditions: Add noise/staleness to training features to match what serving actually sees. Don't train on clean snapshots if serving is messy.

49. Extreme Imbalance Scalability Problem

Rare positives + statistical requirements = need massive negative data
  • The math: Positive rate = 0.01% (1 in 10,000). To get 30 positives per bucket × 20 buckets = 600 positives needed. At 0.01% rate: need 6,000,000 total records. Just to PROFILE one feature.
  • Scalability wall: You need the negatives to establish the base rate, compute enrichment, measure per-bucket purity — but 99.99% of your compute is spent processing negatives that individually contribute almost nothing.
  • Storage/memory: Loading 6M records into memory to find 600 positives. Most ML libraries load full datasets. Pandas/Spark: 6M rows × 100 features = OOM for development.
  • Evaluation instability: With 600 total positives, train/test split gives ~120 positives in test. A single misclassification = ~1% swing in recall. Metrics are extremely noisy.
  • Bucket starvation: 20 buckets × 600 positives = 30 per bucket on average. But distribution is uneven — some buckets get 2-3 positives. Impossible to validate those buckets.

Example: Click fraud detection (0.005% fraud rate). Dataset: 200M impressions, 10,000 fraud events. To profile feature "time_of_day" in 24 hourly buckets: need ~400 fraud per bucket = 9,600 total → nearly all fraud events used just for one feature's profile. No budget left for train/test/validation splits.

Defense:

  • Negative downsampling: Keep all positives, sample 1-10% of negatives. Adjust metrics for the sampling ratio. Sufficient for model training (not for absolute rate estimation).
  • Stratified profiling: Profile only the positive neighborhood — what range do positives occupy? Don't need ALL negatives to establish enrichment.
  • Global rank tests: Mann-Whitney doesn't need bucketing at all. Ranks positives vs negatives directly. Works with any ratio.
  • Wider buckets: 5 buckets instead of 20. Each bucket gets 6× more positives. Trade resolution for reliability.
  • Cascading: First pass on sampled data (find promising features). Second pass on full data (validate only the promising ones). Don't profile all 500 features on 6M records.

50. Duplicate / Highly Correlated Features (Semantic Incoherence)

Near-identical features make models split on arbitrary copies, destroying interpretability
  • Dataset has income, annual_salary, yearly_earnings — same signal, different column names. Model picks among them randomly at each split.
  • Decision tree: first split on income > 50k, deeper split on annual_salary > 48k. Looks like two different decisions — it's the same variable with noise.
  • The tree loses semantic consistency: a human reads the path root-to-leaf and sees contradictory or redundant logic. "Income high AND salary low" — impossible but the tree believes it.
  • Random forests: feature importance diluted across duplicates. Each copy gets 1/N of the credit. Removing duplicates doesn't hurt accuracy but concentrates importance on the real signal.

Example: Ames Housing has GarageArea and GarageCars (r=0.88). A decision tree might split on GarageCars ≥ 2 at depth 1, then GarageArea > 480 at depth 3. Reader thinks these are independent signals — they're the same physical reality (bigger garage = more cars). The tree path reads as two insights but contains one.

Why this is worse than multicollinearity:

  • Linear models: correlated features mess up coefficients but predictions stay sane — regularization handles it
  • Trees: each split is a human-readable decision. Duplicates make the tree lie about its reasoning. You can't prune what you can't interpret.
  • Ensembles: Bagged trees each pick a different duplicate → SHAP values fragment across copies → no single feature looks important

Defense:

  • Pre-training dedup: Cluster features by correlation (|r| > 0.9 or mutual info). Keep one per cluster — the one with clearest semantic name.
  • Semantic grouping: Tag features that measure the same underlying construct. If the pipeline's type/shape profile is identical, flag as candidate duplicate.
  • Post-hoc path audit: Walk tree paths — if two splits along the same path are on features with r > 0.85, the path has redundant logic. Collapse or warn.

51. Positive-Only Data Collection (No Negative Class Design)

Pipeline collects extensive data about positive cases but has no deliberate negative class strategy
  • The trap: Cancer detected → patient enters oncology pipeline → extensive labs, imaging, treatment data collected. Healthy patients? No equivalent data collection. You have rich positives and NO negatives.
  • Why it happens: Data collection follows the intervention. Positive cases trigger action (treatment, investigation, escalation). Negative cases = nothing happened = nothing recorded.
  • The naive fix: "Use everyone else as negative." But "everyone else" includes undiagnosed positives, ambiguous cases, and people who were never tested. Your negatives are contaminated.
  • What "well-defined negative" means: Confirmed absence, not just absence of confirmation. Patient screened AND found negative, not just "never screened."
  • The interference problem: Poorly-defined negatives include latent positives (pre-cancer, undiagnosed fraud, dormant threats). These leak positive signal into the negative class, destroying the decision boundary.

Domains: Cancer detection (tested negative vs never tested), fraud (confirmed legitimate vs uninvestigated), cybersecurity (verified clean vs unscanned), rare disease (confirmed healthy controls vs general population).

The fix: Design the negative class BEFORE building the model. Define inclusion criteria: what evidence confirms someone is truly negative? Budget for negative data collection just like positive. A model is only as good as its worst class.

52. Experiment Provenance Ignored (A/B Test Data Mixed Into Training)

Training data pools observations from multiple A/B test variants without tracking which experiment generated each row
  • The trap: Data warehouse collects all conversion events. Model trains on 6 months of history. But during that period, 12 different A/B tests ran — each actively manipulating the user experience. Feature importance reflects the experimental manipulations, not stable user behavior.
  • Why it matters: An A/B test that changed the checkout flow, button placement, or pricing tier directly alters which features drive conversions. "Button color clicked" becomes important not because it predicts conversion, but because test variant B forced users through a different path.
  • The compounding problem: Sequential tests stack. Test #3's data was collected under test #2's winning variant. The feature relationships learned from test #3's data are conditional on test #2's treatment — which may itself be reverted later.
  • What gets corrupted: Feature importance rankings, SHAP values, partial dependence plots. All reflect the experimental interventions, not the causal structure of the problem. The model learns "which experiment this came from" as a hidden confounder.
  • The subtle version: Even after a test concludes and a winner ships, the historical data still contains 50% of users who saw the losing variant. Their behavior reflects a product state that no longer exists.

Domains: Ecommerce (checkout optimization tests), SaaS (onboarding experiments), marketplace (pricing/matching algorithm tests), content platforms (recommendation experiments).

The fix: Tag every row with experiment_id and variant. Either: (1) train only on control data (consistent experience), (2) include experiment_id as a feature so the model can condition on it, or (3) train only on post-experiment-settled data where the winning variant is universally deployed. At minimum: add experiment provenance as metadata in the feature store.
The pattern: Most pipeline pitfalls are information boundary violations — future leaking into past, test leaking into train, deployment leaking into development. The defense is always the same: strict temporal ordering, entity-level splitting, and "would I have this at prediction time?" as the gatekeeping question for every feature, every transform, every evaluation.
