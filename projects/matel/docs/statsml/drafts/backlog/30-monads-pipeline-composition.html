Monads: Composable Effect Tracking for Pipelines

Discussion — Design Pattern

Core idea: Monads aren't just academic Haskell — they're a design pattern for composing operations that have "something extra" (failure, missing data, multiple results, side effects) while keeping the composition clean. Data pipelines are essentially chains of transforms where each step might fail, produce warnings, need logging, or encounter missing data. Monadic composition makes these concerns explicit and composable rather than scattered as try/catch blocks and null checks.

The Pipeline Problem Monads Solve

Without Monads: Scattered Concerns

Each transform step can:

  • Succeed normally
  • Fail with an error
  • Succeed with warnings
  • Encounter missing data
  • Need to log what it did
  • Produce multiple candidate results

Result: try/catch everywhere, null checks everywhere, logging scattered everywhere, error handling inconsistent across steps, no way to compose cleanly.
With Monads: Composable Plumbing

Each concern gets its own monad — a container that handles the "extra stuff" automatically during composition:

  • Missing data? Maybe/Option propagates absence
  • Failure? Either/Result carries error info
  • Logging? Writer accumulates metadata
  • Multiple results? List explores all paths
  • Side effects? IO isolates impurity

Result: each step is a pure function returning a wrapped value. The monad handles composition. No scattered try/catch.

Key Monads for Data Pipelines

Maybe / Option

Handles: missing data without null checks

A transform that might not produce output. If step 3 of 10 returns Nothing, the rest of the chain short-circuits gracefully — no NullPointerException mid-pipeline.

  • Feature value might be null → Maybe propagates
  • Lookup might not find a match → Option.empty
  • No need for if x is not None at every step
Either / Result

Handles: error information (why did this fail?)

Carries the error context through the chain. When validation fails at step 5, you get a structured error describing what went wrong, what the input was, and which rule was violated — not a cryptic stack trace from step 8.

  • Right(value) — success, continue
  • Left(error) — failure, short-circuit with context
  • Human-readable error messages vs stack traces
Writer

Handles: accumulating metadata alongside computation

Each step produces output AND metadata (logs, row counts, timing, data quality scores). The Writer monad combines the metadata from all steps automatically.

  • Pipeline profiling: row counts at each stage
  • Data quality: warning counts, anomaly flags
  • Transform lineage: record of operations applied
  • No global logger, no side-effect logging calls
List

Handles: multiple possible results

Represents multiple valid outcomes explored in parallel. Replaces nested loops over candidate configurations.

  • Multi-candidate parameter validation
  • Multiple valid interpretations of ambiguous data
  • Exploring all bin sizes, all normality tests, all thresholds
  • Flat composition: List of Lists flattens naturally
This is exactly what statsml does with multi-candidate normality testing — the List monad pattern, implicitly.
IO

Handles: isolating side effects from pure computation

Database reads, file writes, API calls, clock reads — all wrapped in IO. Pure computation stays pure. Side effects are pushed to the edges and explicitly marked. You can test the pure core without mocking anything.

Practical Examples in Data Context

Feature Transform with Maybe

Without:

def transform(row):
    if row['age'] is None:
        return None
    if row['income'] is None:
        return None
    ratio = row['income'] / row['age']
    if ratio < 0:
        return None
    return log(ratio)

With Maybe:

transform = (
    get('age')
    .bind(lambda a: get('income')
    .bind(lambda i: safe_div(i, a)))
    .bind(safe_log)
)

Null propagation is automatic. No manual checks.
Validation with Either

Without:

try:
    result = validate(data)
except ValueError as e:
    # lost context of which step failed
    log(f"failed: {e}")
    return default_value  # silent fallback

With Either:

result = (
    check_not_empty(data)
    .bind(check_numeric)
    .bind(check_range(0, 100))
    .bind(check_normality)
)
# result is either Right(valid_data)
# or Left(ValidationError(step, reason, input))

Error context preserved. No silent fallbacks.
Pipeline Metadata with Writer
def clean_step(df):
    removed = df[df.age < 0]
    result = df[df.age >= 0]
    return Writer(
        value=result,
        log={"rows_removed": len(removed),
             "reason": "negative_age"}
    )

# Compose steps: logs merge automatically
pipeline = (
    clean_step
    .bind(normalize_step)
    .bind(encode_step)
)
# Returns: (final_df, [all_logs_combined])
Multi-Candidate with List
# List monad: explore all valid combinations
candidates = (
    List([5, 10, 20, 50])      # bin counts
    .bind(lambda b:
        List(['sturges', 'fd', 'scott'])  # methods
        .bind(lambda m:
            evaluate(bins=b, method=m)))
)
# Returns: List of ALL (bin, method, score) combos
# Filter to passing candidates
valid = candidates.filter(lambda r: r.score > 0.8)

Replaces nested for-loops with flat composition.

Not Just Haskell

The Pattern Transcends Language
  • Rust: Result<T, E> and Option<T> with ? operator — monadic chaining built into the language
  • Scala: Try, Either, Option, for-comprehensions as monad syntax
  • Python: returns library, or roll your own with @dataclass
  • Java: Optional, Stream (limited but monadic)
  • TypeScript: fp-ts, Effect library
Railway Oriented Programming

Scott Wlaschin's framing: same idea, different branding.

  • Two tracks: success track and failure track
  • Each function is a "switch" that might divert to the failure track
  • Composition connects switches end-to-end
  • Failure track carries error context all the way to the end
  • No try/catch needed — errors are values, not exceptions

This is exactly Either monad with a visual metaphor that's more accessible than category theory.

Connection to statsml

The statsml pipeline already uses monadic patterns implicitly:
  • Multi-candidate validation (multiple normality tests, multiple bin sizes) = List monad
  • Feature might not be classifiable = Maybe/Option pattern
  • Validation that carries reason for failure = Either pattern
  • Profiling metadata accumulated alongside computation = Writer pattern
Making these explicit gives us: composition for free, consistent error handling, testability of the pure logic without mocking.

Key Discussion Points

  • Is monadic composition overkill for a Python-based pipeline? Or does it prevent the "error handling spaghetti" problem?
  • How does this interact with pandas/numpy which don't use monadic patterns? (NaN propagation is a broken Maybe monad)
  • Can we get monadic benefits without the Haskell vocabulary? (Result types, Railway-oriented programming)
  • Relationship to Railway Oriented Programming (Scott Wlaschin) — same idea, different branding
  • Performance overhead: wrapping every value in a container vs letting NaN propagate natively
