Entity Key Granularity: Which Key Combination Defines a Unit?

TO DISCUSS

Choosing the wrong key (or too coarse a key) to group and correlate events is one of the most common analysis mistakes. The "obvious" identifier often mixes distinct contexts, inflating noise or creating impossible aggregations.

Motivating Example: User Behavior Tracking

The Problem with user_id Alone

A single user_id can have:

  • Multiple sessions active simultaneously (laptop + phone + tablet)
  • Multiple devices with different usage contexts (work desktop vs personal phone)
  • Multiple people operating the same account (shared family login, team accounts)
  • Multiple intents happening in parallel (browsing in one tab, checkout in another)

Correlating events by user_id alone mixes all of these into one "behavior" — the resulting patterns are a superposition of multiple distinct activities.

The correct unit of analysis might be (user_id, session_id), or (user_id, device_id, session_id), or even (user_id, session_id, tab_id) depending on the question being asked.
What Goes Wrong
  • False sequences: Event A on phone followed by event B on laptop looks like A→B journey but they're independent
  • Inflated session length: Overlapping sessions counted as one long session
  • Mixed intent: "User searched for X then bought Y" — but X was a different person on the shared account
  • Broken funnels: Conversion funnel assumes linear progression within a key — parallel sessions break this
  • Wrong attribution: Which device/session gets credit for the conversion?

Other Domains Where This Bites

Examples of Key Granularity Mistakes
  • Network security: source_ip alone — NAT means 1000 users share one IP. Need (ip, port, timestamp) or (ip, user_agent) minimum.
  • E-commerce: order_id without line_item_id — aggregating to order level loses product-level signal
  • Healthcare: patient_id without encounter_id — mixing outpatient visit with ICU stay
  • Ad tech: campaign_id without creative_id + placement_id — can't tell if it's the ad or the context
  • IoT/manufacturing: machine_id without shift_id or operator_id — different operators produce different defect rates
  • Finance: account_id without distinguishing joint account holders or authorized signers
The General Pattern

Every analysis question implicitly defines a unit of observation. The key combination must uniquely identify that unit — no more (loses power), no less (mixes contexts).

  • Too coarse: groups heterogeneous things → Simpson's paradox, inflated variance, impossible sequences
  • Too fine: every row is unique → no repetition to learn from, sparse features, overfitting
  • Just right: groups things that are genuinely the same context, same actor, same intent
Can the pipeline detect when a chosen key produces suspiciously mixed behavior? (e.g., bimodal distributions within a single key value, impossible event sequences, concurrent conflicting states)

Key Discussion Points

  • How does the pipeline help a user realize their grouping key is too coarse? (statistical signals: bimodality within groups, impossible transitions, variance inflation)
  • Should the pipeline suggest key refinements? ("Your user_id groups show 3 distinct behavior clusters — consider adding session_id")
  • Relationship to entity resolution: sometimes the "right" key doesn't exist in the data and must be constructed (session stitching, device graph)
  • Temporal dimension: a key might be correct at one time granularity but not another (user_id is fine for monthly, broken for per-minute)
  • How does this interact with the hierarchical relationships backlog item (#24)? (keys often form a hierarchy: user → session → event)
