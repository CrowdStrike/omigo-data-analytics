Partial Ordering of Events & Replication Lag

TO DISCUSS

In distributed systems, total ordering of events is a fiction. Events produced by independent actors have no inherent order — only events with a causal relationship have a guaranteed "happened before." Data systems that assume total ordering break silently under replication lag, network partitions, and multi-region writes.

The Core Problem: Total Order Is a Lie

Why Events Are Only Partially Ordered
  • Independent producers: user A clicks in Tokyo, user B clicks in London — there is NO fact about which happened "first." It depends on whose clock you trust.
  • Causally related events: user A searches → user A clicks result. THESE have an order (search caused click). But it's a partial order, not total.
  • The illusion of timestamps: assigning a timestamp creates a total order — but it's arbitrary. Different observers with different clocks would assign different orders.
A data pipeline that sorts by timestamp and treats the result as ground truth is baking an arbitrary total order onto a partially ordered reality. Any analysis that depends on the ordering of independent events is fragile.
Accepting Partial Order

Design systems and analyses that work correctly given ONLY the causal relationships, not a total timestamp order:

  • Vector clocks / version vectors: track "happened before" without requiring synchronized clocks
  • Causal consistency: guarantee you see causes before effects, but don't impose order on independent events
  • CRDTs: data structures that converge regardless of event delivery order
  • Commutative operations: if the result doesn't depend on order (SUM, COUNT, SET UNION) → safe under reordering
Key insight: if your analysis gives different results depending on the arbitrary ordering of concurrent events, your analysis has a bug — it's sensitive to noise in the timestamp.

Replication Lag: The Practical Manifestation

What Replication Lag Does to Data
  • Read-your-own-writes failure: write to primary, read from replica — data isn't there yet. Pipeline sees stale state.
  • Causal inversion: event B (caused by A) replicates before A. Pipeline sees effect before cause → impossible state → broken analysis.
  • Split-brain reads: query hits two replicas at different lag — rows from different points in time mixed in one result set.
  • Monotonicity violation: read replica at lag=2s, then read same replica at lag=5s (caught up differently). Second read returns EARLIER data than first. Time goes backward.
  • Phantom deletions: row created on primary, read on replica (exists), then replica catches up to a DELETE that happened between the two events. Row disappears retroactively.
The insidious part: replication lag is variable. System works perfectly at lag=0 (tests pass), fails intermittently at lag=50ms (prod), and catastrophically at lag=5s (during incident). Bugs are non-reproducible because lag varies.
Consequences for Data Analysis
  • Inconsistent joins: join users table (replica A, lag=1s) with orders table (replica B, lag=3s) — new user's order exists but user doesn't. Orphan row.
  • Counts disagree: COUNT(*) from orders = 1000. SUM from order_items for those orders = 980 items worth. 20 order_items haven't replicated yet.
  • Feature store inconsistency: feature computed from table A (current) joined with table B (lagging). Feature value is based on a state that never existed.
  • Time-travel artifacts: analytics query captures a snapshot that's internally inconsistent — some tables are at T, others at T-3s. No single point in time this snapshot was real.
If your analysis pipeline reads from replicas (nearly all do for performance), every cross-table analysis is potentially reading an inconsistent snapshot. Do we need snapshot isolation guarantees for profiling?

Design Patterns for Partial Order Awareness

Accept and Design Around It
  • Idempotent processing: if the same event arrives twice (or out of order), result is the same
  • Commutative aggregations: prefer operations where order doesn't matter (SUM, COUNT, MAX, UNION)
  • Watermarks: "I believe all events before time T have arrived" — explicit uncertainty boundary
  • Grace periods: don't close a window until lag_max has elapsed — accept late arrivals
  • Reprocessing: design so you CAN reprocess when late data arrives — immutable source, reproducible transforms
  • Consistent snapshots: read from a single point-in-time snapshot (MVCC, Delta Lake time travel) instead of multiple replicas
What Must NOT Depend on Ordering
  • Correctness: final result should be the same regardless of event delivery order (for concurrent events)
  • Completeness: system should know when it has "enough" data (watermarks) vs waiting forever
  • Determinism: given the same set of events (unordered), produce the same output — don't let arrival order affect results

What CAN depend on ordering:

  • Latency: out-of-order events mean delayed results (wait for watermark)
  • Intermediate states: in-flight aggregations may be temporarily wrong — but converge
  • Efficiency: sorted input is faster to process, but unsorted must still produce correct results

Key Discussion Points

  • Should the profiling pipeline detect operations that are order-dependent and flag them? (e.g., "this rolling window assumes total ordering of independent events")
  • How to handle the tension between "wait for all data" (completeness) and "produce results now" (timeliness)?
  • What's the right abstraction for a pipeline stage that needs to handle late-arriving events? (Retraction? Recompute? Append correction?)
  • Testing under replication lag: can we simulate variable lag in test environments to catch ordering bugs?
  • Relationship to exactly-once semantics: is it achievable? Is at-least-once + idempotency sufficient?
